


**Persistence using ACLs - Rights Abuse**  
«پایداری با استفاده از ACLها — سوء‌استفاده از مجوزها»

«حتی ACLهای جالب‌تر و بیشتری وجود دارند که می‌توان از آن‌ها سوء‌استفاده کرد.  
برای مثال، با دسترسی‌های Domain Admin، می‌توان ACL ریشهٔ دامنه (domain root) را تغییر داد تا حقوق مفیدی مثل `FullControl` یا توانایی اجرای «DCSync» را به یک حساب اختصاص داد.»

## 🔎 تحلیل فنی (چی، چرا و اثرات)

### ۱) چه چیزی گفته می‌شود؟

- منظور این است که مهاجم یا نفوذگر با داشتن امتیازات کافی (مثلاً Domain Admin) می‌تواند **لیست کنترل دسترسی (ACL)** روی شیء «ریشهٔ دامنه» یا دیگر اشیاء سطح‌بالا را طوری تغییر دهد که به یک کاربر/حساب خاص حقوق حیاتی‌ای داده شود.
    
- این حقوق می‌تواند `FullControl` (کنترل کامل) باشد یا حقوقی خاص مرتبط با «تکثیر/Replication» که به مهاجم اجازهٔ اجرای عملیات‌های خواندن اطلاعات حساس دایرکتوری را می‌دهد — معروف‌ترین نمونهٔ چنین عملیاتی **DCSync** است.
    

### ۲) DCSync چیه و چرا مهمه؟

- **DCSync**
نام فنی عملیاتی است که از پروتکل‌های تکرار (Directory Replication) استفاده می‌کند تا از یک کنترل‌کننده دامنه (DC) اطلاعاتی مثل هَش‌های رمز عبور (NTLM/krb) مربوط به کاربران را بخواند.
    
- ابزارهایی مثل Mimikatz می‌توانند با استفاده از مجوزهای مناسب (مجوزهای تکرار) درخواست‌های DRS (Directory Replication Service) شبیه‌سازی کنند و در نتیجه هَش‌های رمز عبور حساب‌ها — از جمله حساب‌های دامنه/اداری — را استخراج کنند.
    
- نتیجهٔ عملی: دسترسی کامل به ‌هَش رمز عبور ادمین‌ها → امکان عبور از احراز هویت و تسلط بر دامنه.
    

### ۳) چه مجوزهایی برای DCSync لازم‌اند؟

(خلاصهٔ فنی، بدون دستورالعمل سوء‌استفاده)

- مجوزهای مربوط به replication که معمولاً به نام‌های LDAP/AD شناخته می‌شوند: مانند `Replicating Directory Changes` و `Replicating Directory Changes All` (یا معادل‌هایی که به‌صورت Access Control Entry قابل‌دادن هستند).
    
- یا داشتن `GenericAll` / `FullControl` روی ریشهٔ دامنه که عملاً همان کار را می‌کند و اجازهٔ خواندن/تغییر همهٔ خصوصیات را می‌دهد.
    
- نکته: نیازی نیست همیشه Domain Admin باشی؛ اگر کسی حق تکرار یا حق خواندن attributes حساس را روی دامنه داشته باشد، می‌تواند DCSync‌گونهٔ بالا را انجام دهد.
    

### ۴) چرا تغییر ACL ریشهٔ دامنه خطرناک است؟

- چون ریشهٔ دامنه به‌عنوان یک آبجکت سطح بالا می‌تواند مجوزها را به‌صورت سرتاسری یا برای اشیاء حساس تسهیم/کنترل کند.
    
- دادن حق تکرار یا FullControl به یک حساب «در یک نقطه» باعث می‌شود آن حساب از طریق مکانیسم‌های تکرار به‌سرعت اطلاعات حساس را استخراج کند.
    
- این تکنیک هم افزایش سطح دسترسی و هم persistence ایجاد می‌کند و می‌تواند کم‌سر و صدا و ماندگار باشد.

## 🛡️ کشف و دفاع (برای جزوه و کار دفاعی)

### الف) چگونه کشف کنیم؟

- **فعال‌سازی Auditing مناسب**: حتماً «Directory Service Changes» و «Directory Service Access» را فعال کن تا تغییرات ACL و دسترسی به attributes حساس ثبت شوند.
    
- **چیزهایی که باید مانیتور شوند**:
    
    - هر تغییر در ACL روی **ریشهٔ دامنه (Domain Root)** یا اشیاء حساس.
        
    - اضافه شدن ACEهای دارای `Replicating Directory Changes`, `Replicating Directory Changes All`, `GenericAll`, `FullControl`.
        
    - درخواست‌های تکرار/Replication از حساب‌هایی که معمولاً چنین کاری نمی‌کنند.
        
    - فعالیت‌های ابزارهای شناخته‌شده (مثل فراخوانی DRSUAPI) یا لاگین‌های غیرمعمول به کنترل‌کننده‌های دامنه.
        
- **رویدادهای مفید (Event IDs)**: برای ثبت تغییرات شیء و permissions از Eventهای مربوط به Directory Service و Security استفاده کن؛ از جمله `5136` (Object modification در Directory Service) و `4662` / `4670` (Object access / permissions change) — توجه کن که برای ثبت این رویدادها باید auditing مربوطه فعال باشد.
    

> هشدار: درخواست‌های DCSync از لحاظ لاگینگ ممکن است خیلی مستقیم و واضح نباشند؛ بنابراین صرفاً تکیه بر لاگ‌های لاگ‌این کافی نیست — باید خودِ مجوزها و ACLها را بازبینی کنی.

**Nishang** یک مجموعه‌ی متن‌باز از اسکریپت‌های PowerShell هست که توسط متخصص امنیتی معروف **Samrat Ashok** ساخته شده. این ابزار شامل اسکریپت‌هایی برای:

- اجرای حملات post-exploitation

- اجرای کد از راه دور

## 🔧 دستور `Set-RemoteWMI` دقیقاً چه کاری انجام می‌ده؟

این دستور برای **تغییر Security Descriptor مربوط به WMI و DCOM** استفاده می‌شه تا به یک کاربر غیرادمین اجازه‌ی دسترسی از راه دور به WMI داده بشه.

### 🎯 کاربرد اصلی:

- دادن مجوز دسترسی به WMI namespaces برای کاربر دلخواه
- ایجاد backdoor سطح WMI برای اجرای کد از راه دور
- استفاده در سناریوهای Persistence یا lateral movement

---

## 🧩 پارامترهای مهم دستور

|پارامتر|توضیح|
|---|---|
|`-UserName`|نام کاربری که می‌خوای بهش دسترسی بدی|
|`-ComputerName`|نام یا IP سیستم هدف|
|`-Credential`|اعتبارنامه برای اتصال به سیستم هدف|
|`-Namespace`|فضای نام WMI که می‌خوای مجوزش رو تغییر بدی (مثل `root\cimv2`)|
|`-NotAllNamespaces`|فقط فضای نام مشخص‌شده رو تغییر بده، نه همه‌ی زیرمجموعه‌ها|
|`-Remove`|حذف مجوزهایی که قبلاً اضافه شده بودن|

---

## 🧠 چرا این دستور مهمه؟

با اجرای `Set-RemoteWMI`، مهاجم می‌تونه:

- به کاربر غیرادمین اجازه بده از راه دور کد اجرا کنه از طریق WMI
- بدون نصب هیچ agent یا فایل مخرب، دسترسی دائمی ایجاد کنه
- از این دسترسی برای اجرای ابزارهای مخرب مثل **EvilWMIProvider** یا **PowerShell payloads** استفاده کنه

## 🧠 تعریف کلی

`Win32_OperatingSystem` یک کلاس WMI در فضای نام `root\CIMV2` هست که نماینده‌ی سیستم‌عامل فعلی روی سیستمه. این کلاس اطلاعاتی مثل نسخه ویندوز، زمان بوت، حافظه، معماری سیستم، و خیلی چیزهای دیگه رو در اختیار قرار می‌ده.

---

## 📦 مهم‌ترین ویژگی‌ها و اطلاعاتی که این کلاس ارائه می‌ده

|ویژگی|توضیح|
|---|---|
|`Caption`|نام سیستم‌عامل (مثلاً Windows 10 Pro)|
|`Version`|نسخه دقیق ویندوز (مثلاً 10.0.19045)|
|`BuildNumber`|شماره بیلد سیستم‌عامل|
|`OSArchitecture`|معماری سیستم‌عامل (مثلاً 64-bit)|
|`LastBootUpTime`|زمان آخرین بوت سیستم|
|`FreePhysicalMemory`|مقدار حافظه RAM آزاد|
|`TotalVisibleMemorySize`|کل حافظه قابل مشاهده|
|`InstallDate`|تاریخ نصب ویندوز|
|`RegisteredUser`|نام کاربر ثبت‌شده|
|`SerialNumber`|شماره سریال ویندوز|
|`Locale`|تنظیمات منطقه‌ای سیستم|
|`NumberOfProcesses`|تعداد پردازش‌های فعال|
|`NumberOfUsers`|تعداد کاربران فعال در حال حاضر|

## 🛠️ چطور از این کلاس در PowerShell استفاده کنیم؟

### مثال ساده برای گرفتن اطلاعات سیستم‌عامل:

```powershell
Get-WmiObject -Class Win32_OperatingSystem
```

یا با فیلتر کردن فقط چند ویژگی:

```powershell
Get-WmiObject -Class Win32_OperatingSystem | Select-Object Caption, Version, OSArchitecture, LastBootUpTime
```

مرحله 1: تغییر Security Descriptorها برای دسترسی بدون ادمین

در این مرحله، مهاجم با دسترسی اولیه (مثلاً یک کاربر دامنه معمولی)، از ابزارهایی مثل **DAMP یا RACE** استفاده می‌کنه تا **ACLهای مربوط به WMI و PowerShell Remoting** رو تغییر بده.

🔧 ابزار: `Set-RemoteWMI`  
📌 هدف: دادن مجوز به کاربر غیرادمین برای اجرای WMI query یا PowerShell command از راه دور

این کار باعث می‌شه که کاربر معمولی بتونه مثل ادمین از راه دور به سیستم دسترسی داشته باشه، بدون اینکه عضو گروه Administrators باشه.

✅ مرحله 2: استخراج هش حساب ماشین بدون ادمین

با استفاده از backdoor رجیستری که در مرحله قبل ایجاد شده، مهاجم می‌تونه با دستور زیر هش حساب ماشین رو بکشه بیرون:

```
Get-RemoteMachineAccountHash -ComputerName dcorp-dc -Verbose
```

🔐 این هش مربوط به حساب `dcorp-dc$` هست که در Kerberos برای سرویس‌های مختلف استفاده می‌شه.

✅ مرحله 3: اجرای حمله Silver Ticket با استفاده از هش

حالا که مهاجم هش حساب ماشین رو داره، می‌تونه با ابزارهایی مثل **Rubeus** یک **Silver Ticket** بسازه. این بلیت جعلی بهش اجازه می‌ده که خودش رو به‌عنوان یک سرویس خاص (مثلاً `host` یا `rpcss`) جا بزنه و از طریق WMI کد اجرا کنه.

📌 مزیت Silver Ticket:

- نیازی به ارتباط با DC نیست
- فقط با داشتن هش حساب سرویس یا ماشین قابل اجراست
- خیلی stealthy و سخت برای شناسایی توسط SIEM یا
