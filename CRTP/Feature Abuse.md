### 🔹 ترجمه

**Feature Abuse (سوءاستفاده از قابلیت‌ها)**

- کاری که ما تا الان انجام می‌دادیم (و در ادامه کلاس هم ادامه می‌دیم) در واقع **سوءاستفاده از قابلیت‌های سیستم** بوده.
    
- سوءاستفاده از قابلیت‌ها فوق‌العاده‌ست، چون خیلی کم پیش میاد براشون پچ ارائه بشه و معمولاً هم تیم‌های امنیتی تمرکز زیادی روشون ندارن!
    
- یکی از سوءاستفاده‌های مورد علاقه من هدف قرار دادن **اپلیکیشن‌های سازمانی** هست که هنگام طراحی و توسعه، **امنیت توی اولویت نبوده**.
    
- روی ویندوز، خیلی از اپلیکیشن‌های سازمانی برای اجرا شدن نیاز به **دسترسی Administrative یا SYSTEM** دارن، که همین موضوع اون‌ها رو به یک راه عالی برای Privilege Escalation تبدیل می‌کنه.
    

---

### 🔹 تحلیل

1. **Feature Abuse یعنی چی؟**  
    به‌جای اینکه دنبال آسیب‌پذیری‌های کلاسیک (مثل Buffer Overflow یا Missing Patch) بگردیم، از **قابلیت‌های خود سیستم یا نرم‌افزار** برای بالا بردن دسترسی سوءاستفاده می‌کنیم.
    
    ➝ مثلاً:
    
    - AlwaysInstallElevated → یک قابلیت ویندوزی، نه باگ.
        
    - AutoLogon → ذخیره رمز به صورت Cleartext، باز هم یک Feature.
        
    - Service misconfiguration → سیستم اجازه داده کاربر عادی باینری سرویس رو تغییر بده.
        
    
    این‌ها همه ویژگی‌های عادی سیستم هستن که میشه ازشون سوءاستفاده کرد.
    

---

2. **چرا این روش خطرناک‌تره؟**
    
    - برای آسیب‌پذیری‌ها (مثل CVEها) معمولاً پچ منتشر میشه → تیم امنیتی سریع باخبر میشه.
        
    - ولی Feature Abuse ذات سیستم یا برنامه‌ست → قابل پچ کردن نیست یا کمتر دیده میشه.
        
    - تیم‌های امنیتی هم بیشتر دنبال Exploitهای شناخته‌شده هستن، نه Feature Abuse.
        

---

3. **Enterprise Applications به‌عنوان هدف**
    
    - خیلی از نرم‌افزارهای سازمانی (مثل ابزارهای مانیتورینگ، نرم‌افزارهای سفارشی، آنتی‌ویروس‌ها، حتی برنامه‌های HR یا ERP) موقع نصب نیاز به Admin یا SYSTEM دارن.
        
    - اگر این برنامه‌ها درست Secure نشده باشن، کاربر عادی می‌تونه از مسیرهای مختلف (DLL Hijacking، تغییر Config، یا Abuse کردن Installer) دسترسی خودش رو به Admin/SYSTEM ارتقا بده.
        

---

✅ **نتیجه نهایی**:  
Feature Abuse یعنی **بازی با قوانین سیستم به نفع خودت**. به جای شکستن قفل، از کلیدهایی که سیستم خودش داده استفاده می‌کنی.  
این یکی از مهم‌ترین راه‌های Privilege Escalation به‌خصوص در شبکه‌های سازمانیه.

---

---

### 🔹 چرا DLL Hijacking روی اپلیکیشن‌های سازمانی جواب میده؟

- خیلی از **Enterprise Appها** (برنامه‌های مانیتورینگ، بکاپ، آنتی‌ویروس، ERP، HR و ...) توسط Vendorها ساخته میشن بدون توجه کافی به Security.
    
- این برنامه‌ها معمولاً:
    
    1. به صورت **Service** با سطح دسترسی `SYSTEM` اجرا میشن.
        
    2. برای Load کردن DLLها به مسیر **غیر امن** (مثل current directory یا یک مسیر قابل‌نوشتن توسط User) مراجعه می‌کنن.
        
    3. امضای دیجیتال یا integrity check روی DLLها ندارن.
        

---

### 🔹 یعنی چه اتفاقی میفته؟

1. برنامه میاد یه DLL (مثلاً `xyz.dll`) رو Load کنه.
    
2. به جای اینکه فقط از مسیرهای امن (مثل `C:\Windows\System32`) بخونه، به مسیرهایی میره که کاربر عادی هم می‌تونه بنویسه.
    
3. تو یک DLL مخرب با همون اسم می‌سازی و توی اون مسیر می‌ذاری.
    
4. وقتی برنامه اجرا میشه، **DLL تو به جای اصلیش Load میشه**.
    
5. چون برنامه با سطح SYSTEM اجرا میشه، DLL تو هم با سطح SYSTEM اجرا میشه → **Privilege Escalation**.
    

---

### 🔹 چرا این Feature Abuse حساب میشه؟

چون **DLL Search Order** یک ویژگی طبیعی ویندوزه، باگ یا CVE خاصی نیست.  
مایکروسافت هم میگه:

> "این رفتار سیستم‌عامله، برنامه‌نویس باید درست پیاده‌سازی کنه."

پس Patch خاصی براش نمیاد. مسئولیت روی دوش Vendor یا Adminه.

---

### 🔹 ابزارهایی که اینو شناسایی می‌کنن

- `Procmon.exe` (Sysinternals) → نشون میده برنامه داره دنبال چه DLLهایی می‌گرده.
    
- `winPEAS` → به‌طور خودکار مسیرهای قابل سوءاستفاده برای DLL Hijacking رو لیست می‌کنه.
    
- `PowerUp` → تابع `Find-ProcessDLLHijack` همین کار رو می‌کنه.

### 🔹 ترجمه

**Feature Abuse – Jenkins**

- بیایم از یک نسخه‌ی قدیمی‌تر Jenkins به عنوان مثال یک اپلیکیشن سازمانی آسیب‌پذیر استفاده کنیم.
    
- Jenkins یک ابزار **Continuous Integration** (یکپارچه‌سازی مداوم) بسیار پرکاربرده.
    
- جنبه‌های جالب زیادی در مورد Jenkins وجود داره، اما فعلاً بحثمون رو محدود می‌کنیم به قابلیتی که اجازه می‌ده روی Jenkins دستورات سیستمی اجرا کنیم.
    
- یک سرور Jenkins در حال اجراست روی **dcorp-ci (172.16.3.11)** روی پورت **8080**.
    

---

### 🔹 تحلیل

1. **چرا Jenkins مثال خوبی برای Feature Abuseه؟**
    
    - Jenkins ذاتاً برای Build و Deployment طراحی شده.
        
    - برای این کار، نیاز داره بتونه روی سیستم یا حتی روی Agentها **دستورات سیستمی اجرا کنه**.
        
    - این یه **Feature** واقعیه، باگ یا CVE نیست.
        
    
    📌 اما اگر Jenkins به درستی Secure نشده باشه (مثلاً دسترسی Anonymous باز باشه یا کاربر Low-privileged بهش دسترسی داشته باشه) → همون Feature میشه راهی برای **Privilege Escalation یا Lateral Movement**.
    

---

2. **قابلیت اجرای دستورات سیستمی**
    
    - Jenkins اجازه می‌ده Build Steps بسازی.
        
    - یکی از Build Stepsها می‌تونه **Execute Windows Batch Command** یا **Execute Shell Command** باشه.
        
    - یعنی هر کسی که به Jenkins UI یا API دسترسی داشته باشه، می‌تونه مستقیم روی ماشین Jenkins دستور اجرا کنه.
        
    - حالا اگر Jenkins روی ویندوز با **LocalSystem** یا روی لینوکس با **root** اجرا بشه → عملاً RCE به سطح سیستم عامل داری.
        

---

3. **چرا میشه گفت Feature Abuse؟**
    
    - این قابلیت ذات Jenkinsه، یعنی قرار بوده باشه.
        
    - حتی اگر پچ هم بزنی، این قابلیت از بین نمی‌ره.
        
    - تنها راه امن‌سازی اینه که:
        
        - دسترسی Jenkins رو محدود کنی.
            
        - نقش‌ها (Roles) و مجوزها رو درست تعریف کنی.
            
        - سرویس Jenkins رو با کاربر محدود اجرا کنی نه SYSTEM/root.
            

---

4. **درس کلیدی برای Pentest/Red Team**
    
    - همیشه دنبال اپلیکیشن‌هایی مثل Jenkins، Tomcat، JBoss، vCenter، SCCM باش.
        
    - اینا برای کارکرد عادی خودشون **بهت Execution Capability میدن** → اگر Misconfig داشته باشن، بدون نیاز به Exploit می‌تونی مستقیم از همون Feature استفاده کنی.
        

---

✅ **نتیجه نهایی:**  
اینجا Jenkins فقط یه نمونه‌ست، ولی مفهوم کلی اینه:  
خیلی از Enterprise Appها **خودشون به صورت قانونی قابلیت اجرای کد دارن**.  
اگر این اپ‌ها درست Secure نشده باشن → به راحتی می‌تونی از همون قابلیت برای گرفتن RCE و Privilege Escalation استفاده کنی.

### 🔹 Jenkins چیه؟

Jenkins یه **نرم‌افزار اتوماسیون**ه که بیشتر توی شرکت‌ها و تیم‌های برنامه‌نویسی استفاده میشه.  
کار اصلیش اینه که:

- وقتی یه Developer کدی رو تغییر میده (مثلاً روی GitHub یا GitLab)، Jenkins به‌صورت خودکار اون کد رو:
    
    1. **بیلد (Build)** کنه.
        
    2. **تست**‌هاش رو اجرا کنه.
        
    3. اگر همه‌چیز اوکی بود، اون رو روی سرور اصلی (Production) **Deploy** کنه.
        

به این پروسه می‌گن **CI/CD (Continuous Integration / Continuous Delivery)**.

---

### 🔹 چرا مهمه؟

- توی اکثر سازمان‌های بزرگ Jenkins پیدا میشه چون DevOpsها عاشقشن.
    
- Jenkins معمولاً روی یه **سرور اختصاصی** اجرا میشه.
    
- خیلی وقت‌ها Jenkins با دسترسی‌های بالا (حتی SYSTEM یا root) نصب و اجرا میشه.
    

---

### 🔹 چرا برای ما (به عنوان Pentester/Red Teamer) مهمه؟

1. **امکان اجرای دستور سیستم**
    
    - Jenkins برای اجرای تست‌ها یا Deployment باید روی سیستم دستور اجرا کنه.
        
    - یعنی اگر تو دسترسی به Jenkins UI (وب‌اینترفیس روی پورت 8080) داشته باشی، می‌تونی **Run Command** کنی.
        
    - این یعنی مستقیم **Remote Code Execution (RCE)**.
        
2. **Credential Storage**
    
    - Jenkins معمولاً Credentialها (پسورد دیتابیس، API keys، SSH keys) رو ذخیره می‌کنه.
        
    - اگر به Jenkins دسترسی بگیری → به کلی Credential حساس میرسی.
        
3. **Privilege Escalation**
    
    - اگه Jenkins با کاربر SYSTEM اجرا بشه، اجرای دستور تو هم در سطح SYSTEM خواهد بود.
        
    - این یه Featureه نه باگ → به همین دلیل Patch خاصی نداره (همون چیزی که توی Feature Abuse گفتیم).

### 🔹 یک مثال واقعی

فرض کن یه شرکت Jenkins رو روی سرور `172.16.3.11:8080` داره.

- اگر تو به وب‌اینترفیس دسترسی داشته باشی (حتی کاربر معمولی باشی)، می‌تونی یه **Job** بسازی که مثلاً این دستور رو بزنه:
    
    ```bash
    whoami
    ```
    
    و خروجی رو بگیری.
    
- حالا به جای `whoami` یه Reverse Shell بذاری → دسترسی مستقیم به سرور داری.
    

---

✅ خلاصه:  
Jenkins برای شرکت‌ها ابزاریه جهت **اتوماسیون توسعه نرم‌افزار**.  
برای ما به‌عنوان مهاجم → یک **در پشتی قانونی** برای اجرای دستور روی سیستم قربانیه، مخصوصاً اگر بد کانفیگ شده باشه.

---



---

### 🔹 ترجمه

- جدا از تعداد زیادی **plugin**، دو روش برای اجرای دستور روی **Jenkins Master** وجود داره.
    
- اگر **Admin access** داشته باشی (در نصب‌های پیش‌فرض قبل از نسخه 2.x)، می‌تونی بری به:
    
    ```
    http://<jenkins_server>/script
    ```
    
- توی **Script Console** می‌تونی **Groovy Script** اجرا کنی:
    
    ```groovy
    def sout = new StringBuffer(), serr = new StringBuffer()
    def proc = '[INSERT COMMAND]'.execute()
    proc.consumeProcessOutput(sout, serr)
    proc.waitForOrKill(1000)
    println "out> $sout err> $serr"
    ```
    
    - `[INSERT COMMAND]` → جایگزین کن با دستور مورد نظرت.
        
    - خروجی دستور توی `sout` و خطاها توی `serr` ذخیره میشن.
        
    - `println` هم خروجی و خطا رو چاپ می‌کنه.
        

---

### 🔹 تحلیل

1. **Script Console چیست؟**
    
    - یک Feature رسمی Jenkins برای Adminها.
        
    - هدفش اینه که Adminها بتونن **Groovy Script** اجرا کنند تا Jenkins رو مدیریت کنن.
        
    - هیچ باگی نیست، کاملاً Feature قانونی.
        
2. **اجرای دستور سیستم**
    
    - توی مثال بالا، `[INSERT COMMAND]`.execute() → دستور روی سیستم اجرا میشه.
        
    - اگر Jenkins با **SYSTEM یا root** اجرا بشه → دستور هم با همون سطح اجرا میشه.
        
    - این یعنی **Privilege Escalation از سطح Admin Jenkins به SYSTEM**.
        
3. **Feature Abuse بودن**
    
    - این قابلیت برای مدیریت Jenkins گذاشته شده → باگ نیست.
        
    - ولی اگر دسترسی Admin به شخصی داده بشه که نباید داشته باشه → همین Feature میشه **راه نفوذ به سیستم عامل**.
        
4. **خطر نسخه‌های قدیمی**
    
    - قبل از Jenkins 2.x، **Admin access پیش‌فرض** بود.
        
    - یعنی به راحتی هر کسی می‌تونست Script Console رو باز کنه و دستور اجرا کنه.
        
    - بعد از 2.x این مشکل کمتر شده ولی Misconfiguration هنوز امکان‌پذیره.
        

---

✅ **جمع‌بندی:**

- Jenkins Script Console یک **در قانونی برای اجرای دستور روی سیستم**ه.
    
- Misconfiguration یا دسترسی Admin → می‌تونه باعث **Privilege Escalation به SYSTEM** بشه.
    
- دقیقاً مثال کلاسیک **Feature Abuse**ه: قابلیت قانونی، ولی اگر کنترل نشده باشه → آسیب‌پذیری ایجاد می‌کنه.

### 🔹 ترجمه

- اگر **دسترسی Admin** نداری، اما می‌تونی **Build Steps** رو اضافه یا ویرایش کنی:
    
    1. یه Build Step اضافه کن.
        
    2. نوعش رو بذار روی **"Execute Windows Batch Command"**.
        
    3. دستور زیر رو وارد کن:
        
        ```
        powershell -c <command>
        ```
        
- با این روش می‌تونی:
    
    - اسکریپت‌ها رو دانلود و اجرا کنی
        
    - اسکریپت‌های Encode شده اجرا کنی
        
    - و کارهای بیشتری انجام بدی
        

---

### 🔹 تحلیل

1. **سطح دسترسی کمتر، ولی هنوز خطرناک**
    
    - حتی بدون Admin، اگر اجازه اضافه کردن یا ویرایش Build Step داشته باشی → می‌تونی **دستورات سیستم** اجرا کنی.
        
    - وقتی Jenkins خودش با **SYSTEM** اجرا میشه → دستورات تو هم با SYSTEM اجرا میشن.
        
2. **چرا Feature Abuse حساب میشه؟**
    
    - اجرای Build Steps یک **Feature قانونی Jenkins**ه.
        
    - هدفش Build کردن پروژه‌هاست، نه اجرای دستور دلخواه کاربر.
        
    - ولی ما از همین Feature قانونی برای Privilege Escalation یا اجرای دستور سیستم استفاده می‌کنیم.
        
3. **مزیت نسبت به Script Console**
    
    - برای کسانی که دسترسی Admin ندارن ولی به Jobها دسترسی دارن.
        
    - خیلی وقت‌ها Misconfiguration اجازه میده این روش کار کنه.
        
4. **کارهایی که میشه کرد**
    
    - دانلود اسکریپت از سرور خودت و اجرای اون
        
    - اجرای PowerShell encoded scripts (برای evasion)
        
    - دسترسی به فایل‌ها یا Credentialهایی که Jenkins باهاش کار می‌کنه
        

---

✅ **جمع‌بندی:**  
حتی بدون Admin، اگر Build Step دستکاری شدنی باشه → میشه از **ویژگی Build Execution** برای اجرای دستورات با سطح Jenkins یا SYSTEM سوءاستفاده کرد.  
این هم یک نمونه کلاسیک **Feature Abuse روی اپلیکیشن سازمانی**ه.
