### Domain Enumeration - User Hunting

	- **یافتن تمام ماشین‌های موجود در دامنه‌ی فعلی که کاربر جاری روی آن‌ها دسترسی Local Administrator دارد**  
	    دستور:
    
    ```powershell
    Find-LocalAdminAccess -Verbose
    ```
    
- این تابع (Function) با استفاده از **Domain Controller (DC)** در دامنه‌ی فعلی یا دامنه‌ی مشخص‌شده، لیست کامپیوترها را جمع‌آوری می‌کند (`Get-NetComputer`).  
    سپس به صورت چند-نخی (**Multi-threaded**) تابع `Invoke-CheckLocalAdminAccess` را روی هر ماشین اجرا می‌کند.
    
- این کار را همچنین می‌توان با ابزارهای مدیریت از راه دور مثل **WMI** و **PowerShell Remoting** هم انجام داد.  
    این روش‌ها زمانی مفید هستند که پورت‌های مورد نیاز برای `Find-LocalAdminAccess` (مثل **RPC** و **SMB**) مسدود شده باشند.
    
- اسکریپت‌های جایگزین برای این کار:
    
    - `Find-WMILocalAdminAccess.ps1`
        
    - `Find-PSRemotingLocalAdminAccess.ps1`
        

---

## 🔹 تحلیل و کاربرد

این دستورات در سناریوی **نفوذ و حرکت جانبی (Lateral Movement)** یا **شناسایی دامنه (Domain Enumeration)** خیلی مهم هستند.

1. **هدف اصلی:**  
    پیدا کردن اینکه کاربر فعلی (که روی یکی از ماشین‌ها لاگین کرده‌ای) کجاها در کل دامنه **Local Admin** هست.
    
2. **روش کار:**
    
    - اول با `Get-NetComputer` لیست تمام کامپیوترهای دامنه گرفته میشه.
        
    - بعد روی هر ماشین بررسی میشه که آیا کاربر فعلی Local Admin هست یا نه (`Invoke-CheckLocalAdminAccess`).
        
    - این کار به صورت **Multi-threaded** انجام میشه تا سریع‌تر بشه.
        
3. **محدودیت:**  
    اگر پورت‌های **RPC** و **SMB** (که برای چک کردن دسترسی‌های Local Admin استفاده میشن) روی ماشین‌ها بسته باشن، دستور `Find-LocalAdminAccess` جواب نمیده.
    
4. **راه‌حل جایگزین:**  
    در این حالت، مهاجم می‌تونه از ابزارهای مدیریتی دیگه مثل:
    
    - **WMI** (اسکریپت: `Find-WMILocalAdminAccess.ps1`)
        
    - **PowerShell Remoting** (اسکریپت: `Find-PSRemotingLocalAdminAccess.ps1`)  
        استفاده کنه تا همون نتیجه رو بگیره.
        

---

## 🔑 خلاصه برای جزوه

- `Find-LocalAdminAccess` → پیدا کردن کامپیوترهایی که کاربر فعلی روی آن‌ها **Local Admin** هست.
    
- مکانیزم: گرفتن لیست همه‌ی کامپیوترهای دامنه (`Get-NetComputer`) + تست دسترسی Local Admin روی هر ماشین.
    
- مشکل: اگر پورت‌های RPC/SMB بسته باشن، کار نمی‌کنه.
    
- راه‌حل: استفاده از **WMI** یا **PS Remoting** با اسکریپت‌های جایگزین.
    
- اهمیت: برای **User Hunting** و **Lateral Movement** حیاتی است، چون نشون میده کجا میشه دسترسی‌های بالاتر گرفت یا حرکت جانبی انجام داد.

### 📌 ماجرا از کجا شروع میشه؟

تابع **Find-LocalAdminAccess** در PowerView کارش اینه که:

1. لیست همه‌ی ماشین‌های دامین رو می‌گیره (با `Get-NetComputer`).
    
2. روی هر ماشین تست می‌کنه که آیا کاربر فعلی (یا کاربر داده‌شده) دسترسی **Local Admin** داره یا نه.
    
    - این تست به طور پیش‌فرض از **RPC** و **SMB** (پورت‌های 135، 445) استفاده می‌کنه.
        

---

### 📌 مشکل

اگر روی شبکه یا فایروال این پورت‌ها **بسته باشند**، PowerView نمی‌تونه بررسی کنه که دسترسی ادمین داری یا نه.  
اینجاست که جایگزین‌ها وارد می‌شن:

---

### 📌 WMI (Windows Management Instrumentation)

- یه روش برای مدیریت از راه دور ویندوز هست (روی پورت 135 و DCOM).
    
- باهاش میشه کوئری زد، سرویس‌ها رو لیست کرد، پردازش‌ها رو اجرا کرد.
    
- PowerView از این استفاده می‌کنه تا **بفهمه آیا می‌تونه روی یه سیستم ریموت عملیات ادمینی انجام بده یا نه**.
    
- اگر بتونه، یعنی کاربر فعلی روی اون ماشین Local Admin هست.
    

---

### 📌 PowerShell Remoting (PSRemoting)

- یک قابلیت ویندوزه که روی پورت 5985 (HTTP) و 5986 (HTTPS) کار می‌کنه.
    
- به کمکش میشه یه Session روی یه ماشین ریموت باز کرد و دستورات رو اجرا کرد.
    
- اگر کاربر فعلی **Local Admin** روی اون سیستم باشه → می‌تونه Session باز کنه.
    
- پس این هم یه روش تست دسترسی ادمینیه.
    

---

### 📌 نتیجه و ربطش

- **RPC/SMB → روش پیش‌فرض** PowerView.
    
- **WMI یا PSRemoting → جایگزین وقتی پورت‌های پیش‌فرض بسته باشن.**
    
- هر سه روش در اصل دارن یک چیز رو تست می‌کنن: "آیا کاربر فعلی روی ماشین مقصد Local Admin هست یا نه؟"
    

---

👉 خلاصه برای جزوه:

- **WMI و PSRemoting** ابزارهای مدیریتی ویندوز هستند.
    
- در PowerView برای **User Hunting** به کار می‌رن، مخصوصاً وقتی پورت‌های RPC/SMB بسته باشند.
    
- هدف: بررسی اینکه کاربر فعلی روی چه سیستم‌هایی دسترسی Local Admin دارد.

### 📖 ترجمه متن

- **Find computers where a domain admin (or specified user/group) has sessions:**  
    پیدا کردن سیستم‌هایی که یک Domain Admin (یا کاربر/گروه مشخص) روی آن‌ها Session فعال دارد.
    
```
Find-DomainUserLocation -Verbose
```
    اجرای دستور برای دیدن جزییات.
    
```
Find-DomainUserLocation -UserGroupIdentity "RDPUsers"
``` 
    به جای Domain Admin، بررسی گروهی به نام RDPUsers.
    
- این تابع:
    
    1. از DC می‌پرسد که اعضای گروه مشخص (به‌طور پیش‌فرض Domain Admins) چه کسانی هستند → با دستور **Get-DomainGroupMember**.
        
    2. لیست کامپیوترهای دامین را می‌گیرد → با دستور **Get-DomainComputer**.
        
    3. روی هر کامپیوتر Sessionها و کاربران لاگین‌شده را بررسی می‌کند → با دستورات **Get-NetSession / Get-NetLoggedon**.
        
- **نکته:** از ویندوز سرور 2019 به بعد، برای دیدن Sessionها نیاز به دسترسی Local Admin روی آن سیستم دارید.
    

---

### 🔎 تحلیل کاربرد

این دستور برای **User Hunting** به کار می‌رود:

- به مهاجم نشان می‌دهد **کدام کاربرهای مهم (مثل Domain Admin)** در حال حاضر روی چه سیستم‌هایی وارد شده‌اند.
    
- یا می‌تواند برای هر گروه دیگری هم استفاده شود (مثلاً RDPUsers).
    

---

### 📌 چرا مهم است؟

1. مهاجم اگر ببیند یک **Domain Admin** روی یک Workstation لاگین کرده → آن Workstation هدف طلایی می‌شود.  
    چون مهاجم می‌تواند با سرقت Credential یا Token از همان Session، به دامین نفوذ کامل کند.
    
2. برای گروه‌های دیگر (مثل RDPUsers) هم می‌توان فهمید چه کسانی به سیستم‌ها دسترسی ریموت دارند.
    

---

### 📌 محدودیت

- در ویندوز سرورهای جدیدتر (2019 به بعد)، برای دیدن Sessionها باید Local Admin باشید.
    
- یعنی اگر مهاجم دسترسی Local Admin نداشته باشد، نمی‌تواند از این قابلیت استفاده کند.
    

---

✅ **خلاصه برای جزوه:**

- دستور `Find-DomainUserLocation` در PowerView برای پیدا کردن محل ورود کاربرها یا گروه‌های مشخص (مثل Domain Adminها) استفاده می‌شود.
    
- مراحل: گرفتن اعضای گروه → گرفتن لیست کامپیوترها → بررسی Session و کاربرهای لاگین‌شده روی هر سیستم.
    
- کاربرد: پیدا کردن سیستم‌هایی که ارزشمندند (مثل Workstationهایی که Domain Admin در آن‌ها لاگین کرده).
    
- محدودیت: از ویندوز سرور 2019 به بعد نیاز به Local Admin دارد.

### 📖 ترجمه متن

- **List sessions on remote machines**  
    لیست‌کردن نشست‌ها (Sessions) روی سیستم‌های ریموت.  
    (لینک ابزار: [Invoke-SessionHunter](https://github.com/Leo4j/Invoke-SessionHunter))
    
- **Invoke-SessionHunter -Failsafe**  
    اجرای دستور با حالت _Failsafe_.
    
- **ویژگی مهم:**  
    این دستور برای دیدن نشست‌ها روی سیستم‌های ریموت نیازی به دسترسی ادمین ندارد.  
    چون از **Remote Registry** استفاده می‌کند و Hive به نام **HKEY_USERS** را کوئری می‌زند.
    
- **نسخه OpSec-friendly (برای ردپا کمتر):**
    

```powershell
Invoke-SessionHunter -NoPortScan -Targets C:\AD\Tools\servers.txt
```

این دستور بدون اسکن پورت و فقط روی سیستم‌های مشخص‌شده در فایل `servers.txt` اجرا می‌شود.

### 🔎 تحلیل کاربرد

ابزار **Invoke-SessionHunter** برای **User Hunting** طراحی شده:

- به جای استفاده از PowerView و دستورات کلاسیک مثل `Get-NetSession` یا `Get-NetLoggedon` که معمولاً به Local Admin نیاز دارند، این ابزار با استفاده از Remote Registry (که در خیلی از محیط‌ها باز است) Sessionها را شناسایی می‌کند.
    
- این باعث می‌شود که مهاجم بدون داشتن Local Admin روی سیستم مقصد هم بتواند بفهمد چه کاربری روی چه ماشینی Session فعال دارد.
    

---

### 📌 مزایا و محدودیت‌ها

✅ **مزایا:**

- نیاز نداشتن به دسترسی Local Admin.
    
- استفاده از Remote Registry → کمتر جلب توجه می‌کند.
    
- امکان محدودکردن هدف‌ها با فایل لیست (opsec friendly).
    

⚠️ **محدودیت‌ها:**

- اگر Remote Registry سرویس بسته یا غیرفعال شده باشد → کار نمی‌کند.
    
- در بعضی سازمان‌ها روی SIEM هشدار فعال می‌کنند برای دسترسی‌های غیرعادی به Remote Registry.
    

---

### 📑 خلاصه برای جزوه

- **Invoke-SessionHunter** ابزاری برای لیست‌کردن Session کاربران روی سیستم‌های ریموت است.
    
- از **Remote Registry (HKEY_USERS)** استفاده می‌کند → نیازی به Local Admin نیست.
    
- دستور پایه:
    

```powershell
Invoke-SessionHunter -Failsafe
```

- دستور امن‌تر (بدون Port Scan، روی سیستم‌های خاص):
    

```powershell
Invoke-SessionHunter -NoPortScan -Targets C:\AD\Tools\servers.txt
```

### 📌 سیستم ریموت یعنی چی؟

- وقتی می‌گیم **Remote Machine (سیستم ریموت)** منظور **یک کامپیوتر یا سرور دیگر داخل شبکه** است.
    
- یعنی سیستمی که تو روش نشستی نیستی، بلکه از راه دور داری بهش وصل می‌شی یا ازش اطلاعات می‌گیری.



---

### 📌 Registry به طور ساده

Registry در ویندوز مثل یک **پایگاه‌داده مرکزی** برای نگه داشتن تنظیمات سیستم و کاربران هست.

- مسیرهای معروف:
    
    - `HKEY_LOCAL_MACHINE` → تنظیمات کل سیستم
        
    - `HKEY_USERS` → تنظیمات مربوط به کاربران
        

---

### 📌 Remote Registry یعنی چی؟

- ویندوز یه قابلیتی داره به اسم **Remote Registry Service**.
    
- وقتی این سرویس روشن باشه، می‌تونی از **یک سیستم دیگه (Remote)** به رجیستری این کامپیوتر دسترسی داشته باشی.
    
- یعنی انگار داری از راه دور Registry اون سیستم رو باز می‌کنی و کوئری می‌زنی.
    

---

### 📌 چرا برای User Hunting مهمه؟

- مهاجم می‌تونه به Hive مربوط به **HKEY_USERS** روی یک سیستم ریموت دسترسی پیدا کنه.
    
- این Hive اطلاعاتی داره که کدوم کاربرها در حال حاضر Session فعال دارن یا اخیراً لاگین کرده‌اند.
    
- ابزارهایی مثل **Invoke-SessionHunter** از همین Remote Registry استفاده می‌کنن → بدون نیاز به Local Admin روی اون سیستم.
    

---

### 📌 مثال کاربردی

فرض کن سه تا سیستم داریم:

- `PC-User01` (سیستم تو)
    
- `PC-User02` (سیستم همکارت)
    
- `DC01` (Domain Controller)
    

تو روی `PC-User01` هستی و می‌خوای ببینی روی `PC-User02` چه کسی لاگین کرده:

1. اگر Remote Registry روی `PC-User02` فعال باشه،
    
2. می‌تونی Hive `HKEY_USERS` اون رو از راه دور بخونی،
    
3. و بفهمی چه Sessionهایی فعال هستن.
    

---

### 📌 مزایا برای مهاجم

- نیاز به Local Admin نداره (برخلاف `Get-NetSession`).
    
- به صورت خیلی بی‌سر و صدا اطلاعات کاربرهای لاگین‌شده رو می‌ده.
    

---

✅ **خلاصه ساده:**

- **Registry** = پایگاه‌داده تنظیمات ویندوز.
    
- **Remote Registry** = قابلیتی که اجازه می‌ده از راه دور Registry یک کامپیوتر دیگه رو بخونی/بنویسی.
    
- در User Hunting از Hive **HKEY_USERS** استفاده می‌شه → برای فهمیدن کاربرهای لاگین‌شده روی سیستم مقصد.
    

---

### 📌 HKEY_USERS چیه؟

- یکی از **Hiveهای رجیستری** ویندوزه.
    
- شامل تنظیمات و پروفایل همه‌ی کاربرانیه که روی سیستم لاگین کرده‌اند.
    
- هر کاربر روی سیستم یک **SID** (Security Identifier) داره → توی `HKEY_USERS` یه شاخه به اسم همون SID ساخته میشه.



### 📌 Hive یعنی چی؟

کلمه‌ی **Hive** (به معنی کندوی عسل 🐝) در ویندوز یعنی:  
یک **فایل یا بخش اصلی رجیستری** که ساختار درختی داره و کلیدها و مقادیر رجیستری رو ذخیره می‌کنه.

هر Hive:

- یه **بخش اصلی** از رجیستریه (Root key).
    
- تنظیمات رو از روی دیسک (فایل‌های سیستمی) بارگذاری می‌کنه.
    
- مثل یک شاخه‌ی درخت عمل می‌کنه که بقیه کلیدها زیر اون قرار دارن.

## 📌 دستور `Get-NetSession` در PowerView

این دستور برای **User Hunting** استفاده میشه و هدفش اینه که ببینه:

- چه کاربرهایی در حال حاضر روی یک **سیستم ریموت** Session فعال دارن.
    

---

### 📖 طرز کار

- `Get-NetSession` به سیستم مقصد (Remote Machine) وصل میشه.
    
- با استفاده از **SMB/RPC** اطلاعات Sessionها رو می‌گیره.
    
- خروجی به شما میگه کدوم یوزرها الان روی اون سیستم لاگین کردن.
    

---

### 📌 پارامتر مهم

```powershell
Get-NetSession -ComputerName <TargetComputer>
```

- `-ComputerName` → مشخص می‌کنه می‌خوای Sessionهای کدوم سیستم رو ببینی.
    
- اگر نزنی، پیش‌فرض روی سیستم فعلی اجرا میشه.
    

---

### 📌 نیازمندی

- برای اجرای موفق روی سیستم‌های ریموت معمولاً باید **Local Admin** روی اون سیستم باشی.
    
- چون از سرور SMB/RPC باید اجازه بگیره که Sessionها رو لیست کنه.
    

---

### 📊 خروجی معمولی

وقتی اجرا بشه، چیزی شبیه این برمی‌گردونه:

|CName|UserName|Time|IdleTime|
|---|---|---|---|
|\PC-User02|amin|0:15:30|0:05:00|
|\PC-User03|domain\it|2:20:10|1:00:00|

- **CName** → اسم کلاینتی که Session داده.
    
- **UserName** → کاربری که لاگین کرده.
    
- **Time** → مدت زمان Session.
    
- **IdleTime** → مدت زمان بیکاری Session.
    

---

### 📌 کاربرد در User Hunting

- مهاجم می‌فهمه چه کاربرهایی الان روی چه سیستمی لاگین کردن.
    
- اگر کاربری مثل **Domain Admin** دیده بشه → اون سیستم هدف طلایی میشه.  
    (چون مهاجم می‌تونه Credential یا Token اون کاربر رو بدزده).
