

##### Trojans

Methods of implanting own code:
-  Code cave
- New section
- Extending section


این بخش از Sektor7 دارد درباره‌ی **Backdooring PE Files** صحبت می‌کند؛ یعنی اضافه کردن کد دلخواه به یک فایل اجرایی ویندوز (PE) به‌طوری که برنامه اصلی همچنان اجرا شود اما کد اضافه‌شده هم قبل یا بعد از آن اجرا گردد. این یک مفهوم مهم در مهندسی معکوس، تحلیل بدافزار و امنیت نرم‌افزار است.

---

# Backdooring PE Files چیست؟

فرض کن یک فایل `notepad.exe` داری.

به‌صورت عادی روند اجرا این است:

```
Windows Loader
      │
      ▼
notepad.exe
      │
      ▼
AddressOfEntryPoint
      │
      ▼
کد اصلی برنامه
```

اگر فایل را Backdoor کنیم، ترتیب اجرا می‌تواند این‌گونه شود:

```
Windows Loader
      │
      ▼
AddressOfEntryPoint
      │
      ▼
کد اضافه شده
      │
      ▼
پرش به EntryPoint اصلی
      │
      ▼
برنامه بدون مشکل اجرا می‌شود
```

در نتیجه کاربر احساس نمی‌کند چیزی تغییر کرده، اما کد اضافه‌شده نیز اجرا شده است.

---

# Trojan چیست؟

در این زمینه، Trojan یعنی:

> برنامه‌ای که ظاهراً همان برنامهٔ اصلی است، اما علاوه بر عملکرد عادی، کد دیگری نیز اجرا می‌کند.

بنابراین:

```
Original Program
+
Injected Code
=
Trojanized Program
```

---

# سه روش رایج

Sektor7 سه روش را معرفی می‌کند.

---

# 1. Code Cave

این قدیمی‌ترین روش است.

داخل فایل PE معمولاً بخش‌هایی وجود دارد که استفاده نمی‌شوند.

مثلاً:

```
.text

AAAAAAAAAAAAAAAAAAAAAA

000000000000000000000

BBBBBBBBBBBBBBBBBBBBB
```

آن صفرها همان فضای خالی هستند.

دلیل وجودشان Alignment است.

مثلاً:

```
.text

Code.............

Padding

000000000000000000000
```

این Padding هیچ‌وقت اجرا نمی‌شود.

می‌توان آن را با Shellcode پر کرد.

```
.text

Code

Shellcode

Padding
```

سپس EntryPoint را تغییر داد تا ابتدا Shellcode اجرا شود.

مزایا:

- نیاز به اضافه کردن Section جدید نیست.
    
- اندازه فایل تغییر کمی می‌کند.
    

معایب:

- فضای خالی ممکن است کم باشد.
    
- اگر Shellcode بزرگ باشد، جا نمی‌شود.
    
- بسیاری از ابزارهای تحلیل، Code Caveهای غیرعادی را بررسی می‌کنند.
    

---

# 2. New Section

در این روش یک Section جدید به فایل اضافه می‌شود.

قبل:

```
.text
.rdata
.data
.rsrc
```

بعد:

```
.text
.rdata
.data
.rsrc
.backdoor
```

داخل `.backdoor` کد دلخواه قرار می‌گیرد.

در Header نیز اطلاعات Section ثبت می‌شود.

نمونه:

```
IMAGE_SECTION_HEADER

Name

VirtualAddress

VirtualSize

RawSize

Characteristics
```

EntryPoint به این Section اشاره می‌کند.

پس:

```
Loader

↓

.backdoor

↓

jmp OriginalEntryPoint
```

مزایا:

- فضای زیادی در اختیار دارید.
    
- سازمان‌یافته‌تر از Code Cave است.
    

معایب:

- فایل PE تغییر ساختاری پیدا می‌کند.
    
- اضافه شدن یک Section جدید برای بسیاری از ابزارها قابل مشاهده است.
    

---

# 3. Extending Section

در این روش Section جدیدی ایجاد نمی‌شود، بلکه یکی از Sectionهای موجود بزرگ‌تر می‌شود.

مثلاً:

```
.text

Code

Code

Code
```

بعد:

```
.text

Code

Code

Code

Shellcode
```

یعنی:

```
VirtualSize

RawSize
```

را افزایش می‌دهیم.

در نتیجه Shellcode انتهای `.text` قرار می‌گیرد.

EntryPoint نیز به آن منتقل می‌شود.

---

# مقایسه سه روش

|روش|فایل بزرگ‌تر می‌شود؟|Header تغییر می‌کند؟|فضای قابل استفاده|
|---|---|---|---|
|Code Cave|تقریباً خیر|معمولاً خیر|کم|
|New Section|بله|بله|زیاد|
|Extending Section|کمی|بله|متوسط تا زیاد|

---

# چرا این روش‌ها ممکن است شناسایی شوند؟

ابزارهای امنیتی هنگام بررسی فایل‌های PE به مواردی مانند این توجه می‌کنند:

- آیا تعداد Sectionها نسبت به نسخهٔ اصلی تغییر کرده است؟
    
- آیا `AddressOfEntryPoint` به جایی غیرمعمول اشاره می‌کند؟

    
- آیا فضای Padding شامل کد اجرایی شده است؟
    
- آیا اندازهٔ یک Section ناگهان افزایش یافته است؟
    
- آیا بخشی که قبلاً فقط داده بوده، اکنون مجوز اجرا (Execute) دارد؟
    

به همین دلیل، هر تغییری در ساختار PE می‌تواند نشانه‌ای برای تحلیل بیشتر باشد.

---

## ارتباط این مبحث با Windows Internals

برای درک عمیق این تکنیک‌ها، بهتر است با ساختار PE آشنا باشی:

```
DOS Header
        │
        ▼
NT Headers
        │
        ├── File Header
        │
        ├── Optional Header
        │        │
        │        ├── ImageBase
        │        ├── AddressOfEntryPoint
        │        ├── SectionAlignment
        │        └── FileAlignment
        │
        ▼
Section Table
        │
        ├── .text
        ├── .data
        ├── .rdata
        ├── .rsrc
        └── ...
```

سه روشی که Sektor7 معرفی می‌کند، در واقع همگی با همین بخش‌ها سروکار دارند:

- **Code Cave** از فضای بلااستفاده داخل یک Section موجود استفاده می‌کند.
    
- **New Section** یک `IMAGE_SECTION_HEADER` جدید به جدول Sectionها اضافه می‌کند.
    
- **Extending Section** اندازهٔ یکی از Sectionهای موجود (`VirtualSize` و `SizeOfRawData`) را افزایش می‌دهد.
    



# Code Cave یعنی چه؟

به زبان ساده:

> **Code Cave یک فضای خالی داخل یک Section از فایل PE است که می‌توان از آن برای قرار دادن کد جدید استفاده کرد.**

به این فایل نگاه کن:

```text
.text

+-----------------------------+
| 55 8B EC ...                |
| 83 EC 20 ...                |
| E8 12 34 ...                |
|                             |
| 00 00 00 00 00 00 00 00     |
| 00 00 00 00 00 00 00 00     |
|                             |
+-----------------------------+
```

آن قسمت پر از `00` معمولاً هیچ دستور اجرایی نیست.

همین قسمت را **Code Cave** می‌نامند.

---

# چرا این فضای خالی وجود دارد؟

دلیل اصلی **Alignment** است.

ویندوز Sectionها را با اندازه‌های مشخص هم‌تراز (Align) می‌کند.

فرض کن کد واقعی برنامه:

```
1500 Bytes
```

باشد.

اما Alignment برابر:

```
4096 Bytes
```

است.

پس فایل روی دیسک چیزی شبیه این می‌شود:

```text
.text

Code

#########################

Padding

000000000000000000000000
```

کد فقط 1500 بایت است.

بقیه تقریباً 2500 بایت فضای بلااستفاده است.

---

# مثال تصویری

فرض کن `.text` این شکلی باشد:

```text
0x1000

mov eax,1
call foo
jmp bar

....

0x1500

00000000000000000000000

0x2000
```

بین `0x1500` تا `0x2000`

هیچ دستور واقعی وجود ندارد.

پس می‌توانیم آن را با Shellcode پر کنیم.

---

# بعد از قرار دادن Shellcode

فرض کن Shellcode را آنجا گذاشتیم.

```text
.text

Original Code

...

Shellcode

...

Padding
```

حالا Entry Point را تغییر می‌دهیم:

```
OEP

↓

Code Cave

↓

Shellcode

↓

jmp OEP
```

دقیقاً همین کاری است که در Sektor7 مشاهده می‌کنی.

---

# چرا اسمش Cave است؟

چون شبیه یک **غار خالی** داخل Section است.

```
.text

██████████████████

██████████████████

□□□□□□□□□□□□□□□

██████████████████
```

قسمت سفید همان Cave است.

---

# از کجا می‌فهمیم Cave وجود دارد؟

ابزارهایی مثل:

- x64dbg
    
- PE-bear
    
- LordPE
    
- CFF Explorer
    

می‌توانند فایل را نشان دهند.

حتی داخل Hex Editor هم مشخص است.

مثلاً:

```text
4D 5A
90 00
....

55 8B EC

83 EC 10

E8 11 22

00 00 00 00

00 00 00 00

00 00 00 00
```

آن قسمت `00` ها احتمالاً یک Code Cave است.

---

# آیا همیشه صفر است؟

خیر.

ممکن است این‌ها را هم ببینی:

```text
90 90 90 90
```

که همان NOP است.

یا

```text
CC CC CC CC
```

که دستور `INT3` است و گاهی برای Debugging یا پر کردن فضا استفاده می‌شود.

در هر سه حالت، اگر آن ناحیه واقعاً توسط برنامه استفاده نشود، می‌تواند یک Code Cave باشد.

---

# چرا از Code Cave استفاده می‌کنیم؟

چون لازم نیست ساختار فایل را تغییر دهیم.

اگر Section جدید بسازی:

```
.text
.data
.rdata
.backdoor
```

همان لحظه ابزارهای تحلیل متوجه می‌شوند فایل تغییر کرده است.

اما با Code Cave:

```
.text

Code

Shellcode

Padding
```

هیچ Section جدیدی اضافه نشده است.

---

# محدودیت Code Cave

فرض کن Cave فقط:

```
180 Bytes
```

جا داشته باشد.

اما Shellcode تو:

```
900 Bytes
```

باشد.

دیگر جا نمی‌شود.

در این حالت باید سراغ روش‌هایی مثل:

- Extending Section
    
- New Section
    

بروی.

---

# ارتباط با PE Format

اگر ساختار PE را در نظر بگیریم:

```text
IMAGE_SECTION_HEADER (.text)

VirtualSize      = 0x1850
SizeOfRawData    = 0x2000
```

ممکن است:

- **VirtualSize** اندازه واقعی کد و داده‌های معتبر باشد.
    
- **SizeOfRawData** به خاطر File Alignment بزرگ‌تر باشد.
    

اختلاف این دو مقدار اغلب همان فضایی است که می‌تواند به‌صورت Code Cave وجود داشته باشد (البته همیشه قابل استفاده نیست و باید بررسی شود).

---

## خلاصه

می‌توان Code Cave را این‌گونه تعریف کرد:

```text
یک ناحیهٔ بلااستفاده داخل یک Section موجود
که معمولاً به علت Alignment ایجاد شده
و می‌توان بدون اضافه کردن Section جدید
کد اجرایی را در آن قرار داد.
```

این یکی از قدیمی‌ترین و همچنان پرکاربردترین تکنیک‌های **PE Backdooring** است و به همین دلیل Sektor7 آموزش آن را از همین مبحث شروع می‌کند.



# اصلاً Alignment یعنی چه؟

Alignment یعنی:

> **داده‌ها باید از آدرس‌هایی شروع شوند که مضربی از یک عدد مشخص هستند.**

مثلاً فرض کن قانون این باشد:

```text
هر چیزی باید از مضرب 16 شروع شود.
```

اگر کدت 10 بایت باشد:

```text
شروع:

0

کد:

##########
```

آخر کد می‌شود:

```text
10
```

اما چون باید مضرب 16 باشد، ویندوز آن را تا 16 پر می‌کند.

```text
0                16

##########......

```

آن نقطه‌ها همان **Padding** هستند.

---

# چرا اصلاً Alignment وجود دارد؟

دلیل اصلی سرعت است.

CPU و سیستم‌عامل دوست دارند داده‌ها را از مرزهای مشخص بخوانند.

فرض کن قرار باشد CPU این را بخواند:

```text
123456789ABCDEF
```

اگر از وسط شروع شود:

```text
6789ABCDEF
```

ممکن است مجبور شود دو بار حافظه را بخواند.

اما اگر از مرز مناسب شروع شود:

```text
0000000012345678
```

خواندن سریع‌تر و ساده‌تر است.

به همین دلیل تقریباً تمام سیستم‌عامل‌ها از Alignment استفاده می‌کنند.

---

# Alignment داخل فایل PE

در PE دو نوع Alignment داریم.

---

## 1. File Alignment

این مربوط به **فایل روی دیسک** است.

مثلاً:

```text
FileAlignment = 0x200
```

یعنی:

هر Section باید مضربی از

```text
512 Bytes
```

باشد.

---

فرض کن Section فقط

```text
300 Bytes
```

داده دارد.

اما چون Alignment برابر 512 است:

```text
300 Bytes

+

212 Bytes Padding
```

در فایل ذخیره می‌شود.

---

یعنی روی دیسک:

```text
512 Bytes
```

اشغال می‌کند.

---

## 2. Section Alignment

این مربوط به زمانی است که ویندوز فایل را داخل RAM لود می‌کند.

مثلاً:

```text
SectionAlignment = 0x1000
```

یعنی

هر Section باید از مرز

```text
4096 Bytes
```

شروع شود.

چون اندازه Page در ویندوز 4096 بایت است.

---

مثلاً:

```text
.text

1500 Bytes
```

داخل حافظه تبدیل می‌شود به:

```text
4096 Bytes
```

---

# یک مثال کامل

فرض کن:

```text
.text

واقعاً

700 Bytes
```

است.

---

### روی دیسک

FileAlignment

```text
512
```

است.

پس:

```text
700
```

باید به:

```text
1024
```

گرد شود.

```
700 Bytes Code

324 Bytes Padding
```

---

### داخل حافظه

SectionAlignment

```text
4096
```

است.

پس:

```text
1024
```

تبدیل می‌شود به

```text
4096
```

---

داخل RAM:

```text
700 Bytes Code

3396 Bytes Empty
```

---

# این Padding از کجا می‌آید؟

فرض کن:

```
.text
```

این شکلی باشد.

```text
+--------------------------------------+
| Real Code                            |
|                                      |
| mov                                  |
| call                                 |
| add                                  |
| ret                                  |
|                                      |
| 00 00 00 00 00 00 00                 |
| 00 00 00 00 00 00                    |
+--------------------------------------+
```

آن صفرها را برنامه استفاده نمی‌کند.

فقط برای Alignment هستند.

---

# حالا Code Cave از همین جا متولد می‌شود

فرض کن این فایل را داری.

```text
.text

Code

Code

Code

0000000000000000000000000000
```

یک نفر می‌گوید:

"چرا این قسمت خالی را استفاده نکنیم؟"

در نتیجه:

```text
.text

Code

Code

Code

Shellcode

jmp OEP
```

بدون اینکه Section جدید بسازد.

---

# چرا این روش محبوب بود؟

چون Header فایل تغییر نمی‌کند.

قبلاً:

```text
.text

Code

Padding
```

بعداً:

```text
.text

Code

Shellcode
```

هیچ Section جدیدی اضافه نشده.

---

# یک مثال عددی

فرض کن:

```
VirtualSize
```

برابر است با:

```text
0x730
```

یعنی

```
1840 Bytes
```

---

اما

```
SizeOfRawData
```

برابر است با:

```text
0x800
```

یعنی

```
2048 Bytes
```

اختلاف:

```text
2048

-

1840

=

208 Bytes
```

این 208 بایت همان فضای اضافه‌ای است که به خاطر Alignment ایجاد شده است.

اگر برنامه واقعاً از آن استفاده نکند، می‌تواند یک **Code Cave** باشد.

---

# یک نکته مهم (که معمولاً در دوره‌های مقدماتی گفته نمی‌شود)

همیشه اختلاف `VirtualSize` و `SizeOfRawData` به معنی وجود یک Code Cave قابل استفاده نیست.

چرا؟

چون ممکن است:

- آن ناحیه توسط داده‌های دیگری استفاده شود.
    
- Compiler عمداً آن را برای توسعه آینده یا ساختارهای داخلی رزرو کرده باشد.
    
- یا در زمان اجرا مقداردهی شود.
    

به همین دلیل ابزارهایی مثل **Shellter** یا **PE-bear** صرفاً اختلاف اندازه‌ها را نگاه نمی‌کنند؛ آن‌ها محتوای واقعی ناحیه (مثلاً دنباله‌ای از `00` یا `90`) و قابل اجرا بودن آن را نیز بررسی می‌کنند.

---

# تصویر کلی

اگر همه چیز را کنار هم بگذاریم:

```text
               PE File
                  │
                  ▼
        +-------------------+
        |     .text         |
        +-------------------+
        |                   |
        |   Real Code       |
        |                   |
        |-------------------|
        | Padding           |  ← به خاطر Alignment
        | 00 00 00 00       |
        | 00 00 00 00       |
        +-------------------+
                  │
                  ▼
           Code Cave Candidate
                  │
                  ▼
      جای مناسب برای قرار دادن Shellcode
```

## خلاصه در یک جمله

- **Alignment** باعث می‌شود اندازه و محل قرارگیری Sectionها طبق مرزهای مشخص (مثل ۵۱۲ بایت روی دیسک و ۴۰۹۶ بایت در حافظه) تنظیم شوند.
    
- این هم‌ترازسازی اغلب **فضاهای خالی (Padding)** ایجاد می‌کند.
    
- اگر این فضاها واقعاً استفاده نشده باشند، به آن‌ها **Code Cave** می‌گوییم و می‌توان از آن‌ها برای قرار دادن کد جدید استفاده کرد، بدون اینکه لازم باشد Section جدیدی به فایل اضافه شود.
    

این همان ارتباط مستقیمی است که Sektor7 بین **Alignment → Padding → Code Cave** نشان می‌دهد و یکی از پایه‌های درک Backdooring فایل‌های PE است.****



اتفاقاً سؤال خیلی خوبی است، چون **Alignment اصلاً برای بدافزارها یا PE به وجود نیامده است.** Alignment یک مفهوم بنیادی در معماری کامپیوتر و سیستم‌عامل‌هاست. بعداً توسعه‌دهندگان بدافزار از آن سوءاستفاده کردند.

بیاییم اصلاً ویندوز و PE را فراموش کنیم.

# فرض کن یک انبار داری

داخل انبار قفسه‌هایی وجود دارد که هر کدام **۴ متر** طول دارند.

قانون انبار این است:

> هر کالا باید از ابتدای یک قفسه شروع شود.

حالا یک جعبه ۳ متری داری.

```text
|----------- قفسه 4 متری -----------|

[جعبه 3 متری][1 متر خالی]
```

چرا آن ۱ متر را با نصف جعبه بعدی پر نمی‌کنند؟

مثل این:

```text
|----------- قفسه -----------|

[جعبه اول][نصف جعبه دوم]
```

چون وقتی لیفتراک بخواهد جعبه دوم را بردارد، باید اول جعبه اول را کنار بزند.

کار سخت‌تر و کندتر می‌شود.

به همین دلیل می‌گویند:

> هر جعبه از ابتدای یک قفسه شروع شود.

این همان مفهوم Alignment است.

# اینجا Code Cave متولد می‌شود

یک Malware Developer نگاه می‌کند و می‌گوید:

> "این قسمت که خالی است و برنامه از آن استفاده نمی‌کند؛ چرا Shellcode خودم را اینجا قرار ندهم؟"

در نتیجه:

```text
قبل

██████████████

□□□□□□□□□□□□
```

بعد:

```text
██████████████

SHELLCODE
```

یعنی Code Cave اصلاً برای بدافزار ساخته نشده است.

**Code Cave فقط یک اثر جانبی (Side Effect) از Alignment است.**

---

## اگر بخواهم همه را در یک جمله خلاصه کنم:

- **Alignment** برای این به وجود آمد که داده‌ها و کدها با نظم و کارایی بیشتری روی دیسک و در حافظه قرار بگیرند و سیستم‌عامل و سخت‌افزار بتوانند آن‌ها را سریع‌تر و ساده‌تر مدیریت کنند.
    
- **Padding** نتیجهٔ طبیعی Alignment است.
    
- **Code Cave** زمانی ایجاد می‌شود که بخشی از این Padding واقعاً بدون استفاده باقی بماند.
    
- **Malware Developerها** بعدها از همین فضای بلااستفاده برای قرار دادن کد خود استفاده کردند.
    

به همین دلیل، Alignment یک مفهوم بنیادی در معماری کامپیوتر است؛ بدافزارها فقط از یکی از پیامدهای آن، یعنی فضای خالی ایجادشده، بهره می‌برند.


# خلاصه
###### Alignment 
به وجود آمده تا داده‌ها و Sectionها روی مرزهای مشخص (مضرب‌های معین) قرار بگیرند. این کار باعث می‌شود سیستم‌عامل و سخت‌افزار بتوانند داده‌ها را با نظم و کارایی بیشتری مدیریت کنند. اگر اندازهٔ واقعی کد از اندازهٔ مرز تعیین‌شده کمتر باشد، Linker فضای باقی‌مانده را با Padding (معمولاً صفر) پر می‌کند تا اندازهٔ Section مطابق Alignment شود. سپس Windows Loader هنگام اجرای برنامه، همین Sectionها را با رعایت Section Alignment داخل حافظه قرار می‌دهد.




###### اگر اندازهٔ واقعی داده یا کد از اندازهٔ تعیین‌شده توسط Alignment کمتر باشد، فضای اضافه‌ای به نام Padding ایجاد می‌شود. اگر بخشی از این Padding واقعاً توسط برنامه استفاده نشود، می‌تواند به عنوان یک Code Cave در نظر گرفته شود. در حوزهٔ توسعهٔ بدافزار یا تحلیل امنیتی، از این Code Cave می‌توان برای قرار دادن Shellcode یا Payload استفاده کرد. ابزاری یا تکنیکی که فایل PE را تغییر داده و این کد را داخل آن قرار می‌دهد، به طور کلی PE Injection یا PE Backdooring نامیده می‌شود.

از **مرحلهٔ ۵ به بعد**، یعنی تغییر مسیر اجرای برنامه و اجرای Shellcode، وارد قلمرو تکنیک‌های مورد استفاده در بدافزارها می‌شوی. برای یادگیری ساختار PE و Windows Loader، همان چهار مرحلهٔ اول تقریباً تمام مفاهیم مهم را به تو آموزش می‌دهند، بدون اینکه نیاز باشد وارد پیاده‌سازی رفتارهای تهاجمی شوی.




بله، اتفاقاً اگر هدفت **یادگیری PE Format، Windows Loader و نحوهٔ Patch کردن فایل‌های PE** باشد، چند پروژهٔ متن‌باز خیلی ارزشمند وجود دارد. البته یک نکته را در نظر داشته باش:
