

نام‌گذاری در WinAPI (Windows API) از قواعد خاص و سنتی پیروی می‌کند که عمدتاً بر پایه **Hungarian Notation** (نومِنگلاری مجاری) بنا شده است. این سبک توسط "چارلز سیمونی" (Charles Simonyi) در مایکروسافت ابداع شد تا برنامه‌نویسان بتوانند تنها با نگاه کردن به نام یک متغیر، نوع داده‌ای (Data Type) آن را تشخیص دهند.

در ادامه، دسته‌بندی دقیق این استانداردها را بررسی می‌کنیم:

### ۱. قراردادهای نام‌گذاری متغیرها (Hungarian Notation)
در این روش، یک یا چند حرف کوچک به عنوان پیشوند (Prefix) به ابتدای نام متغیر اضافه می‌شود.

*   **`h` (Handle):** برای هندل‌ها استفاده می‌شود (مانند `hWnd` برای هندل پنجره یا `hInst` برای هندل نمونه).
*   **`lp` (Long Pointer):** نشان‌دهنده یک اشاره‌گر ۳۲ یا ۶۴ بیتی است (مانند `lpCursorName`).
*   **`p` (Pointer):** نشان‌دهنده یک اشاره‌گر معمولی.
*   **`dw` (Double Word):** برای متغیرهای ۳۲ بیتی بدون علامت (unsigned 32-bit integer) مانند `dwExStyle`.
*   **`w` (Word):** برای متغیرهای ۱۶ بیتی بدون علامت.
*   **`sz` (String Zero-terminated):** رشته‌هایی که به کاراکتر تهی (null) ختم می‌شوند.
*   **`n` (Integer):** برای اعداد صحیح.
*   **`b` (Boolean):** برای مقادیر منطقی (True/False).
*   **`cb` (Count of Bytes):** معمولاً برای نشان دادن اندازه یک ساختار یا بافر به بایت.

### ۲. نام‌گذاری توابع (PascalCase)
توابع در WinAPI همیشه با حروف بزرگ شروع می‌شوند و هر کلمه جدید نیز با حرف بزرگ آغاز می‌شود (**PascalCase**). این توابع معمولاً با یک فعل شروع می‌شوند که عملکرد تابع را توصیف می‌کند.

*   مثال: `CreateWindowEx`, `GetMessage`, `ShowWindow`, `DispatchMessage`.

### ۳. پسوندهای A و W (ANSI vs Unicode)
بسیاری از توابع WinAPI که با رشته‌ها (Strings) سر و کار دارند، دو نسخه دارند:
*   **پسوند `A` (ANSI):** برای رشته‌های ۸ بیتی (Windows-1252 یا ASCII).
    *   مثال: `CreateWindowExA`
*   **پسوند `W` (Wide):** برای رشته‌های یونیکد ۱۶ بیتی (UTF-16).
    *   مثال: `CreateWindowExW`
*   **نکته:** برنامه‌نویسان معمولاً از نام بدون پسوند (مانند `CreateWindowEx`) استفاده می‌کنند و کامپایلر بر اساس تنظیمات پروژه (Unicode یا Multi-byte)، آن را به نسخه صحیح نگاشت می‌کند.

### ۴. نام‌گذاری ساختارها (Structures)
ساختارها (Structs) معمولاً با حروف بزرگ نام‌گذاری می‌شوند و پیشوند ندارند، اما متغیرهایی که از نوع آن ساختار تعریف می‌شوند، طبق قواعد Hungarian نام‌گذاری می‌شوند.

#### SNAKE CASE

پس استراکچر ها به صورت Snake Case  نوشته میشن 

*   نام ساختار: `WNDCLASSEX`
*   نام متغیر از آن نوع: `wc`

### ۵. ثابت‌ها و ماکروها (UPPER_CASE)
ثابت‌ها (Constants) و ماکروها کاملاً با حروف بزرگ نوشته می‌شوند و کلمات با خط تیره زیرین (`_`) از هم جدا می‌شوند. معمولاً یک پیشوند برای شناسایی دسته‌بندی آن‌ها وجود دارد:

*   **`WM_` (Window Message):** مانند `WM_PAINT`, `WM_CLOSE`.
*   **`WS_` (Window Style):** مانند `WS_OVERLAPPEDWINDOW`.
*   **`ID_` (Identifier):** برای شناسه‌های منابع.
*   **`VK_` (Virtual Key):** برای کدهای کلیدهای کیبورد مانند `VK_RETURN`.

### ۶. انواع داده‌ای خاص (Typedefs)
WinAPI به جای استفاده مستقیم از انواع داده‌ای استاندارد C (مانند `int` یا `char`)، از `typedef`های اختصاصی خود استفاده می‌کند تا سازگاری (Compatibility) در پلتفرم‌های مختلف حفظ شود:

*   `DWORD`: unsigned 32-bit integer.
*   `LONG`: signed 32-bit integer.
*   `LPSTR`: اشاره‌گر به یک رشته ANSI.
*   `LPCSTR`: اشاره‌گر به یک رشته ANSI ثابت (Constant).
*   `LRESULT`: مقدار بازگشتی تابع پنجره (معمولاً ۶۴ بیت در سیستم‌های ۶۴ بیتی).

### چرا این سبک استفاده می‌شود؟
اگرچه امروزه در زبان‌هایی مثل C# یا جاوا، استفاده از Hungarian Notation منسوخ شده است، اما در WinAPI به دلایل زیر همچنان حیاتی است:
1.  **سازگاری عقب‌رو (Backward Compatibility):** تغییر این نام‌ها باعث شکستن کدهای قدیمی (Legacy) می‌شود.
2.  **مدیریت حافظه در C/C++:** در این زبان‌ها دانستن نوع دقیق داده (اشاره‌گر، عدد صحیح و غیره) برای جلوگیری از خطاهای حافظه بسیار مهم است.

**خلاصه ساختار:**
`[Prefixes][BaseName]`
مانند: `lpszClassName` -> `lp` (Long Pointer) + `sz` (String Zero) + `ClassName` (نام توصیفی).


در برنامه‌نویسی سیستمی و به‌ویژه در محیط ویندوز، **Calling Convention** (قرارداد فراخوانی) مجموعه‌ای از قوانین است که تعیین می‌کند توابع چگونه با یکدیگر ارتباط برقرار کنند. این قوانین مشخص می‌کنند که:

1.  پارامترها با چه ترتیبی (از راست به چپ یا چپ به راست) وارد **Stack** شوند.
2.  پارامترها در کجا قرار بگیرند (Stack یا ثبّات‌های پردازنده/Registers).
3.  مسئولیت پاک‌سازی Stack پس از اتمام تابع بر عهده چه کسی باشد (فراخوان‌کننده یا تابعِ فراخوانی‌شده).

در ادامه، سه مورد اصلی که نام بردید را بررسی می‌کنیم:

---

### ۱. `__cdecl` (C Declaration)
این قرارداد فراخوانی پیش‌فرض در زبان‌های C و C++ است.

*   **ترتیب پارامترها:** از راست به چپ (Right-to-Left) در پشته (Stack) قرار می‌گیرند.
*   **پاک‌سازی Stack:** بر عهده **فراخوان‌کننده (Caller)** است. یعنی بعد از بازگشت از تابع، کدِ اصلی باید فضای پشته را آزاد کند.
*   **ویژگی خاص:** به دلیل اینکه فراخوان‌کننده مسئول پاک‌سازی است، این قرارداد اجازه می‌دهد که توابعی با **تعداد پارامتر متغیر** (Variable Arguments) مانند `printf` ساخته شوند.
*   **نام‌گذاری (Decoration):** یک علامت آندرلاین به ابتدای نام اضافه می‌شود (مثلاً `_MyFunction`).

### ۲. `__stdcall` (Standard Call)
این قرارداد استاندارد برای اکثر توابع **WinAPI** است.

*   **ترتیب پارامترها:** از راست به چپ (Right-to-Left) در پشته قرار می‌گیرند.
*   **پاک‌سازی Stack:** بر عهده **خودِ تابع (Callee)** است. قبل از خروج، تابع با دستور `ret n` فضای پشته را پاک می‌کند.
*   **ویژگی خاص:** حجم کد نهایی کمی کمتر از `__cdecl` می‌شود، زیرا کد پاک‌سازی پشته فقط یک بار (در داخل تابع) نوشته می‌شود، نه هر بار که تابع فراخوانی می‌گردد. اما این نوع فراخوانی اجازه استفاده از پارامترهای متغیر را نمی‌دهد.
*   **نام‌گذاری (Decoration):** یک آندرلاین در ابتدا و علامت `@` به همراه تعداد بایت‌های پارامترها در انتها اضافه می‌شود (مثلاً `_MyFunction@12`).

### ۳. `__fastcall`
همان‌طور که از نامش پیداست، برای افزایش سرعت طراحی شده است.

*   **نحوه انتقال:** سعی می‌کند تا حد امکان از **Registerها (ثبّات‌های پردازنده)** به جای پشته استفاده کند. در معماری x86، معمولاً دو پارامتر اول در ثبّات‌های `ECX` و `EDX` قرار می‌گیرند و مابقی در پشته.
*   **پاک‌سازی Stack:** مانند `__stdcall` بر عهده **خودِ تابع (Callee)** است.
*   **ویژگی خاص:** برای توابع کوچک که زیاد فراخوانی می‌شوند بسیار سریع است، زیرا دسترسی به Register بسیار سریع‌تر از RAM (Stack) است.
*   **نام‌گذاری (Decoration):** یک علامت `@` در ابتدا و یک علامت `@` به همراه تعداد بایت‌ها در انتها (مثلاً `@MyFunction@8`).

---

### جدول مقایسه‌ای (در معماری x86)

| ویژگی | `__cdecl` | `__stdcall` | `__fastcall` |
| :--- | :--- | :--- | :--- |
| **ترتیب پارامترها** | راست به چپ | راست به چپ | ثبّات‌ها + پشته |
| **پاک‌کننده پشته** | فراخوان‌کننده (Caller) | تابع (Callee) | تابع (Callee) |
| **تعداد پارامتر متغیر** | بله (پشتیبانی می‌شود) | خیر | خیر |
| **کاربرد اصلی** | برنامه‌های C/C++ | توابع WinAPI | بهینه‌سازی سرعت |

### نکته مهم در مورد معماری x64:
در سیستم‌های **۶۴ بیتی (x64)**، این تفاوت‌ها تا حد زیادی از بین رفته‌اند. ویندوز در حالت ۶۴ بیتی از یک قرارداد واحد به نام **"Microsoft x64 Calling Convention"** استفاده می‌کند که ترکیبی از این روش‌هاست (۴ پارامتر اول در ثبّات‌ها و مابقی در پشته، و پاک‌سازی معمولاً توسط Caller). بنابراین، این کلمات کلیدی در کد ۶۴ بیتی توسط کامپایلر نادیده گرفته می‌شوند یا به مدل استاندارد x64 نگاشت می‌شوند.

**چرا دانستن این‌ها مهم است؟**
اگر شما یک DLL با قرارداد `__stdcall` بنویسید اما در برنامه اصلی آن را به صورت `__cdecl` فراخوانی کنید، پشته به درستی پاک نمی‌شود و برنامه با خطای **Stack Imbalance** کرش (Crash) می‌کند. این یکی از رایج‌ترین خطاها در هنگام استفاده از توابع WinAPI یا کتابخانه‌های خارجی است.



منظور از **Generic Function Prototype** در ویندوز (WinAPI)، مکانیزمی است که به برنامه‌نویس اجازه می‌دهد یک کد واحد بنویسد که هم در سیستم‌های **ANSI** (رشته‌های ۸ بیتی) و هم در سیستم‌های **Unicode** (رشته‌های ۱۶ بیتی) بدون تغییر کار کند.

در واقع، این یک لایه انتزاعی (Abstraction) است که توسط پیش‌پردازنده (Preprocessor) مدیریت می‌شود.

### ۱. مکانیزم کارکرد (The Mapping)
در WinAPI، اکثر توابعی که با رشته‌ها سر و کار دارند، در واقع وجود خارجی ندارند! آنچه وجود دارد، دو نسخه مجزا از آن تابع است:
1.  نسخه‌ای که به **A** ختم می‌شود (مانند `MessageBoxA` برای ANSI).
2.  نسخه‌ای که به **W** ختم می‌شود (مانند `MessageBoxW` برای Wide/Unicode).

**Generic Prototype** یک ماکرو (Macro) است که بسته به تنظیمات پروژه، به یکی از این دو نسخه اشاره می‌کند.

### ۲. مثال عملی: `MessageBox`
اگر به فایل‌های هدر ویندوز (`winuser.h`) نگاه کنید، چیزی شبیه به این می‌بینید:

```cpp
#ifdef UNICODE
    #define MessageBox  MessageBoxW
#else
    #define MessageBox  MessageBoxA
#endif
```

*   اگر در تنظیمات کامپایلر شما، کلمه **`UNICODE`** تعریف شده باشد، هر جا بنویسید `MessageBox` ، کامپایلر آن را به `MessageBoxW` تبدیل می‌کند.
*   اگر تعریف نشده باشد، به `MessageBoxA` تبدیل می‌شود.

### ۳. پیش‌نیازهای استفاده از Generic Prototypes
برای اینکه کد شما واقعاً "Generic" یا عمومی باشد، نمی‌توانید فقط از نام تابع استفاده کنید؛ باید از **Generic Data Types** نیز استفاده کنید:

*   **به جای `char` یا `wchar_t`:** از **`TCHAR`** استفاده کنید.
*   **به جای `char*`:** از **`LPTSTR`** استفاده کنید.
*   **به جای `const char*`:** از **`LPCTSTR`** استفاده کنید.
*   **برای رشته‌های ثابت:** از ماکروی **`TEXT()`** یا **`_T()`** استفاده کنید.

#### مثال کد کاملاً Generic:
```cpp
// این کد به طور خودکار با هر دو تنظیمات ANSI و Unicode سازگار است
TCHAR* text = TEXT("Hello, World!"); 
MessageBox(NULL, text, TEXT("Caption"), MB_OK);
```

### ۴. چرا از Generic Prototypes استفاده می‌کنیم؟
1.  **قابلیت حمل (Portability):** کد شما روی نسخه‌های قدیمی ویندوز (که فقط ANSI بودند) و نسخه‌های مدرن (که مبتنی بر Unicode هستند) اجرا می‌شود.
2.  **یکپارچگی:** لازم نیست نگران باشید که کدام تابع `A` یا `W` را فراخوانی کنید؛ سیستم خودش بهترین گزینه را بر اساس تنظیمات پروژه انتخاب می‌کند.
3.  **استانداردسازی:** مایکروسافت از زمان ویندوز NT به بعد، برنامه‌نویسان را تشویق کرد که از نسخه Unicode استفاده کنند، اما برای حفظ سازگاری، این سیستم Generic را ایجاد کرد.

### ۵. تفاوت در نوع داده‌های خروجی
Generic Prototype
فقط برای نام تابع نیست، بلکه برای ساختارها (Structures) هم وجود دارد.
مثلاً ساختار `WNDCLASS` در واقع یک ماکرو است که به `WNDCLASSA` یا `WNDCLASSW` اشاره می‌کند.

### خلاصه مفاهیم:
| نوع (Generic) | نسخه ANSI | نسخه Unicode |
| :--- | :--- | :--- |
| **تابع** | `SetWindowTextA` | `SetWindowTextW` | **`SetWindowText`** |
| **نوع داده** | `char` | `wchar_t` | **`TCHAR`** |
| **اشاره‌گر** | `LPSTR` | `LPWSTR` | **`LPTSTR`** |
| **ثابت متنی** | `"text"` | `L"text"` | **`TEXT("text")`** |

**نکته مدرن:** امروزه تقریباً تمام برنامه‌های ویندوز به صورت **Unicode** کامپایل می‌شوند، بنابراین در اکثر پروژه‌های جدید، Generic Prototypeها به نسخه **W** ختم می‌شوند. اما یادگیری این ساختار برای درک معماری WinAPI و نگهداری کدهای قدیمی ضروری است.


### کالبدشکافی `LPCTSTR`

این نام مخفف عبارت زیر است:
*   **L** = **L**ong (یادگار گذشته، به معنی اشاره‌گر ۳۲ یا ۶۴ بیتی)
*   **P** = **P**ointer (اشاره‌گر)
*   **C** = **C**onst (ثابت و غیرقابل تغییر بودنِ متن)
*   **T** = **T**CHAR (کاراکتر جنریک - بخش جادویی داستان!)
*   **STR** = **Str**ing (رشته متنی که به صفر ختم می‌شود)

در کل یعنی: **«یک اشاره‌گر به یک رشته متنی ثابت از نوع TCHAR»**.

---

### چرا این نوع داده Generic (عمومی) است؟

بر اساس اینکه پروژه شما روی حالت **Unicode** تنظیم شده باشد یا **ANSI**، این نوع داده تغییر ماهیت می‌دهد:

#### حالت اول: پروژه روی Unicode تنظیم شده است (حالت پیش‌فرض امروزی)
در این حالت، کامپایلر `LPCTSTR` را به نوع داده زیر تبدیل می‌کند:
*   **`LPCWSTR`** (که حرف **W** مخفف Wide است).
*   در زبان C++ معمولی، این معادل است با: **`const wchar_t*`** (هر کاراکتر ۲ بایت فضا می‌گیرد).

#### حالت دوم: پروژه روی ANSI تنظیم شده است (سیستم‌های قدیمی)
در این حالت، کامپایلر `LPCTSTR` را به نوع داده زیر تبدیل می‌کند:
*   **`LPCSTR`** (بدون حرف T یا W).
*   در زبان C++ معمولی، این معادل است با: **`const char*`** (هر کاراکتر ۱ بایت فضا می‌گیرد).

---

### تعریف `LPCTSTR` در هدرهای ویندوز به چه صورت است؟

ویندوز در فایل‌های هدر خود (مانند `winnt.h`) این رفتار را با دستورات شرطی کامپایلر (Preprocessor) این‌گونه تعریف کرده است:

```cpp
#ifdef UNICODE
    typedef LPCWSTR LPCTSTR; // به اشاره‌گر ۱۶ بیتی (Wide) متصل می‌شود
#else
    typedef LPCSTR LPCTSTR;  // به اشاره‌گر ۸ بیتی (ANSI) متصل می‌شود
#endif
```

---

### ارتباط آن با تابع `MessageBox`

تابع `MessageBox` به این صورت تعریف شده است:

```cpp
int MessageBox(
  HWND    hWnd,
  LPCTSTR lpText,     // متن داخل جعبه پیام
  LPCTSTR lpCaption,  // عنوان پنجره
  UINT    uType
);
```

وقتی شما این تابع را فراخوانی می‌کنید، دو سناریو رخ می‌دهد:

#### ۱. اگر پروژه Unicode باشد:
تابع به `MessageBoxW` تبدیل می‌شود و آرگومان‌های آن از نوع `LPCWSTR` (`const wchar_t*`) خواهند بود. بنابراین شما باید رشته خود را با حرف `L` یا ماکروی `TEXT` بنویسید:
```cpp
MessageBox(NULL, L"hello world", L"title", MB_OK);
// یا روش جنریک:
MessageBox(NULL, TEXT("hello world"), TEXT("title"), MB_OK);
```

#### ۲. اگر پروژه ANSI باشد:
تابع به `MessageBoxA` تبدیل می‌شود و آرگومان‌های آن از نوع `LPCSTR` (`const char*`) خواهند بود:
```cpp
MessageBox(NULL, "Hello World", "Title", MB_OK);
```

### نتیجه‌گیری
استفاده از `LPCTSTR` به شما این اطمینان را می‌دهد که کدی که نوشته‌اید، بدون توجه به اینکه کامپایلر روی چه حالتی (Unicode یا ANSI) تنظیم شده است، بدون خطای کامپایل (Type Mismatch) به درستی کامپایل و اجرا خواهد شد.**



ساختار امضای توابع در WinAPI (مانند `MessageBox`) از یک الگوی بسیار دقیق و مهندسی‌شده پیروی می‌کند. بیایید تابعی را که مثال زدید، یعنی **`MessageBox`**، کالبدشکافی کنیم تا با اجزای آن آشنا شوید.

تعریف واقعی این تابع در هدر فایل‌های ویندوز به این صورت است:

```cpp
int WINAPI MessageBox(
  _In_opt_ HWND    hWnd,
  _In_opt_ LPCTSTR lpText,
  _In_opt_ LPCTSTR lpCaption,
  _In_     UINT    uType
);
```

در ادامه، هر بخش را با جزئیات توضیح می‌دهم:

---

### ۱. SAL (Source Annotation Language) - مانند `_In_`
این بخش که با آندرلاین شروع می‌شود (مثل `_In_` یا `_In_opt_`)، ابداع مایکروسافت برای کمک به **تحلیل ایستا (Static Analysis)** کد است. این‌ها در واقع کد اجرایی نیستند، بلکه راهنمایی برای کامپایلر و ابزارهای خطایابی هستند.

*   **`_In_`**: یعنی این آرگومان فقط **ورودی** است. تابع فقط آن را می‌خواند و تغییری در آن ایجاد نمی‌کند.
*   **`_Out_`**: یعنی تابع قرار است مقداری را در این آرگومان بنویسد (معمولاً برای اشاره‌گرها).
*   **`_In_opt_`**: کلمه **opt** مخفف **Optional** است. یعنی این ورودی اختیاری است و شما می‌توانید به جای آن مقدار `NULL` پاس بدهید.
*   **`_Inout_`**: یعنی پارامتر هم به عنوان ورودی استفاده می‌شود و هم تابع نتیجه را در همان متغیر برمی‌گرداند.

### ۲. Calling Convention - کلمه `WINAPI`
قبل از نام تابع، عبارت `WINAPI` را می‌بینید.
*   این در واقع یک ماکرو است که به **`__stdcall`** تبدیل می‌شود (همان قراردادی که در پیام قبلی توضیح دادم). این مشخص می‌کند که پشته چگونه مدیریت شود.

### ۳. Data Type (نوع داده) - مانند `HWND`
این‌ها اسامی مستعاری (Typedef) هستند که ویندوز برای انواع داده استاندارد C استفاده می‌کند تا در سیستم‌های مختلف سازگار بمانند.

*   **`HWND`**: مخفف **H**andle to a **W**indow. یک عدد ۳۲ یا ۶۴ بیتی که ویندوز از آن برای شناسایی یک پنجره استفاده می‌کند.
*   **`UINT`**: مخفف **U**nsigned **Int**eger (عدد صحیح مثبت).
*   **`LPCTSTR`**: همان‌طور که قبلاً بررسی کردیم، اشاره‌گر به یک رشته متنی ثابت و جنریک است.

### ۴. Argument Name (نام آرگومان) - مانند `hWnd`
این نامی است که برنامه‌نویس در بدنه تابع از آن استفاده می‌کند. در WinAPI، این نام‌ها هم از **Hungarian Notation** پیروی می‌کنند:
*   در `hWnd`: حرف `h` نشان‌دهنده Handle و `Wnd` مخفف Window است.
*   در `lpText`: عبارت `lp` نشان‌دهنده Long Pointer و `Text` محتوای آن است.

---

### مثال کامل با تحلیل:

اگر بخواهیم ساختار را طبق درخواست شما فرمول‌بندی کنیم:

`[Return Type] [Calling Convention] [Function Name] (`
   `[SAL] [Data Type] [Argument Name]`
`)`

**تحلیل یک خط از تابع:**
`_In_opt_ HWND hWnd`

1.  **`_In_opt_` (SAL):** به کامپایلر می‌گوید: «این یک ورودی است که می‌تواند NULL هم باشد؛ پس اگر کاربر NULL فرستاد، خطا نگیر.»
2.  **`HWND` (DataType):** به سیستم می‌گوید: «من به اندازه‌ی یک Handle فضا نیاز دارم تا آدرس پنجره را نگه دارم.»
3.  **`hWnd` (Argument):** نام متغیری است که در کدِ داخلی تابع برای ارجاع به آن پنجره استفاده می‌شود.

### چرا SAL اهمیت دارد؟
فرض کنید تابعی دارید که یک اشاره‌گر می‌گیرد (`_In_`). اگر شما به اشتباه `NULL` به آن پاس بدهید، Visual Studio قبل از اینکه حتی برنامه را اجرا کنید، زیر کد خط قرمز می‌کشد و هشدار می‌دهد که این تابع طبق SAL نباید مقدار تهی دریافت کند. این کار باعث کاهش چشمگیر باگ‌های حافظه می‌شود.




بله، کاملاً درست است. در ادبیات برنامه‌نویسی ویندوز (WinAPI)، به این فرآیند **Text Mapping** یا **Character Set Mapping** نیز گفته می‌شود.

دلیل این نام‌گذاری این است که این مکانیزم، «متن‌ها» و «توابع مرتبط با متن» را بر اساس تنظیمات پروژه، به یکی از دو مجموعه کاراکتری (ANSI یا Unicode) **نگاشت (Map)** می‌کند.

در اینجا ۳ لایه اصلی که در عملیات **Text Mapping** نقش دارند را بررسی می‌کنیم:

### ۱. نگاشت نوع داده‌ها (Type Mapping)
این لایه تعیین می‌کند که هر کاراکتر چند بایت باشد.
*   **`TCHAR`** نگاشت می‌شود به `char` (در ANSI) یا `wchar_t` (در Unicode).
*   **`LPTSTR`** نگاشت می‌شود به `char*` یا `wchar_t*`.

### ۲. نگاشت توابع (Function Mapping)
این لایه تعیین می‌کند که کدام نسخه از تابع فراخوانی شود.
*   تابع جنریک **`SetWindowText`** نگاشت می‌شود به نسخه **`SetWindowTextA`** یا **`SetWindowTextW`**.
*   تقریباً تمام توابعی که آرگومان رشته‌ای می‌گیرند، مشمول این نگاشت (Mapping) هستند.

### ۳. نگاشت ثابت‌های رشته‌ای (Literal Mapping)
این لایه تعیین می‌کند که رشته‌هایی که در کد می‌نویسید (داخل کوتیشن) چگونه توسط کامپایلر تفسیر شوند.
*   ماکروی **`TEXT("Hello")`** یا **`_T("Hello")`** وظیفه این نگاشت را دارد.
*   در حالت ANSI، به همان صورت `"Hello"` (رشته ۸ بیتی) باقی می‌ماند.
*   در حالت Unicode، به `L"Hello"` (رشته ۱۶ بیتی) تبدیل می‌شود.

---

### چرا اصطلاح "Mapping" دقیق است؟
اصطلاح "Mapping" به این دلیل استفاده می‌شود که در فایل‌های هدر ویندوز (مانند `TCHAR.H`)، یک جدول تناظر بزرگ وجود دارد. این فایل‌ها به جای بازنویسی کدها، صرفاً با دستورات پیش‌پردازنده (`#define`)، نام جنریک را به نام اختصاصی **وصل** یا **نگاشت** می‌کنند.

**مثال از داخل فایل هدر:**
```cpp
#ifdef UNICODE
  #define SetWindowText SetWindowTextW  // نگاشت به یونیکد
#else
  #define SetWindowText SetWindowTextA  // نگاشت به ANSI
#endif
```

### مزیت Text Mapping برای برنامه‌نویس:
اگر از این سیستم استفاده کنید، کد شما **Single-Source** باقی می‌ماند. یعنی برای تولید دو نسخه از نرم‌افزار (یکی برای سیستم‌های قدیمی و یکی برای سیستم‌های مدرن)، نیازی به تغییر حتی یک خط از کد ندارید؛ فقط کافی است تنظیمات پروژه (Character Set) را در Visual Studio تغییر دهید و دوباره کامپایل کنید.

**خلاصه:**
**Text Mapping** یعنی «تطبیق هوشمندانه تمام زیرساخت‌های متنیِ کد با استانداردِ هدف (ANSI یا Unicode)».


--- 

سیستم **Generic (Text Mapping)** هیچ وابستگی خاصی به C++ ندارد و در زبان **C** نیز دقیقاً به همان صورت کار می‌کند. در واقع، زیرساخت اصلی WinAPI با زبان C طراحی شده است.

برای اینکه در یک پروژه C از `MessageBox` به صورت Generic استفاده کنید، باید مراحل زیر را رعایت کنید:

### ۱. هدرهای مورد نیاز
در زبان C، علاوه بر `<windows.h>`، بهتر است هدر `<tchar.h>` را هم اضافه کنید تا به ماکروی `_T` دسترسی داشته باشید.

```c
#include <windows.h>
#include <tchar.h> // برای دسترسی به _T و TCHAR
```

### ۲. نحوه استفاده در کد
کد شما به زبان C خالص (Pure C) به این صورت خواهد بود:

```c
#include <windows.h>
#include <tchar.h>

int main() {
    // استفاده از TCHAR برای تعریف رشته
    TCHAR* message = _T("این یک پیام جنریک است");
    TCHAR* title = _T("عنوان پنجره");

    // فراخوانی تابع به صورت جنریک
    MessageBox(NULL, message, title, MB_OK | MB_ICONINFORMATION);

    return 0;
}
```

### ۳. تفاوت `_T` و `TEXT` در زبان C
شاید بپرسید فرق این دو چیست؟
*   **`TEXT()`**: در هدر `winnt.h` تعریف شده و بخشی از خودِ WinAPI است.
*   **`_T()`** یا **`_TEXT()`**: در هدر `tchar.h` تعریف شده‌اند. این‌ها بخشی از کتابخانه Runtime زبان C (CRT) مایکروسافت هستند.

در عمل، هر دو یک کار را انجام می‌دهند: اگر پروژه شما روی Unicode باشد، حرف `L` را پشت رشته می‌گذارند (مثلاً `"Hello"` تبدیل می‌شود به `L"Hello"`) و اگر روی ANSI باشد، هیچ کاری نمی‌کنند.

### ۴. تنظیمات پروژه (بسیار مهم)
حتی اگر شما از `_T` و `MessageBox` استفاده کنید، تا زمانی که به کامپایلر نگویید کدام حالت را می‌خواهید، Mapping انجام نمی‌شود.

در محیط **Visual Studio** برای یک پروژه C:
1.  روی پروژه راست‌کلیک کنید و **Properties** را بزنید.
2.  به مسیر **Configuration Properties > Advanced** بروید.
3.  گزینه **Character Set** را پیدا کنید:
    *   اگر روی **Use Unicode Character Set** باشد: `_T` به `L` تبدیل شده و `MessageBox` به `MessageBoxW` تبدیل می‌شود.
    *   اگر روی **Use Multi-Byte Character Set** باشد: `_T` حذف شده و `MessageBox` به `MessageBoxA` تبدیل می‌شود.

### چرا در C هم از این روش استفاده می‌کنیم؟
دقیقاً به همان دلایلی که در C++ استفاده می‌شود:
1.  **بدون تغییر کد:** اگر فردا بخواهید برنامه را برای یک نسخه قدیمی ویندوز که یونیکد را خوب پشتیبانی نمی‌کند خروجی بگیرید، فقط یک تنظیم را در کامپایلر عوض می‌کنید.
2.  **سازگاری با استانداردها:** امروزه استاندارد ویندوز بر پایه Unicode (UTF-16) است. استفاده از `_T` تضمین می‌کند که برنامه شما با کمترین هزینه با استانداردهای روز منطبق بماند.

**نکته برای پروژه‌های C:**
در زبان C، حتماً دقت کنید که اگر از توابع رشته‌ای استاندارد مثل `strlen` یا `strcpy` استفاده می‌کنید، باید نسخه جنریک آن‌ها را هم به کار ببرید:
*   به جای `strlen` از **`_tcslen`** استفاده کنید.
*   به جای `strcpy` از **`_tcscpy`** استفاده کنید.
(این توابع در همان `tchar.h` تعریف شده‌اند).

## Hungarian Notation


**نشان‌گذاری مجارستانی (Hungarian Notation)** یکی از معروف‌ترین قراردادهای نام‌گذاری (Naming Conventions) در تاریخ برنامه‌نویسی است که ارتباط بسیار تنگاتنگی با توسعه سیستم‌عامل ویندوز و **Windows API** دارد. این روش توسط یکی از برنامه‌نویسان ارشد مایکروسافت به نام «چارلز سیمونی» (Charles Simonyi) که اصالتاً مجارستانی بود، ابداع شد و به همین دلیل این نام را به خود گرفت.

در ادامه، این قرارداد نام‌گذاری و نحوه استفاده از آن در Windows API را به صورت ساختاریافته بررسی می‌کنیم:

### مفهوم و ساختار کلی
در نشان‌گذاری مجارستانی، نام هر متغیر از دو بخش اصلی تشکیل می‌شود:
1. **پیشوند (Prefix):** یک یا چند حرف کوچک در ابتدای نام متغیر که **نوع داده (Data Type)** یا هدف متغیر را مشخص می‌کند.
2. **نام پایه (Base Name):** نام اصلی متغیر که با حروف بزرگ شروع می‌شود (PascalCase) و نشان‌دهنده **موجودیت یا کاربرد** متغیر است.

**فرمول کلی:** `[Prefix][BaseName]`
مثال: `hwndMainWindow` (پیشوند `hwnd` + نام پایه `MainWindow`)

---

### نشان‌گذاری مجارستانی در Windows API
کتابخانه‌های سنتی ویندوز (Win32 API) که عمدتاً به زبان C و ++C نوشته شده‌اند، به شدت از نوع خاصی از این روش به نام **Systems Hungarian** استفاده می‌کنند. در این نوع، پیشوند دقیقاً نوع داده متغیر در حافظه را توصیف می‌کند.

در زیر لیستی از رایج‌ترین پیشوندهایی که در مستندات و کدهای Windows API با آن‌ها مواجه می‌شوید آورده شده است:

#### پیشوندهای مربوط به متغیرهای پایه (Primitives)
*   **`b`**: متغیر منطقی (BOOL) — مثال: `bIsReady`
*   **`c`** یا **`cb`**: شمارنده (Count) یا تعداد بایت‌ها (Count of Bytes) — مثال: `cbSize` (تعداد بایت‌های یک ساختار)
*   **`w`**: کلمه ۱۶ بیتی (WORD) — مثال: `wFlags`
*   **`dw`**: کلمه مضاعف ۳۲ بیتی (DWORD / Double Word) — مثال: `dwThreadId`
*   **`i`** یا **`n`**: عدد صحیح (Integer) — مثال: `nWidth`
*   **`l`**: عدد صحیح طولانی (Long) — مثال: `lResult`

#### پیشوندهای مربوط به رشته‌ها (Strings)
*   **`sz`**: رشته‌ای که با کاراکتر Null پایان می‌یابد (String Zero-terminated) — مثال: `szClassName`
*   **`p`** یا **`lp`**: اشاره‌گر (Pointer) یا اشاره‌گر طولانی (Long Pointer)
*   **`lpsz`**: ترکیب دو مورد قبل؛ اشاره‌گر طولانی به یک رشته ختم شده با Null — مثال: `lpszMenuName`
*   **`wsz`**: رشته از نوع Wide Character (برای یونیکد) — مثال: `wszFilePath`

#### پیشوندهای مربوط به هندل‌ها (Handles)
ویندوز برای مدیریت منابع سیستم (مثل پنجره‌ها، فایل‌ها، آیکون‌ها) از شناسه‌هایی به نام Handle استفاده می‌کند که همگی با پیشوند `h` شروع می‌شوند:
*   **`hWnd`**: هندل یک پنجره (Handle to a Window) — مثال: `hWndParent`
*   **`hInstance`**: هندل یک نمونه از برنامه اجرایی — مثال: `hInstanceApp`
*   **`hDC`**: هندل Device Context (برای گرافیک و رسم) — مثال: `hDCPrinter`
*   **`hFile`**: هندل یک فایل — مثال: `hFileStream`

---

### نمونه‌های واقعی در معماری ویندوز
اگر به توابع کلاسیک ویندوز نگاه کنید، این روش را به وضوح می‌بینید. به عنوان مثال، تابع معروف `CreateWindowEx` برای ساخت یک پنجره در ویندوز:

```cpp
HWND CreateWindowExA(
  DWORD     dwExStyle,      // پیشوند dw: متغیر ۳۲ بیتی برای استایل‌های پیشرفته
  LPCSTR    lpClassName,    // پیشوند lp: اشاره‌گر طولانی به نام کلاس (رشته)
  LPCSTR    lpWindowName,   // پیشوند lp: اشاره‌گر طولانی به نام پنجره
  DWORD     dwStyle,        // پیشوند dw: استایل پنجره
  int       X,              // (استثنا: گاهی نام‌های ساده استفاده شده‌اند)
  int       Y,
  int       nWidth,         // پیشوند n: عدد صحیح برای عرض
  int       nHeight,        // پیشوند n: عدد صحیح برای ارتفاع
  HWND      hWndParent,     // پیشوند hWnd: هندل پنجره پدر
  HMENU     hMenu,          // پیشوند h: هندل منو
  HINSTANCE hInstance,      // پیشوند h: هندل نمونه برنامه
  LPVOID    lpParam         // پیشوند lp: اشاره‌گر طولانی به پارامترهای سفارشی
);
```

---

### چرا این روش ابداع شد و چرا امروز کمتر استفاده می‌شود؟

**دلایل محبوبیت در گذشته:**
در دهه‌های ۸۰ و ۹۰ میلادی، محیط‌های توسعه (IDE) هوشمند نبودند. برنامه‌نویسان زبان C به سادگی نمی‌توانستند نوع یک متغیر را با نگه‌داشتن موس روی آن ببینند. با استفاده از این روش، برنامه‌نویس بلافاصله با دیدن `lpszName` می‌فهمید که نباید با آن مثل یک عدد (Integer) رفتار کند، بلکه این یک اشاره‌گر به رشته است. این کار از خطاهای حافظه به شدت جلوگیری می‌کرد.

**دلایل منسوخ شدن در کدهای مدرن:**
1. **IDE های مدرن:** امروزه محیط‌هایی مثل Visual Studio با قابلیت IntelliSense به راحتی نوع متغیرها را نمایش می‌دهند.
2. **Refactoring سخت:** اگر بخواهید نوع متغیری را از `int` (`nCount`) به `long` (`lCount`) تغییر دهید، مجبورید نام آن را در کل برنامه عوض کنید.
3. **زبان‌های شی‌گرا:** در ++C مدرن یا #C، تمرکز روی مفاهیم و کلاس‌ها است تا نوع داده‌های پایه در حافظه. (مایکروسافت در مستندات رسمی #C استفاده از این روش را ممنوع کرده است).

**نتیجه‌گیری:**
اگرچه در توسعه نرم‌افزارهای مدرن دیگر از Hungarian Notation استفاده نمی‌شود، اما برای هر کسی که می‌خواهد کدهای سطح پایین ویندوز (C/C++ Win32 API)، درایورها یا کدهای قدیمی مایکروسافت را بخواند و درک کند، شناخت این پیشوندها کاملاً ضروری است.
