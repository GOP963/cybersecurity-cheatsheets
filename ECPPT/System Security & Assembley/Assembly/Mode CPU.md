### 📌 1. حالت‌های مختلف CPU در معماری x86

پردازنده‌های خانواده 8086 و بعدی چند **mode (حالت کاری)** دارن:

1. **Real Mode (حالت واقعی)**
    
    - حالت اولیه بعد از بوت شدن CPU.
        
    - همه چیز 16 بیتی.
        
    - حافظه فقط تا 1MB قابل دسترسیه (به خاطر محدودیت آدرس‌دهی).
        
    - هیچ مکانیزم امنیتی نداره → هر برنامه‌ای می‌تونه به کل حافظه و سخت‌افزار دسترسی داشته باشه.
        
    - مثل همون دوران **DOS**.
        
2. **Protected Mode (حالت حفاظت‌شده)**
    
    - از پردازنده 80286 معرفی شد و روی 80386 به بلوغ رسید.
        
    - پشتیبانی کامل از **32-bit addressing** → دسترسی به تا 4 گیگابایت حافظه.
        
    - وجود **memory protection**:
        
        - دیگه هر پروسه نمی‌تونه بره حافظه پروسه دیگه رو دستکاری کنه.
            
        - سیستم‌عامل می‌تونه سطوح دسترسی (privilege levels یا همون ring ها) تعریف کنه.
            
    - امکان اجرای چند برنامه به صورت همزمان (**multitasking**).
        
    - مکانیزم مدیریت **virtual memory** → استفاده از paging و segmentation.
        
    - این همون حالتیه که ویندوز، لینوکس و اکثر سیستم‌عامل‌های مدرن روش کار می‌کنن.
        
3. **Virtual 8086 Mode (حالت شبیه‌سازی 8086)**
    
    - زیرمجموعه‌ای از Protected Mode هست.
        
    - یعنی CPU هنوز تو Protected Mode قرار داره، اما می‌تونه یک محیط مجازی مثل **real mode قدیمی** شبیه‌سازی کنه.
        
    - برای اجرای برنامه‌های قدیمی DOS روی ویندوز استفاده می‌شد.
        
    - هر Virtual 8086 مثل یه پروسه در محیط حفاظت‌شده اجرا میشه → امنیت همچنان حفظ میشه.
        

---

### 📌 2. چرا اسمش Protected Mode؟

چون برعکس Real Mode، پردازنده اینجا **محافظت سخت‌افزاری از حافظه و منابع** رو ارائه می‌ده. یعنی یه برنامه خراب یا مخرب نمی‌تونه مستقیم کل سیستم رو کرش کنه (البته باز هم می‌تونه اگه کرنل ضعیف باشه 😅).

---

### 📌 3. تفاوت Protected Mode و Virtual 8086

- **Protected Mode**: حالت کامل و پیشرفته سیستم‌عامل‌های مدرن.
    
- **Virtual 8086 Mode**: یه حالت خاص داخل Protected Mode برای اجرای برنامه‌های 16بیتی.
    

---

👉 به زبان ساده:

- Real Mode = ساده و ناامن، فقط برای بوت.
    
- Protected Mode = امن، چندوظیفه‌ای، حافظه زیاد → دنیای سیستم‌عامل‌های مدرن.
    
- Virtual 8086 Mode = اجرای نرم‌افزارهای خیلی قدیمی در دل Protected Mode.

## 🟢 1. **SMM Mode (System Management Mode) – همون God Mode**
- معرفی‌شده در پردازنده‌های 80386SL توسط اینتل.  
- وقتی CPU وارد این حالت میشه، همه‌ی حالت‌های دیگه (Real, Protected, Long, Virtual-8086) **متوقف** میشن.  
- برای کارهای خیلی حساس و سطح پایین طراحی شده، مثل:  
  - مدیریت مصرف انرژی (power management)  
  - کنترل سخت‌افزار (مثلاً لپ‌تاپ‌های قدیمی برای مدیریت باتری)  
  - امنیت سطح پایین بایوس/UEFI  
- کدی که تو این حالت اجرا میشه، در **SMRAM** (System Management RAM) ذخیره میشه. این قسمت رم برای سیستم‌عامل یا برنامه‌ها قابل دسترسی نیست.  
- چون دسترسی کامل به کل سخت‌افزار و حافظه داره → بهش لقب **God Mode** میدن.  
- اگه هکری بتونه وارد SMM بشه، **کنترل مطلق CPU و سیستم** رو به‌دست میاره (حتی قوی‌تر از کرنل سیستم‌عامل).  

---

## 🟢 2. **Long Mode**
- این حالت مخصوص پردازنده‌های **x86-64 (AMD64/Intel64)** هست.  
- برای اینکه CPU وارد Long Mode بشه باید اول در **Protected Mode** باشه.  
- امکانات:  
  - اجرای **64-bit instructions**.  
  - آدرس‌دهی حافظه تا **16 exabytes** (ولی فعلاً پردازنده‌ها محدودش کردن به چند صد ترابایت).  
  - پشتیبانی همزمان از:  
    - **Compatibility Mode** → اجرای برنامه‌های 32-bit.  
    - **Legacy Mode** → اجرای برنامه‌های 16-bit (تا حدی).  
- سیستم‌عامل‌های مدرن مثل ویندوز 64بیتی و لینوکس روی همین حالت اجرا میشن.  

---

## 📌 مقایسه سریع حالت‌ها
| Mode | توضیح کوتاه | کاربرد |
|------|-------------|--------|
| **Real Mode** | 16-bit, بدون امنیت، دسترسی به 1MB | بوت، سیستم‌های قدیمی |
| **Protected Mode** | 32-bit, امنیت، multitasking | ویندوز/لینوکس 32بیتی |
| **Virtual 8086 Mode** | شبیه‌سازی Real داخل Protected | اجرای برنامه‌های DOS |
| **Long Mode** | 64-bit, آدرس‌دهی عظیم | سیستم‌عامل‌های مدرن 64bit |
| **SMM (God Mode)** | مدیریت سطح‌سخت‌افزار، غیرقابل‌دسترس برای OS | BIOS, مدیریت انرژی، Rootkits خیلی خطرناک |

---

👉 پس:  
- **Protected Mode** انقلاب امنیت و multitasking رو آورد.  
- **Long Mode** دنیا رو برد به 64bit.  
- **SMM** یه حالت پنهانیه که دسترسی کامل به CPU داره (حتی قوی‌تر از OS).  

---

## 🟢 SMRAM = System Management RAM
- یه **بخش خاص از حافظه RAM** هست که فقط وقتی CPU توی **System Management Mode (SMM)** باشه قابل دسترسه.  
- سیستم‌عامل (ویندوز، لینوکس) یا حتی درایورها **هیچوقت بهش دسترسی ندارن**.  
- فقط کدی که توسط **BIOS/UEFI** یا میکروکد CPU اجرا میشه می‌تونه توش بخونه یا بنویسه.  

---

## 📌 چرا وجود داره؟
وقتی CPU وارد **SMM (God Mode)** میشه، باید یه جا داشته باشه برای ذخیره و اجرای کدهایی که مدیریت سخت‌افزار رو انجام میدن.  
این کدها معمولاً:  
- مدیریت **مصرف انرژی** (مثلاً Sleep, Hibernate)  
- مدیریت **فن، باتری، سنسورها**  
- کنترل‌های خیلی پایین سخت‌افزار (مثل ACPI)  
رو انجام میدن.  

این کارها رو نمی‌خوان سیستم‌عامل ببینه یا دستکاری کنه → برای همین توی SMRAM ذخیره میشن.  

---

## 🛡️ امنیت
- SMRAM خیلی حساسه چون شامل **کدهایی با دسترسی مطلق به سیستم** هست.  
- هکر اگه بتونه بهش دسترسی پیدا کنه → می‌تونه Rootkit سطح **SMM** بنویسه (قوی‌تر از Kernel و Hypervisor).  
- Rootkit توی SMRAM می‌تونه همیشه فعال بمونه چون سیستم‌عامل اصلاً نمی‌فهمه.  

---

## 📊 مثال ساده
فرض کن حافظه RAM کل شهره:  
- هر اپلیکیشن (برنامه‌ها) → خونه‌های معمولی.  
- سیستم‌عامل (OS Kernel) → شهرداری.  
- SMRAM → یه **پایگاه مخفی ارتش** وسط شهر که فقط با اجازه فرمانده (CPU در SMM) میشه واردش شد.  
بقیه حتی نمی‌دونن دقیقاً کجاست یا چه خبره اونجا.  

---

👉 خلاصه:  
**SMRAM = حافظهٔ مخفی CPU که فقط در حالت SMM قابل دسترسه.**  
مثل یک پناهگاه زیرزمینی برای اجرای کدهای BIOS/UEFI و مدیریت سخت‌افزار.

## 🟢 Bootkit کجاست؟

Bootkit معمولاً روی **Boot Process سیستم** می‌شینه، یعنی جایی که سیستم هنوز کامل بوت نشده:

1. **MBR Bootkit** → خودش رو توی Master Boot Record (بخش اول هارد دیسک) می‌نویسه.
    
    - قبل از اینکه ویندوز/لینوکس بوت بشه، Bootkit اجرا میشه.
        
2. **UEFI Bootkit** → خودش رو توی UEFI Firmware یا EFI Partition می‌نویسه.
    
    - این مدل جدیدتره و خیلی خطرناک‌تره چون Secure Boot رو دور میزنه.
        

📍 یعنی Bootkit دقیقاً قبل از سیستم‌عامل اجرا میشه و کنترل کل فرآیند Boot رو می‌گیره.

---

## 🔴 فرقش با SMM Rootkit

- **Bootkit** → توی **storage (هارد/SSD/firmware)** قرار می‌گیره و در **مرحله بوت** فعال میشه.
    
- **SMM Rootkit** → توی **SMRAM (حافظه مخفی CPU)** قرار می‌گیره و فقط موقعی که CPU وارد **SMM Mode** میشه اجرا میشه.
    

---

## 🛠️ مثالی برای تفکیک

🔹 Bootkit → مثل اینه که توی **دروازه‌ی شهر (Boot Loader)** کمین کنی، و قبل از ورود هر کسی (سیستم‌عامل) جلوشو بگیری و دستکاری کنی.  
🔹 SMM Rootkit → مثل اینه که توی **پایگاه مخفی ارتش (SMRAM)** نفوذ کنی و همه‌ی فرمان‌ها رو از داخل تغییر بدی بدون اینکه کسی بفهمه.

---

## 📊 مقایسه سریع

|نوع|محل ذخیره|زمان اجرا|قدرت|
|---|---|---|---|
|**Bootkit**|MBR / UEFI / EFI Partition|قبل از لود سیستم‌عامل|کنترل کامل Boot و Kernel|
|**SMM Rootkit**|SMRAM (CPU)|در حالت SMM|بالاتر از Kernel/Hypervisor (God Mode)|

---

🔑 نتیجه:

- **Bootkit** بیشتر مربوط به مرحله‌ی **Boot** و **Loader** هست.
    
- **SMM Rootkit** به مرحله‌ی **CPU Execution در God Mode** مربوط میشه.

## 🔹 تعریف مفهومی MBR

**MBR یا Master Boot Record یک سکتور ویژه در ابتدای دیسک هست که به سیستم می‌گه "سیستم‌عامل کجاست و از کجا باید بوت بشه".**  
یعنی در واقع مثل "نقشه شروع" برای کل هارددیسک عمل می‌کنه.

---

## 🔹 تعریف فنی MBR

- MBR همیشه توی **سکتور صفر (LBA 0)** دیسک قرار داره.
    
- طولش دقیقاً **512 بایت** هست.
    
- سه بخش داره:
    
    1. **Bootloader code (446 بایت اول)** → یک کد اسمبلی کوچیک که اولین برنامه اجراشده بعد از BIOS هست.
        
    2. **Partition Table (64 بایت بعدی)** → حاوی اطلاعات پارتیشن‌ها (حداکثر ۴ تا primary partition).
        
    3. **Boot Signature (2 بایت آخر → 0x55AA)** → برای شناسایی معتبر بودن MBR.
        

---

## 🔹 پس میشه گفت:

👉 **MBR = Bootloader Code + Partition Table + Boot Signature**  
که توی سکتور صفر هارد قرار داره و اولین چیزی هست که CPU بعد از روشن شدن (از طریق BIOS) اجراش می‌کنه.

---

### 📌 مثال خیلی ساده:

اگر دیسکت (قدیمی) یا هارد رو تصور کنی، اولین بخشش این شکلیه:

```
Offset  | Data
--------|--------------------------
0x000   | Bootloader code (446 bytes)
0x1BE   | Partition table (64 bytes)
0x1FE   | Boot signature (0x55AA)
```

---


آها، خیلی سؤال خوبیه مارتین 👌  
ببین، چون **MBR (Master Boot Record)** خیلی سطح پایین (low-level) هست، معمولاً با زبان‌های سطح بالا مثل C نوشته نمی‌شه. دلیلش اینه که **کد MBR باید دقیقاً 512 بایت باشه** و مستقیم توسط CPU بعد از روشن شدن اجرا می‌شه.

حالا قدم به قدم توضیح میدم:

---

### 1️⃣ شروع با اسمبلی (Assembly)

معمولاً نویسنده‌ها MBR رو با اسمبلی می‌نویسن. چون اسمبلی مستقیم روی رجیسترها و سخت‌افزار کار می‌کنه.

مثلاً یک کد ساده MBR توی اسمبلی (برای چاپ یک متن روی صفحه):

```asm
[BITS 16]           ; CPU در لحظه بوت در real mode و 16-bit هست
[ORG 0x7C00]        ; بایوس MBR رو در آدرس 0x7C00 لود می‌کنه

start:
    mov si, msg      ; آدرس متن رو توی SI می‌ریزیم
    call print

hang:
    jmp hang         ; سیستم رو همین‌طور نگه می‌داره

print:               ; تابع چاپ کاراکتر
    lodsb            ; کاراکتر بعدی رو از SI بخون
    or al, al        ; اگه صفر بود یعنی پایان رشته
    jz done
    mov ah, 0x0E     ; سرویس چاپ کاراکتر در BIOS
    int 0x10
    jmp print
done:
    ret

msg db "Hello MBR!", 0

times 510-($-$$) db 0  ; پر کردن بقیه سکتور تا 510 بایت
dw 0xAA55              ; امضای MBR (حتماً باید آخرش باشه)
```

🔹 وقتی اینو کامپایل و روی سکتور صفر دیسک بنویسی، سیستم بوت میشه و روی صفحه می‌نویسه:

```
Hello MBR!
```

---

### 2️⃣ زبان C هم میشه؟

مستقیم نه، چون C وابسته به کتابخونه‌ها و محیط (OS) هست.  
اما میشه:

- با C یک Bootloader نوشت (که مثلاً فایل‌سیستم رو لود کنه).
    
- بعد اون Bootloader رو با اسمبلی ترکیب کرد و در MBR قرار داد.
    

یعنی بخش اولیه (اولین سکتور = 512 بایت) رو حتماً با اسمبلی مینویسن، بعداً میشه کدهای پیچیده‌تر رو با C نوشت و در سکتورهای بعدی دیسک ذخیره کرد، و MBR اونارو لود کنه.

---

### 3️⃣ ابزارها برای شروع

- اسمبلی: **NASM** یا **FASM** برای نوشتن و کامپایل.
    
- برای تست: شبیه‌سازهایی مثل **QEMU** یا **Bochs** (تا لپ‌تاپت رو خراب نکنی 😅).
    
- دستور dd (در لینوکس) برای نوشتن MBR روی فایل یا دیسک.
    

مثال برای تست روی QEMU:

```bash
nasm -f bin mbr.asm -o mbr.bin
qemu-system-x86_64 -hda mbr.bin
```

---

🔑 پس خلاصه:

- شروع با اسمبلی (حتی ساده‌ترین MBR).
    
- بعد میشه ادامه رو با C نوشت، ولی همیشه اون 512 بایت اول باید اسمبلی باشه.
    

---

آها مارتین، این یه موضوع خیلی جالب و کمی پیچیده‌ست 😎  
ببین، وقتی درباره‌ی **Ring-3 تا Ring-0** حرف می‌زنیم، داریم **سطوح دسترسی (Privilege Levels)** پردازنده x86 رو توضیح می‌دیم. حالا Ring-3 پایین‌ترین سطح (یوزر)، Ring-0 کرنل، و بعضی‌ها Ring-1 و Ring-2 رو برای سیستم‌های خاص استفاده می‌کنن. اما Ring-(-3) چیز دیگه‌ست، که بهش گاهی **SMM / God Mode** میگن.

---

## 🔹 Ring -3 (SMM)

- Ring-3 → برنامه‌های یوزر (User Mode)
    
- Ring-0 → کرنل سیستم‌عامل (Kernel Mode)
    
- Ring -3 → **System Management Mode (SMM)**
    
    - یه سطح **بالاتر از کرنل**
        
    - CPU وقتی وارد SMM می‌شه، همه‌ی Ringها (0 تا 3) رو نادیده می‌گیره.
        
    - دسترسی کامل به **کل سخت‌افزار و حافظه** داره.
        
    - کدهایی که توی این سطح اجرا میشن، توی **SMRAM** ذخیره می‌شن (System Management RAM).
        

---

### 🔹 ویژگی‌های Ring -3

1. فقط وقتی CPU سیگنال **SMI (System Management Interrupt)** می‌گیره، واردش میشه.
    
2. سیستم‌عامل هیچ دسترسی به Ring-3 نداره. حتی Root یا Kernel هم نمی‌تونن ببیننش.
    
3. وظایف معمول:
    
    - مدیریت انرژی (ACPI, Sleep, Hibernate)
        
    - کنترل فن، باتری، سنسورها
        
    - امنیت سطح پایین Firmware/BIOS
        
4. هکرها اگه بتونن Ring -3 رو آلوده کنن → **کامل‌ترین کنترل ممکن روی CPU و سیستم** رو دارن.
    

---

### 🔹 مقایسه Ringها (برای شفافیت)

|Ring|سطح دسترسی|مثال|
|---|---|---|
|3|پایین‌ترین، User Mode|مرورگر، Word|
|2|Device Drivers (کم استفاده)|درایورهای خاص|
|1|Device Drivers (کم استفاده)|درایورهای خاص|
|0|کرنل سیستم‌عامل|ویندوز/لینوکس کرنل|
|-3|SMM / God Mode|BIOS, ACPI, SMRAM|

---

🔑 نکته: Ring-(-3) خیلی بالاتر از کرنل هست، به همین دلیل بهش میگن **God Mode**.  
حتی اگر سیستم‌عامل خراب بشه یا کرنل هک بشه، Ring-3 تا Ring-0 هیچ کنترلی روی Ring-(-3) ندارن.
