## ✅ SPN چیه؟ (Service Principal Name)

**SPN = شناسه‌ی منحصربه‌فرد یک سرویس در دامین**

وقتی توی دامین از یک سرویس (مثل MSSQL، HTTP، LDAP، CIFS و ...) استفاده می‌کنی که از **Kerberos Authentication** پشتیبانی می‌کنه، اون سرویس باید توی Active Directory **با یه نام مشخص (SPN)** ثبت شده باشه تا کاربران بتونن با اون سرویس ارتباط بگیرن.

---

## 📌 فرمت SPN به چه شکله؟

SPN همیشه به این شکل تعریف می‌شه:

```
<service-type>/<hostname>:<port>
```

مثال‌ها:

```
HTTP/webserver1.contoso.com
MSSQLSvc/sqlserver.contoso.com:1433
CIFS/file-server.domain.local
```

---

## 🧠 چرا SPN مهمه؟

وقتی یه کلاینت (کاربر) می‌خواد به یه سرویس در شبکه وصل شه، باید بدون Kerberos برای کدوم **service account** تیکت صادر کنه. اینجا SPN وارد عمل می‌شه:

|مرحله|شرح|
|---|---|
|1️⃣|کاربر درخواست اتصال به مثلاً MSSQL روی یک سرور خاص می‌ده.|
|2️⃣|سیستم با SPN شناسایی می‌کنه که کدوم اکانت Active Directory مسئول این سرویسه.|
|3️⃣|DC (Domain Controller) یه تیکت Kerberos رمز شده با hash اون سرویس‌اکانت برمی‌گردونه.|
|4️⃣|این تیکت برای احراز هویت به سرویس داده می‌شه.|

---

## 👤 SPN به چه اکانت‌هایی اختصاص داده می‌شه؟

SPN می‌تونه روی این‌ها تنظیم بشه:

- اکانت‌های کامپیوتر (Computer Account)
    
- اکانت‌های سرویس (Service Accounts)
    
- اکانت‌های کاربری معمولی (User Accounts)
    

---

## 🔎 چطور SPNها رو ببینیم یا تغییر بدیم؟

### دیدن SPNها:

```powershell
setspn -L <AccountName>
```

مثال:

```powershell
setspn -L sqlsvc
```

### اضافه کردن SPN:

```powershell
setspn -A MSSQLSvc/sqlserver.domain.com:1433 sqlsvc
```

### حذف SPN:

```powershell
setspn -D MSSQLSvc/sqlserver.domain.com:1433 sqlsvc
```

---

## 🧨 چطور Kerberoasting از SPN سوءاستفاده می‌کنه؟

- اکانتی که SPN داره، به این معنیه که **برای اون سرویس، تیکت Kerberos قابل دریافت هست**.
    
- اون تیکت رمز شده با **hash پسورد اکانت سرویسیه**.
    
- مهاجم این تیکت رو می‌گیره و سعی می‌کنه hash پسورد سرویس‌اکانت رو کرک کنه.

| مشکل                                                         | نتیجه                         |
| ------------------------------------------------------------ | ----------------------------- |
| تعریف SPN برای اکانت با پسورد ضعیف                           | قابل کرک با Kerberoasting     |
| تنظیم SPN روی اکانت‌هایی با دسترسی بالا (مثلاً Domain Admin) | خطر کرک و تسلط کامل بر دامنه  |
| تعریف چند SPN برای یک سرویس (duplicated SPN)                 | اختلال در احراز هویت Kerberos |

## 🥷 Kerberoasting چیه؟

**Kerberoasting** یک **تکنیک حمله در Active Directory** هست که توسط مهاجم‌ها استفاده می‌شه تا **هش پسورد اکانت‌های Service** رو استخراج کنن، مخصوصاً اکانت‌هایی که با **Service Principal Name (SPN)** ثبت شدن.

هدف نهایی:

> گرفتن هش‌ها از سرویس‌هایی که با Kerberos کار می‌کنن، و کرک کردن اون هش‌ها برای به‌دست آوردن پسوردهای plaintext.

---

## 🧠 پشت‌پرده چیه؟ (Kerberos Overview)

برای درک Kerberoasting، باید بدونیم Kerberos چطوری کار می‌کنه:

1. کاربر به **Domain Controller** وصل می‌شه و TGT می‌گیره (Ticket Granting Ticket).
    
2. با TGT، از **TGS (Ticket Granting Service)**، یک تیکت برای سرویس خاص می‌گیره.
    
3. این تیکت (TGS Ticket) برای احراز هویت به سرویس مورد نظر داده می‌شه.
    

❗ نکته مهم: **تیکت TGS با کلید کاربر سرویسی که بهش دسترسی می‌خوای رمز شده** (که معمولاً همون password hash اون سرویسه).

---

## 🎯 Kerberoasting چیکار می‌کنه؟

مهاجم:

1. با اکانت معمولی (نه ادمین) وارد دامنه می‌شه.
    
2. با دستور مثل `Get-SPN` یا ابزارهایی مثل `PowerView`، لیست اکانت‌هایی که SPN دارن رو پیدا می‌کنه.
    
3. از Domain Controller تیکت TGS برای اون سرویس‌ها درخواست می‌کنه.
    
4. تیکت‌ها رو ذخیره می‌کنه. این تیکت‌ها با **hash پسورد اکانت سرویسی** رمز شدن.
    
5. این هش‌ها رو به ابزارهایی مثل **Hashcat** یا **John the Ripper** می‌ده تا آفلاین کرک بشن و پسورد plaintext به‌دست بیاد.
    

---

## 💥 چرا این حمله خطرناک‌ـه؟

- چون از **ویژگی واقعی و قانونی Kerberos** استفاده می‌کنه (نه باگ یا exploit).
    
- **نیاز به دسترسی ادمین نداره** — یک کاربر دامنه عادی هم می‌تونه انجامش بده.
    
- اگه سرویسی پسورد ساده داشته باشه، به راحتی کرک می‌شه.
    
- بعضی از این اکانت‌های سرویس، **دسترسی‌های بالایی دارن** (مثلاً ادمین SQL Server یا حتی Domain Admin).

## 🔐 جمله اصلی:

> **تیکت TGS با کلید کاربر سرویسی که بهش دسترسی می‌خوای رمز شده**  
> _(و این کلید معمولاً همون password hash اون کاربر سرویسیه)_

---

## 🧠 اول باید بدونیم "کلید" یعنی چی؟

در Kerberos، **کلید رمزنگاری (key)** برای رمزگذاری تیکت‌ها استفاده می‌شه.  
این کلید معمولاً از **هش رمز عبور (hash of the password)** کاربر/سرویس ساخته می‌شه.

مثلاً اگر یک سرویس‌اکانت پسوردش `P@ssw0rd123` باشه:

- کلید Kerberos = `hash(P@ssw0rd123)` ← مثلاً با الگوریتم `RC4-HMAC` یا `AES256`
    

---

## 🎟️ حالا تیکت TGS چیه؟

وقتی کاربر بخواد به یه سرویس مثل MSSQL یا HTTP در شبکه وصل بشه، باید از Domain Controller یک تیکت دسترسی (TGS = Ticket Granting Service) برای اون سرویس بگیره.

### چی داخل تیکت TGS هست؟

- اطلاعات مربوط به سرویس و کاربر
    
- **این اطلاعات با کلید مخصوص سرویس رمز شده** (همون hash پسورد سرویس‌اکانت)
    

---

## 🧨 چرا این مهمه برای مهاجم؟

چون:

1. مهاجم به راحتی می‌تونه با یک اکانت معمولی این تیکت‌ها رو درخواست کنه (با ابزارهایی مثل Rubeus یا Impacket).
    
2. تیکت رمز شده رو دریافت می‌کنه.
    
3. حالا چون این تیکت با **hash پسورد سرویس‌اکانت** رمز شده، اگه مهاجم بتونه این هش رو بشکنه (کرک کنه)، پسورد اون سرویس‌اکانت رو به دست میاره.
    

---

## 📦 مثال واقعی:

فرض کن اکانت `sqlsvc` یک سرویس SPN به شکل زیر داره:

```
MSSQLSvc/sqlserver.contoso.local:1433
```

و این اکانت پسوردش `Welcome123!` هست.

وقتی مهاجم با دستور (مثلاً):

```bash
GetUserSPNs.py contoso.local/user:pass -request
```

درخواست تیکت برای این SPN می‌ده:

- Domain Controller یک **تیکت TGS می‌سازه**.
    
- این تیکت با **hash("Welcome123!")** رمز می‌شه.
    
- تیکت به مهاجم داده می‌شه.
    
- مهاجم می‌تونه این هش رو بده به `Hashcat` و بگه:
    
    ```bash
    hashcat -m 13100 ticket.hash rockyou.txt
    ```
    

اگه پسورد ضعیف باشه → پسورد بدست میاد → مهاجم دسترسی می‌گیره ✅

|"قابل کرک"|چون تیکت در اختیار مهاجم قرار می‌گیره و رمزنگاری‌شده‌ست، می‌شه آفلاین کرکش کرد|

## ❓ سؤال تو:

> وقتی من به‌عنوان مهاجم با اکانت دامنه TGS برای یک سرویس می‌گیرم،  
> **آیا تیکت TGS با پسورد خود من رمز شده (کاربری که می‌خواد وصل شه)،  
> یا با پسورد اون سرویسی که دارم درخواست می‌دم؟**

### ✅ جواب کوتاه:

**❗ تیکت TGS با پسورد (در واقع hash پسورد) خودِ سرویس رمز شده. نه پسورد کاربر.**

## 🧠 توضیح فنی‌تر:

### ساختار Kerberos:

وقتی کاربر دامنه (مثلاً `user1`) بخواد به یک سرویس مثل MSSQL روی سرور `sql1.contoso.com` وصل شه:

1. کاربر ابتدا از DC یک **TGT (Ticket Granting Ticket)** می‌گیره ← این با hash کاربر رمز می‌شه.
    
2. بعدش با TGT از DC می‌خواد به **سرویس مشخصی** دسترسی پیدا کنه.
    
    - مثلاً SPN: `MSSQLSvc/sql1.contoso.com:1433`
        
3. DC بررسی می‌کنه که این SPN مال کدوم اکانت سرویسی در AD هست.
    
    - مثلاً اکانت `sqlsvc@contoso.com`
        
4. DC یک تیکت TGS تولید می‌کنه و:
    
    - اطلاعات کاربر، timestamp و session key رو توی تیکت قرار می‌ده
        
    - این تیکت رو با **hash پسورد sqlsvc** رمز می‌کنه
        
5. این تیکت رمز شده به کاربر برمی‌گرده.
    
6. حالا کاربر این تیکت رو به MSSQL می‌ده. چون اون سرویس کلید خودش (hash پسورد sqlsvc) رو داره، می‌تونه تیکت رو باز کنه و کاربر رو احراز کنه.

|مورد|پاسخ|
|---|---|
|تیکت TGS رمز شده با چی؟|**hash پسورد سرویس‌اکانت (sqlsvc)**|
|مهاجم با این تیکت چی کار می‌کنه؟|اون هش رمزنگاری رو جدا می‌کنه و با Hashcat کرک می‌کنه|
|پسوردی که به‌دست میاد مال کیه؟|**سرویسی که SPN داره، نه خود کاربر**|

## 🔓 نکته مهم امنیتی:

مهاجم هیچ‌وقت نیاز نداره به سرویس وصل شه یا credential اون سرویس رو داشته باشه.

تنها کاری که می‌کنه اینه که:

1. می‌فهمه چه اکانت‌هایی SPN دارن (مثلاً با PowerView یا `GetUserSPNs.py`)
    
2. برای اون‌ها تیکت TGS درخواست می‌کنه
    
3. هش موجود در تیکت‌ها رو جدا می‌کنه و سعی می‌کنه پسورد سرویس‌اکانت رو کرک کنه
    

---

## 📦 مثال عینی برای درک کامل:

فرض کن این SPN در دامنه هست:

```
MSSQLSvc/sql.contoso.local:1433 → مرتبط با اکانت sqlsvc
```

تو با `user1` وارد شبکه شدی. حالا اینو اجرا می‌کنی:

```bash
GetUserSPNs.py CONTOSO/user1:Pass123 -dc-ip 10.0.0.5 -request
```

→ DC به تو یک تیکت TGS می‌ده که با **hash پسورد sqlsvc** رمز شده  
→ تو اون هش رو ذخیره می‌کنی و کرک می‌کنی  
→ پسورد sqlsvc رو به دست میاری (مثلاً `SqlP@ss2023!`)  
→ حالا می‌تونی با اون اکانت لاگین کنی، به MSSQL وصل شی، یا privilege escalation انجام بدی

|---|---|
|آیا تیکت TGS رمز شده با پسورد کاربر درخواست‌کننده‌ست؟|❌ خیر|
|آیا تیکت TGS رمز شده با hash پسورد سرویسه؟|✅ بله|
|پسوردی که با کرک کردن هش بدست می‌آد مال کیه؟|سرویس‌اکانت (مثلاً sqlsvc)|

|این حمله credential harvesting محسوب می‌شه؟|✅ بله، و می‌تونه منجر به privilege escalation بشه|

## 🔐 آیا Kerberoasting ربطی به **pre-authentication** داره؟

### ✅ جواب کوتاه:

**نه مستقیماً، ولی مفاهیمشون به هم نزدیک‌ان و هر دو به عملکرد داخلی Kerberos مربوط می‌شن.**

---

## 🔎 اول: pre-authentication چیه؟

در Kerberos:

وقتی کاربر بخواد اولین تیکت خودش (TGT) رو بگیره، باید:

1. به DC بگه: «من فلانی هستم» (یعنی user@domain)
    
2. DC می‌گه: «بسیار خوب، ولی اول پسوردت رو ثابت کن»
    

پس کاربر باید:

- Timestamp رو با **hash پسورد خودش رمز کنه** و برای DC بفرسته
    

اگر DC موفق شد اون رمز رو با **کلید خودش رمزگشایی کنه**، یعنی:

- پسورد کاربر درسته
    
- پس بهش یک **TGT** می‌ده
    

---

## ⛔ اگر "Do not require Kerberos pre-authentication" فعال باشه چی؟

- DC بدون اینکه بخواد کاربر ثابت کنه رمز عبورش درسته، TGT رو می‌ده
    
- و این باعث می‌شه که مهاجم بتونه از DC بخواد برای هر اکانتی یه تیکت pre-auth ساخته‌شده بفرسته  
    → در نتیجه حمله‌ای به نام **AS-REP Roasting** اتفاق می‌افته
    

---

## حالا برگردیم به Kerberoasting:

### ✳️ تفاوت اصلی:

|مورد|Kerberoasting|AS-REP Roasting|
|---|---|---|
|نیاز به pre-auth|❌ نه|✅ فقط وقتی pre-auth غیرفعاله|
|نوع تیکت|TGS (سرویس)|AS-REP (اولیه)|
|رمز تیکت با کیه؟|hash پسورد سرویس|hash پسورد کاربر|
|هدف|کرک کردن سرویس‌اکانت‌ها|کرک کردن اکانت‌هایی که pre-auth ندارن|

---

## ✅ نتیجه نهایی:

🔸 **Kerberoasting** کاملاً جدا از pre-authentication عمل می‌کنه:

- کاربر مهاجم از قبل TGT داره (پس مرحله pre-auth رو رد کرده)
    
- حالا داره درخواست **TGS** می‌ده برای SPNهای ثبت‌شده
    
- و این تیکت‌ها با **hash سرویس‌اکانت** رمز می‌شن، نه کاربر
    
- پس Kerberoasting حتی **اگر pre-auth فعال باشه هم قابل اجراست**

## 📌 در یک جمله:

> Kerberoasting به **TGS و سرویس‌اکانت** مربوط می‌شه  
> در حالی که **pre-auth** و AS-REP Roasting به مرحله‌ی **اولیه‌ی احراز هویت کاربر** مربوط می‌شن

### ✅ **اقدامات دفاعی برای جلوگیری از Kerberoasting:**

---

#### 🔐 1. **استفاده از رمزهای قوی برای حساب‌های سرویسی (Service Accounts):**

- اگر رمز عبور حساب سرویسی ساده یا قابل کرک باشد، مهاجم به‌راحتی می‌تواند هش TGS را کرک کند.
    
- از رمزهایی با طول و پیچیدگی بالا استفاده کنید.
    
- رمزهای حساب‌های سرویسی را به صورت دوره‌ای تغییر دهید.
    

---

#### ⚠️ 2. **محدود کردن استفاده از حساب‌های سرویسی با SPN:**

- تنها به حساب‌هایی SPN اختصاص دهید که واقعاً به آن نیاز دارند.
    
- حساب‌هایی با SPN مشخص، هدف Kerberoasting هستند.
    
- استفاده از Managed Service Accounts (MSA) یا Group Managed Service Accounts (gMSA) در ویندوز سرور باعث کاهش ریسک می‌شود.
    

---

#### 🔒 3. **عدم استفاده از حساب‌های دارای امتیاز بالا (مثل Domain Admin) به‌عنوان Service Account:**

- اگر مهاجم پسورد یک حساب سرویسی را کرک کند و آن حساب دسترسی بالایی داشته باشد، مهاجم می‌تواند به دامنه نفوذ کند.
    
- حساب‌های سرویسی باید حداقل سطح دسترسی موردنیاز را داشته باشند (اصل Least Privilege).
    

---

#### 👁‍🗨 4. **مانیتورینگ و شناسایی رفتارهای مشکوک:**

- بررسی لاگ‌های زیر می‌تواند کمک کند:
    
    - `Event ID 4769` – درخواست TGS
        
- اگر کاربری تعداد زیادی درخواست TGS برای سرویس‌های مختلف ثبت کند، احتمال Kerberoasting وجود دارد.
    
- بررسی اینکه چه کسی TGS برای SPNهای زیاد می‌گیرد.
    

---

#### ⛔ 5. **استفاده از ویژگی جدید Windows به نام AES Encryption Enforcement:**

- در ویندوزهای جدید می‌توان تنظیم کرد که فقط رمزنگاری AES برای Kerberos استفاده شود (RC4 ضعیف‌تر است).
    
- این مورد حمله را سخت‌تر می‌کند (اگرچه به‌تنهایی کافی نیست).
    

---

#### 🔐 6. **Active Directory Tiering و تقسیم شبکه:**

- اجرای اصول Tiered Administration به‌طوری‌که حساب‌های حیاتی فقط در سیستم‌های امن استفاده شوند.
    

---

#### ⚠️ 7. **استفاده از ابزارهای تشخیص مانند:**

- Microsoft Defender for Identity (MDE)
    
- Elastic (با قوانین شناسایی درست)
    
- SIEM برای شناسایی رفتار مشکوک مانند استخراج لیست SPNها یا حجم بالای TGS
    

---

### 💡 جمع‌بندی:

Kerberoasting بیشتر به خاطر ضعف در **رمز عبور حساب‌های سرویسی** و **در دسترس بودن هش آن‌ها از طریق درخواست TGS** قابل انجام است. پس تمرکز دفاعی شما باید روی **تقویت رمز عبورها، محدودسازی SPNها، مانیتورینگ، و اصل Least Privilege** باشد.

### ✅ **پیش‌نیازها:**

1. دسترسی اولیه به شبکه دامنه (Domain Joined System)
    
2. اعتبار کاربری در دامنه (مثلاً کاربری با دسترسی معمولی - Domain User)
    
3. نصب بودن PowerView یا استفاده از ابزارهای مشابه (مانند Rubeus یا Impacket)

## ⚙️ مراحل حمله Kerberoasting با PowerView:

### 🔹 مرحله اول: شناسایی سرویس‌اکانت‌ها (Service Accounts با SPN)

```powershell
Import-Module .\PowerView.ps1
Get-DomainUser -SPN
```

📌 این دستور کاربران دامنه‌ای را نشان می‌دهد که به آن‌ها SPN (Service Principal Name) اختصاص داده شده — که نشان‌دهنده‌ی سرویس‌هایی‌ست که آن کاربر به عنوان حساب سرویس استفاده می‌کند.


همچنین میتونیم با استفاده از دستور 
```
	setspn -T research -Q */*
```

تمایمه spn های user account را پیدا کنیم

همچنین میتونیم تمامیه تیکت هایی که کش شده اند رو هم ببینیم


دستور `klist` یک ابزار خط فرمان در ویندوز (و لینوکس) است که برای **نمایش تیکت‌های Kerberos که در حال حاضر کش شده‌اند** استفاده می‌شود.

---

### 📌 کاربرد اصلی `klist`:

نمایش تیکت‌های موجود در حافظه کاربر فعلی، شامل:

- تیکت TGT (Ticket Granting Ticket)
    
- تیکت‌های TGS (برای سرویس‌هایی که قبلاً بهشون متصل شدی)
    

---

### ✅ دستور ساده:

```powershell
klist
```

### 🧾 نمونه خروجی:

```text
Current LogonId is 0:0x3e7

Cached Tickets: (2)

#0> Client: user@RESEARCH.LOCAL
    Server: krbtgt/RESEARCH.LOCAL@RESEARCH.LOCAL
    Ticket Expires: 7/23/2025 11:42:00
    Ticket Flags: 0x40e10000 -> forwardable renewable initial pre_authent

    ...
```

---

### 📍 کاربردهای مهم در تست نفوذ و دفاع:

|کاربرد|توضیح|
|---|---|
|دیدن تیکت‌های فعلی|برای فهمیدن اینکه کاربر چه تیکت‌هایی داره|
|بررسی TGT|ببینی آیا TGT داره یا نه، برای حملاتی مثل Pass-the-Ticket مهمه|
|بعد از درخواست TGS|وقتی TGS درخواست کردی (مثلاً در Kerberoasting)، با `klist` می‌تونی تیکت مربوطه رو ببینی|
|حذف کش Kerberos|با `klist purge` می‌تونی تیکت‌ها رو پاک کنی|

---

### 🔻 مثال پیشرفته: پاک کردن تیکت‌ها

```powershell
klist purge
```

> پاک می‌کنه تمام تیکت‌های Kerberos کش‌شده کاربر فعلی رو. خیلی مهمه وقتی می‌خوای با `Rubeus` یا ابزارهای دیگه کار کنی.

### 🔹 مرحله دوم: گرفتن Ticket Granting Service (TGS) برای آن SPNها

می‌توانی از ابزار Rubeus استفاده کنی که با همان TGT فعلی (که از قبل با لاگین داریم) می‌تواند درخواست TGS کند:

```bash
Rubeus.exe kerberoast
```

یا برای خروجی hash مخصوص کرک کردن:

```bash
Rubeus.exe kerberoast /output:hashes.txt
```

این هش‌ها از نوع **Kerberos TGS-REP** هستند و معمولاً از نوع **RC4_HMAC** یا **AES256** و قابل کرک با ابزارهایی مثل Hashcat و John هستند.

---

### 🔹 مرحله سوم: کرک هش‌ها

مثلاً با Hashcat:

```bash
hashcat -m 13100 hashes.txt wordlist.txt
```

> -m 13100 مخصوص هش‌های Kerberos 5 TGS-REP Hash است.




همچنین میتونیم با استفاده از ابجکت های C# بیایم و یک توکن kerberose برای اون SPN مد نظرمون ایجاد کنیم 

```
ps> Add-Type -AssembleName System.IdentityModel
ps> New-Object System.IdentityModel.Tokens.KerberosRequestorSecurityToken -Argumentlist "SPN_NAME" exmaple "mysql/charon.local:3306"
```


ما با استفاده از این ابجکت C# در پاورشل میتونیم یک توکن TGS ایجاد کنیم 





```
ps> invoke-mimikatz -command '"kerberos::list /export"'
```

با استفاده از این دستور از mimikatz میتونیم بیایم و اون TGS هارو استخراج کنیم و در نهایت  میتونیم با استفاد اسکریپت tgscrack.py بیایم و عملیات کرک رو انجام بدیم 

یا با استفاده از Rubeus.exe اینکارو انجام میدیم

#سوال : یعنی تاکتیک تکنیک ها به این صورت میشه که من با intial access داشتن بر روی سیستم هدف و داشتن TGT سیستم هدف میام و به نوعی privilage میکنم 
یا نه تو این سناریو به این صورته که حتی من دسترسی به اون سرویس ندارم و میخوام به نوعی رمز اون سرویس رو به دست بیارم 


---

## 🎯 خلاصه‌ی اصلی:

Kerberoasting یک تکنیک در تاکتیک **Credential Access** هست،  
که مهاجم از طریق یک اکانت عادی در دامنه می‌خواد **پسورد سرویس‌اکانت‌های دارای SPN** رو کرک کنه  
(و از این طریق احتمالاً privilege escalation انجام بده).

---

## 🧭 دو سناریوی اصلی که پرسیدی:

### ✅ سناریو ۱:

> «من Initial Access دارم (مثلاً با phishing وارد یه سیستم دامنه شدم)، و یک TGT دارم. حالا با TGT می‌خوام privilege escalation انجام بدم»

✅ **این دقیقاً همون استفاده‌ی معمول Kerberoasting هست.**

- تو با یه اکانت عادی دامنه لاگین کردی (نیازی به local admin هم نیست)
    
- چون عضو دامنه‌ای، پس TGT به‌صورت خودکار داری (در زمان logon)
    
- با همون TGT، می‌تونی از DC بخوای برات TGS برای SPNهای موجود بفرسته
    
- این تیکت‌ها رو جمع می‌کنی و هش‌هاشون رو کرک می‌کنی
    

🎯 هدف: privilege escalation با به‌دست آوردن credentials سرویس‌های حساس

---

### ✅ سناریو ۲:

> «من دسترسی به اون سرویس ندارم، فقط می‌خوام رمز اون سرویس‌اکانت رو به دست بیارم»

✅ این هم کاملاً ممکنه و رایجه.

- تو لازم نیست به خود **سرویس** دسترسی داشته باشی (مثلاً لازم نیست به MSSQL وصل شی)
    
- فقط کافی SPN اون سرویس توی Active Directory تعریف شده باشه
    
- تیکت‌ها رو با Kerberos درخواست می‌دی، چون SPN ثبت شده، تیکت تولید می‌شه
    
- هش رو می‌گیری و کرکش می‌کنی
    

📌 در واقع تو از **Kerberos برای دسترسی غیرمستقیم به هش استفاده می‌کنی**، بدون اینکه به سرویس لاگین کرده باشی.

## 🔐 چرا این حمله خطرناک‌ـه؟

|ویژگی|توضیح|
|---|---|
|❌ نیازی به دسترسی ادمین نداره|اکانت دامنه معمولی کافیه|
|❌ نیازی به اتصال به سرویس نیست|فقط تیکت از DC بگیری کافیه|
|✅ کرک آفلاین انجام می‌شه|بدون تولید ترافیک مشکوک|
|🔓 پسورد سرویس‌ها ممکنه به‌دست بیاد|مخصوصاً اگه ضعیف باشن یا اشتراکی باشن|

## 🧪 Tactics & Techniques (MITRE ATT&CK)

|بخش|مقدار|
|---|---|
|Tactic|Credential Access|
|Technique|**T1558.003 – Kerberoasting**|
|Requirement|دسترسی به اکانت دامنه + TGT|
|هدف نهایی|استخراج و کرک hash سرویس‌اکانت‌های دارای SPN|

---

## 🎯 هدف Kerberoasting:

- پیدا کردن اکانت‌های با SPN
    
- گرفتن تیکت‌هاشون (TGS) که رمز شدن با hash پسوردشون
    
- کرک کردن هش‌ها برای رسیدن به plaintext password
    
- استفاده از اون پسورد برای privilege escalation یا lateral movement
    

---

## ✅ جمع‌بندی:

|مورد|جواب|
|---|---|
|نیاز به دسترسی اولیه به دامنه؟|بله (ولی فقط در حد کاربر عادی)|
|نیاز به دسترسی به خود سرویس؟|❌ نه|
|هدف چیه؟|دستیابی به credential سرویس‌ها|
|آیا privilege escalation محسوب می‌شه؟|✅ بله، چون ممکنه پسورد admin بدست بیاد|


---

## 🔹 نکته مهم

- برای **Kerberoasting** تو نیاز نداری که کل تیکت رو به شکل فایل خام (باینری) داشته باشی.
    
- چیزی که باید از این تیکت استخراج کنی، **هش Kerberos (فرمت `$krb5tgs$...`)** هست.
    
- این فرمت همونیه که ابزارهایی مثل **Hashcat** و **John** می‌تونن بفهمن و روش کرک انجام بدن.
    

---

## 🔹 ابزارهای استخراج هش از تیکت

بسته به سیستمی که استفاده می‌کنی (Windows یا Linux)، ابزارهای مختلفی وجود دارن:

### 1. در ویندوز

- **Rubeus**:
    
    ```powershell
    Rubeus kerberoast /format:hashcat
    ```
    
    یا اگر تیکت رو از فایل `.kirbi` داری:
    
    ```powershell
    Rubeus asktgs /ticket:service.kirbi /extract
    ```
    
- **Mimikatz**:
    
    ```mimikatz
    kerberos::list /export
    ```
    
    این کار تیکت‌ها رو dump می‌کنه (به صورت kirbi). بعد باید اون kirbi رو با ابزارهای دیگه به hash تبدیل کنی.
    

---

### 2. در لینوکس

- **Impacket – GetUserSPNs**:
    
    ```bash
    GetUserSPNs.py domain/user:password -dc-ip DC_IP -request
    ```
    
    خروجی مستقیم بهت هش `$krb5tgs$23$...` می‌ده که آماده کرک با Hashcat/John هست.
    
- **kirbi2john.py** (بخشی از John the Ripper Jumbo):
    
    ```bash
    kirbi2john.py ticket.kirbi > hash.txt
    ```
    

---

## 🔹 مرحله بعد (کرک)

وقتی هش رو استخراج کردی، خروجی شبیه این می‌شه:

```
$krb5tgs$23$*SQLService$CORP.LOCAL$MSSQLSvc/sql01.corp.local:1433*$31adf6c18c9f8bd978...
```

حالا می‌تونی:

- با **Hashcat**:
    
    ```bash
    hashcat -m 13100 -a 0 hash.txt wordlist.txt
    ```
    
- یا با **John**:
    
    ```bash
    john --wordlist=wordlist.txt hash.txt
    ```
    

---

✅ پس چیزی که الان داری (اون باینری که فرستادی) **هنوز آماده کرک نیست**.  
باید اول با یکی از ابزارهایی مثل **Rubeus / Impacket / kirbi2john** تبدیلش کنی به هش قابل خواندن برای کرک.
