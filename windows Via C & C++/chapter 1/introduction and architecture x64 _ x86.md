

### خلاصه‌ی فصل مقدمه و ویندوز ۶۴ بیتی

ویندوز یک سیستم‌عامل بسیار پیچیده است و یادگیری کامل آن برای یک نفر ممکن نیست. بهترین روش یادگیری، شروع از **سطح پایین** و درک **بلوک‌های سازنده‌ی پایه‌ای ویندوز** است. با فهم این مبانی، یادگیری مفاهیم سطح بالاتر بسیار ساده‌تر می‌شود.  
این کتاب دقیقاً با همین رویکرد نوشته شده و روی مفاهیم بنیادی‌ای تمرکز دارد که هر برنامه‌نویس ویندوز باید بداند.

تمرکز اصلی کتاب:

- معرفی **بلوک‌های سازنده‌ی پایه‌ای ویندوز**
    
- توضیح نحوه‌ی استفاده‌ی خود سیستم از این بلوک‌ها
    
- آموزش استفاده‌ی صحیح از آن‌ها در برنامه‌های C و ++C
    
- ساخت abstractionها و بلوک‌های ترکیبی توسط برنامه‌نویس
    

مفاهیمی مثل **COM** و **CLR** مستقیماً محور کتاب نیستند، اما چون این فناوری‌ها خودشان بر پایه‌ی مفاهیم بنیادی مثل:

- Process
    
- Thread
    
- Memory Management
    
- DLL
    
- Unicode
    

ساخته شده‌اند، یادگیری این مبانی باعث می‌شود درک COM و .NET بسیار ساده‌تر شود. رد کردن این مرحله و رفتن مستقیم سراغ معماری‌های پیچیده، معمولاً باعث ضعف عمیق در دانش و کدنویسی می‌شود.

### خلاصه‌ی ویندوز ۶۴ بیتی

مایکروسافت از ویندوز ۶۴ بیتی پشتیبانی می‌کند و آینده‌ی سیستم‌ها به‌طور کامل به سمت پردازنده‌های ۶۴ بیتی رفته است. به همین دلیل، توسعه‌دهندگان باید مطمئن شوند برنامه‌هایشان روی ویندوز ۶۴ بیتی به‌درستی اجرا می‌شود.

نکات کلیدی ویندوز ۶۴ بیتی:

- هسته‌ی ۶۴ بیتی همان هسته‌ی ۳۲ بیتی است که پورت شده؛ مفاهیم پایه تغییری نکرده‌اند.
    
- Windows API در هر دو معماری **یکسان** است.
    
- برنامه‌های ۳۲ بیتی روی ویندوز ۶۴ بیتی اجرا می‌شوند، اما نسخه‌ی ۶۴ بیتی عملکرد بهتری دارد.
    
- مهم‌ترین مزیت ۶۴ بیت، **فضای آدرس‌دهی بسیار بزرگ‌تر** (تا چند ترابایت) است.
    
- بیشتر انواع داده همچنان ۳۲ بیتی هستند؛ فقط **Pointerها و Handleها ۶۴ بیتی شده‌اند**.
    
- مهاجرت از ۳۲ بیت به ۶۴ بیت معمولاً ساده است و نیاز به بازنویسی کامل برنامه ندارد.
    

در نهایت، کتاب طوری نوشته شده که با **یک کد منبع واحد** بتوان برنامه را هم برای ویندوز ۳۲ بیتی و هم ۶۴ بیتی کامپایل کرد.

## فصل ۱: مدیریت خطا (Error Handling)


وقتی یک تابع ویندوزی را فراخوانی می‌کنید، ابتدا پارامترهایی را که به آن داده‌اید بررسی (Validate) می‌کند و سپس تلاش می‌کند وظیفه‌ی خود را انجام دهد. اگر پارامتر نامعتبر باشد یا به هر دلیل دیگری عملیات قابل انجام نباشد، **مقدار بازگشتی (Return Value)** تابع نشان می‌دهد که تابع به نوعی شکست خورده است.  
جدول ۱-۱ نوع داده‌هایی را نشان می‌دهد که اکثر توابع ویندوز برای اعلام نتیجه استفاده می‌کنند.


```c
int MessageBox(
  [in, optional] HWND    hWnd,
  [in, optional] LPCTSTR lpText,
  [in, optional] LPCTSTR lpCaption,
  [in]           UINT    uType
);
```


### انواع متداول مقادیر بازگشتی توابع ویندوز

**VOID**  
این تابع اصولاً امکان شکست ندارد. تعداد بسیار کمی از توابع ویندوز مقدار بازگشتی از نوع VOID دارند.

**BOOL**  
اگر تابع شکست بخورد، مقدار بازگشتی ۰ است؛ در غیر این صورت مقدار غیرصفر بازمی‌گرداند.  
بهتر است مقدار بازگشتی را مستقیماً با TRUE مقایسه نکنید؛ بهترین کار این است که بررسی کنید مقدار آن **مخالف FALSE** باشد.

```c++
int main(){
	auto a = bool Method2 ([in] sint32 InParam);
		if (a != 0){
			std::cout << "function stated successfuly" << std::endl;
		}else {
			std::cout << "error" << std::enl;
			DWORD GetLastError(a);
		}
}
```

**HANDLE**  
در صورت شکست، مقدار بازگشتی معمولاً **NULL** است؛ در غیر این صورت، HANDLE یک شیء را مشخص می‌کند که می‌توانید با آن کار کنید.  
در این مورد باید دقت کنید، چون بعضی از توابع به‌جای NULL مقدار **INVALID_HANDLE_VALUE** را برمی‌گردانند که مقدار آن **-1** است. مستندات Platform SDK به‌وضوح مشخص می‌کند که هر تابع در صورت شکست، NULL برمی‌گرداند یا INVALID_HANDLE_VALUE.

**PVOID**  
در صورت شکست، مقدار بازگشتی NULL است؛ در غیر این صورت، PVOID آدرس حافظه‌ی یک بلوک داده را مشخص می‌کند.

**LONG / DWORD**  
این مورد کمی پیچیده است. توابعی که مقدار شمارشی (Count) برمی‌گردانند، معمولاً از LONG یا DWORD استفاده می‌کنند. اگر تابع نتواند مقدار موردنظر را بشمارد، معمولاً مقدار **۰ یا -۱** را برمی‌گرداند (بسته به تابع).  
اگر با تابعی کار می‌کنید که LONG یا DWORD برمی‌گرداند، حتماً مستندات Platform SDK را با دقت مطالعه کنید تا نحوه‌ی صحیح تشخیص خطا را بدانید.

## دریافت کد خطا (GetLastError)

وقتی یک تابع ویندوزی با خطا برمی‌گردد، معمولاً دانستن دلیل شکست بسیار مهم است. مایکروسافت فهرستی از تمام کدهای خطای ممکن تهیه کرده و به هر خطا یک عدد ۳۲ بیتی اختصاص داده است پس به همین خاطر از DWORD برای تابع GetLastError استفاده میکنیم 

DWORD ---> 32bit
QWORD ---> 64bit

در داخل سیستم، وقتی یک تابع ویندوزی خطایی را تشخیص می‌دهد، از مکانیزمی به نام **Thread-Local Storage** استفاده می‌کند تا شماره‌ی خطا را به Thread فراخواننده اختصاص دهد (این مفهوم در فصل ۲۱ توضیح داده می‌شود).  
این مکانیزم اجازه می‌دهد Threadها به‌صورت مستقل از یکدیگر اجرا شوند، بدون اینکه کدهای خطای همدیگر را تحت تأثیر قرار دهند.
وقتی تابع به شما برمی‌گردد، مقدار بازگشتی آن نشان می‌دهد که خطا رخ داده است. برای فهمیدن اینکه دقیقاً چه خطایی اتفاق افتاده، باید تابع زیر را فراخوانی کنید:

```c
DWORD GetLastError();
```

این تابع صرفاً **آخرین کد خطای ۳۲ بیتی مربوط به Thread جاری** را که توسط آخرین تابع تنظیم شده، برمی‌گرداند.

وقتی که ما کد خطلا را گرفتیم باید بیایم و اون رو به چیزی قابل فهم تبدیل کنیم که هدر فایل WinError.h دقیقا همینکار رو میکند 

پس از به‌دست آوردن کد خطا، باید آن را به چیزی قابل فهم تبدیل کنید. فایل هدر **WinError.h** شامل فهرست کدهای خطای تعریف‌شده توسط مایکروسافت است. نمونه‌ای از آن:

```c
#define ERROR_SUCCESS 0L
#define ERROR_INVALID_FUNCTION 1L
#define ERROR_FILE_NOT_FOUND 2L
#define ERROR_PATH_NOT_FOUND 3L
#define ERROR_TOO_MANY_OPEN_FILES 4L
#define ERROR_ACCESS_DENIED 5L
```

هر خطا سه نمایش دارد:

1. **Message ID** (ماکرو برای استفاده در کد)
    
2. **Message Text** (توضیح متنی انگلیسی خطا)
    
3. **عدد خطا** (که بهتر است مستقیماً از آن استفاده نکنید)
    

همیشه از **Message ID** استفاده کنید، نه عدد خام.  
فایلی که این مثال از آن انتخاب شده بسیار بزرگ است—بیش از **۳۹٬۰۰۰ خط**!

### نکات مهم درباره GetLastError

- بلافاصله بعد از شکست یک تابع، `GetLastError` را صدا بزنید؛ چون ممکن است با فراخوانی تابع ویندوزی دیگر، مقدار آن **بازنویسی شود**.
    
- حتی توابعی که موفق می‌شوند نیز ممکن است مقدار خطا را با `ERROR_SUCCESS` تغییر دهند.
    
- بعضی توابع می‌توانند به **چند دلیل مختلف موفق شوند**.  
    مثلاً `CreateEvent` ممکن است:
    
    - یک Event جدید بسازد
        
    - یا متوجه شود Event با همان نام از قبل وجود دارد
        
    
    در این حالت، با فراخوانی `GetLastError` می‌توانید بفهمید کدام حالت رخ داده است (مثلاً `ERROR_ALREADY_EXISTS`).


### دیباگ کردن کد خطا در Visual Studio

در زمان دیباگ، دیدن آخرین کد خطای Thread بسیار مفید است. در **Visual Studio** می‌توانید در پنجره‌ی Watch مقدار زیر را وارد کنید:


```c
$err,hr
```

این کار:

- عدد خطا
    
- و توضیح متنی آن
    

را نمایش می‌دهد.

مثلاً اگر `CreateFile` مقدار `INVALID_HANDLE_VALUE` برگرداند و Watch مقدار خطای `0x00000002` را نشان دهد، یعنی:

> The system cannot find the file specified.

که همان متنی است که در WinError.h برای خطای شماره ۲ آمده است.

Visual Studio همچنین ابزاری به نام **Error Lookup** دارد که کدهای خطا را به توضیح متنی تبدیل می‌کند.


### چرا لیست کامل خطاها وجود ندارد؟

گاهی افراد می‌پرسند آیا مایکروسافت فهرست جامعی از تمام خطاهای ممکن برای همه‌ی توابع ویندوز منتشر کرده است یا نه.  
پاسخ متأسفانه **خیر** است—و هرگز هم چنین فهرستی منتشر نخواهد شد.

دلیلش این است که:

- یک تابع ممکن است در داخل خودش چندین تابع دیگر را فراخوانی کند.
    
- هرکدام از این توابع ممکن است به دلایل مختلفی شکست بخورند.
    
- گاهی تابع سطح بالاتر می‌تواند از خطا بازیابی کند و همچنان عملیات را انجام دهد.
    

برای ساخت چنین فهرستی، مایکروسافت باید مسیر اجرای تمام توابع را ردیابی کند که کاری بسیار دشوار استو با هر نسخه‌ی جدید ویندوز، این مسیرها تغییر می‌کنند.

## تعریف کدهای خطای اختصاصی (Defining Your Own Error Codes)

تا اینجا توضیح دادم که توابع ویندوز چگونه خطاها را به فراخواننده اعلام می‌کنند. مایکروسافت این مکانیزم را در اختیار شما هم قرار داده است تا در **توابع خودتان** از آن استفاده کنید.  
فرض کنید در حال نوشتن تابعی هستید که دیگران قرار است آن را فراخوانی کنند. تابع شما ممکن است به دلایل مختلفی با شکست مواجه شود و شما باید این شکست را به فراخواننده اعلام کنید.

برای اعلام شکست، کافی است **کد خطای آخر Thread** را تنظیم کنید و سپس تابع خود را با یکی از مقادیر مناسب مانند `FALSE`، `INVALID_HANDLE_VALUE`، `NULL` یا هر مقدار معنادار دیگری بازگردانید.

برای تنظیم کد خطای آخر Thread، کافی است تابع زیر را فراخوانی کنید:

```c
VOID SetLastError(DWORD dwErrCode);
```


و یک عدد ۳۲ بیتی را که مناسب می‌دانید به آن بدهید.

من معمولاً سعی می‌کنم از کدهایی استفاده کنم که از قبل در فایل WinError.h تعریف شده‌اند—به شرطی که آن کدها به‌خوبی بیانگر خطایی باشند که می‌خواهم گزارش کنم.
اگر احساس می‌کنید هیچ‌کدام از کدهای موجود در WinError.h خطای موردنظر شما را به‌درستی توصیف نمی‌کنند، می‌توانید کد خطای مخصوص خودتان را تعریف کنید.

کد خطا یک عدد ۳۲ بیتی است که به بخش‌هایی تقسیم می‌شود؛ همان‌طور که در جدول ۱-۲ نشان داده شده است.
جدول ۱-۲: فیلدهای کد خطا
بیت‌ها	31–30	29	28	27–16	15–0
محتوا	Severity	Microsoft / Customer	Reserved	Facility Code	Exception Code

معنی فیلدها:

    Severity (شدت خطا)

        0 = موفقیت (Success)

        1 = اطلاع‌رسانی (Informational)

        2 = هشدار (Warning)

        3 = خطا (Error)

    Microsoft / Customer (بیت 29)

        0 = کد تعریف‌شده توسط مایکروسافت

        1 = کد تعریف‌شده توسط کاربر / برنامه‌نویس

    Reserved (بیت 28)

        باید حتماً 0 باشد

    Facility Code (بیت‌های 27–16)

        256 مقدار اول رزرو شده توسط مایکروسافت هستند

        بقیه می‌توانند توسط برنامه‌ی شما تعریف شوند

    Exception Code (بیت‌های 15–0)

        کد خطای خاص (تعریف‌شده توسط مایکروسافت یا برنامه‌نویس)

نکته‌ی بسیار مهم درباره‌ی بیت 29

این فیلد تنها بخشی است که در حال حاضر باید حتماً به آن توجه کنید:

    مایکروسافت تضمین می‌کند که تمام کدهای خطای خودش در بیت 29 مقدار 0 دارند.

    اگر شما کد خطای اختصاصی تعریف می‌کنید، باید مقدار این بیت را 1 قرار دهید.

با این کار:

    مطمئن می‌شوید کد خطای شما هرگز با کدهای مایکروسافت تداخل نخواهد داشت

    چه کدهای فعلی و چه کدهایی که در آینده اضافه می‌شوند

توجه داشته باشید که فیلد Facility آن‌قدر بزرگ است که 4096 مقدار مختلف را پشتیبانی می‌کند. از این تعداد:

    256 مقدار اول مخصوص مایکروسافت است

    بقیه کاملاً در اختیار برنامه‌ی شماست
