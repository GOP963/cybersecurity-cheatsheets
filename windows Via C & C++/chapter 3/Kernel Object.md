


### شیء کرنل (Kernel Object) چیست؟

به‌عنوان یک توسعه‌دهندهٔ نرم‌افزار در ویندوز، شما به‌طور منظم **اشیای کرنل** را ایجاد می‌کنید، باز می‌کنید و آن‌ها را دست‌کاری (manipulate) می‌کنید. سیستم‌عامل خودش انواع مختلفی از اشیای کرنل را ایجاد و مدیریت می‌کند؛ از جمله:

- اشیای توکن دسترسی (Access Token Objects)
    
- اشیای رویداد (Event Objects)
    
- اشیای فایل (File Objects)
    
- اشیای نگاشت فایل (File-Mapping Objects)
    
- اشیای پورت تکمیل ورودی/خروجی (I/O Completion Port Objects)
    
- اشیای Job
    
- اشیای Mailslot
    
- اشیای Mutex
    
- اشیای Pipe
    
- اشیای پردازه (Process Objects)
    
- اشیای Semaphore
    
- اشیای نخ (Thread Objects)
    
- اشیای تایمر قابل انتظار (Waitable Timer Objects)
    
- اشیای Thread Pool Worker Factory
    

ابزار رایگان **WinObj** از مجموعهٔ Sysinternals  
(در نشانی https://learn.microsoft.com/en-us/sysinternals/downloads/winobj
به شما اجازه می‌دهد فهرست تمام انواع اشیای کرنل را مشاهده کنید. توجه داشته باشید که برای دیدن این فهرست، باید برنامه را از طریق **Windows Explorer** و با سطح دسترسی **Administrator** اجرا کنید.

---

این اشیا با فراخوانی توابع مختلفی ایجاد می‌شوند که نام آن‌ها الزاماً با نوع شیء در سطح کرنل یکسان نیست. برای مثال، تابع **CreateFileMapping** باعث می‌شود سیستم یک File Mapping ایجاد کند که در سطح کرنل متناظر با یک **Section Object** است؛ همان‌طور که می‌توانید این موضوع را در WinObj مشاهده کنید.

هر شیء کرنل در واقع تنها یک **بلوک حافظه** است که توسط کرنل تخصیص داده می‌شود و **فقط برای خود کرنل قابل دسترسی است**. این بلوک حافظه یک ساختار داده (Data Structure) است که اعضای آن اطلاعات مربوط به آن شیء را نگه می‌دارند. برخی از این اعضا (مانند **توصیف‌گر امنیتی**، **تعداد استفاده** و موارد مشابه) در تمام انواع اشیای کرنل مشترک هستند، اما بیشتر اعضا مخصوص نوع خاصی از شیء می‌باشند.

برای مثال:

- یک **شیء پردازه (Process Object)** شامل شناسهٔ پردازه (Process ID)، اولویت پایه (Base Priority) و کد خروج (Exit Code) است.
    
- در حالی که یک **شیء فایل (File Object)** شامل offset بایت، حالت اشتراک‌گذاری (Sharing Mode) و حالت باز شدن (Open Mode) می‌باشد.


---

از آنجا که ساختارهای دادهٔ اشیای کرنل فقط توسط خود کرنل قابل دسترسی هستند، برای یک برنامه غیرممکن است که این ساختارها را در حافظه پیدا کرده و مستقیماً محتوای آن‌ها را تغییر دهد. مایکروسافت عمداً این محدودیت را اعمال کرده است تا اطمینان حاصل شود که اشیای کرنل همواره در یک وضعیت سازگار و صحیح باقی می‌مانند. این محدودیت همچنین به مایکروسافت اجازه می‌دهد که بدون شکستن سازگاری برنامه‌ها، اعضای این ساختارها را **اضافه، حذف یا تغییر** دهد.

---

اگر ما نمی‌توانیم این ساختارها را مستقیماً تغییر دهیم، پس برنامه‌ها چگونه با اشیای کرنل کار می‌کنند؟

پاسخ این است که ویندوز مجموعه‌ای از توابع را فراهم می‌کند که این ساختارها را به شیوه‌هایی **مشخص و کنترل‌شده** دست‌کاری می‌کنند. اشیای کرنل همیشه از طریق همین توابع قابل دسترسی هستند.

وقتی تابعی را فراخوانی می‌کنید که یک شیء کرنل ایجاد می‌کند، آن تابع یک **Handle (هندل)** برمی‌گرداند که آن شیء را شناسایی می‌کند. می‌توانید این هندل را به‌عنوان یک مقدار **Opaque** (غیرشفاف) در نظر بگیرید که هر نخ (Thread) در همان پردازه می‌تواند از آن استفاده کند.

- در یک پردازهٔ ۳۲ بیتی، هندل یک مقدار ۳۲ بیتی است.
    
- در یک پردازهٔ ۶۴ بیتی، هندل یک مقدار ۶۴ بیتی است.


## شمارش میزان استفاده (Usage Counting)

اشیای کرنل متعلق به **کرنل** هستند، نه متعلق به یک پردازه (Process). به بیان دیگر، اگر پردازهٔ شما تابعی را فراخوانی کند که یک شیء کرنل ایجاد می‌کند و سپس پردازهٔ شما خاتمه یابد، آن شیء کرنل الزاماً از بین نمی‌رود. در اغلب شرایط، شیء از بین می‌رود؛ اما اگر پردازهٔ دیگری در حال استفاده از شیء کرنلی باشد که پردازهٔ شما ایجاد کرده است، کرنل می‌داند که نباید آن شیء را تا زمانی که پردازهٔ دیگر استفاده از آن را متوقف نکرده، نابود کند.
## نکتهٔ مهمی که باید به خاطر بسپارید این است که **یک شیء کرنل می‌تواند عمری طولانی‌تر از پردازه‌ای داشته باشد که آن را ایجاد کرده است**.


کرنل می‌داند که چند پردازه از یک شیء کرنل خاص استفاده می‌کنند، زیرا هر شیء کرنل دارای یک **شمارندهٔ استفاده (Usage Count)** است. این شمارنده یکی از اعضای داده‌ای مشترک بین تمام انواع اشیای کرنل محسوب می‌شود.

- زمانی که یک شیء برای اولین بار ایجاد می‌شود، مقدار Usage Count آن برابر با ۱ است.
    
- وقتی پردازهٔ دیگری به یک شیء کرنل موجود دسترسی پیدا می‌کند، مقدار Usage Count افزایش می‌یابد.
    
- زمانی که یک پردازه خاتمه پیدا می‌کند، کرنل به‌صورت خودکار مقدار Usage Count تمام اشیای کرنلی را که آن پردازه هنوز باز (Open) نگه داشته بود، کاهش می‌دهد.
    
- اگر مقدار Usage Count یک شیء به صفر برسد، کرنل آن شیء را نابود می‌کند.
    

این مکانیزم تضمین می‌کند که هیچ شیء کرنلی در سیستم باقی نماند، مگر اینکه حداقل یک پردازه هنوز به آن ارجاع داشته باشد.

- چه کسی مالک شیء است (معمولاً سازندهٔ آن)

- کدام کاربران یا گروه‌ها به‌طور صریح از دسترسی به شیء منع شده‌اند
    

Security Descriptorها معمولاً هنگام نوشتن **برنامه‌های سمت سرور** استفاده می‌شوند. با این حال، از زمان معرفی **Windows Vista**، این قابلیت در برنامه‌های سمت کاربر (Client-side) نیز، به‌ویژه با **Private Namespaceها**، بیشتر قابل مشاهده شده است؛ همان‌طور که بعداً در این فصل و همچنین در بخش

## امنیت (Security)

اشیای کرنل می‌توانند با استفاده از **Security Descriptor (توصیف‌گر امنیتی)** محافظت شوند. یک Security Descriptor مشخص می‌کند:

- چه کسی مالک شیء است (معمولاً سازندهٔ آن)
    
- کدام کاربران یا گروه‌ها اجازهٔ دسترسی یا استفاده از شیء را دارند
    
- کدام کاربران یا گروه‌ها به‌طور صریح از دسترسی به شیء منع شده‌اند
    

Security Descriptorها معمولاً هنگام نوشتن **برنامه‌های سمت سرور** استفاده می‌شوند. با این حال، از زمان معرفی **Windows Vista**، این قابلیت در برنامه‌های سمت کاربر (Client-side) نیز، به‌ویژه با **Private Namespaceها**، بیشتر قابل مشاهده شده است؛ همان‌طور که بعداً در این فصل و همچنین در بخش  
**«When Administrator Runs as a Standard User»** در صفحهٔ ۱۱۰ خواهید دید.

تقریباً تمام توابعی که اشیای کرنل را ایجاد می‌کنند، یک اشاره‌گر به ساختار **SECURITY_ATTRIBUTES** به‌عنوان پارامتر دریافت می‌کنند. برای مثال، تابع **CreateFileMapping** به شکل زیر است:

```c
HANDLE CreateFileMapping(
    HANDLE hFile,
    PSECURITY_ATTRIBUTES psa,
    DWORD flProtect,
    DWORD dwMaximumSizeHigh,
    DWORD dwMaximumSizeLow,
    PCTSTR pszName
);
```

بیشتر برنامه‌ها مقدار **NULL** را برای این پارامتر ارسال می‌کنند تا شیء با تنظیمات امنیتی پیش‌فرض و بر اساس **Security Token** پردازهٔ فعلی ایجاد شود.  
اما شما می‌توانید یک ساختار SECURITY_ATTRIBUTES تخصیص داده، آن را مقداردهی اولیه کنید و آدرس آن را به این پارامتر بدهید.

ساختار SECURITY_ATTRIBUTES به شکل زیر تعریف شده است:

```c
typedef struct _SECURITY_ATTRIBUTES {
    DWORD  nLength;
    LPVOID lpSecurityDescriptor;
    BOOL   bInheritHandle;
} SECURITY_ATTRIBUTES;
```

با اینکه نام این ساختار **SECURITY_ATTRIBUTES** است، در واقع فقط **یک عضو** آن مستقیماً به امنیت مربوط می‌شود و آن هم **lpSecurityDescriptor** است.

اگر بخواهید دسترسی به یک شیء کرنلی که ایجاد می‌کنید را محدود کنید، باید یک **Security Descriptor** بسازید و سپس ساختار SECURITY_ATTRIBUTES را به صورت زیر مقداردهی کنید:

```c
SECURITY_ATTRIBUTES sa;
sa.nLength = sizeof(sa);              // برای نسخه‌بندی
sa.lpSecurityDescriptor = pSD;         // آدرس SD مقداردهی‌شده
sa.bInheritHandle = FALSE;             // بعداً توضیح داده می‌شود

HANDLE hFileMapping = CreateFileMapping(
    INVALID_HANDLE_VALUE,
    &sa,
    PAGE_READWRITE,
    0,
    1024,
    TEXT("MyFileMapping")
);
```

از آنجا که عضو **bInheritHandle** ارتباطی با امنیت ندارد، توضیح آن به بخش  
**«Using Object Handle Inheritance»** در صفحهٔ ۴۳ موکول می‌شود.

## دسترسی به اشیای کرنل موجود

وقتی می‌خواهید به یک شیء کرنل موجود دسترسی پیدا کنید (نه اینکه یک شیء جدید بسازید)، باید **نوع عملیاتی** را که قصد انجام آن را دارید مشخص کنید.

برای مثال، اگر بخواهم به یک **File-Mapping Object** موجود دسترسی پیدا کنم تا داده‌ای از آن بخوانم، تابع **OpenFileMapping** را به شکل زیر فراخوانی می‌کنم:

```c
HANDLE hFileMapping = OpenFileMapping(
    FILE_MAP_READ,
    FALSE,
    TEXT("MyFileMapping")
);
```

با ارسال مقدار **FILE_MAP_READ** به‌عنوان پارامتر اول، اعلام می‌کنم که قصد دارم پس از دریافت دسترسی، فقط عملیات خواندن انجام دهم.

تابع OpenFileMapping قبل از بازگرداندن یک هندل معتبر، ابتدا یک **بررسی امنیتی** انجام می‌دهد:

- اگر کاربر واردشده (Logged-on User) اجازهٔ دسترسی داشته باشد، تابع یک هندل معتبر برمی‌گرداند.
    
- اگر دسترسی رد شود، تابع مقدار **NULL** را برمی‌گرداند و فراخوانی تابع **GetLastError** مقدار **۵ (ERROR_ACCESS_DENIED)** را بازمی‌گرداند.
    

توجه داشته باشید که اگر هندل بازگردانده‌شده برای فراخوانی APIای استفاده شود که به مجوزی غیر از FILE_MAP_READ نیاز دارد، همان خطای **Access Denied** رخ خواهد داد.

با این حال، از آنجا که اغلب برنامه‌ها از امنیت استفاده نمی‌کنند، نویسنده وارد جزئیات بیشتر این موضوع نمی‌شود.

## اهمیت در نظر گرفتن امنیت

اگرچه بسیاری از برنامه‌ها نیازی به درگیر شدن با امنیت ندارند، اما بسیاری از توابع ویندوز از شما می‌خواهند که **سطح دسترسی امنیتی موردنظر** را مشخص کنید.

چندین برنامه که برای نسخه‌های قدیمی‌تر ویندوز طراحی شده‌اند، روی **Windows Vista** به‌درستی کار نمی‌کنند، زیرا هنگام پیاده‌سازی، امنیت به اندازهٔ کافی در نظر گرفته نشده است.

برای مثال، فرض کنید برنامه‌ای هنگام اجرا مقداری داده از یک زیرکلید رجیستری می‌خواند. برای انجام صحیح این کار، کد باید تابع **RegOpenKeyEx** را با فلگ **KEY_QUERY_VALUE** فراخوانی کند.

اما بسیاری از برنامه‌ها که قبل از Windows 2000 نوشته شده‌اند، هیچ توجهی به امنیت نداشته‌اند. برخی توسعه‌دهندگان RegOpenKeyEx را با فلگ **KEY_ALL_ACCESS** فراخوانی می‌کردند، چون ساده‌تر بود و نیازی به فکر کردن دربارهٔ سطح دسترسی موردنیاز نداشت.

مشکل اینجاست که یک زیرکلید رجیستری مانند **HKLM** ممکن است برای یک کاربر غیرادمین **قابل خواندن** باشد اما **قابل نوشتن نباشد**. بنابراین در Windows Vista، فراخوانی RegOpenKeyEx با KEY_ALL_ACCESS شکست می‌خورد و اگر بررسی خطا به‌درستی انجام نشده باشد، برنامه می‌تواند رفتار کاملاً غیرقابل پیش‌بینی از خود نشان دهد.

اگر توسعه‌دهنده فقط کمی به امنیت فکر کرده بود و KEY_ALL_ACCESS را به **KEY_QUERY_VALUE** تغییر می‌داد (که در این مثال کافی است)، برنامه روی تمام نسخه‌های ویندوز به‌درستی کار می‌کرد.

نادیده گرفتن فلگ‌های صحیح دسترسی امنیتی، یکی از **بزرگ‌ترین اشتباهات توسعه‌دهندگان** است. استفاده از فلگ‌های درست، فرآیند انتقال (Port کردن) برنامه بین نسخه‌های مختلف ویندوز را بسیار ساده‌تر می‌کند.

البته باید توجه داشت که هر نسخهٔ جدید ویندوز محدودیت‌های امنیتی جدیدی نیز به همراه دارد. برای مثال، در Windows Vista باید به ویژگی **User Account Control (UAC)** توجه ویژه‌ای داشت. به‌طور پیش‌فرض، UAC باعث می‌شود برنامه‌ها حتی اگر کاربر عضو گروه Administrators باشد، در یک **بافت محدود (Restricted Context)** اجرا شوند. UAC در فصل ۴ با عنوان **«Processes»** بررسی خواهد شد.

## تفاوت Kernel Object با User و GDI Object

علاوه بر اشیای کرنل، برنامهٔ شما ممکن است از انواع دیگری از اشیا مانند:

- منوها
    
- پنجره‌ها
    
- مکان‌نماهای ماوس
    
- براش‌ها
    
- فونت‌ها
    

استفاده کند. این اشیا، **User Objects** یا **GDI Objects** هستند، نه اشیای کرنل.

در ابتدای برنامه‌نویسی ویندوز، ممکن است تشخیص تفاوت بین این اشیا و اشیای کرنل کمی گیج‌کننده باشد. برای مثال:  
آیا یک **Icon** یک User Object است یا یک Kernel Object؟

ساده‌ترین راه برای تشخیص این موضوع این است که تابعی را بررسی کنید که شیء را ایجاد می‌کند. تقریباً تمام توابعی که اشیای کرنل ایجاد می‌کنند، پارامتری برای مشخص کردن **Security Attributes** دارند؛ مانند تابع CreateFileMapping که قبلاً دیدیم.

در مقابل، **هیچ‌کدام** از توابعی که User Object یا GDI Object ایجاد می‌کنند، پارامتر **PSECURITY_ATTRIBUTES** ندارند. برای مثال، تابع **CreateIcon** به شکل زیر است:

```c
HICON CreateIcon(
    HINSTANCE hinst,
    int nWidth,
    int nHeight,
    BYTE cPlanes,
    BYTE cBitsPixel,
    CONST BYTE *pbANDbits,
    CONST BYTE *pbXORbits
);
```


## جدول هندل اشیای کرنلِ یک پردازه

_(A Process’ Kernel Object Handle Table)_

وقتی یک پردازه مقداردهی اولیه می‌شود، سیستم برای آن یک **Handle Table (جدول هندل)** تخصیص می‌دهد. این جدول هندل **فقط برای اشیای کرنل** استفاده می‌شود و **برای User Objectها یا GDI Objectها کاربردی ندارد**.

جزئیات دقیق ساختار و نحوهٔ مدیریت این جدول هندل **مستندسازی نشده‌اند**. معمولاً من از صحبت دربارهٔ بخش‌های مستندنشدهٔ سیستم‌عامل خودداری می‌کنم، اما در این مورد یک استثنا قائل شده‌ام، چون معتقدم یک برنامه‌نویس حرفه‌ای ویندوز باید بداند که جدول هندل یک پردازه چگونه مدیریت می‌شود.

از آنجا که این اطلاعات مستند نیستند:

- ممکن است همهٔ جزئیات کاملاً دقیق نباشند
    
- پیاده‌سازی داخلی آن در نسخه‌های مختلف ویندوز متفاوت است
    

بنابراین، مطالب زیر را برای **افزایش درک مفهومی** مطالعه کنید، نه به‌عنوان توصیف دقیق پیاده‌سازی واقعی سیستم.

## ایجاد یک شیء کرنل

_(Creating a Kernel Object)_

وقتی یک پردازه برای اولین بار مقداردهی اولیه می‌شود، جدول هندل آن **خالی** است.

زمانی که یکی از نخ‌های (Threadهای) داخل پردازه تابعی را فراخوانی می‌کند که یک شیء کرنل ایجاد می‌کند (مانند **CreateFileMapping**)، مراحل زیر رخ می‌دهد:

1. کرنل یک بلوک حافظه برای شیء کرنل تخصیص می‌دهد و آن را مقداردهی اولیه می‌کند.
    
2. سپس کرنل جدول هندل پردازه را اسکن می‌کند تا یک خانهٔ خالی پیدا کند.
    
3. از آنجا که جدول هندل در ابتدا خالی است، کرنل ساختار مربوط به **اندیس ۱** را پیدا کرده و مقداردهی می‌کند.
    
4. در این ساختار:
    
    - عضو Pointer به آدرس داخلی ساختار دادهٔ شیء کرنل اشاره می‌کند
        
    - Access Mask روی **Full Access** تنظیم می‌شود
        
    - Flagها مقداردهی می‌شوند  
        (Flagها در بخش «Using Object Handle Inheritance» صفحهٔ ۴۳ بررسی خواهند شد)

## معنی واقعی مقدار هندل

در واقع، مقدار هندل باید بر **۴ تقسیم شود** (یا دو بیت آخر آن نادیده گرفته شود) تا **اندیس واقعی** در جدول هندل پردازه به دست آید؛ زیرا دو بیت آخر هندل به‌صورت داخلی توسط ویندوز استفاده می‌شوند.

به همین دلیل است که هنگام دیباگ کردن یک برنامه، مقدار هندل‌ها اغلب عددهای کوچکی مانند **4، 8، 12** و … هستند.

⚠️ توجه داشته باشید:

- معنی دقیق مقدار هندل **مستند نشده**
    
- و ممکن است در نسخه‌های مختلف ویندوز تغییر کند
    

---

## استفاده از هندل در فراخوانی توابع

هر زمان که تابعی را فراخوانی می‌کنید که یک هندل شیء کرنل را به‌عنوان پارامتر می‌پذیرد، شما مقدار هندلی را ارسال می‌کنید که قبلاً از یکی از توابع **Create*** دریافت کرده‌اید.

در داخل سیستم:

1. ویندوز با استفاده از این مقدار، به جدول هندل پردازه نگاه می‌کند
    
2. آدرس شیء کرنل متناظر را پیدا می‌کند
    
3. سپس ساختار دادهٔ آن شیء را به‌صورت کنترل‌شده دست‌کاری می‌کند
    

اگر یک هندل نامعتبر ارسال شود:

- تابع با شکست مواجه می‌شود
    
- و **GetLastError** مقدار **6 (ERROR_INVALID_HANDLE)** را برمی‌گرداند
    

از آنجا که هندل‌ها به‌عنوان اندیس جدول هندل استفاده می‌شوند:

- آن‌ها **وابسته به پردازه** هستند
    
- و در پردازه‌های دیگر قابل استفاده نیستند
    

اگر تلاش کنید از هندل یک پردازه در پردازه‌ای دیگر استفاده کنید، در واقع به شیء کرنلی اشاره می‌کنید که در همان اندیس جدول هندل پردازهٔ مقصد قرار دارد—بدون اینکه بدانید آن شیء چیست.

## مقدار بازگشتی هندل در صورت خطا

اگر تابعی که یک شیء کرنل ایجاد می‌کند با خطا مواجه شود، معمولاً مقدار بازگشتی برابر **0 (NULL)** است. به همین دلیل، اولین مقدار هندل معتبر معمولاً **4** است.

این اتفاق معمولاً فقط در شرایطی مانند:

- کمبود شدید حافظه
    
- یا مشکل امنیتی
    

رخ می‌دهد.

⚠️ اما نکتهٔ بسیار مهم:

برخی توابع در صورت خطا مقدار **-1** را برمی‌گردانند که با نام **INVALID_HANDLE_VALUE** (تعریف‌شده در WinBase.h) شناخته می‌شود.

برای مثال:

- اگر تابع **CreateFile** نتواند فایل مشخص‌شده را باز کند، مقدار **INVALID_HANDLE_VALUE** را برمی‌گرداند، نه NULL.
    

بنابراین، هنگام بررسی مقدار بازگشتی توابع ایجادکنندهٔ اشیای کرنل، باید **بسیار دقت کنید**.

---

### مثال‌های اشتباه در بررسی خطا

❌ کد زیر اشتباه است:

```c
HANDLE hMutex = CreateMutex(...);
if (hMutex == INVALID_HANDLE_VALUE) {
    // این کد هرگز اجرا نمی‌شود
    // چون CreateMutex در صورت خطا NULL برمی‌گرداند
}
```

❌ این کد هم اشتباه است:

```c
HANDLE hFile = CreateFile(...);
if (hFile == NULL) {
    // این کد هرگز اجرا نمی‌شود
    // چون CreateFile در صورت خطا INVALID_HANDLE_VALUE (-1) برمی‌گرداند
}
```

---

اگر به اخر همه این توابع دقت کرده باشید متوجه میشوید که یک پارامتر مشترک دارند *pszName*

وقتی NULL را این پارامتر ارسال می‌کنید، به سیستم نشان می‌دهید که می‌خواهید یک شیء هسته‌ای نام‌ناپذیر (نامرئی) ایجاد کنید. وقتی شیء نامرئی ایجاد می‌کنید، می‌توانید شیء را در میان فرآیندها با استفاده از ارث‌بری (همان‌طور که در بخش قبلی بحث شد) یا DuplicateHandle (در بخش بعدی بحث می‌شود) به اشتراک بگذارید. برای به اشتراک گذاشتن شیء با نام، باید به شیء نام بدهید.

اگر NULL را برای پارامتر pszName ارسال نکنید، باید آدرس یک رشته نام صفر-متوقف شده را ارسال کنید. این نام می‌تواند تا حداکثر طول MAX_PATH (تعریف شده به عنوان 260) باشد.

```c
HANDLE hMutex = CreateMutex(NULL, FALSE, TEXT("JeffObj"));
HANDLE hSem = CreateSemaphore(NULL, 1, 1, TEXT("JeffObj"));
DWORD dwErrorCode = GetLastError();
```

اگر پس از اجرای کد قبلی، مقدار dwErrorCode را بررسی کنید، کد بازگشت ۶ (ERROR_INVALID_HANDLE) را مشاهده خواهید کرد. این کد خطا بسیار توصیف‌کننده نیست، اما چه می‌توانید انجام دهید؟

حالا که می‌دانی چگونه یک شیء را نام‌گذاری کنی، بیایید ببینیم چگونه می‌توانی اشیا را به این روش به اشتراک بگذاری. فرض کن فرایند A شروع به کار می‌کند و تابع زیر را فروانی می‌کند:

```c++
HANDLE hMutexProcessA = CreateMutex(NULL, FALSE, TEXT("JeffMutex"));
```

این فراخوانی تابع یک شیء جدید قفل هسته‌ای ایجاد می‌کند و آن را با نام «JeffMutex» اختصاص می‌دهد. توجه داشته باشید که در دستگیره فرایند A، hMutexProcessA یک دستگیره ارث‌بر نیست—و نیازی به آن نیست وقتی که فقط اشیاء را نام‌گذاری می‌کنید.

وقتی فراخوانی CreateMutex توسط فرایند B انجام می‌شود، سیستم ابتدا بررسی می‌کند تا مشخص کند آیا یک شیء هسته‌ای با نام «JeffMutex» قبلاً وجود دارد یا خیر. چرا که یک شیء با این نام وجود دارد، هسته سپس شیء را بررسی می‌کند چرا که ما در حال ایجاد یک قفل و شیء با نام «JeffMutex» نیز یک قفل است سیستم یک بررسی امنیتی انجام می‌دهد تا ببیند caller دسترسی کامل به شیء دارد یا خیر. اگر دسترسی وجود داشته، سیستم یک ورودی خالی در جدول دستگیره‌های فرایند B پیدا می‌کند و آن را به شیء هسته‌ای موجود اشاره می‌دهد. اگر نوع‌های شی مطابقت نداشته باشند یا به caller انکار، CreateMutex ناموفق می‌شود (NULL بازمی‌گرداند).
## توجه: توابع ایجاد شیء هسته‌ای (مانند Create) همیشه دستگیره‌هایی دسترسی کامل بازمی‌گردانند اگر می‌خواهید حقوق دسترسی موجود برای یک دستگیره را محدود کنید، می‌توانید

وقتی فراخوانی CreateMutex توسط فرایند B موفقیت‌آمیز است، در واقع یک قفل ایجاد نمی‌شود. به جای آن، فرایند B یک مقدار دستگیره نسبی فرایند به خود اختصاص می‌دهد که هویت شی قفل در هسته را مشخص می‌کند البته، چون یک ورودی جدید جدول دستگیره‌های فرایند به این شی اشاره می‌، شمارنده استفاده شی افزایش مییابد. شی تا زمانی که هم فرایند A و هم فرایند B دسته‌های خود را به شی‌اند، تخریب نخواهد شد. توجه داشته باشید که مقادیر دستگیره در دو احتمالاً مقادیر متفاوتیند داشت. این موضوع ع است. فرایند A از مقدار دسته خود و فرایند B از مقدار دستگیره خود برای دستکاری شی قفل هسته‌ای واحد خواهد کرد.
نکته هنگام داشتن اشیای هستهای با نام‌های مشترک، یک جزئیات بسیار مهم توجه کنید.
وقتی فرایند BMutex را فراخوانی می‌کند، اطلاعات ویژگی امنیتی و یکامتر دوم را به تابع‌گذارد. این پارترها در صورتی نده گرفته می‌شوند که با نام مشخص شده قبلاً وجود داشته باشد! یک برنامه می‌تواند تعیین کند که آیا واقعاً یک شی هسته‌ای جدید ایجاد کرده است یا صرفا یک شی موجود را باز کرده است، با فراخوانی GetLastErrorافاصله پس از فراخوانی تابع Create*


```c++
HANDLE hMutex = CreateMutex(&sa, FALSE, TEXT("JeffObj"));
if (GetLastError() == ERROR_ALREADY_EXISTS) {
// Opened a handle to an existing object.
// sa.lpSecurityDescriptor and the second parameter
// (FALSE) are ignored.
} else {
// Created a brand new object.
// sa.lpSecurityDescriptor and the second parameter
// (FALSE) are used to construct the object.
}
```

## Using Object Handle Inheritance

ارث‌بری **handle** اشیاء (Object handle inheritance) تنها زمانی قابل استفاده است که پروسه‌ها دارای رابطه والد-فرزندی (parent-child relationship) باشند. در این سناریو، یک یا چند **handle** شیء هسته‌ای (kernel object handles) برای پروسه والد در دسترس است، و پروسه والد تصمیم می‌گیرد یک پروسه فرزند را **spawn** کند و دسترسی به اشیاء هسته‌ای والد را به فرزند بدهد. برای اینکه این نوع ارث‌بری کار کند، پروسه والد باید چندین مرحله را انجام دهد. در ابتدا، هنگامی که پروسه والد یک شیء هسته‌ای (kernel object) ایجاد می‌کند، والد باید به سیستم نشان دهد که می‌خواهد **handle** شیء، قابلیت ارث‌بری (inheritable) داشته باشد. گاهی اوقات می‌شنوم که افراد از اصطلاح ارث‌بری شیء (object inheritance) استفاده می‌کنند. با این حال، چیزی به نام ارث‌بری شیء وجود ندارد؛ ویندوز از ارث‌بری **handle** شیء (object handle inheritance) پشتیبانی می‌کند. به عبارت دیگر، این **handle**ها هستند که قابل ارث‌بری هستند، نه خود اشیاء.


**برای اینکه child process بتونه handle رو از parent process ارث ببره باید یک ساختار SECURITY_ATTRIBUTES را اختصاص داده و اولیه‌سازی کند و آدرس این ساختار را به تابع ایجاد خاص بدهد. کد زیر یک شی قفل موقت ایجاد می‌کند و یک دستگیره ارثبر به آن بازمی‌اند**

```c++
SECURITY_ATTRIBUTES sa;
sa.nLength = sizeof(sa);
sa.lpSecurityDescriptor = NULL;
sa.bInheritHandle = TRUE; // Make the returned handle inheritable.
HANDLE hMutex = CreateMutex(&sa, FALSE, NULL);
```

این کد یک ساختار_ATTRIBUTES را اولیه‌سازی میکند که نشان می‌دهد باید با امنیت پیش‌فر ایجاد شود و دستگیرهگشتی باید ارث‌ باشد.

**This code initializes a SECURITY_ATTRIBUTES structure indicating that the object should be created using default security
and that the returned handle should be inheritable.
Now we come to the flags that are stored in a process' handle table entry. Each handle table entry has a flag bit indicating
whether the handle is inheritable. If you pass NULL as the PSECURITY_ATTRIBUTES parameter when you create a kernel
object, the handle returned is not inheritable and this bit is zero. Setting the bInheritHandle member to TRUE causes**


در مرحله بعدی که باید از این ارث بریه انجام شود در قدم اول باید  یک child process توسط parent process به وجود بی آید . این کار با استفاده از تابع **CreateProcess** انجام می‌شود.

```c
BOOL CreateProcess(
PCTSTR pszApplicationName,
PTSTR pszCommandLine,
PSECURITY_ATTRIBUTES psaProcess,
PSECURITY_ATTRIBUTES psaThread,
BOOL bInheritHandles,
DWORD dwCreationFlags,
PVOID pvEnvironment,
PCTSTR pszCurrentDirectory,
LPSTARTUPINFO pStartupInfo,
PPROCESS_INFORMATION pProcessInformation);
```

ما در فصل بعدی به طور دقیق این تابع را بررسی خواهیم کرد، اما برای حالا می‌خواهم توجه شما را به پارامتر «bInheritHandles» جلب کنم. معمولاً وقتی فرآیندی را ایجاد می‌کنید، برای این پارامتر مقدار FALSE را ارسال می‌کن. این مقدار به سیستم اطلاع می‌دهد که شما نمی‌خواهید فرآیند فرزند، دستگیره‌های ارث‌بر از جدول دستگیره‌های فرآیند والد را به ارث ببرد.
اگر برای این پارامتر TRUE را ارسال کنید، با این حال، فرزند مقادیر دستگیره قابل ارث والد را به ارث می‌برد.
وقتی TRUE را ارسال می‌کنید، سیستم عامل فرایند فرزند جدید ایجاد می‌کند اما اجازه نمیدهد فرایند فرزند بلافاصله کد را اجرا کند. البته، سیستم یک جدول خالی شناسه فرایند برای فرزند ایجاد می‌کند - درست مثل هر فرایند جدید دیگری. اما چون را به پارامتر bInherit CreateProcess ارسال کرده‌اید سیستم یک کار بیشتر انجام می‌: آن سیستم جدول شناسه فرایند را پیمایش می‌کند برای هر ورودی که حاوی یکه ارزشمند به ارث برده باشد، سیستم آن ورودی دقیقاً به جدول شناسه فرزند کپی می‌کند. ورودی در همان موقعیت دقیق در جدوله فرایند فرزند کپی می‌ همانطور که در جدول شناسه است. این واقعیت مهم است به این معنی است که مقدار شناس‌ای که یک شیء هستهای را در هر دو فرایند والد فرزند شناسایی می‌کند، یک است.

به‌علاوه کپی کردن ورودی جدول دستگیره، سیستم شمارش استفاده از شیء هسته‌ای را افزایش می‌دهد زیرا دو فرآیند اکنون از شیء استفاده می‌کنند. برای تخریب شیء هسته‌ای، هر دو فرآیند والد و فرزند باید یا روی شیء CloseHandle فراخ کنند یا خاتمه یابند. فرزند نیازی به خات یافتن اول ندارد - اما نیز ندارد. در واقع، فرند والد می‌تواند دستگیر خود را به شیء بلاف پس از بازگشت تابع CreateProcess بدونگذاری بر توانایی فرزند در دستکاریء ببندد.

![[Pasted image 20260119001217.png]]

نمایش‌دهنده جدول دستگیره‌های فرآیند فرزند بلافاصله قبل از اینکه فرآیند مجاز به اجرای کد شود. می‌توانید ببینید که ورودی‌های 1 و 2 اولیه‌سازی نشده‌اند و بنابراین دستگیره‌های نامعتبر فرآیند فرزند به‌حساب می‌آیند. اما شاخص 3 یک شیء هسته‌ای را شناسایی می‌کند. در واقع، آن را به شیء هسته‌ای در آدرس 0xF0000010 اشاره می‌کند—شیء مشابهی که در جدول دستگیره‌های فرآیند والد وجود دارد.


به دور از هر چیز، رایج‌ترین روش برای تعیین مقدار دستگیره (handle) شیء هسته‌ای مورد انتظار توسط یک فرآیند فرزند، گذاشتن مقدار دستگیره به عنوان یک آرگومان خط فرمان به فرآیند فرزند است. کد اولیه‌سازی فرآیند فرزند خط فرمان تجزیه می‌کند (معمولاً با فراخ stscanf_s) و مقدار دستگیره را استخراج‌کند. پس از اینکهآیند فرزند مقدار دستگیر را به دست آورد، دسترسیی به شیء خواهد داشت کهآیند والد دارد. توجه داشته باشید که تنها دلیل کارکرد ارث‌بری دستگیره، بودن مقدار دستگیره شیء هسته‌ای مشترک در هر دوآیند والد و فرزند است این دلیل، توانایی فرآیند والد در گذاشتن مقدار دسته به عنوان یک آرگومان خط فرمان را فراهم می‌کند.

## Changing a Handle's Flags

در برخی موارد، ممکن است با وضعیتی مواجه شوید که در آن یک فرایند والد یک شیء هسته‌ای را ایجاد می‌کند، یک دستگیره قابل ارث را بازیابی می‌کند و سپس دو فرایند فرزند را ایجاد می‌کند. فرایند والد می‌خواهد فقط یک فرایند فرزند دستگیره شیء هسته‌ای را ارث‌بری کند. به عبارت دیگر، گاهی ممکن است بخواهید کنترل کنید که کدام فرایندهای فرزند دستگیره‌های شیء‌های هسته‌ای را ارث‌بری می‌کنند. برای تغییر پرچم ارث‌بری یک دستگیره شیء هسته‌ای، می‌توانید تابع SetHandleInformation را فراخوانی کنید.

```c++
BOOL SetHandleInformation(
HANDLE hObject,
DWORD dwMask,
DWORD dwFlags);
```

همان‌طور که می‌بینید، این تابع سه پارامتر می‌گیرد. اولین پارامتر، hObject، یک دستگیره معتبر را شناسایی می‌کند. پارامتر دوم، dwMask، به تابع می‌گوید که کدام پرچم یا پرچم‌ها را می‌خواهید تغییر دهید. در حال حاضر، دو پرچم با هر دستگیره مرتبط است:

```c++
#define HANDLE_FLAG_INHERIT 0x00000001
#define HANDLE_FLAG_PROTECT_FROM_CLOSE 0x00000002
```

شما می‌توانید عملیات OR بیتی را بر روی هر دو پرچم این اشیاء به‌طور همزمان انجام دهید اگر می‌خواهید پرچم‌های هر شیء را به‌طور همزمان تغییر دهید.
پارامتر سوم SetHandleInformation، dwFlags، نشان‌دهنده چیزی است که می‌خواهید پرچم‌ها را به آن تنظیم کنید. برای مثال، برای فعال کردن پرچم ارث‌بری برای یک دستگیره شیء هسته، به این صورت عمل کنید:

```c++
SetHandleInformation(hObj, HANDLE_FLAG_INHERIT, HANDLE_FLAG_INHERIT);
```

To turn off this flag, do this:

```c++
SetHandleInformation(hObj, HANDLE_FLAG_INHERIT, 0);
```

پرچم HANDLE_FLAG_PROTECT_FROM_CLOSE به سیستم می‌گوید که این دستگیره نباید اجازه بسته شدن داشته باشد:

```c++
SetHandleInformation(hObj, HANDLE_FLAG_PROTECT_FROM_CLOSE,
HANDLE_FLAG_PROTECT_FROM_CLOSE);
CloseHandle(hObj); // Exception is raised
```

تنظیم اطلاعات دستگیره (SetHandleInformation) را برای (hobj) با پرچم محافظت از بسته شدن برابر صفر تنظیم می‌کند؛ دستگیره را بسته می‌شود (CloseHandle(hObj)); فرآیند والد بر این فرض است که فرآیند فرزند این کد را اجرا نخ کرد. البته، والد همچنین بر این فرض است که فرآیند فرزند فرآیند نوه را ایجاد می‌کند، بنابراین این شرط آنقدرها هم خطرناک نیست

برای کامل بودن، من همچنین دریافت اطلاعات دستگیره را ذکر‌کنم: BOOL GetHandleInformation(HANDLE hObject, PDWORD pdwFlags); این تابع تنظیمات فعلی پرچم‌ها برای دستگیره مشخص شده را در دست و چهارده بیتی که آن اشاره می‌کند، برمی‌گرداند. برای بررسی اینکه آیا یک دستگیره قابل ار است یا خیر، به این صورت عمل کنید:


```c++
BOOL GetHandleInformation(HANDLE hObject, PDWORD pdwFlags);
```

این تابع تنظیمات فعلی پرچم‌ها را برای دستگیره مشخص شده که به pdwFlags اشاره می‌کند، برمی‌گرداند. برای بررسی اینکه یک دستگیره قابل ارث است یا خیر، موارد زیر را انجام دهید:

```c++
DWORD dwFlags;
GetHandleInformation(hObj, &dwFlags);
BOOL fHandleIsInheritable = (0 != (dwFlags & HANDLE_FLAG_INHERIT));
```

نام‌گذاری اشیاء
روش دومی که برای اشتراک‌گذاری اشیاء هسته‌ای در مرزهای فرآیندها در دسترس است، نام‌گذاری اشیاء است. بسیاری از اشیاء هسته‌ای -چند نه همه - قابل نام‌ هستند. برای مثال، تمام توابع اشیاء هسته‌ای نام‌گذاری‌شده را ایجاد می‌:

```c++
HANDLE CreateMutex(
PSECURITY_ATTRIBUTES psa,
BOOL bInitialOwner,
PCTSTR pszName);

HANDLE CreateEvent(
PSECURITY_ATTRIBUTES psa,
BOOL bManualReset,
BOOL bInitialState,
PCTSTR pszName);

HANDLE CreateSemaphore(
PSECURITY_ATTRIBUTES psa,
LONG lInitialCount,
LONG lMaximumCount,
PCTSTR pszName);

HANDLE CreateWaitableTimer(
PSECURITY_ATTRIBUTES psa,
BOOL bManualReset,
PCTSTR pszName);

HANDLE CreateFileMapping(
HANDLE hFile,
PSECURITY_ATTRIBUTES psa,
DWORD flProtect,
Windows via C/C++, Fifth Edition by Jeffrey Richter and Christophe Nasarre
DWORD dwMaximumSizeHigh,
DWORD dwMaximumSizeLow,
PCTSTR pszName);

HANDLE CreateJobObject(
PSECURITY_ATTRIBUTES psa,
PCTSTR pszName);
```


همه این توابع یک پارامتر مشترک به نام pszName دارند. وقتی NULL را برای این پارامتر ارسال می‌کنید، به سیستم نشان می‌دهید که می‌خواهید یک شیء هسته‌ای بدون نام (نامناپذیر) ایجاد کنید وقتی شیء بدون نام ایجاد می‌شود، می‌توانید آن را در بین فرآیندها استفاده از ارث‌بری (همان‌طور که در بخشلی بحث شد) یا Duplicate (در بخش بعدی بحث می‌شود) به اشتراک بگذارید. برای به اشتراک گذاشتن یک شیء نام، باید به آن نامیدهید.
اگر NULL را برای پارامتر pszName ارسال نکنید، باید آدرس یک رشته نام‌گذاری‌شده صفر-متوقف را ارسال کنید این نام می‌تواند تا طول_PATH (تعریف‌ به عنوان 260) باشد. متأسفانه، مایکروسافت هیچ راهنمایی اختصاص نام به اشیاء هسته‌ای ارائه نمی‌کند. مثال، اگر تلاش کنید شیئی به نام "JeffObj" ایجاد، تضمینی وجود ندارد که شیئی به همین نام قبلاً وجود نداشته باشد. بدتر از، همه این اشیاء یک فضای نام واحد را به اشتر می‌گذارند، حتی اگر آن‌ها یکسان نباشد. به همین دلیل، فراخ CreateSemaphore همیشه NULL بازمی‌گرداند، زیرا یک قفل (mutex) با همان ناماً وجود دارد.


```c++
HANDLE hMutex = CreateMutex(NULL, FALSE, TEXT("JeffObj"));
HANDLE hSem = CreateSemaphore(NULL, 1, 1, TEXT("JeffObj"));
DWORD dwErrorCode = GetLastError();
```

اگر شما مقدار dwErrorCode را پس از اجرای کد قبلی بررسی کنید، متوجه خواهید شد که یک کد بازگشت 6 (ERROR_INVALID_HANDLE) وجود دارد. این کد خطا توصیفی نیست، اما چه کاری می‌توانید انجام دهید؟
حال که می‌دانید چگونه یک شیء را نام‌گذاری کنید، بید ببینیم چگونه می‌توانید اشیاء را به این روش به اشتراک بگذارید. فرض کنید فرآیند A شروع به کار می‌کند و تابع را فراخوانی می‌کند


```c++
HANDLE hMutexProcessA = CreateMutex(NULL, FALSE, TEXT("JeffMutex"));
```

این فراخوانی تابع یک شی جدید قفل هسته‌ای ایجاد می‌کند و آن را با نام «JeffMutex» اختصاص می‌دهد. توجه داشته باشید که در دستگیره فرایند A، hMutexProcessA یک دستگیره ارث‌بر نیست—و نیازی هم ندارد باشد، زمانی که شما فقط اشیاء را نام‌گذاری می‌کنید.
سپس، در یک زمان بعد، یک فرایند فرایند B را ایجاد می‌کند. فرایند B لزوماً فرزند فرایند A نیست؛ ممکن است از کاوشگر ویندوز یا هر برنامه دیگری ایجاد شود. واقعیت اینکه فرایند B لزوماً فرزند فرایند A نیست، مزیتی از استفاده از اشیاء نام‌گذاری شده به جای ارث‌بری است. زمانی که فرایند B شروع به اجرا می‌کند، کد زیر را اجرا می‌کند:

```c++
HANDLE hMutexProcessB = CreateMutex(NULL, FALSE, TEXT("JeffMutex"));
```

هنگام فراخوانی CreateMutex توسط فرایند B، سیستم ابتدا بررسی می‌کند که آیا یک شیء هسته‌ای با نام «JeffMutex» وجود دارد یا خیر. چرا که یک شیء با این نام وجود دارد، هسته سپس نوعء را بررسی می‌کند. که ما در حال ایجاد یک مکس هستیم و شیء با نام «JeffMutex» نیز یک موتکس است، سیستم یک بررسی امنیتی انجام می‌دهد تا ببیند فراخواننده دسترسی کامل بهء دارد یا خیر. اگر دسترسی وجود داشته باشد، سیستم یک ورودیالی در جدول دستگیره‌ فرایند B پیدا می‌کند و آن را به شیء هسته‌ای موجود اشاره می‌دهد. اگر نوعء‌ها مطابقت ند باشد یا دسترسی رد شود، Create ناموفق می‌شود (NULLمی‌گرداند).
توجه: توابع ایجاد شیء هستهای (مانند CreateSemaphore) همیشه دستگیره‌هایی با دسترسی کامل بازمی‌گردانند. اگر میخواهید دسترسی‌های موجود برای یک دستگیره را محدود کنید، می‌توانید از نسخه‌های‌یافته توابع ایجاد شیء هسته‌ای (با پسوند Ex) استفاده کنید که یک پارامتر dwDesiredAccess اضافی می‌پذیرند. برای مثال، می‌توانید اجازه یا عدم اجازه فراخوانی ReleaseSemaphore را بر روی یک دسته سِمافور با استفاده یا عدم استفاده از SEMAPHORE_MODIFY_STATE در فراخوانی CreateSemaphoreEx بدهید. مستندات SDK ویندوز را برایئیات حقوق خاص مربوط به هر نوع شیء هسته‌ای بخوان.


وقتی فراخوانی CreateMutex توسط فرایند B موفق می‌شود، در واقع یک قفل ایجاد نمی‌شود. به جای آن، فرایند B یک مقدار دستگیره نسبی فرایند به خود اختصاص می‌دهد که هویت شی قفل موجود در هسته را مشخص می‌کند.

نکته: هنگامی که اشیای هسته‌ای دارای نامهای مشترک هستند، به یکئیات بسیار مهم توجه کنید.هنگامی که فرایند B Create را فراخوانی می‌کند، اطلاعات ویژگی‌های امنیتی یک پارامتر دوم را به تابع می‌گذارد. اگر با نام مشخص شده قبلاً داشته باشد، این پارامترها نادیده گرفته میشوند! یک برنامه می‌تواند تعیین کند که آیا واقعا یک شی هسته‌ای جدید ایجاد کرده است یا فقط یک شی را باز کرده است، با فراخوانی GetLastError بلاف پس از فراخوانی Create*


```c++
HANDLE hMutex = CreateMutex(&sa, FALSE, TEXT("JeffObj"));
if (GetLastError() == ERROR_ALREADY_EXISTS) {
// Opened a handle to an existing object.
// sa.lpSecurityDescriptor and the second parameter
// (FALSE) are ignored.
} else {
// Created a brand new object.
// sa.lpSecurityDescriptor and the second parameter
// (FALSE) are used to construct the object.
}
```

یک روش جایگزین برای به اشتراک گذاشتن اشیاء بر اساس نام وجود دارد. به جای فراخوانی یک تابع Create*، یک فرایند می‌تواند یکی از توابع Open* نشان داده شده در اینجا را فراخوانی کند:


```c++
HANDLE OpenMutex( DWORD dwDesiredAccess, BOOL bInheritHandle, PCTSTR pszName);
HANDLE OpenEvent( DWORD dwDesiredAccess, BOOL bInheritHandle, PCTSTR pszName);
HANDLE OpenSemaphore( DWORD dwDesiredAccess, BOOL bInheritHandle, PCTSTR pszName);
HANDLE OpenWaitableTimer( DWORD dwDesiredAccess, BOOL bInheritHandle, PCTSTR pszName);
HANDLE OpenFileMapping( DWORD dwDesiredAccess, BOOL bInheritHandle, PCTSTR pszName);
HANDLE OpenJobObject( DWORD dwDesiredAccess, BOOL bInheritHandle, PCTSTR pszName);
```

توجه داشته باشید که تمام این توابع دارای پروتوتایپ مشابهی هستند. پارامتر آخر، pszName، نام یک شیء هسته‌ای را نشان می‌دهد. نمی‌توانید NULL را برای این پارامتر ارسال کنید؛ باید آدرس یک رشته صفر-پایان را ارسال کنید. این توابع فضای نام یکتای شیء‌های هسته‌ای را جستجو می‌کنند تا مطابقت پیدا کنند. اگر هیچ شیء هسته‌ای با نام مشخص‌شده وجود نداشته باشد، توابع NULL را بازمی‌گردانند و GetLastError عدد ۲ (ERROR_FILE_NOT_FOUND) را برمی‌گرداند. با این حال، اگر یک شیء هسته‌ای با نام مشخص‌شده وجود داشته باشد، اما نوع متفاوتی داشته باشد، توابع NULL را بازمی‌گردانند و GetLastError عدد ۶ را برمی‌گرداند.

تفاوت اصلی بین فراخوانی تابع Create* و* در این است که اگر شی قبلاً وجود نداشته باشد Create* آن را ایجاد می‌کند، در حالی که Open* صرفً شکست می‌خورد.



شیء‌های نام‌دار معمولاً برای جلوگیری از اجرای چندین نمونه از یک برنامه استفاده می‌شوند. برای انجام این کار، صرفاً تابع Create* را در تابع _tmain یا _tWinMain خود فراخوانی کنید تا یک شیء نام‌دار ایجاد شود. (مهم نیست چه نوع شیئی ایجاد می‌کنید.) هنگامی که تابع Create* بازگشتی، GetLastError را فراخوانی کنید. اگر GetLastError خطای ERROR_ALREADY_EXISTS را بازگرداند، نمونه دیگری از برنامه شما در حال اجرا است و نمونه جدید می‌تواند خاتمه یابد. اینجا قطعه‌ای کد است که این موضوع را نشان می‌دهد:

```c++
int WINAPI _tWinMain(HINSTANCE hInstExe, HINSTANCE, PTSTR pszCmdLine,
int nCmdShow) {
HANDLE h = CreateMutex(NULL, FALSE,
TEXT("{FA531CC1-0497-11d3-A180-00105A276C3E}"));
if (GetLastError() == ERROR_ALREADY_EXISTS) {
// There is already an instance of this application running.
// Close the object and immediately return.
CloseHandle(h);
return(0);
}
// This is the first instance of this application running.
...
// Before exiting, close the object.
CloseHandle(h);

}
```
