میتونیم از Privilege استفاده کنیم 

یکی از مهم تریم Privilege ها داخل ویندوز Privilege Debug هستش

وقتی که این دستور رو بزنیم پشت صحنه یک دسترسی برای ما فعال میشه تحت عنوان SeDebugPrivilege

این سطح دسترسی برای Mimikatz این امکان رو فراهم میکنه debug روی سایر پروسس ها انجام بده 

در اصل mimikatz میره lsass رو debug میکنه برای فرایند credential dumping 

به طور کلی با استفاده از این سطح دسترسی میتونیم read و write روی memory process های دیگر داشته باشیم


```
Privilege::Debug
```

---

### 🔹 SeDebugPrivilege چیست؟
- توی ویندوز یک سری **Privileges (حق دسترسی‌های ویژه)** وجود دارن که به پروسه‌ها یا یوزرها اجازه میدن کارهایی فراتر از سطح عادی انجام بدن.  
- یکی از این‌ها **SeDebugPrivilege** هست.  
- **کارکرد اصلی:** اجازه میده یک پروسه به حافظه‌ی پروسه‌های دیگه دسترسی کامل پیدا کنه (حتی پروسه‌هایی که متعلق به یوزرهای دیگه یا خود سیستم هستن).  
- به همین خاطر این دسترسی برای **دیباگرها (Debugger)** لازمه، چون باید بتونن داخل حافظه‌ی پروسه‌ها رو ببینن، breakpoint بذارن و بررسی کنن.  

به زبان ساده:  
اگر یک یوزر یا پروسه SeDebugPrivilege داشته باشه، می‌تونه به راحتی بره سراغ پروسه‌های حساس مثل **LSASS.exe** و از داخلش اطلاعات مثل هش‌ها یا پسوردها رو استخراج کنه.

---

### 🔹 privilege::debug در Mimikatz
- وقتی توی Mimikatz دستور `privilege::debug` رو اجرا می‌کنی، در واقع داری به Mimikatz میگی که تلاش کنه **SeDebugPrivilege** رو برای پروسه‌ی خودش فعال کنه.  
- اگه فعال بشه، پیام `Privilege '20' OK` (یا مشابهش) میده.  
- شماره 20 در واقع **شناسه‌ی SeDebugPrivilege** هست.  

یعنی:  
- بدون داشتن این privilege، Mimikatz نمی‌تونه بره حافظه‌ی LSASS یا پروسه‌های دیگه رو dump کنه.  
- با داشتنش، می‌تونه آزادانه حافظه‌ی پروسه‌ها رو بخونه → که پایه‌ی بیشتر حملات و قابلیت‌های Mimikatz هست.

---

### 🔹 ارتباط دقیق:
1. **SeDebugPrivilege (سطح ویندوز)**: یک دسترسی سیستمی که اجازه‌ی Debug کردن پروسه‌های دیگه رو میده.  
2. **privilege::debug (سطح Mimikatz)**: دستوری برای درخواست و فعال کردن همین دسترسی توی پروسه‌ی Mimikatz.  

---

👉 نتیجه:  
هر وقت می‌بینی توی آموزش‌ها یا ویدئوها اول کار با Mimikatz `privilege::debug` زده میشه، دلیلش اینه که برنامه بتونه SeDebugPrivilege رو فعال کنه و به پروسه‌های حساس دسترسی پیدا کنه.

و یا حتی متیونیم به ریجستری هایی مثله HKLM,HKCU

```
privilege::driver
```


---

### 🔹 SeLoadDriverPrivilege چیست؟

این یک **ویژگی امنیتی (Privilege)** در ویندوزه که به یوزر یا پروسه اجازه میده **درایور (Driver) کرنل** رو بارگذاری (Load) یا حذف (Unload) کنه.

- درایورها در سطح **Kernel Mode** اجرا میشن → یعنی دسترسی بالاتر از سطح ادمین (Ring 0).
    
- هر کسی که این privilege رو داشته باشه می‌تونه یک درایور جدید توی سیستم Register کنه و اون رو به سرویس سیستم اضافه کنه.
    

---

### 🔹 کاربرد قانونی

- ادمین‌ها یا سرویس‌هایی مثل **Plug and Play**، **Windows Update** یا **Vendor Drivers** از این privilege استفاده می‌کنن تا درایورهای سخت‌افزار (مثل کارت شبکه، کارت گرافیک و ...) رو نصب یا آپدیت کنن.
    
- برای نصب درایور معمولاً باید امضا (Digital Signature) هم معتبر باشه، مخصوصاً توی ویندوزهای جدید.
    

---

### 🔹 ریسک و سوءاستفاده امنیتی

اگر مهاجم بتونه این privilege رو بگیره، خیلی خطرناکه چون:

1. می‌تونه یک **درایور مخرب** لود کنه.
    
    - این درایور می‌تونه مستقیماً به حافظه کرنل دسترسی داشته باشه.
        
    - یعنی محدودیت‌های User Mode (مثل UAC، آنتی‌ویروس یا EDR) رو دور بزنه.
        
2. می‌تونه **درایورهای قانونی رو جایگزین یا تغییر بده** و یک Backdoor در سطح سیستم ایجاد کنه.
    
3. چون درایور در **Ring 0** اجرا میشه، مهاجم عملاً کنترل کامل روی سیستم پیدا میکنه (حتی بالاتر از Admin).
    

---

### 🔹 سناریوی هکی

- مهاجم یک درایور دست‌ساز (مثلاً برای Dump کردن LSASS یا غیرفعال کردن AV) می‌نویسه.
    
- بعد با داشتن SeLoadDriverPrivilege، اون درایور رو توی سیستم قربانی Load میکنه.
    
- حالا در سطح Kernel، به همه چیز دسترسی پیدا می‌کنه → خیلی خطرناک!
    

---

### 🔹 جمع‌بندی

- **SeDebugPrivilege** → اجازه‌ی Debug کردن پروسه‌ها در سطح User Mode.
    
- **SeLoadDriverPrivilege** → اجازه‌ی نصب/لود کردن درایور در سطح Kernel Mode.
    

⚠️ از نظر خطر، SeLoadDriverPrivilege حتی قوی‌تر از SeDebugPrivilege هست چون مستقیم به کرنل دسترسی میده.

- حتی بعضی ابزارها رو تنظیم کنه که **لاگ‌های خودشون رو پاک یا غیرفعال کنن** تا شناسایی نشن.

### SeSecurityPrivilege چیست؟

این privilege اجازه میده که یک یوزر یا پروسه:

1. **Security Log** ها (Security Event Log) رو بخونه.
    
    - به طور پیش‌فرض فقط Administrator و LocalSystem می‌تونن Security Event Log رو ببینن.
        
    - با این privilege، حتی اگه محدودیت باشه، پروسه می‌تونه Eventهای حساس (مثل لاگین‌ها، شکست‌ها، تغییرات policy) رو بخونه.
✅ پس:

- `privilege::security` = فعال کردن SeSecurityPrivilege
    
- SeSecurityPrivilege = دسترسی برای خواندن و تغییر **Security Log** ها و **Audit Policy** سیستم.

## 🔹 دستور `privilege::sysenv`

وقتی این دستور رو توی Mimikatz بزنی:

```powershell
privilege::sysenv
```

در واقع داره privilege ویندوز به اسم **SeSystemEnvironmentPrivilege** رو فعال می‌کنه.

---

## 🔹 SeSystemEnvironmentPrivilege یعنی چی؟

این privilege یکی از حساس‌ترین دسترسی‌های ویندوزه.  
به پروسه اجازه میده که **متغیرهای محیطی سطح سیستم (System Environment Variables)** رو بخونه یا تغییر بده.

❗ ولی اینجا منظور فقط متغیرهای ساده مثل PATH نیست!  
بلکه بیشتر به **Firmware Environment Variables** (مثل تنظیمات UEFI/BIOS و Boot Configuration Data) ربط داره.

---

## 🔹 چه کارایی میشه باهاش کرد؟

1. **تغییر تنظیمات Boot**
    
    - مثلاً تغییر Boot Order یا تغییر پارامترهای بوت سیستم.
        
    - دستکاری BCD (Boot Configuration Data).
        
2. **حمله‌های Bootkit / Rootkit**
    
    - مهاجم می‌تونه کدی رو به محیط بوت تزریق کنه.
        
    - با این کار قبل از بالا اومدن کامل ویندوز، کد خودش اجرا میشه.
        
3. **دستکاری Secure Boot یا Firmware Variables**
    
    - ممکنه با این privilege مهاجم بتونه Secure Boot رو غیرفعال کنه یا پارامترهای UEFI رو تغییر بده.
        

---

## 🔹 کاربرد قانونی

- ابزارهای مدیریت سیستم یا OEMها (شرکت‌های سازنده لپ‌تاپ/مادربرد) ممکنه نیاز داشته باشن این privilege رو برای تغییر Firmware یا تنظیمات خاص استفاده کنن.
    
- مثال: تغییر دادن Boot Configuration با `bcdedit`.

## 🔹 Event ID 4672 – Special privileges assigned to new logon

این لاگ زمانی ثبت میشه که **یک کاربر وارد سیستم میشه** (Logon اتفاق میفته) و اون کاربر **Special Privileges** (یعنی دسترسی‌های خیلی سطح بالا) رو به صورت پیش‌فرض دریافت می‌کنه.

---

## 🔹 چه کسانی این لاگ رو تولید می‌کنن؟

- اکانت‌های **ادمین** (مثل Domain Admin یا Local Administrator).
    
- اکانت **SYSTEM** یا سرویس‌هایی که با دسترسی‌های خیلی بالا اجرا میشن.
    

وقتی این‌ها لاگین کنن → ویندوز یه سری privilege مثل `SeDebugPrivilege`, `SeTcbPrivilege`, `SeBackupPrivilege` و ... رو بهشون میده.  
این همون چیزیه که توی **Event ID 4672** ثبت میشه.

---

## 🔹 جزئیات لاگ

این Event نشون میده:

- **Account Name** → چه کاربری وارد شده.
    
- **Logon ID** → شناسه نشست اون لاگین.
    
- **Privileges** → لیست privilegeهایی که به اون کاربر داده شدن (مثلاً: `SeDebugPrivilege`, `SeImpersonatePrivilege`).

اگر یکی از این privilege ها فعال شوند


```
 event id 4672
```

لاگ میشود 




## 🔹 Event ID 4703 – A user right was adjusted

این لاگ زمانی ثبت میشه که یک **Privilege (User Right)** روی یک پروسه توسط کاربر **فعال یا غیرفعال** بشه.

به عبارتی:  
هر وقت ویندوز یکی از **Privilegeهای حساس** مثل `SeDebugPrivilege` ، `SeLoadDriverPrivilege` یا همون‌هایی که توی Mimikatz فعال می‌کنیم (`privilege::debug`, `privilege::tcp`, `privilege::sysenv` و ...)، برای یه پروسه روشن/خاموش بشن → این رویداد تولید میشه.

---

## 🔹 جزئیات لاگ

وقتی Event 4703 اتفاق میفته، اطلاعات زیر توی Security Log ثبت میشه:

- **Subject:**
    
    - کدوم کاربر/اکانت این تغییر رو اعمال کرده.
        
- **Target Process:**
    
    - کدوم پروسه privilege رو گرفته.
        
- **Privilege:**
    
    - اسم اون privilege (مثلاً `SeDebugPrivilege`).
        
- **Operation:**
    
    - فعال (Enabled) یا غیرفعال (Disabled).
