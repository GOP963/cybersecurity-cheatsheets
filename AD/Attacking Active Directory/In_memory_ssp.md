## 📌 اول: SSP (Security Support Provider) چیه؟

- ویندوز برای **احراز هویت (Authentication)** از **SSPI (Security Support Provider Interface)** استفاده می‌کنه.
    
- این SSPI در واقع APIای هست که سرویس‌های مختلف مثل **Kerberos، NTLM، Negotiate، CredSSP** و حتی پروتکل‌های Third-party می‌تونن بهش وصل بشن.
    
- هر **SSP** به شکل یک DLL توی حافظه‌ی پروسه‌ی **LSASS** لود میشه.
    

👉 یعنی وقتی یه یوزر لاگین می‌کنه، LSASS میاد از این DLLها کمک می‌گیره تا عملیات احراز هویت رو انجام بده.

---

## 📌 حالا حمله In-Memory SSP چیه؟

ایده‌ی اصلی:  
🔴 مهاجم میاد یک **DLL مخرب (Fake SSP)** می‌سازه و اونو **مستقیم در حافظه‌ی LSASS تزریق (Inject)** می‌کنه → بدون اینکه توی دیسک ذخیره بشه یا توی رجیستری ثبت بشه.

این باعث میشه:

1. LSASS اون DLL رو به عنوان یک SSP معتبر لود کنه.
    
2. همه‌ی **کرِدهای جدید (username/password)** که یوزرها لاگین می‌کنن، به اون DLL مخرب هم ارسال بشه.
    
3. مهاجم می‌تونه پسوردها و هش‌ها رو همون لحظه در حافظه جمع‌آوری کنه.
    

---

## 📌 تفاوت با SSP معمولی

- توی حمله‌ی عادی SSP، مهاجم باید یه DLL (مثل mimilib.dll) رو توی مسیر سیستم بذاره و مسیرشو توی رجیستری اضافه کنه:
    
    ```
    HKLM\SYSTEM\CurrentControlSet\Control\Lsa\Security Packages
    ```
    
    → ولی این نیاز به ری‌استارت سیستم یا سرویس LSASS داره.
    
- اما توی **In-Memory SSP**، DLL مستقیم توی حافظه LSASS تزریق میشه →
    
    - نیازی به ریبوت نداره
        
    - اثری روی رجیستری نمیذاره
        
    - ماندگاری کمتره (بعد از ریبوت می‌پره)، ولی **خیلی Stealth** هست.
        

---

## 📌 ابزارهایی که این حمله رو دارن

- **Mimikatz** دقیقاً این قابلیت رو داره:
    
    ```
    mimikatz # misc::memssp
    ```
    
    با این دستور، یک SSP در حافظه LSASS لود میشه که هر لاگین جدید رو لاگ می‌کنه و پسوردش رو لو میده.
    

---

## 📌 استفاده Red Teamها

- خیلی کاربردی برای **Credential Harvesting زنده** توی شبکه‌های واقعی.
    
- مهاجم میره روی یه ماشین حساس (مثل سرور اپلیکیشن یا DC Member)، **In-Memory SSP** لود می‌کنه → بعد منتظر میشه ادمین یا یوزر لاگین کنه → بلافاصله کرِدها رو جمع می‌کنه.
	    
- نیازی به ریبوت یا تغییر ماندگار توی سیستم نیست، پس خیلی سخت‌تر Detect میشه.
    

---

## 📌 از دید مدافع (Defender)

- پیدا کردن این حمله خیلی سخته چون روی دیسک چیزی ثبت نمیشه.
    
- راه‌های مانیتور:
    
    - بررسی **LSASS memory injection** با EDR/XDR.
        
    - فعال کردن **LSASS Protection (RunAsPPL)**.
        
    - بررسی غیرعادی بودن DLLهای لودشده توی LSASS.
        
    - Event ID مربوط به **Authentication Packages** (ولی همیشه کافی نیست).
        

---

🔑 خلاصه:  
**In-Memory SSP** یعنی یک DLL مخرب به‌عنوان Security Support Provider به صورت مستقیم در حافظه‌ی LSASS تزریق بشه تا کرِدهای جدید رو به دست بیاره؛ سریع، بی‌صدا، و خیلی خطرناک.
