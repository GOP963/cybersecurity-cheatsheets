

## مقدمه

برنامه‌نویسی هسته‌ی ویندوز در نظر بسیاری یک «هنر تاریک» محسوب می‌شود که تنها عده‌ی معدودی موفق به کشف رازهای آن می‌شوند. اما توسعه در سطح هسته، دست‌کم از نظر کلی، تفاوتی با توسعه در سطح user-mode ندارد. در هر دو حالت، درک خوب از پلتفرم برای تولید کد باکیفیت ضروری است.

این کتاب راهنمایی است برای برنامه‌نویسی در هسته‌ی ویندوز با استفاده از محیط توسعه‌ی یکپارچه‌ی Visual Studio. این محیط برای بسیاری از توسعه‌دهندگان در اکوسیستم مایکروسافت آشناست، بنابراین منحنی یادگیری تنها به درک هسته، کدنویسی و دیباگ محدود می‌شود و اصطکاک کمتری با ابزارهای توسعه وجود دارد.

کتاب بر **درایورهای نرم‌افزاری** تمرکز دارد — اصطلاحی که نویسنده برای درایورهایی به‌کار می‌برد که با سخت‌افزار سروکار ندارند. درایورهای نرم‌افزاری هسته دسترسی کامل به هسته دارند و می‌توانند هر عملیاتی را که هسته مجاز می‌داند انجام دهند. برخی درایورهای نرم‌افزاری تخصصی‌تر هستند، مانند **file system mini-filter** که در کتاب توضیح داده شده است.

## این کتاب برای چه کسانی است

کتاب برای توسعه‌دهندگانی نوشته شده که هدفشان هسته‌ی ویندوز است و برای رسیدن به اهدافشان نیاز به نوشتن درایور دارند. یکی از رایج‌ترین کاربردها در حوزه‌ی **امنیت سایبری** است، جایی که درایورهای هسته مکانیزم اصلی برای دریافت اعلان رویدادهای مهم و قطع برخی عملیات‌ها هستند.

C++ در جاهایی به‌کار رفته که مزایایش در نگهداری، خوانایی یا مدیریت منابع آشکار است. از ساختارهای پیچیده‌ی C++ مانند template metaprogramming استفاده نشده. این کتاب درباره‌ی C++ نیست، بلکه درباره‌ی درایورهای هسته‌ی ویندوز است.

### پروسه‌ها (Processes)

یک **پروسه** یک شیء مدیریتی است که نمایانگر یک نمونه‌ی در حال اجرای برنامه است. عبارت رایج «پروسه اجرا می‌کند» دقیق نیست — **پروسه‌ها مدیریت می‌کنند، ریسمان‌ها (Threads) هستند که کد را اجرا می‌کنند.**


![[Pasted image 20260526142603.png]]

هر پروسه مالک موارد زیر است:

- **برنامه‌ی اجرایی**: کد و داده‌ی اولیه
- **فضای آدرس مجازی خصوصی**: برای تخصیص حافظه
- **توکن دسترسی (Primary Token)**: زمینه‌ی امنیتی پروسه
- **جدول Handle خصوصی**: برای اشیاء اجرایی مانند event، semaphore و فایل
- **یک یا چند ریسمان**: پروسه‌ی user-mode معمولاً با یک ریسمان شروع می‌شود؛ پروسه بدون ریسمان عملاً بی‌فایده است و توسط هسته از بین می‌رود

هر پروسه با یک **Process ID** منحصربه‌فرد شناسایی می‌شود. این ID تا زمانی که شیء هسته‌ای پروسه وجود دارد یکتاست و پس از آن ممکن است برای پروسه‌های جدید بازاستفاده شود.

فایل اجرایی به‌تنهایی شناسه‌ی یکتای پروسه نیست — مثلاً می‌توان پنج نمونه از `notepad.exe` را همزمان اجرا کرد که هر کدام فضای آدرس، ریسمان‌ها، جدول Handle و Process ID مستقل دارند، اما همه از یک فایل تصویری مشترک استفاده می‌کنند.

یک پروسه با **Process ID** منحصربه‌فردش شناسایی می‌شود که تا زمانی که شیء هسته‌ای پروسه وجود دارد یکتاست. پس از نابودی آن، همان ID ممکن است برای پروسه‌های جدید بازاستفاده شود. مهم است بدانیم که فایل اجرایی به‌تنهایی شناسه‌ی یکتای پروسه نیست. مثلاً ممکن است پنج نمونه از `notepad.exe` همزمان در حال اجرا باشند. هر یک از این نمونه‌های Notepad فضای آدرس، ریسمان‌ها، جدول Handle و Process ID مخصوص به خود را دارد. هر پنج پروسه از همان فایل تصویری (`notepad.exe`) به‌عنوان کد و داده‌ی اولیه استفاده می‌کنند. شکل ۱-۲ تصویری از تب Details در Task Manager را نشان می‌دهد که پنج نمونه از Notepad.exe را با ویژگی‌های مستقل هر کدام به نمایش می‌گذارد.

## حافظه‌ی مجازی (Virtual Memory)

هر پروسه فضای آدرس مجازی، خصوصی و خطی مخصوص به خود دارد. این فضا در ابتدا تقریباً خالی است؛ اولین چیزهایی که نگاشت می‌شوند **executable image** و **NtDll.dll** هستند، سپس DLLهای زیرسیستم. پس از شروع اجرای thread اصلی، احتمالاً حافظه تخصیص داده می‌شود، DLLهای بیشتری بارگذاری می‌شوند و غیره. این فضای آدرس **خصوصی** است، یعنی پروسه‌های دیگر نمی‌توانند مستقیماً به آن دسترسی داشته باشند.

---

### محدوده‌ی فضای آدرس

فضای آدرس از صفر شروع می‌شود (از نظر فنی، ۶۴ کیلوبایت اول و آخر قابل commit نیستند) و تا حداکثری ادامه می‌یابد که به **bitness** پروسه و سیستم‌عامل بستگی دارد:

| پروسه | سیستم‌عامل | حداکثر فضای آدرس |
|---|---|---|
| ۳۲ بیتی | ۳۲ بیتی (پیش‌فرض) | **2 GB** |
| ۳۲ بیتی + `LARGEADDRESSAWARE` | ۳۲ بیتی با تنظیم افزایش فضا | **3 GB** |
| ۶۴ بیتی | ۶۴ بیتی | **8 TB** (ویندوز ۸ و قبل) / **128 TB** (ویندوز ۸.۱ و بعد) |
| ۳۲ بیتی + `LARGEADDRESSAWARE` | ۶۴ بیتی | **4 GB** |
| ۳۲ بیتی بدون فلگ | ۶۴ بیتی | **2 GB** |

> **چرا فلگ `LARGEADDRESSAWARE` لازم است؟**
> محدوده‌ی ۲ گیگابایتی تنها به ۳۱ بیت نیاز دارد و بیت پرارزش (MSB) آزاد می‌ماند. برخی برنامه‌ها از این بیت برای اهداف خود استفاده می‌کنند. این فلگ اعلام می‌کند که برنامه از بیت ۳۱ استفاده نمی‌کند و بنابراین آدرس‌های بزرگ‌تر از ۲ گیگابایت (که این بیت را set می‌کنند) مشکلی ایجاد نمی‌کنند.

---

### نسبی بودن آدرس‌ها

هر پروسه فضای آدرس مستقل دارد، بنابراین آدرس‌ها **نسبی** هستند نه مطلق. مثلاً آدرس `0x20000` به‌تنهایی کافی نیست؛ باید مشخص شود این آدرس متعلق به کدام پروسه است.

---

### مجازی بودن حافظه

حافظه «مجازی» نامیده می‌شود چون رابطه‌ای غیرمستقیم بین آدرس و محل فیزیکی آن در RAM وجود دارد. یک بافر ممکن است:
- در **RAM** نگاشت شده باشد، یا
- موقتاً در یک **فایل** (مثل page file) قرار داشته باشد.

از دیدگاه اجرا، نیازی نیست بدانیم حافظه‌ای که می‌خواهیم به آن دسترسی داشته باشیم در RAM هست یا نه:

- اگر حافظه در RAM باشد: CPU ترجمه‌ی **virtual → physical** را انجام می‌دهد و به داده دسترسی پیدا می‌کند.
- اگر حافظه در RAM نباشد (**page fault**): CPU یک استثنا (page fault exception) ایجاد می‌کند که باعث می‌شود **page fault handler** مدیر حافظه:
  1. داده را از فایل مربوطه واکشی کند
  2. آن را در RAM کپی کند
  3. تغییرات لازم را در **page table entries** اعمال کند
  4. به CPU دستور دهد دوباره تلاش کند

شکل ۱-۳ این نگاشت مفهومی از حافظه‌ی مجازی به فیزیکی را برای دو پروسه نشان می‌دهد.

## صفحه (Page) — واحد مدیریت حافظه

واحد مدیریت حافظه **page** نام دارد. هر ویژگی مرتبط با حافظه — مثل حفاظت (protection) یا وضعیت (state) — همیشه در گرانولاریتی یک page تعریف می‌شود. اندازه‌ی page توسط نوع CPU تعیین می‌شود و مدیر حافظه باید از آن پیروی کند. اندازه‌ی **page معمولی (small)** در تمام معماری‌های پشتیبانی‌شده توسط ویندوز **4 کیلوبایت** است.

---

### Large Pages و Huge Pages

علاوه بر page معمولی، ویندوز از **large pages** نیز پشتیبانی می‌کند:

| نوع | اندازه | معماری |
|---|---|---|
| Small page | 4 KB | همه |
| Large page | 2 MB | x86 / x64 / ARM64 |
| Large page | 4 MB | ARM |
| Huge page | 1 GB | ویندوز ۱۰ و Server 2016 به بعد |

Large pages از **Page Directory Entry (PDE)** برای نگاشت مستقیم استفاده می‌کنند (بدون page table)، که نتیجه‌اش:
- ترجمه‌ی سریع‌تر
- استفاده‌ی بهتر از **TLB** (Translation Lookaside Buffer — کش ترجمه‌های اخیر در CPU)

یک entry واحد در TLB برای large page، حافظه‌ی بسیار بیشتری نسبت به small page پوشش می‌دهد.

**معایب large pages:**
- حافظه باید در RAM **پیوسته (contiguous)** باشد — در صورت کمبود یا fragmentation ممکن است شکست بخورد
- همیشه **non-pageable** هستند (نمی‌توانند به page file منتقل شوند)
- فقط از حفاظت **read/write** پشتیبانی می‌کنند

Huge pages (1 GB) به‌صورت خودکار در کنار large pages استفاده می‌شوند، اگر تخصیص حداقل 1 GB باشد و آن فضا به‌صورت پیوسته در RAM موجود باشد.

---

### وضعیت‌های Page (Page States)

هر page در حافظه‌ی مجازی می‌تواند در یکی از سه وضعیت باشد:

**Free (آزاد)**
page به هیچ شکلی تخصیص نیافته. هر تلاش برای دسترسی به آن منجر به **access violation exception** می‌شود. اکثر pageهای یک پروسه‌ی تازه‌ساخته در این وضعیت هستند.

**Committed (تخصیص‌یافته)**
عکس Free؛ یک page تخصیص‌یافته که می‌توان با موفقیت به آن دسترسی داشت (مشروط به عدم تعارض با ویژگی‌های حفاظتی؛ مثلاً نوشتن روی یک page فقط‌خواندنی باعث access violation می‌شود). Committed pages یا در RAM نگاشت شده‌اند یا در یک فایل (مثل page file).

**Reserved (رزرو‌شده)**
page در وضعیت committed نیست، اما محدوده‌ی آدرس برای استفاده‌ی احتمالی در آینده رزرو شده است. از دیدگاه CPU، مثل Free است — هر تلاش برای دسترسی باعث access violation می‌شود. اما تخصیص‌های جدید از طریق `VirtualAlloc` (یا `NtAllocateVirtualMemory`) که آدرس مشخصی تعیین نکنند، در ناحیه‌ی رزرو‌شده تخصیص نمی‌یابند. مثال کلاسیک استفاده از reserved memory برای حفظ فضای آدرس مجازی پیوسته، در بخش **Thread Stacks** همین فصل توضیح داده شده است.

---

### حافظه‌ی سیستم (System Memory)

بخش پایینی فضای آدرس برای پروسه‌های user-mode است. اما سیستم‌عامل نیز باید جایی قرار بگیرد — و آن جا **بخش بالایی** فضای آدرس است:

| پیکربندی | محدوده‌ی سیستم |
|---|---|
| ۳۲ بیتی، بدون تنظیم افزایش فضا | `0x80000000` تا `0xFFFFFFFF` (2 GB بالایی) |
| ۳۲ بیتی، با 3 GB user space | `0xC0000000` تا `0xFFFFFFFF` (1 GB بالایی) |
| ۶۴ بیتی، ویندوز ۸ / Server 2012 و قبل | 8 TB بالایی |
| ۶۴ بیتی، ویندوز ۸.۱ / Server 2012 R2 و بعد | 128 TB بالایی |

شکل ۱-۴ چیدمان حافظه‌ی مجازی را برای دو حالت افراطی نشان می‌دهد: پروسه‌ی ۳۲ بیتی روی سیستم ۳۲ بیتی (چپ) و پروسه‌ی ۶۴ بیتی روی سیستم ۶۴ بیتی (راست).

### ویژگی‌های فضای سیستم

برخلاف فضای user، **system space فرآیند-نسبی نیست** — همان kernel، همان HAL، همان درایورها به تمام پروسه‌ها سرویس می‌دهند. بنابراین آدرس‌های system space **مطلق** هستند نه نسبی، چون از context هر پروسه‌ای یکسان به نظر می‌رسند. البته دسترسی مستقیم از user mode به system space منجر به access violation می‌شود.

**نکات مهم درباره‌ی kernel drivers:**
- در system space قرار دارند و به‌طور خودکار از دسترسی مستقیم user mode محافظت می‌شوند
- تأثیر بالقوه‌ی **سیستم‌گستر** دارند — مثلاً اگر یک kernel driver حافظه leak کند، آن حافظه حتی پس از unload شدن درایور آزاد نمی‌شود
- در مقابل، پروسه‌های user-mode هرگز نمی‌توانند چیزی فراتر از طول عمر خود leak کنند؛ kernel مسئول بستن تمام handleها و آزاد کردن تمام حافظه‌ی خصوصی یک پروسه‌ی مُرده است


## فضای سیستم (System Space)

فضای سیستم فرآیند-نسبی نیست — در نهایت، همان سیستم، همان هسته و همان درایورها هستند که به تمام پروسه‌های روی سیستم سرویس می‌دهند (استثنا برخی حافظه‌های سیستمی است که به ازای هر session جداگانه‌اند، اما برای این بحث اهمیتی ندارند). از این رو، هر آدرس در system space **مطلق** است نه نسبی، چون از context هر پروسه‌ای یکسان «دیده» می‌شود. البته دسترسی واقعی از user mode به system space منجر به **access violation exception** می‌شود.

System space محل قرارگیری خود هسته، **HAL (Hardware Abstraction Layer)** و درایورهای هسته پس از بارگذاری است. بنابراین kernel drivers به‌طور خودکار از دسترسی مستقیم user mode محافظت می‌شوند. همچنین به این معناست که تأثیر بالقوه‌ی **سیستم‌گستر** دارند. مثلاً اگر یک kernel driver حافظه leak کند، آن حافظه حتی پس از unload شدن درایور آزاد نخواهد شد. پروسه‌های user-mode در مقابل هرگز نمی‌توانند چیزی فراتر از طول عمر خود leak کنند. هسته مسئول بستن و آزاد کردن تمام منابع خصوصی یک پروسه‌ی مُرده است (تمام handleها بسته و تمام حافظه‌ی خصوصی آزاد می‌شود).

## Threads

موجودیت‌های واقعی که کد را اجرا می‌کنند **thread** نام دارند. یک thread درون یک پروسه قرار دارد و از منابعی که پروسه در اختیار می‌گذارد — مثل حافظه‌ی مجازی و handleها به kernel objects — برای انجام کار استفاده می‌کند.

مهم‌ترین اطلاعاتی که یک thread در اختیار دارد:

- **Current access mode** — یا user mode یا kernel mode
- **Execution context** — شامل رجیسترهای پردازنده و وضعیت اجرا
- **یک یا دو stack** — برای تخصیص متغیرهای محلی و مدیریت فراخوانی توابع
- **آرایه‌ی TLS (Thread Local Storage)** — روشی برای ذخیره‌ی داده‌های خصوصی هر thread با معناشناسی دسترسی یکنواخت
- **اولویت پایه (base priority) و اولویت جاری (dynamic priority)**
- **Processor affinity** — مشخص می‌کند thread مجاز است روی کدام پردازنده‌(ها) اجرا شود

---

### وضعیت‌های Thread

رایج‌ترین وضعیت‌هایی که یک thread می‌تواند در آن‌ها باشد:

**Running (در حال اجرا)**
در حال اجرای کد روی یک پردازنده‌ی (منطقی) است.

**Ready (آماده)**
منتظر زمان‌بندی برای اجرا است، چون تمام پردازنده‌های مرتبط مشغول یا در دسترس نیستند.

**Waiting (در انتظار)**
منتظر وقوع یک رویداد است تا بتواند ادامه دهد. پس از وقوع رویداد، thread به وضعیت Ready منتقل می‌شود.

شکل ۱-۵ نمودار وضعیت‌های این سه حالت را نشان می‌دهد. اعداد داخل پرانتز شماره‌ی وضعیت‌ها هستند، همان‌طور که ابزارهایی مثل **Performance Monitor** نمایش می‌دهند. توجه داشته باشید که وضعیت Ready یک حالت خواهر به نام **Deferred Ready** دارد که مشابه آن است و برای کاهش قفل‌گذاری داخلی (internal locking) وجود دارد.

## Stack های Thread

هر thread یک stack دارد که در حین اجرا از آن استفاده می‌کند — برای ذخیره‌ی متغیرهای محلی، پارامترهای ارسالی به توابع (در برخی موارد) و آدرس‌های بازگشتی قبل از فراخوانی توابع.

---

### انواع Stack

هر thread حداقل **یک stack در فضای kernel** دارد که اندازه‌ی آن نسبتاً کوچک است:
- پیش‌فرض در سیستم‌های **32-bit**: 12 KB
- پیش‌فرض در سیستم‌های **64-bit**: 24 KB

یک thread در user-mode علاوه بر این، **یک stack دوم در فضای user-space** پروسه‌ی خود دارد که به‌مراتب بزرگ‌تر است و به‌طور پیش‌فرض می‌تواند تا **1 MB** رشد کند.

شکل ۱-۶ مثالی با سه user-mode thread و stack‌هایشان را نشان می‌دهد؛ thread 1 و 2 در پروسه‌ی A و thread 3 در پروسه‌ی B قرار دارند.

---

### ویژگی‌های Kernel Stack

kernel stack تا زمانی که thread در وضعیت **Running** یا **Ready** است، همیشه در **RAM** باقی می‌ماند. دلیل این موضوع ظریف است و در ادامه‌ی همین فصل توضیح داده خواهد شد. در مقابل، user-mode stack مثل هر حافظه‌ی user-mode دیگری می‌تواند **page out** شود.

---

### مکانیزم رشد User-Mode Stack

user-mode stack از نظر مدیریت اندازه با kernel-mode stack متفاوت است. این stack به شکل زیر کار می‌کند:

1. در ابتدا مقدار کمی حافظه **commit** می‌شود (حتی می‌تواند به اندازه‌ی یک page باشد)
2. page بعدی با attribute ویژه‌ی **PAGE_GUARD** commit می‌شود
3. بقیه‌ی فضای آدرس stack به حالت **reserved** باقی می‌ماند تا حافظه هدر نرود

مکانیزم رشد به این صورت عمل می‌کند:

- اگر thread به فضای بیشتری نیاز داشته باشد، به **guard page** دسترسی پیدا می‌کند
- این دسترسی یک **page-guard exception** ایجاد می‌کند
- **memory manager** حفاظت guard را برمی‌دارد، یک page اضافی commit می‌کند و آن را با **PAGE_GUARD** علامت‌گذاری می‌کند
- به این ترتیب stack به‌تدریج و بر اساس نیاز رشد می‌کند، بدون اینکه از ابتدا تمام حافظه commit شده باشد

## اندازه‌ی User-Mode Stack

اندازه‌های user-mode stack یک thread به این صورت تعیین می‌شوند:

- **PE header** فایل اجرایی دارای مقادیر **stack commit** و **reserved** است که به‌عنوان پیش‌فرض استفاده می‌شوند — همیشه برای **اولین thread** پروسه اعمال می‌شوند.
- هنگام ساخت thread با `CreateThread` (یا توابع مشابه)، فراخواننده می‌تواند اندازه‌ی stack را مشخص کند — یا **committed** یا **reserved** (نه هر دو)، بسته به flag ارسالی. مقدار صفر از پیش‌فرض‌های PE header استفاده می‌کند.

نکته‌ی جالب: توابع `CreateThread` و `CreateRemoteThread(Ex)` فقط یک مقدار می‌پذیرند. تابع native (مستندنشده‌ی) `NtCreateThreadEx` امکان تعیین **هر دو مقدار** را فراهم می‌کند.

## System Services (System Calls)

برنامه‌ها برای عملیاتی مثل تخصیص حافظه، باز کردن فایل و ساخت thread نیاز دارند که در نهایت کد **kernel-mode** اجرا شود. اما چطور کد user-mode می‌تواند چنین عملیاتی انجام دهد؟

### مثال: باز کردن فایل در Notepad

مسیر فراخوانی به این شکل است:

Notepad (user mode)
    └─► CreateFile()          [kernel32.dll]
            └─► NtCreateFile()    [ntdll.dll — پایین‌ترین لایه‌ی user mode]
                    └─► syscall / sysenter  ← انتقال به kernel mode
                            └─► System Service Dispatcher
                                    └─► SSDT[index] → NtCreateFile()  [kernel I/O manager]


### مراحل انتقال به Kernel Mode

1. `NtCreateFile` در `ntdll.dll` یک عدد به نام **system service number** را در رجیستر `EAX` قرار می‌دهد
2. دستور CPU ویژه صادر می‌شود:
   - `syscall` روی x64
   - `sysenter` روی x86
3. CPU به **kernel mode** سوئیچ می‌کند و به روتین **system service dispatcher** می‌پرد
4. dispatcher از مقدار `EAX` به‌عنوان ایندکس در **SSDT** (System Service Dispatch Table) استفاده می‌کند
5. کد به system call واقعی — `NtCreateFile` در kernel — پرش می‌کند
6. پس از اتمام، thread به user mode بازمی‌گردد

### نکات کلیدی

- `NtCreateFile` در `ntdll.dll` و `NtCreateFile` در kernel **نام و پارامترهای یکسانی** دارند؛ نسخه‌ی kernel پیاده‌سازی واقعی است.
- **SSDT** جدولی است که system service numberها را به توابع kernel نگاشت می‌کند.
- این مکانیزم مرز امنیتی بین user mode و kernel mode را حفظ می‌کند.

## معماری Windows (Figure 1-9)

### لایه‌های User Mode

| مؤلفه | توضیح |
|---|---|
| **User Processes** | پروسه‌های معمولی مثل notepad.exe، cmd.exe، explorer.exe |
| **Subsystem DLLs** | پیاده‌سازی API ویندوز: kernel32.dll، user32.dll، gdi32.dll و... از Windows 8.1 فقط یک subsystem باقی مانده: Windows Subsystem |
| **NTDLL.DLL** | پایین‌ترین لایه‌ی user mode؛ مسئول انتقال به kernel mode، Heap Manager، Image Loader و thread pool |
| **Service Processes** | پروسه‌هایی که با SCM (services.exe) ارتباط دارند؛ معمولاً زیر حساب‌های Local System، Network Service یا Local Service اجرا می‌شوند |
| **System Processes** | پروسه‌هایی که «فقط هستند» مثل Smss.exe، Lsass.exe، Winlogon.exe؛ برخی critical هستند و kill کردنشان crash می‌دهد |
| **Subsystem Process (Csrss.exe)** | یک instance به ازای هر session؛ critical process — kill شدنش = crash سیستم |

### لایه‌های Kernel Mode

| مؤلفه                  | توضیح                                                                                                |
| ---------------------- | ---------------------------------------------------------------------------------------------------- |
| **Executive**          | لایه‌ی بالایی NtOskrnl.exe؛ شامل Object Manager، Memory Manager، I/O Manager، PnP Manager و...       |
| **Kernel**             | لایه‌ی پایینی؛ thread scheduling، interrupt/exception dispatching، primitives مثل mutex و semaphore  |
| **Device Drivers**     | ماژول‌های loadable در kernel mode؛ موضوع اصلی این کتاب                                               |

| **Hyper-V Hypervisor** | در Windows 10 / Server 2016+ با VBS؛ دو سطح VTL 0 (kernel/user معمولی) و VTL 1 (secure kernel + IUM) |

## Handles و Objects

**Objects** ساختارهای داده‌ای در system space هستند که توسط Object Manager ساخته می‌شوند و **reference counted** هستند — وقتی آخرین reference آزاد شود، object نابود می‌شود.

**Handle** یک ایندکس به جدولی در kernel space است که به یک kernel object اشاره می‌کند؛ این جدول per-process است.

User Mode                Kernel SpaceSystem Space
─────────────────────────────────────────────────────────────
Handle (e.g. 4)  ──►  Handle Table Entry  ──►  Kernel Object
Handle (e.g. 8)  ──►  Handle Table Entry  ──►  Kernel Object


نکات مهم:
- Handle valueها **مضرب 4** هستند؛ اولین handle معتبر **4** است، صفر هرگز معتبر نیست
- اکثر توابع در شکست **null (0)** برمی‌گردانند، اما `CreateFile` استثناست و **INVALID_HANDLE_VALUE (-1)** برمی‌گرداند
- kernel code می‌تواند با `ObReferenceObjectByHandle` از handle به pointer تبدیل کند؛ این reference count را افزایش می‌دهد تا pointer dangling نشود
- فراموش کردن `ObDereferenceObject` = **resource leak** تا reboot بعدی

## Object Names

- **Process و Thread** نام ندارند — ID دارند (به همین دلیل `OpenProcess` یک عدد می‌گیرد نه string)
- **File** هم نام object ندارد — نام فایل با نام object متفاوت است
- نام thread از Windows 10 با `SetThreadDescription` قابل تنظیم است، اما این یک **friendly name** برای debugging است نه نام واقعی object

### فضای نام‌گذاری

نام ارسالی به `CreateMutex` و مشابه، به‌طور خودکار prefix می‌گیرد:

| حالت | Prefix |
|---|---|
| Session معمولی (x) | `\Sessions\x\BaseNamedObjects\` |
| Session 0 | `\BaseNamedObjects\` |
| AppContainer | `\Sessions\x\AppContainerNamedObjects\{SID}\` |
| اشتراک بین sessions | پیشوند `Global\` در نام → زیر `\BaseNamedObjects\` |

> AppContainerها نمی‌توانند از namespace سشن 0 استفاده کنند.

این سلسله‌مراتب با ابزار **WinObj** از Sysinternals قابل مشاهده است.


## نمایش Handle‌ها در Process Explorer

### نام‌گذاری در ستون Name

Process Explorer به‌صورت پیش‌فرض فقط handle‌هایی را نشان می‌دهد که **نام دارند**. برای دیدن همه، از منوی View گزینه‌ی **Show Unnamed Handles and Mappings** را فعال کنید.

ستون Name بسته به نوع object معنای متفاوتی دارد:

| نوع Object | چه چیزی نشان داده می‌شود |
|---|---|
| Mutex, Semaphore, Event, Section, ALPC Port, Job, Timer, Directory | **نام واقعی object** |
| Process, Thread | **ID** آن‌ها |
| File | **مسیر فایل یا device** (نه نام object؛ نمی‌توان از این نام handle گرفت) |
| Registry Key | **مسیر کلید** (مثل File، نام واقعی object نیست) |
| Token | **نام کاربری** ذخیره‌شده در token |

> تمایز مهم: File و Registry Key **نام object ندارند** — آنچه نشان داده می‌شود صرفاً اطلاعات مرتبط است، نه نام kernel object.

## Access Mask

ستون **Access** در Process Explorer، access mask مورد استفاده هنگام open/create کردن handle را نشان می‌دهد. این mask تعیین می‌کند چه عملیاتی با آن handle مجاز است.

مثال عملی — kill کردن یک process:

```c
bool KillProcess(DWORD pid) {
    // حداقل PROCESS_TERMINATE لازم است
    HANDLE hProcess = OpenProcess(PROCESS_TERMINATE, FALSE, pid);
    if (!hProcess)
        return false;

    BOOL success = TerminateProcess(hProcess, 1);

    CloseHandle(hProcess);  // همیشه handle را ببندید
    return success != FALSE;
}
```

منطق کار:
1. `OpenProcess` با access mask مشخص → kernel بررسی می‌کند آیا caller مجاز است
2. اگر موفق شد، `TerminateProcess` **حتماً** موفق می‌شود (چون access قبلاً تأیید شده)
3. ستون **Decoded Access** همین mask را به متن قابل‌خواندن تبدیل می‌کند

## Object Properties

دابل‌کلیک روی یک handle → پنجره‌ی **properties مربوط به object** (نه handle):

- نام object (در صورت وجود)
- نوع object
- آدرس در kernel memory
- تعداد handle‌های باز (Handle Count)
- اطلاعات خاص object (مثلاً state یک Event)

### Reference Count واقعی

Process Explorer از Windows 8.1 به بعد **Pointer Count واقعی را نشان نمی‌دهد**. برای دیدن مقدار دقیق باید از kernel debugger استفاده کرد:

lkd> !object 0xFFFFA08F948AC0B0
Object: ffffa08f948ac0b0  Type: (ffffa08f684df140) Event
HandleCount: 2  PointerCount: 65535
Name: ShellDesktopSwitchEvent

lkd> !trueref ffffa08f948ac0b0
HandleCount: 2  PointerCount: 65535  RealPointerCount: 3


- `PointerCount: 65535` → مقدار نمایشی (نادرست)
- `RealPointerCount: 3` → مقدار واقعی که `!trueref` محاسبه می‌کند
