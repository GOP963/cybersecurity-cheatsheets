

x86
یک معماری با ساختار **little-endian** است که بر پایه پردازنده Intel 8086 ساخته شده است.

برای هدف این فصل، منظور از x86 پیاده‌سازی 32 بیتی معماری اینتل (IA-32) است که در Intel Software Development Manual تعریف شده است.

به طور کلی، این معماری می‌تواند در دو حالت کار کند:

- حالت واقعی (real mode)
    
- حالت محافظت‌شده (protected mode)
    

حالت real mode زمانی است که پردازنده برای اولین بار روشن می‌شود و فقط از مجموعه دستورات 16 بیتی پشتیبانی می‌کند.

حالت protected mode حالتی است که در آن از حافظه مجازی، paging و سایر قابلیت‌ها پشتیبانی می‌شود. این همان حالتی است که سیستم‌عامل‌های مدرن در آن اجرا می‌شوند.

نسخه 64 بیتی این معماری x64 یا x86-64 نام دارد. این فصل درباره معماری x86 در حالت protected mode صحبت می‌کند.

## Whatis VirtualMode 


در معماری x86 چیزی به اسم virtualmode وجود داره اما دقیقا چیه؟ CPU داخل حالت protected mode اجرا میشه، ولی یک محیط 16 بیتی (real mode) رو به صورت ایزوله و مجازی شبیه‌سازی می‌کنه.
یادت باشه CPU حالت‌های مختلف داره:

- Real Mode → حالت 16-bit قدیمی
- Protected Mode → حالت مدرن (OS ها)
- Long Mode → 64-bit

حالا داخل **Protected Mode**، این امکان وجود داره که:

 یک برنامه فکر کنه توی Real Mode اجرا میشه  
در حالی که در واقع داخل Protected Mode اجرا میشه

این میشه
🔹 Virtual 8086 Mode (VM86)
### ⚙️ چرا این حالت وجود داره؟

برای backward compatibility (سازگاری با برنامه‌های قدیمی)

مثلاً:

- برنامه‌های DOS
- برنامه‌های 16-bit قدیمی

بدون VM86 باید کل سیستم می‌رفت Real Mode (که برای OSهای مدرن خطرناک بود)

### Virtual 8086 Mode

- CPU هنوز در Protected Mode است
- ولی یک محیط 16-bit شبیه‌سازی می‌شود
- دسترسی‌ها کنترل شده‌اند
- OS کامل کنترل دارد

کلاً این قابلیت‌ها در x86 برای **سازگاری (compatibility) با برنامه‌های قدیمی 16-bit مثل DOS** ایجاد شدند.

---

x86
از مفهوم **تفکیک سطح دسترسی (privilege separation)** از طریق یک انتزاع به نام **ring level** پشتیبانی می‌کند.

پردازنده چهار سطح حلقه (ring) را پشتیبانی می‌کند که از 0 تا 3 شماره‌گذاری شده‌اند.  
(حلقه‌های 1 و 2 معمولاً استفاده نمی‌شوند، بنابراین در اینجا توضیح داده نشده‌اند.)

- Ring 0 بالاترین سطح دسترسی است و می‌تواند همه تنظیمات سیستم را تغییر دهد.
    
- Ring 3 پایین‌ترین سطح دسترسی است و فقط می‌تواند بخشی از تنظیمات سیستم را بخواند یا تغییر دهد.
    

به همین دلیل، سیستم‌عامل‌های مدرن معمولاً تفکیک کاربر و هسته (user/kernel) را این‌گونه پیاده‌سازی می‌کنند:

- برنامه‌های کاربری در Ring 3 اجرا می‌شوند
    
- هسته سیستم‌عامل در Ring 0 اجرا می‌شود

![[Priv_rings.svg]]

سطح ring در رجیستر CS کدگذاری می‌شود و در مستندات رسمی گاهی با نام **Current Privilege Level (CPL)** نیز شناخته می‌شود.

### Register Set and Data Types

زمانی که پردازنده در حالت **protected mode** کار می‌کند، معماری x86 دارای هشت رجیستر عمومی ۳۲ بیتی (General-Purpose Registers یا GPRs) است:

- EAX
- EBX
- ECX
- EDX
- EDI
- ESI
- EBP
- ESP

برخی از این رجیسترها را می‌توان به بخش‌های کوچک‌تر 8 بیتی و 16 بیتی نیز تقسیم کرد.
نشانگر دستور (Instruction Pointer) در رجیستر **EIP** ذخیره می‌شود.

| ECX      | Counter in loops                        |
| ESI      | Source in string/memory operations      |

| EBP      | Base frame pointer                      |

**فصل ۱ ■ x86 و x64**

انواع داده‌های رایج به شرح زیر هستند:

■ بایت (Byte) — ۸ بیت. مثال: AL، BL، CL  
■ ورد (Word) — ۱۶ بیت. مثال: AX، BX، CX  
■ دابل‌ورد (Double Word) — ۳۲ بیت. مثال: EAX، EBX، ECX  
■ کوادورد (Quad Word) — ۶۴ بیت. در حالی که معماری x86 به‌صورت مستقیم رجیسترهای ۶۴ بیتی ندارد، می‌تواند در برخی سناریوها دو رجیستر را با هم ترکیب کند (معمولاً EDX:EAX) و آن‌ها را به‌عنوان یک مقدار ۶۴ بیتی در نظر بگیرد. برای مثال، دستور RDTSC مقدار ۶۴ بیتی را در EDX:EAX ذخیره می‌کند.

رجیستر ۳۲ بیتی **EFLAGS** برای ذخیره وضعیت عملیات‌های محاسباتی و سایر وضعیت‌های اجرای برنامه استفاده می‌شود (مثل Trap Flag). برای مثال، اگر نتیجه‌ی عملیات جمع قبلی برابر صفر باشد، فلگ ZF برابر ۱ می‌شود. فلگ‌های موجود در EFLAGS عمدتاً برای پیاده‌سازی شاخه‌زنی شرطی (conditional branching) استفاده می‌شوند.

علاوه بر GPRها، رجیسترهای EIP و EFLAGS، رجیسترهایی نیز وجود دارند که مکانیزم‌های سطح پایین سیستم مانند حافظه مجازی، وقفه‌ها و دیباگینگ را کنترل می‌کنند. برای مثال:

- CR0 تعیین می‌کند که Paging فعال است یا نه
    
- CR2 شامل آدرس خطی‌ای است که باعث Page Fault شده است
    
- CR3 آدرس پایه‌ی ساختار Paging را نگه می‌دارد
    
- CR4 تنظیمات مجازی‌سازی سخت‌افزاری را کنترل می‌کند
    

رجیسترهای DR0 تا DR7 برای تنظیم breakpointهای حافظه استفاده می‌شوند. ما بعداً در بخش «System Mechanism» دوباره به این رجیسترها برمی‌گردیم.

**نکته:**  
با اینکه ۷ رجیستر دیباگ وجود دارد، سیستم فقط اجازه استفاده از ۴ breakpoint حافظه (DR0 تا DR3) را می‌دهد. بقیه رجیسترها برای وضعیت (status) استفاده می‌شوند.

همچنین رجیسترهای مخصوص مدل (Model-Specific Registers یا MSR) نیز وجود دارند. همان‌طور که از نامشان پیداست، این رجیسترها ممکن است بین پردازنده‌های مختلف Intel و AMD متفاوت باشند. هر MSR با یک نام و یک عدد ۳۲ بیتی شناخته می‌شود و از طریق دستورهای RDMSR و WRMSR قابل خواندن و نوشتن هستند.

این رجیسترها فقط برای کدی که در حلقه 0 (Ring 0) اجرا می‌شود قابل دسترسی هستند و معمولاً برای ذخیره شمارنده‌های خاص و پیاده‌سازی قابلیت‌های سطح پایین استفاده می‌شوند.

برای مثال، دستور SYSENTER اجرای برنامه را به آدرسی منتقل می‌کند که در MSR با نام IA32_SYSENTER_EIP (با مقدار 0x176) ذخیره شده است؛ این آدرس معمولاً هندلر system call سیستم‌عامل است.

MSRها در طول کتاب هرجا لازم باشد بررسی خواهند شد.

### نکته 

در معماری های 64bit ما همین ریجستری هارو برای ورود به کرنل داریم اما تحت عنوان IA32_LSTAR که با این مقدار شناسایی میشود (0xC0000082) این MSR آدرس handler SYSTEMCALL رو نگه می‌داره

### Instruction Set



مجموعه دستورالعمل‌های x86 از نظر انعطاف‌پذیری در انتقال داده بین رجیسترها و حافظه بسیار گسترده است. این انتقال داده به پنج روش کلی تقسیم می‌شود:

■ مقدار فوری به رجیستر (Immediate to register)  
■ رجیستر به رجیستر (Register to register)  
■ مقدار فوری به حافظه (Immediate to memory)  
■ رجیستر به حافظه و برعکس (Register to memory and vice versa)  
■ حافظه به حافظه (Memory to memory)

چهار روش اول در تمام معماری‌های مدرن پشتیبانی می‌شوند، اما روش پنجم (حافظه به حافظه) مخصوص معماری x86 است.

در یک معماری RISC کلاسیک مانند ARM، داده‌ها فقط از طریق دستورهای load/store از حافظه خوانده یا در آن نوشته می‌شوند (LDR و STR). برای مثال، یک عملیات ساده مانند افزایش یک مقدار در حافظه نیاز به سه دستور دارد:

1. خواندن داده از حافظه به رجیستر (LDR)
    
2. اضافه کردن ۱ به رجیستر (ADD)
    
3. نوشتن مقدار رجیستر به حافظه (STR)
    

اما در x86 چنین عملیاتی فقط با یک دستور انجام می‌شود (مثل INC یا ADD)، زیرا این معماری می‌تواند مستقیماً به حافظه دسترسی داشته باشد. دستور MOVS نیز می‌تواند هم‌زمان عملیات خواندن و نوشتن در حافظه را انجام دهد.

---

**ARM**

```
01: 1B 68 LDR R3, [R3]
; خواندن مقدار از آدرس داخل R3
02: 5A 1C ADDS R2, R3, #1
; اضافه کردن ۱
03: 1A 60 STR R2, [R3]
; نوشتن مقدار جدید در حافظه
```

**x86**

```
01: FF 00 inc dword ptr [eax]
; افزایش مستقیم مقدار در آدرس EAX
```

---

یکی دیگر از ویژگی‌های مهم x86 این است که اندازه دستورها (instruction size) متغیر است؛ یعنی طول دستور می‌تواند بین ۱ تا ۱۵ بایت باشد.

در مقابل، در معماری ARM طول دستورها ثابت است و معمولاً ۲ یا ۴ بایت هستند.


## Syntax

### Intel

```
mov ecx, AABBCCDDh
mov ecx, [eax]
mov ecx, eax
```

### AT&T

```
movl $0xAABBCCDD, %ecx
movl (%eax), %ecx
movl %eax, %ecx
```

---

نکته مهم این است که این‌ها در واقع یک دستور یکسان هستند، اما به شکل‌های متفاوت نوشته شده‌اند.

تفاوت‌های مهم بین notationهای Intel و AT&T:

■ در AT&T قبل از رجیستر علامت % گذاشته می‌شود و برای مقادیر فوری (immediate) از $ استفاده می‌شود. در Intel این موارد وجود ندارد.

■ در AT&T یک پسوند به دستور اضافه می‌شود تا اندازه عملیات را مشخص کند؛ مثلاً MOVL (برای ۳۲ بیت)، MOVB (برای بایت) و غیره. در Intel این کار انجام نمی‌شود.

■ در AT&T ترتیب عملوندها برعکس است: ابتدا source و سپس destination می‌آید. در Intel این ترتیب برعکس است (اول destination بعد source).

---

ابزارهای disassembler/assembler و ابزارهای مهندسی معکوس (مثل IDA Pro، OllyDbg، MASM و غیره) در ویندوز معمولاً از notation نوع Intel استفاده می‌کنند، در حالی که در سیستم‌های UNIX معمولاً AT&T (مثل GCC) رایج است.

در عمل، notation اینتل رایج‌تر و غالب‌تر است و در کل این کتاب نیز از همین سبک استفاده شده است.


## Data Movement


## انتقال داده (Data Movement)

دستورالعمل‌ها روی مقادیری کار می‌کنند که از رجیسترها یا حافظه اصلی (main memory) می‌آیند. رایج‌ترین دستور برای جابه‌جایی داده، دستور **MOV** است.

ساده‌ترین حالت استفاده، انتقال مقدار از یک رجیستر یا مقدار فوری (immediate) به رجیستر دیگر است. برای مثال:

```asm
01: BE 3F 00 0F 00 mov esi, 0F003Fh   ; تنظیم ESI = 0xF003
02: 8B F1          mov esi, ecx       ; تنظیم ESI = ECX
```

---

استفاده رایج بعدی، انتقال داده به/از حافظه است. مانند سایر قراردادهای اسمبلی، در x86 از کروشه `[]` برای نشان دادن دسترسی به حافظه استفاده می‌شود. (تنها استثنا دستور **LEA** است که از `[]` استفاده می‌کند اما واقعاً به حافظه دسترسی ندارد.)

دسترسی به حافظه می‌تواند به شکل‌های مختلفی انجام شود، بنابراین ابتدا ساده‌ترین حالت را بررسی می‌کنیم:

```asm
01: C7 00 01 00 00+ mov dword ptr [eax], 1
   ; مقدار 1 را در آدرس ذخیره‌شده در EAX قرار بده

02: 8B 08 mov ecx, [eax]
   ; مقدار موجود در آدرس EAX را در ECX قرار بده

03: 89 18 mov [eax], ebx
   ; مقدار EBX را در آدرس EAX ذخیره کن

04: 89 46 34 mov [esi+34h], eax
   ; مقدار EAX را در آدرس (ESI + 0x34) ذخیره کن

05: 8B 46 34 mov eax, [esi+34h]
   ; مقدار موجود در آدرس (ESI + 0x34) را در EAX قرار بده

06: 8B 14 01 mov edx, [ecx+eax]
   ; مقدار موجود در آدرس (ECX + EAX) را در EDX قرار بده
```



در اسمبلی x86:

```asm
[ ]  = یعنی برو داخل حافظه
```

## معادل در C (Pseudo C)

```c
01: *eax = 1;
02: ecx = *eax;
03: *eax = ebx;
04: *(esi+34) = eax;
05: eax = *(esi+34);
06: edx = *(ecx+eax);
```

---

این مثال‌ها نشان می‌دهند که دسترسی به حافظه می‌تواند با استفاده از یک **رجیستر پایه (base register)** و یک **offset (جابجایی)** انجام شود؛ این offset می‌تواند یک رجیستر یا یک مقدار فوری باشد.

این روش معمولاً برای دسترسی به اعضای ساختارها (structures) یا بافرهای داده‌ای که در زمان اجرا محاسبه می‌شوند استفاده می‌شود.

---

مثال: فرض کنید ECX به یک ساختار از نوع **KDPC** اشاره می‌کند:

```
kd> dt nt!_KDPC
+0x000 Type : UChar
+0x001 Importance : UChar
+0x002 Number : Uint2B
+0x004 DpcListEntry : _LIST_ENTRY
+0x00c DeferredRoutine : Ptr32 void
+0x010 DeferredContext : Ptr32 Void
+0x014 SystemArgument1 : Ptr32 Void
+0x018 SystemArgument2 : Ptr32 Void
+0x01c DpcData : Ptr32 Void
```

و در زمینه زیر استفاده می‌شود:

```asm
01: 8B 45 0C        mov eax, [ebp+0Ch]
02: 83 61 1C 00     and dword ptr [ecx+1Ch], 0
03: 89 41 0C        mov [ecx+0Ch], eax
04: 8B 45 10        mov eax, [ebp+10h]
05: C7 01 13 01 00+  mov dword ptr [ecx], 113h
06: 89 41 10        mov [ecx+10h], eax
```

## معادل در C

```c
KDPC *p = ...;
p->DpcData = NULL;
p->DeferredRoutine = ...;
*(int *)p = 0x113;
p->DeferredContext = ...;
```

---

توضیح خطوط:

- خط 1 یک مقدار را از حافظه می‌خواند و در EAX ذخیره می‌کند.
    
- خط 3 مقدار DeferredRoutine را برابر همان مقدار قرار می‌دهد.
    
- خط 2 فیلد DpcData را با AND کردن با 0 پاک می‌کند.
    
- خط 4 مقدار دیگری از حافظه را در EAX می‌ریزد.
    
- خط 6 مقدار DeferredContext را تنظیم می‌کند.
    

---

نکته مهم:

در خط 5 مقدار 0x113 (یک double-word) در ابتدای ساختار نوشته می‌شود. اما چرا وقتی اولین فیلد فقط ۱ بایت است، یک مقدار ۴ بایتی نوشته می‌شود؟

آیا این باعث نمی‌شود فیلدهای **Importance** و **Number** هم تغییر کنند؟

پاسخ: بله، همین اتفاق می‌افتد.

(در ادامه کتاب توضیح داده می‌شود که تبدیل 0x113 به باینری چه اثری روی ساختار دارد.)

دستور **MOV** ساده‌ترین و رایج‌ترین دستور انتقال داده است. یکی از ویژگی‌های مهم x86 این است که داده‌ها می‌توانند از حافظه به رجیستر و بالعکس منتقل شوند.

در کد زیر:

```asm
01: 8B 45 0C mov eax, [ebp+0Ch]
02: 83 61 1C 00 and dword ptr [ecx+1Ch], 0
03: 89 41 0C mov [ecx+0Ch], eax
04: 8B 45 10 mov eax, [ebp+10h]
05: C7 01 13 01 00+ mov dword ptr [ecx], 113h
06: 89 41 10 mov [ecx+10h], eax
```

کامپایلر تصمیم گرفته چند دستور را در یک دستور فشرده کند، چون مقادیر از قبل مشخص بوده‌اند و هدف، کاهش حجم کد بوده است.

نسخه‌ی سه‌دستور در مجموع ۱۳ بایت فضا اشغال می‌کند، در حالی که نسخه‌ی تک‌دستور فقط ۶ بایت است.

یک نکته مهم دیگر این است که دسترسی به حافظه در سه سطح انجام می‌شود:

- بایت (byte)
    
- ورد (word)
    
- دابل‌ورد (double word)
    

حالت پیش‌فرض ۴ بایت (dword) است، اما می‌توان با prefix آن را به ۱ یا ۲ بایت تغییر داد. در مثال بالا، prefixهای override شامل **C6** و **66** هستند.

## نوع دیگر دسترسی به حافظه: آرایه‌ها

فرمت کلی:

```

```

مثال‌ها:

```asm

; یعنی: mov esi, [_KdLogBuffer + esi * 4]

```

- خط 3: استفاده از آن به‌عنوان base برای آرایه
    
- خط 7: افزایش اندیس
    
- خط 8: مقایسه اندیس با مقدار size در offset +0

### Stack Operations and Function Invocation



استک (Stack) یکی از ساختارهای داده‌ی بنیادی در زبان‌های برنامه‌نویسی و سیستم‌عامل‌ها است.  
برای مثال، متغیرهای محلی در زبان C داخل فضای استک مربوط به توابع ذخیره می‌شوند. همچنین زمانی که سیستم‌عامل از سطح دسترسی **ring 3** به **ring 0** سوئیچ می‌کند، اطلاعات وضعیت (state) را روی استک ذخیره می‌کند.

از نظر مفهومی، استک یک ساختار داده از نوع **Last-In First-Out (LIFO)** است؛ یعنی آخرین داده‌ای که وارد می‌شود، اولین داده‌ای است که خارج می‌شود. این ساختار دو عملیات اصلی دارد:

- **Push**: قرار دادن یک داده روی بالای استک
    
- **Pop**: برداشتن (حذف) داده از بالای استک
    

---

از دید عملی در معماری x86:

استک یک ناحیه‌ی پیوسته از حافظه است که توسط رجیستر **ESP** اشاره می‌شود و **به سمت پایین (آدرس‌های کوچکتر)** رشد می‌کند.

عملیات‌های Push و Pop با دستورهای **PUSH** و **POP** انجام می‌شوند و این دستورها به‌صورت ضمنی مقدار ESP را تغییر می‌دهند:

- دستور **PUSH**:
    
    1. ابتدا مقدار ESP را کاهش می‌دهد
        
    2. سپس داده را در آدرسی که ESP به آن اشاره می‌کند می‌نویسد
        
- دستور **POP**:
    
    1. داده را از آدرسی که ESP به آن اشاره می‌کند می‌خواند
        
    2. سپس مقدار ESP را افزایش می‌دهد
        

---

مقدار پیش‌فرض افزایش/کاهش ESP برابر **۴ بایت** است، اما با استفاده از prefix می‌توان آن را به ۱ یا ۲ تغییر داد.  
در عمل، تقریباً همیشه مقدار ۴ استفاده می‌شود، چون سیستم‌عامل نیاز دارد که استک به صورت **double-word (۴ بایتی)** هم‌تراز (aligned) باشد.

---

### مثال:

فرض کنید مقدار اولیه ESP برابر **0xb20000** باشد و کد زیر اجرا شود:

```asm
; initial ESP = 0xb20000
01: B8 AA AA AA AA mov eax,0AAAAAAAAh
02: BB BB BB BB BB mov ebx,0BBBBBBBBh
03: B9 CC CC CC CC mov ecx,0CCCCCCCCh
04: BA DD DD DD DD mov edx,0DDDDDDDDh
05: 50 push eax
```

- در اینجا مقدار `eax` که برابر **0xAAAAAAAA** است روی استک قرار می‌گیرد
    
- آدرس **0xb1fffc** این مقدار را نگه می‌دارد
    
- مقدار ESP می‌شود:  
    `0xb20000 - 4 = 0xb1fffc`
    

---

```asm
06: 53 push ebx
```

- مقدار `ebx` یعنی **0xBBBBBBBB** روی استک قرار می‌گیرد
    
- آدرس **0xb1fff8** این مقدار را نگه می‌دارد
    
- ESP می‌شود:  
    `0xb1fffc - 4 = 0xb1fff8`
    

---

```asm
07: 5E pop esi
```

- مقدار بالای استک (**0xBBBBBBBB**) داخل رجیستر `esi` قرار می‌گیرد
    
- ESP افزایش پیدا می‌کند:  
    `0xb1fff8 + 4 = 0xb1fffc`
    

---

```asm
08: 5F pop edi
```

- مقدار بعدی (**0xAAAAAAAA**) داخل `edi` قرار می‌گیرد
    
- ESP برمی‌گردد به مقدار اولیه:  
    `0xb1fffc + 4 = 0xb20000`
    

---

در شکل 1-3، نحوه‌ی چیدمان استک (stack layout) نشان داده شده است.

---

در حالی که در زبان‌های سطح بالا (مثل C) مفهومی به نام «تابع» (Function) داریم که می‌توان آن را فراخوانی کرد و از آن بازگشت، پردازنده خودش چنین abstractionـی ندارد.  
در پایین‌ترین سطح، پردازنده فقط با چیزهای واقعی و ملموس مثل **رجیسترها** یا **داده‌های موجود در حافظه** کار می‌کند.

**تابع‌ها در سطح ماشین چطور پیاده‌سازی می‌شوند؟**

پاسخ:  
تابع‌ها با استفاده از **ساختار داده‌ی استک (Stack)** پیاده‌سازی می‌شوند.

## قبل از ورود به جزئیات:

### بررسی دستورهای CALL و RET

### دستور **CALL** دو کار انجام می‌دهد:

1. آدرس بازگشت (آدرسی که بلافاصله بعد از CALL است) را روی استک **push** می‌کند
    
2. مقدار رجیستر **EIP** را به آدرس تابع تغییر می‌دهد (یعنی کنترل برنامه را به تابع منتقل می‌کند)
    

---

### دستور **RET**:

- آدرسی که بالای استک قرار دارد را **pop** کرده و داخل **EIP** قرار می‌دهد
    
- سپس اجرای برنامه را از آن آدرس ادامه می‌دهد
    

به‌نوعی می‌توان گفت RET شبیه این است:

```asm
pop eip
```

(البته چنین دستوری در x86 واقعاً وجود ندارد، ولی رفتار RET همین است)

---

### مثال جالب:

اگر بخواهید اجرای برنامه را به آدرس `0x12345678` منتقل کنید:

```asm
01: 68 78 56 34 12   push 0x12345678
02: C3               ret
```

یعنی:

- آدرس را روی استک می‌گذارید
    
- RET آن را داخل EIP می‌ریزد و اجرا از آنجا ادامه پیدا می‌کند
    

🔥 این دقیقاً یکی از پایه‌های مهم در exploit development هست (مثل ROP)

---

## Calling Convention چیست؟

Calling Convention مجموعه‌ای از قوانین است که مشخص می‌کند **فراخوانی تابع در سطح ماشین چطور انجام شود**.

این قوانین توسط **ABI (Application Binary Interface)** تعریف می‌شوند.

---

### این قوانین چه چیزهایی را مشخص می‌کنند؟

- پارامترها چطور پاس داده شوند؟
    
    - از طریق استک؟
        
    - از طریق رجیسترها؟
        
    - یا ترکیبی؟
        
- ترتیب ارسال پارامترها:
    
    - از چپ به راست؟
        
    - یا از راست به چپ؟
        
- مقدار بازگشتی کجا قرار بگیرد؟
    
    - در رجیستر؟
        
    - روی استک؟
        
    - یا هر دو؟
        

---

### انواع معروف Calling Convention:

- **CDECL**
    
- **STDCALL**
    
- **THISCALL**
    
- **FASTCALL**
    

(کامپایلر می‌تواند conventionهای اختصاصی هم بسازد، ولی اینجا بررسی نمی‌شوند)

---

در جدول 1-2 خلاصه‌ای از رفتار این calling conventionها ارائه شده است.

در خطوط **1** و **3**، دو پارامتر روی استک **push** می‌شوند؛  
رجیسترهای **ECX** و **EAX** به‌ترتیب به‌عنوان پارامتر اول و دوم استفاده شده‌اند.

در خط **4**، تابع **addme** با استفاده از دستور **CALL** فراخوانی می‌شود.

شکل **1-4** نحوه‌ی چیدمان استک را بعد از اجرای خط 4 نشان می‌دهد.

بعد از اجرای خط **4**، وارد بدنه‌ی تابع **addme** می‌شویم.

در خط **1**، مقدار رجیستر **EBP** روی استک **push** می‌شود.  
در خط **2**، مقدار **EBP** برابر با مقدار فعلی **ESP** قرار می‌گیرد.

این دنباله‌ی دو دستوری معمولاً به عنوان **function prologue** شناخته می‌شود، چون یک **فریم جدید برای تابع (stack frame)** ایجاد می‌کند.

---

در خط **4**، مقدار موجود در آدرس **EBP+8** خوانده می‌شود که همان **پارامتر اول** تابع روی استک است.  
در خط **5**، پارامتر دوم خوانده می‌شود.

نکته مهم این است که پارامترها با استفاده از **EBP به‌عنوان رجیستر پایه** (base register) دسترسی پیدا می‌کنند.

در این حالت، به **EBP** گفته می‌شود:

👉 **Base Frame Pointer**  
چون به فریم استک مربوط به تابع فعلی اشاره می‌کند و پارامترها و متغیرهای محلی نسبت به آن آدرس‌دهی می‌شوند.

---

کامپایلر می‌تواند طوری تنظیم شود که از **EBP** به‌عنوان base frame pointer استفاده نکند.  
این کار از طریق بهینه‌سازی‌ای به نام:

👉 **Frame Pointer Omission (FPO)**

انجام می‌شود.

در این حالت:

- دسترسی به پارامترها و متغیرهای محلی نسبت به **ESP** انجام می‌شود
    
- و **EBP** می‌تواند مثل یک رجیستر عمومی (مثل EAX، EBX، ECX) استفاده شود
    

---

در خط **6**، دو عدد با هم جمع می‌شوند و نتیجه داخل **EAX** ذخیره می‌شود.

در خط **8**، مقدار **ESP** برابر با **EBP** قرار داده می‌شود (بازگرداندن استک به وضعیت قبل از تابع).

در خط **9**، مقدار ذخیره‌شده‌ی **EBP** (از خط 1) از استک **pop** شده و به **EBP** برمی‌گردد.

---

این دنباله‌ی دو دستوری (خط 8 و 9) به‌عنوان:

👉 **Function Epilogue**

شناخته می‌شود، چون در انتهای تابع قرار دارد و فریم قبلی را **بازیابی (restore)** می‌کند.

---

در این لحظه، بالای استک شامل **آدرس بازگشت** است که توسط دستور CALL در آدرس **0x4129F9** ذخیره شده بود.

در خط **10**، دستور **RET** اجرا می‌شود:

- مقدار بالای استک را برمی‌دارد
    
- داخل **EIP** قرار می‌دهد
    
- و اجرای برنامه را از آدرس **0x4129FE** ادامه می‌دهد
    

---

در قطعه‌کد فراخوانی، خط **5** (یعنی `add esp, 8`) باعث می‌شود استک **۸ بایت کوچک‌تر شود**،  
چون طبق calling convention نوع **CDECL**، این **فراخواننده (caller)** است که باید استک را پاک‌سازی کند.

---

اگر تابع **addme** متغیرهای محلی داشت:

- بعد از خط 2 باید با کم کردن مقدار **ESP**، فضای استک را **بزرگ‌تر (allocate)** می‌کرد
    
- در این صورت، متغیرهای محلی با **offsetهای منفی نسبت به EBP** قابل دسترسی بودند
    

---

## تمرین‌ها

1. با توجه به آنچه درباره‌ی **CALL** و **RET** یاد گرفتید، توضیح دهید چگونه می‌توان مقدار **EIP** را خواند؟  
    چرا نمی‌توان به‌سادگی دستور `MOV EAX, EIP` را نوشت؟
    
2. حداقل دو روش (code sequence) ارائه دهید که مقدار **EIP** را برابر با `0xAABBCCDD` قرار دهند.
    
3. در تابع مثال **addme**، اگر قبل از اجرای **RET** مقدار **stack pointer (ESP)** به‌درستی بازگردانده نشود، چه اتفاقی می‌افتد؟
    
4. در تمام calling conventionهایی که توضیح داده شد، مقدار بازگشتی در یک رجیستر ۳۲ بیتی (**EAX**) ذخیره می‌شود.  
    اگر مقدار بازگشتی در ۳۲ بیت جا نشود چه اتفاقی می‌افتد؟
    
    یک برنامه بنویسید و این موضوع را آزمایش کنید.  
    آیا این مکانیزم بین کامپایلرهای مختلف تفاوت دارد؟

## Control Flow


Control Flow
یعنی مسیر اجرای برنامه که CPU با تغییر دادن EIP/RIP تعیین می‌کند کدام دستور بعدی اجرا شود.  
این مسیر می‌تواند خطی باشد (مثل اجرای پشت‌سرهم دستورها)، یا با شرط‌ها تغییر کند (if/else با jz، jnz).  
همچنین با حلقه‌ها مسیر به عقب برمی‌گردد (مثل jl یا jmp برای تکرار).  
در توابع هم با call وارد یک مسیر جدید می‌شویم و با ret به مسیر قبلی برمی‌گردیم.  
مثلاً `cmp eax,0 ; jz label` یا `call func ; ret` نمونه‌های ساده تغییر Control Flow هستند.

# 🧠 1. Conditional Codes (فلگ‌ها و شرط‌ها)

در CPU تعداد زیادی **فلگ شرطی (EFLAGS)** وجود دارد.  
حداکثر ۱۶ نوع condition code داریم، اما مهم‌ترین‌ها این‌ها هستند:

---

## 📌 جدول شرط‌ها:

### 🔹 Below / Above (Unsigned)

- **B / NAE**
    
    - یعنی: کوچکتر (unsigned)
        
    - شرط: `CF = 1`
        
- **NB / AE**
    
    - یعنی: بزرگتر یا مساوی (unsigned)
        
    - شرط: `CF = 0`
        

---

### 🔹 Equal / Zero

- **E / Z**
    
    - برابر یا صفر
        
    - شرط: `ZF = 1`
        
- **NE / NZ**
    
    - نابرابر / غیر صفر
        
    - شرط: `ZF = 0`
        

---

### 🔹 Signed Comparison

- **L (Less)**
    
    - کوچکتر (signed)
        
    - شرط: `(SF XOR OF) = 1`
        
- **GE (Greater or Equal)**
    
    - بزرگتر یا مساوی (signed)
        
    - شرط: `(SF XOR OF) = 0`
        
- **G (Greater)**
    
    - بزرگتر (signed)
        
    - شرط: `((SF XOR OF) OR ZF) = 0`
        

---

## 🧠 نکته مهم:

چون assembly type system نداره، تنها راه تشخیص signed یا unsigned همین فلگ‌هاست.

### System Mechanism

بخش‌های قبلی، مکانیزم‌ها و دستوراتی را توضیح دادند که برای کدی که در همه سطوح دسترسی (privilege levels) اجرا می‌شود در دسترس هستند. برای اینکه درک بهتری از معماری به‌دست آوریم، این بخش دو مکانیزم بنیادی در سطح سیستم را بررسی می‌کند: **ترجمه آدرس مجازی (virtual address translation)** و **مدیریت استثناها و وقفه‌ها (exception/interrupt handling)**. شما می‌توانید در اولین مطالعه، این بخش را نادیده بگیرید.


### Address Translation

حافظه فیزیکی در یک سیستم کامپیوتری به واحدهای ۴ کیلوبایتی تقسیم می‌شود که به آن‌ها **صفحه (Page)** گفته می‌شود. (البته اندازه صفحه می‌تواند بیشتر از ۴KB هم باشد، اما در اینجا به آن نمی‌پردازیم.)

آدرس‌های حافظه به دو دسته تقسیم می‌شوند: **مجازی (Virtual)** و **فیزیکی (Physical)**.

آدرس‌های مجازی همان آدرس‌هایی هستند که دستورات پردازنده هنگام فعال بودن paging از آن‌ها استفاده می‌کنند. برای مثال:

```
mov eax, [0x12345678]   ; خواندن از آدرس مجازی 0x12345678

mov [eax], ecx          ; نوشتن مقدار ECX در آدرس مجازی موجود در EAX
```

آدرس‌های فیزیکی، آدرس‌های واقعی حافظه هستند که پردازنده برای دسترسی به RAM از آن‌ها استفاده می‌کند.

واحد مدیریت حافظه پردازنده (**MMU**) به‌صورت شفاف (transparent) هر آدرس مجازی را قبل از دسترسی، به یک آدرس فیزیکی تبدیل می‌کند. بنابراین اگرچه برای برنامه‌نویس یک آدرس مجازی فقط یک عدد به نظر می‌رسد، اما در سطح سخت‌افزار این آدرس دارای ساختار مشخصی است.

در سیستم‌های x86 که از قابلیت **PAE (Physical Address Extension)** پشتیبانی می‌کنند، یک آدرس مجازی به بخش‌هایی تقسیم می‌شود که به عنوان اندیس در چند جدول استفاده می‌شوند:  
**Page Directory Pointer Table (PDPT)**، **Page Directory (PD)**، **Page Table (PT)** و در نهایت **Page Table Entry (PTE)**.

- PDPT
- شامل آرایه‌ای از ۴ عنصر ۸ بایتی است که هرکدام به یک PD اشاره می‌کنند.
    
- PD
- شامل ۵۱۲ عنصر ۸ بایتی است که هرکدام به یک PT اشاره دارند.
    
- PT
- شامل ۵۱۲ عنصر ۸ بایتی است که هرکدام یک PTE را نگه می‌دارند.
    

برای مثال، آدرس مجازی `0xBF80EE6B` را می‌توان همان‌طور که در شکل 1-5 نشان داده شده، به این بخش‌ها تقسیم کرد و تفسیر نمود.

![[Pasted image 20260411172114.png]]

ورودی‌های ۸ بایتی در این جدول‌ها شامل اطلاعات مربوط به خود جدول‌ها، سطح دسترسی حافظه (memory permission) و سایر ویژگی‌های حافظه هستند. برای مثال، بیت‌هایی وجود دارند که مشخص می‌کنند یک صفحه حافظه **فقط خواندنی (read-only)** یا **خواندنی/نوشتنی (read/write)** است، آیا **قابل اجرا (executable)** هست یا **غیرقابل اجرا (non-executable)**، و همچنین اینکه آیا برای کاربر قابل دسترسی است یا نه، و موارد مشابه.

فرآیند ترجمه آدرس (address translation) حول سه جدول و رجیستر **CR3** انجام می‌شود. رجیستر CR3 آدرس فیزیکی پایه‌ی **PDPT (Page Directory Pointer Table)** را نگه می‌دارد. ادامه این بخش، ترجمه آدرس مجازی `0xBF80EE6B` را در یک سیستم واقعی بررسی می‌کند (به شکل 1-5 مراجعه شود):

---

### 🔧 در محیط کرنل (kd):

```text
kd> r @cr3
cr3=085c01e0
```

CR3 آدرس فیزیکی پایه PDPT را نشان می‌دهد.

---

```text
kd> !dq @cr3+2*8 L1
# 85c01f0 00000000`0d66e001
```

طبق مستندات، ۱۲ بیت پایین PDPT entry شامل فلگ‌ها و بیت‌های رزرو شده است، و بقیه بیت‌ها آدرس فیزیکی پایه PD را تشکیل می‌دهند.

بیت 63 در PAE، فلگ NX (Non-Executable) است، بنابراین باید آن را هم در نظر گرفت. در این مثال نیازی به پاک کردن آن نیست چون از قبل صفر است (این صفحه قابل اجرا است).

---

پس:

طبق مستندات، در PD هم ۱۲ بیت پایین برای فلگ‌ها استفاده می‌شود و بقیه بیت‌ها آدرس پایه PT را می‌دهند.

---

### 📌 محاسبه:

```text

→ 0x0964b000
```

پس:  
👉 آدرس پایه PT برابر است با `0x0964b000`

## 🧠 توضیح مفهومی آخر:

سیستم‌عامل‌های مدرن از این مکانیزم برای **جدا کردن فضای آدرس هر پردازش (process isolation)** استفاده می‌کنند.  
هر پردازش یک CR3 جدا دارد، بنابراین هرکدام فضای حافظه مجازی مستقل خود را دارند.

در واقع این همان “جادو”یی است که باعث می‌شود هر برنامه تصور کند کل RAM متعلق به خودش است.

## 🧠 وقفه‌ها (Interrupts) و استثناها (Exceptions)

این بخش به‌صورت خلاصه درباره **interrupts** و **exceptions** توضیح می‌دهد، چون جزئیات کامل پیاده‌سازی در فصل ۳ با عنوان _“The Windows Kernel”_ بررسی شده است.

---

در سیستم‌های کامپیوتری مدرن، پردازنده معمولاً از طریق یک **باس داده (data bus)** مثل PCI Express، FireWire یا USB به دستگاه‌های جانبی (peripheral devices) متصل است.

---

وقتی یک دستگاه به توجه پردازنده نیاز دارد، یک **interrupt (وقفه)** ایجاد می‌کند که باعث می‌شود پردازنده کار فعلی خود را متوقف کرده و درخواست آن دستگاه را رسیدگی کند.

---

## 🧠 پردازنده از کجا می‌فهمد چه کاری انجام دهد؟

در سطح بالا، می‌توان interrupt را به‌عنوان یک **عدد (ID)** در نظر گرفت که برای **ایندکس کردن یک آرایه از اشاره‌گرهای تابع (function pointers)** استفاده می‌شود.

وقتی پردازنده یک interrupt دریافت می‌کند:

- تابع مربوط به آن شماره را اجرا می‌کند
    
- سپس اجرای برنامه را از همان جایی که متوقف شده بود ادامه می‌دهد
    

به این‌ها **hardware interrupts** گفته می‌شود چون توسط سخت‌افزار ایجاد می‌شوند و ذاتاً **ناهمزمان (asynchronous)** هستند.

---

## 🧠 Exception چیست؟

در هنگام اجرای دستورها، پردازنده ممکن است با **استثنا (exception)** مواجه شود.

مثال‌ها:

- تقسیم بر صفر
    
- دسترسی به آدرس نامعتبر
    
- یا تغییر سطح دسترسی (privilege level transition)
    

---

## 🧠 انواع exception:

در این بحث، exceptionها به دو دسته تقسیم می‌شوند:

### 1️⃣ Fault (خطای قابل اصلاح)

این نوع exception قابل اصلاح است.

مثال مهم:

- **Page Fault**
    

وقتی پردازنده به یک آدرس معتبر اشاره می‌کند اما داده در RAM نیست (مثلاً به دیسک منتقل شده)، این خطا رخ می‌دهد.

مراحل:

1. وضعیت فعلی CPU ذخیره می‌شود
    
2. handler مربوط به page fault اجرا می‌شود
    
3. داده از حافظه ثانویه به RAM آورده می‌شود
    
4. همان دستور دوباره اجرا می‌شود
    

---

### 2️⃣ Trap (تله / استثنای عمدی)

Trap زمانی رخ می‌دهد که یک دستور خاص اجرا شود.

مثال:

- دستور `SYSENTER`
    

این دستور باعث می‌شود پردازنده وارد handler سیستم‌کال شود.

بعد از پایان handler:  
👉 اجرای برنامه دقیقاً از **دستور بعد از SYSENTER** ادامه پیدا می‌کند.

---

## 🧠 تفاوت مهم Fault و Trap:

- **Fault** → بعد از اصلاح، همان دستور دوباره اجرا می‌شود
    
- **Trap** → اجرای برنامه از دستور بعدی ادامه پیدا می‌کند
    

---

## 🧠 نتیجه مهم:

سیستم‌عامل‌ها معمولاً از مکانیزم **interrupt و exception** برای پیاده‌سازی **system call** ها استفاده می‌کنند.

# تمرین‌ها

---

### 1. تکرار Walk-through و رسم Stack Layout

دوباره همین بررسی را خودت انجام بده. چیدمان استک را رسم کن، شامل پارامترها و متغیرهای محلی.

---

### 2. دیکامپایل طبیعی‌تر (Natural Decompilation)

در مثال walkthrough، ما یک ترجمه تقریباً یک‌به‌یک از اسمبلی به C انجام دادیم. به‌عنوان تمرین، کل این تابع را دوباره دیکامپایل کن به شکلی که طبیعی‌تر و شبیه کد واقعی نوشته‌شده توسط انسان باشد.

### Data Movement

x64
از مفهومی به نام RIP-relative addressing پشتیبانی می‌کند. این قابلیت اجازه می‌دهد دستورها به داده‌ها نسبت به RIP دسترسی داشته باشند.

مثال:

```asm
01: 0000000000000000 48 8B 05 00 00+ mov rax, qword ptr cs:loc_A
02: ; originally written as "mov rax, [rip]"
03: 0000000000000007 loc_A:
04: 0000000000000007 48 31 C0 xor rax, rax
05: 000000000000000A 90 nop
```

خط ۱ آدرس loc_A را در RAX قرار می‌دهد.

### Canonical Address

در x64 آدرس‌ها ۶۴ بیتی هستند، اما معمولاً فقط ۴۸ بیت استفاده می‌شود.

آدرس باید canonical باشد؛ یعنی بیت‌های بالا باید با بیت ۴۷ یکسان باشند.

اگر آدرس canonical نباشد، CPU exception تولید می‌کند.


## Canonical Address در x64

### اول بفهمیم چرا ۴۸ بیت؟

در x64 رجیسترها ۶۴ بیتی هستند، ولی CPU فیزیکاً فقط **۴۸ بیت** از آدرس رو decode می‌کنه. یعنی:

$$2^{48} = 256 \text{ TB}$$

این مقدار برای هر نیاز عملی کافیه، پس Intel تصمیم گرفت بقیه بیت‌ها رو "هدر" نده و یه قرارداد بذاره.

---

### قرارداد Canonical چیه؟

بیت‌های **63 تا 48** باید **کپی دقیق بیت 47** باشند:

بیت 47 = 0  →  بیت‌های 63:48 همه باید 0 باشند
بیت 47 = 1  →  بیت‌های 63:48 همه باید 1 باشند


یعنی فضای آدرس به دو ناحیه تقسیم میشه:

0x0000000000000000
        ↕  (فضای User Mode)
0x00007FFFFFFFFFFF   ← بیت 47 = 0

--- ناحیه ممنوع (non-canonical) ---

0xFFFF800000000000   ← بیت 47 = 1
        ↕  (فضای Kernel Mode)
0xFFFFFFFFFFFFFFFF


---

### چرا این قرارداد وجود داره؟

دلیل اصلی **آینده‌نگری** هست:

امروز:   48 بیت استفاده میشه
فردا:    57 بیت (Intel Ice Lake به بعد با LA57)
پس‌فردا: شاید 64 بیت کامل


اگه CPU بیت‌های بالا رو ignore می‌کرد:
- آدرس `0xDEAD000000001234` با `0x0000000000001234` یکی می‌شد
- وقتی CPU آپگرید بشه و بیت‌های بیشتری decode کنه، **کد قدیمی می‌شکست**

با قرارداد canonical، CPU می‌تونه بعداً بیت‌های بیشتری اضافه کنه بدون اینکه چیزی بشکنه.

---

### مثال عملی:

```asm
; آدرس canonical معتبر (user mode)
mov rax, 0x00007FFFFFFFFFFF   ; ✅ بیت 47 = 0، بیت‌های بالا هم 0

; آدرس canonical معتبر (kernel mode)  
mov rax, 0xFFFF800000000000   ; ✅ بیت 47 = 1، بیت‌های بالا هم 1

; آدرس NON-canonical
mov rax, 0xDEAD000000001234   ; ❌ بیت 47 = 1 ولی بیت‌های بالا 0xDEAD
mov [rax], rbx                ; → CPU فوری #GP exception میده
```

---

### چه exception ای میده؟

#GP (General Protection Fault)  →  اگه آدرس در دستور معمولی باشه
#SS (Stack Fault)               →  اگه آدرس در RSP باشه


---

### خلاصه یه خطی:

> بیت‌های بالا باید sign-extend بیت ۴۷ باشند تا CPU بتونه بعداً آدرس‌دهی رو گسترش بده بدون شکستن کدهای قبلی.
