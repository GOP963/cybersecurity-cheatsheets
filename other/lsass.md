

## ✅ برای دسترسی به توابع امنیتی `lsasrv.dll` باید از `advapi32.dll` استفاده کنیم؛ چرا؟

### 💡 دلیل فنی:

- `lsasrv.dll` درون فرآیند بحرانی `lsass.exe` بارگذاری می‌شه و بیشتر توابع اون **export نشده‌اند** (نه برای برنامه‌نویس قابل استفاده هستن و نه مستند شدن).
    
- اما مایکروسافت یک واسط عمومی برای دسترسی به این توابع طراحی کرده، و اونم هست:
    

> **📌 `advapi32.dll`**

که مخفف **Advanced API for Windows** هست.




آفرین مارتین دقیقاً درست فهمیدی! 🎯

## برای دسترسی به توابع امنیتی `lsasrv.dll` باید از `advapi32.dll` استفاده کنیم؛ چرا؟

### 💡 دلیل فنی:

- `lsasrv.dll` درون فرآیند بحرانی `lsass.exe` بارگذاری می‌شه و بیشتر توابع اون **export نشده‌اند** (نه برای برنامه‌نویس قابل استفاده هستن و نه مستند شدن).
    
- اما مایکروسافت یک واسط عمومی برای دسترسی به این توابع طراحی کرده، و اونم هست:
    

> **📌 `advapi32.dll`**

که مخفف **Advanced API for Windows** هست.

---

### ⚙️ چه اتفاقی پشت‌صحنه می‌افته؟

به شکل ساده:

```plaintext
[برنامه شما] ← (calls) → advapi32.dll ← (calls internally) → lsasrv.dll ← (داخل) → lsass.exe
```

پس `advapi32.dll` در واقع:

- مثل یک **دروازه‌بان** عمل می‌کنه،
    
- توابعی که در سطح کاربر قابل دسترسی هستن رو ارائه می‌ده (مثلاً `LsaLogonUser`)
    
- خودش پشت صحنه ارتباط برقرار می‌کنه با `lsasrv.dll`
    

---

### 🔐 چرا این معماری خوبه؟

1. **امنیت بالا**: برنامه‌ها نمی‌تونن مستقیماً با `lsass` ارتباط داشته باشن.
    
2. **کنترل بهتر توسط مایکروسافت**: فقط توابع مشخص‌شده قابل استفاده هستن.
    
3. **کاهش خطر کرش یا نفوذ**: چون برنامه‌نویس فقط به APIهای امن دسترسی داره.
    

---

### 📘 مثال عملی

مثلاً تابع زیر در `advapi32.dll` تعریف شده:

```csharp
LsaLogonUser()
```

اما واقعاً کار اصلیش رو `lsasrv.dll` انجام می‌ده. تو فقط به لایه‌ی امن بالا دسترسی داری.

## 🧠 جمع‌بندی:

|موضوع|توضیح|
|---|---|
|`lsasrv.dll`|هسته‌ی واقعی سیستم امنیتی ویندوز، ولی مخفی و بدون دسترسی مستقیم|
|`advapi32.dll`|واسط رسمی برای برنامه‌ها جهت استفاده از قابلیت‌های امنیتی|
|دلیل استفاده|چون `lsasrv.dll` فقط برای سیستم طراحی شده، نه برنامه‌نویس‌ها|
