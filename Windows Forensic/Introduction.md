## ۱- مقدمه بر دانش پزشکی قانونی دیجیتال (DF: Digital Forensic)

### تعریف علمی
پزشکی قانونی دیجیتال شاخه‌ای از علم پزشکی قانونی است که به **شناسایی، جمع‌آوری، حفظ، تحلیل و مستندسازی** شواهد دیجیتال با رعایت اصول **قانونی** و **فنی** می‌پردازد. هدف نهایی، ارائه یک روایت **قابل دفاع در دادگاه** از یک رخداد دیجیتال است.

---

### ۲- اهداف اصلی در هر عملیات DFIR
| هدف | توضیح عملیاتی |
| :--- | :--- |
| **شناسایی (Identification)** | تشخیص اینکه کدام سیستم‌ها، شبکه‌ها یا دستگاه‌ها در حادثه نقش داشته‌اند. |
| **حفظ (Preservation)** | جلوگیری از تغییر داده‌ها (با استفاده از تصویربرداری بایت‌به‌بایت و محاسبه هش). |
| **جمع‌آوری (Collection)** | استخراج داده از منابع فرار (RAM) و غیرفرار (HDD/SSD) با رعایت تقدم (Order of Volatility). |
| **تحلیل (Analysis)** | کشف الگوها، زمان‌بندی‌ها، رویدادها و رفتارهای مخرب با استفاده از ابزارهای تخصصی. |
| **ارائه (Presentation)** | مستندسازی نتایج به صورتی که برای قاضی، هیئت منصفه و تیم مدیریت قابل فهم باشد. |

---

### ۳- ترتیب اولویت جمع‌آوری داده‌ها (Order of Volatility)
داده‌ها بر اساس **میزان فرّاریت** اولویت‌بندی می‌شوند (از کم‌دوام‌ترین به بادوام‌ترین):

| اولویت | داده | ابزار/منبع |
| :--- | :--- | :--- |
| ۱ | حافظه RAM (ثبات‌ها، کش CPU، صفحه‌بندی) | `WinPmem`, `FTK Imager`, `DumpIt` |
| ۲ | اتصالات شبکه فعال | `netstat -anob`, `Sysmon Event 3` |
| ۳ | فرآیندهای در حال اجرا | `tasklist`, `pslist` از Sysinternals |
| ۴ | فایل‌های سیستمی | MFT, USN Journal, Prefetch, Registry |
| ۵ | فایل‌های لاگ (Event Logs) | `C:\Windows\System32\winevt\Logs` |
| ۶ | داده‌های روی دیسک | تصویربرداری کامل از دیسک (E01/DD) |

### ۴- دانش فنی موردنیاز برای یک تحلیلگر DFIR (Digital Forensic Knowledge)

یک تحلیلگر سطح یک (Tier 1) در حین ورود به فارنزیک باید در **۵ حوزه** زیر دانش پایه داشته باشد:

#### حوزه ۱: سیستم‌عامل
| سیستم‌عامل | موضوعات کلیدی |
| :--- | :--- |
| **ویندوز** | ساختار رجیستری، Event Logs (4688, 4624, 4656)، سرویس‌ها، `$MFT`، Prefetch، `AmCache.hve` |
| **لینوکس** | `bash_history`, `auth.log`, `syslog`, `lastlog`, `/var/log`, inodes, `crontab` |
| **macOS** | لاگ‌های Unified، `plist`ها، Keychain، `fseventsd` |

#### حوزه ۲: شبکه
| موضوع | توضیح |
| :--- | :--- |
| **PCAP** | آنالیز هدرهای TCP/IP، DNS queries، HTTP requests |
| **NetFlow** | شناسایی ارتباطات غیرعادی (Beaconing) |
| **Proxy/FW Logs** | استخراج IP مبدأ/مقصد، URL درخواستی |

#### حوزه ۳: تحلیل حافظه (Memory Forensics)
| ابزار | کاربرد |
| :--- | :--- |
| **Volatility 3** | استخراج لیست فرآیندها، DLLهای بارگذاری‌شده، کانکشن‌های شبکه، دستورات PowerShell اجراشده |
| **Rekall** | تحلیل ساختارهای هسته ویندوز و لینوکس |

#### حوزه ۴: ابزارهای فارنزیک
| ابزار | کاربرد اصلی |
| :--- | :--- |
| **FTK Imager** | تصویربرداری قانونی (E01) و مشاهده فقط‌خوان |
| **KAPE** | جمع‌آوری سریع آثار (Triage) و تجزیه خودکار |
| **MFTECmd + PECmd** | تحلیل `$MFT` و Prefetch |
| **Timeline Explorer** | ساخت گاهشمار (Timeline) از داده‌های CSV |

#### حوزه ۵: مفاهیم حقوقی (Legal)
| مفهوم | توضیح |
| :--- | :--- |
| **Chain of Custody** | مستندسازی کامل جابجایی ادله از لحظه جمع‌آوری تا حضور در دادگاه |
| **Write Blocker** | سخت‌افزار یا نرم‌افزاری که از نوشتن روی دیسک اصلی جلوگیری می‌کند |
| **Hash Validation** | محاسبه MD5/SHA-1 قبل و بعد از هر انتقال |

---

### ۵- مدل استاندارد DFIR (مراحل شش‌گانه SANS)

| مرحله | نام | توضیح عملیاتی |
| :--- | :--- | :--- |
| ۱ | **Preparation** | نصب ابزارها، تنظیم Sysmon/EDR، دسترسی به لاگ‌ها |
| ۲ | **Identification** | تأیید وقوع حادثه از طریق هشدارها یا گزارش کاربران |
| ۳ | **Containment** | جلوگیری از گسترش حمله (قطع ارتباط شبکه، مسدود کردن حساب) |
| ۴ | **Eradication** | حذف بدافزار، بستن آسیب‌پذیری‌ها |
| ۵ | **Recovery** | بازگرداندن سیستم‌ها به وضعیت عادی |
| ۶ | **Lessons Learned** | تهیه گزارش نهایی و بهبود پروسه‌های امنیتی |

---

### ۶- مهارت‌های نرم موردنیاز برای جزوه (برای ارتقا به Tier 2)

| مهارت | کاربرد |
| :--- | :--- |
| **تحلیل زمانی (Timeline Analysis)** | ترکیب داده‌های Event Log، MFT، Prefetch و Registry برای بازسازی توالی رویدادها |
| **تحلیل رفتاری (Behavioral Analysis)** | تشخیص رفتار غیرعادی فرآیندها (مثلاً `winword.exe` که `cmd.exe` اجرا کند) |
| **گزارش‌نویسی فنی** | نوشتن گزارش به زبان ساده اما با استناد به شواهد دیجیتال (IP، PID، Hash، Timestamp) |

### ۱. 🕵️ تکنیک‌های تحقیق و بررسی (Investigate Techniques)

#### تعریف:
مجموعه‌ای از روش‌های سیستماتیک برای **کشف، استخراج و تحلیل** شواهد دیجیتال با رعایت اصول علمی و حقوقی.

#### تکنیک‌های کلیدی (برای جزوه):

| تکنیک | توضیح عملیاتی | ابزار/منبع |
| :--- | :--- | :--- |
| **تحلیل زمانی (Timeline Analysis)** | مرتب‌سازی تمام رویدادها بر اساس زمان برای بازسازی توالی حمله | `Timeline Explorer`, `MFTECmd` + `PECmd` |
| **تحلیل زنجیره‌ای (Chain Analysis)** | دنبال کردن Parent-Child فرآیندها برای کشف منبع اجرای بدافزار | Sysmon Event 1, Event 4688 |
| **تحلیل رفتاری (Behavioral Analysis)** | تشخیص الگوهای غیرعادی (مثلاً `winword.exe` → `cmd.exe`) | EDR, Sysmon, Event Logs |
| **تحلیل رجیستری (Registry Analysis)** | جستجوی کلیدهای persistence، MRU، UserAssist | `RegRipper`, `Registry Explorer` |
| **تحلیل حافظه (Memory Analysis)** | استخراج فرآیندهای مخفی، دستورات PowerShell، کانکشن‌ها | `Volatility 3`, `Rekall` |
| **تحلیل شبکه (Network Analysis)** | بررسی PCAP، DNS، NetFlow برای یافتن C2 یا Data Exfiltration | `Wireshark`, `Zeek`, `RITA` |
| **تحلیل فایل (File Analysis)** | شناسایی فایل‌های مخرب، متادیتا، هش، امضا | `YARA`, `Strings`, `VirusTotal` |
| **تحلیل لاگ (Log Analysis)** | جستجوی رویدادهای خاص (Login, Process Creation, File Access) | `Get-WinEvent`, `wevtutil`, `grep` |

#### نکته عملیاتی:
> **هیچ‌وقت به یک تکنیک اکتفا نکن.**  
> ترکیب Timeline + Chain + Behavioral Analysis، قوی‌ترین روش برای کشف حملات پیشرفته است.

### ۲. 🗣️ مهارت‌های ارتباطی (Communication Skills)

#### تعریف:
توانایی **انتقال دقیق و مؤثر** یافته‌های فنی به مخاطبان مختلف (مدیران، تیم حقوقی، همکاران فنی، دادگاه).

#### مخاطبان و نحوه ارتباط:

| مخاطب | نیاز | نحوه ارائه |
| :--- | :--- | :--- |
| **مدیران ارشد** | تصویر کلی حادثه، تأثیر بر کسب‌وکار، هزینه‌ها | گزارش یک‌صفحه‌ای با خلاصه و جدول ریسک |
| **تیم SOC/EDR** | جزئیات فنی، IOCها، روش شناسایی | گزارش فنی با IP, Hash, PID, دستورات دقیق |
| **تیم حقوقی/قاضی** | زنجیره مستندات (Chain of Custody)، اعتبار شواهد | گزارش حقوقی با تأکید بر یکپارچگی داده‌ها |
| **تیم مدیریت حادثه** | اقدامات انجام‌شده، اقدامات بعدی، زمان‌بندی | گزارش وضعیت (Status Report) با مراحل انجام‌شده |

#### اصول طلایی ارتباط (برای جزوه):

| اصل | توضیح |
| :--- | :--- |
| **شفافیت** | از اصطلاحات فنی برای غیرفنی‌ها استفاده نکن. |
| **دقت** | هر ادعا را با شواهد دیجیتال (زمان، IP، PID) پشتیبانی کن. |
| **خلاصه‌سازی** | گزارش را با یک خلاصه (Executive Summary) شروع کن. |
| **مستندسازی** | تمام مکالمات و تصمیمات را ثبت کن. |

# 🔎 Digital Forensic Investigation Process

```text
1️⃣ Identification
       ↓
2️⃣ Preparation & Preservation
       ↓
3️⃣ Collection & Evidence Seizure
       ↓
4️⃣ Examination & Analysis
       ↓
5️⃣ Documentation & Presentation
```

نکته مهم اینه که این مراحل صرفاً اسم چند مرحله نیستند؛ هر مرحله یک هدف مشخص دارد.

---

## 1️⃣ Identification — شناسایی 🔍

در این مرحله مشخص می‌کنیم:

**چه اتفاقی افتاده؟ چه سیستم‌ها و چه شواهدی ممکن است مرتبط باشند؟**

مثلاً در یک Incident:

- 🖥️ کدام سیستم مشکوک است؟
    
- 👤 کدام User درگیر بوده؟
    
- 🌐 چه IP/Hostهایی مرتبط هستند؟
    
- 💾 چه Storageهایی ممکن است Evidence داشته باشند؟
    
- 📋 چه نوع Artifactهایی احتمالاً وجود دارند؟
    

### مثال واقعی در SOC

فرض کن در EDR می‌بینی:

```text
powershell.exe
    ↓
Encoded Command
    ↓
Outbound Connection
```

هنوز Analysis کامل انجام ندادی.

در Identification می‌گویی:

> این Endpoint و فعالیت PowerShell احتمالاً بخشی از Incident هستند و باید Evidence مربوط به آن بررسی شود.

# 2️⃣ Preparation & Preservation — آماده‌سازی و حفظ شواهد 🛡️

## 🎯 این Root Cause چیست؟

**تعریف عملیاتی:**  
درواقع **Root Cause** یا **علت ریشه‌ای**، **پایین‌ترین سطح (عمیق‌ترین لایه) از زنجیره‌ی رویدادها** است که اگر آن را حذف یا اصلاح کنی، **کل زنجیره‌ی حمله از بین می‌رود** و حادثه‌ی مشابه دیگر تکرار نمی‌شود.

به عبارت دیگر:  
> درواقع **Root Cause همان نقطه‌ی شکستی (Point of Failure) است که اگر در آن زمان درست عمل می‌کردیم، حمله هرگز موفق نمی‌شد.**

---

## 🔍 تفاوت Symptom, Cause, و Root Cause

برای درک بهتر، این ۳ سطح را با هم مقایسه کن:

| سطح | تعریف | مثال در یک حادثه |
| :--- | :--- | :--- |
| **Symptom (نشانه)** | چیزی که می‌بینی و بهت می‌گه «یک اتفاق بد افتاده» | بدافزار در سیستم شناسایی شده است. |
| **Cause (علت مستقیم)** | عملی که مستقیماً منجر به حادثه شده | کاربر روی لینک فیشینگ کلیک کرده و بدافزار دانلود شده است. |
| **Root Cause (علت ریشه‌ای)** | چرا آن عملی که منجر به حادثه شد، امکان‌پذیر بود؟ | کاربر **آموزش امنیتی ندیده** بود، یا **فیلتر ایمیل** لینک فیشینگ را مسدود نکرده بود، یا **MFA** فعال نبود. |

> **نکته:** اگر فقط Cause را برطرف کنی (مثلاً بدافزار را پاک کنی)، حمله‌ی بعدی با همان Root Cause دوباره تکرار می‌شود.

---

## 🧩 چگونه به Root Cause می‌رسیم؟ (روش‌شناسی عملیاتی)

رسیدن به Root Cause یک **فرآیند ۵ مرحله‌ای** است که در آن از **نشانه‌ها** به **علت** و سپس به **ریشه** می‌رسی:

| مرحله | عنوان | اقدام عملیاتی |
| :--- | :--- | :--- |
| ۱ | **جمع‌آوری داده** | تصویربرداری از دیسک، دامپ RAM، استخراج Event Logs، Network Logs |
| ۲ | **بازسازی Timeline** | تمام رویدادها را بر اساس زمان مرتب کن (از اولین نشانه تا آخرین اثر) |
| ۳ | **تحلیل زنجیره‌ای (Chain Analysis)** | ببین کدام فرآیند، کدام را اجرا کرده (Parent-Child). نقطه‌ی ورود را پیدا کن. |
| ۴ | **شناسایی علت مستقیم** | ببین کدام عملیات (مثلاً کلیک روی لینک، باز کردن فایل، یا ضعف رمز) منجر به حمله شده. |
| ۵ | **شناسایی علت ریشه‌ای** | بپرس «چرا این عملیات ممکن شد؟» تا به **نقص زیرساختی، انسانی یا فرآیندی** برسی. |

---

## 📋 جدول مصداق‌های Root Cause (برای جزوه)

| سناریوی حمله | علت مستقیم (Direct Cause) | Root Cause (علت ریشه‌ای) |
| :--- | :--- | :--- |
| **نفوذ از طریق ایمیل فیشینگ** | کاربر روی لینک مخرب کلیک کرده. | **فیلتر اسپم ضعیف** است یا **آموزش کاربران** کافی نیست. |
| **نفوذ از طریق RDP** | مهاجم رمز کاربر را حدس زده. | **سیاست رمز عبور ضعیف** (عدم وجود MFA، رمز ساده) |
| **اجرای بدافزار از طریق USB** | کاربر یک فلش آلوده را وصل کرده. | **سیاست عدم استفاده از USB** وجود ندارد یا **آنتی‌ویروس** USB را اسکن نکرده. |
| **نفوذ از طریق آسیب‌پذیری نرم‌افزار** | مهاجم از یک CVE استفاده کرده. | **سیستم Patch Management** به‌روز نیست. |
| **دسترسی غیرمجاز به داده** | یک کاربر داخلی به داده‌های حساس دسترسی داشته. | **سیاست Least Privilege** (حداقل دسترسی) اجرا نشده است. |
| **پاک‌شدن لاگ‌ها** | مهاجم Event Logs را پاک کرده. | **لاگ‌ها به صورت متمرکز (SIEM) ارسال نمی‌شوند** و دسترسی کاربران به Event Logs محدود نشده است. |

---

## 🧠 چرا Root Cause برای سازمان حیاتی است؟

| دلیل | توضیح برای جزوه |
| :--- | :--- |
| **پیشگیری از تکرار** | اگر Root Cause را برطرف نکنی، همان حمله با همان روش دوباره تکرار می‌شود. |
| **بهبود دفاع (Defense Enhancement)** | با دانستن Root Cause، می‌توانی کل سیستم دفاعی را ارتقا دهی (نه فقط یک نقطه). |
| **مدیریت ریسک** | به مدیران ارشد نشان می‌دهی که کدام نقاط ضعف استراتژیک باید اصلاح شوند. |
| **کاهش هزینه‌ها** | هزینه‌ی برطرف کردن یک Root Cause (مثلاً فعال‌سازی MFA) بسیار کمتر از هزینه‌ی مهار یک حمله‌ی بزرگ است. |
| **گزارش‌دهی حرفه‌ای** | یک گزارش فارنزیک که به Root Cause می‌رسد، بسیار ارزشمندتر از گزارشی است که صرفاً بدافزار را معرفی می‌کند. |

## 📊 چارچوب تحلیلی برای رسیدن به Root Cause (مدل ۵ WHY)

یکی از ساده‌ترین و مؤثرترین روش‌های رسیدن به Root Cause، تکنیک **۵ چرا (5 Whys)** است:

| مرحله | سوال | پاسخ (مثال: حمله از طریق فیشینگ) |
| :--- | :--- | :--- |
| ۱ | چرا بدافزار اجرا شد؟ | چون کاربر روی لینک کلیک کرد. |
| ۲ | چرا کاربر روی لینک کلیک کرد؟ | چون ایمیل را معتبر تشخیص داد. |
| ۳ | چرا ایمیل را معتبر تشخیص داد؟ | چون ایمیل از طرف یک همکار به نظر می‌رسید و فیلتر اسپم آن را نگرفته بود. |
| ۴ | چرا فیلتر اسپم آن را نگرفت؟ | چون دامنه‌ی مهاجم جدید بود و در لیست سیاه نبود. |
| ۵ | چرا دامنه‌ی جدید در لیست سیاه نبود؟ | چون فرآیند **به‌روزرسانی لیست‌های سیاه به صورت خودکار** انجام نمی‌شود و **تحلیل تهدید (Threat Intelligence)** فعال نیست. |

این**Root Cause نهایی:**  
> **نبود فرآیند خودکار برای به‌روزرسانی لیست‌های سیاه دامنه‌ها و نبود Threat Intelligence برای شناسایی دامنه‌های جدید مخرب.**
> در نهایت یه خروجی مثبت واسه سازمان که میتونه یه detection rule باشه میتونه یه سیاست امنیتی باشه

 نکتههههههههههههه **، داده‌های غیرفرّار (Non-Volatile) هم روی مموری (RAM) وجود دارند و می‌شه ازشون استفاده کرد، اما روشش کاملاً با اکسترکشن از هارد دیسک فرق داره.**

برای اینکه این موضوع رو کامل بفهمی، باید سه مفهوم رو از هم جدا کنیم:

---

### 🧠 ۱. تفاوت ذاتی «حافظه» و «فضای ذخیره‌سازی» در لحظه

| مفهوم | تعریف در فارنزیک | مثال |
| :--- | :--- | :--- |
| **داده‌های فرّار (Volatile)** | داده‌هایی که با قطع برق از بین می‌روند. محل ذخیره‌ی اونها **RAM (حافظه با دسترسی تصادفی)** هست. | Process list، ارتباطات شبکه‌ی فعال، کلیدهای رمزگشایی، دستورات PowerShell در حال اجرا . |
| **داده‌های غیرفرّار (Non-Volatile)** | داده‌هایی که پس از قطع برق باقی می‌مانند. محل ذخیره‌ی اونها **هارد دیسک (HDD/SSD)**، فلش مموری یا حافظه‌های NAND هست. | فایل‌های سیستمی، Event Logs، Registry Hives، و تمام فایل‌هایی که روی دیسک ذخیره شده‌اند . |

> **نکته‌ی کلیدی که باید توی جزوه‌ات ثبت کنی:**
> **«داده‌های غیرفرّار» به صورت مستقیم و دائم در RAM نیستند، اما پردازنده برای اجرای اونها، اونها رو از هارد به RAM **بارگذاری (Load)** می‌کنه. در نتیجه، در لحظه‌ی اجرا، **یک کپی از اون داده‌های غیرفرّار در RAM وجود داره**. 

---

### 🔍 ۲. چطور از داده‌های غیرفرّار «درون RAM» استفاده کنیم؟

توی مموری، ما به دنبال **بارگذاری‌های لحظه‌ای** اون داده‌ها هستیم. این شامل موارد زیر میشه :

#### a) دامپ گرفتن از RAM
برای استفاده از این داده‌ها، **اولین قدم** اینه که از محتویات RAM یک **تصویر (Memory Dump)** تهیه کنی. این کار معمولاً با ابزارهایی مثل `WinPmem`، `DumpIt` و یا حتی `FTK Imager` انجام میشه .

#### b) تحلیل دامپ با ابزارهایی مثل Volatility
بعد از اینکه دامپ رو گرفتی، با ابزارهایی مثل **Volatility Framework** می‌تونی محتویات اون رو解析 کنی .

#### c) چه چیزهایی از داده‌های غیرفرّار توی RAM پیدا می‌شه؟
- **کلیدهای رمزگشایی (Encryption Keys)**: خیلی وقت‌ها کلیدهای رمزگشایی فایل‌ها یا هارد دیسک‌های رمز شده، وقتی سیستم روشنه در RAM نگهداری می‌شن. این یکی از مهم‌ترین کاربردهای تحلیل حافظه‌ست .
- **کدهای اجرایی بدافزار (In-Memory Payloads)**: بدافزارهای پیشرفته (مثل بدافزارهای بدون فایل یا Fileless Malware) اصلاً روی دیسک نمی‌نویسن و مستقیم توی RAM اجرا می‌شن. ردپای اونها فقط در همین داده‌های بارگذاری‌شده در RAM قابل مشاهده‌ست .
- **دستورات PowerShell یا ابزارهای خط فرمان**: دستوراتی که در حین حمله اجرا شدن، ممکنه به صورت داغ (Hot) در RAM باشن، حتی اگه لاگش پاک شده باشه .

---

### 🧊 ۳. چه زمانی از RAM نمی‌شه استفاده کرد؟ و راهکار چیست؟

اگر سیستم **خاموش (Shut Down)** شده باشه، محتوای RAM با قطع برق از بین می‌ره . اما حتی اینجا هم یک تکنیک پیشرفته به اسم **Cold Boot Attack** وجود داره:

- در واقع **Cold Boot Attack**: با سرد کردن سریع تراشه‌های RAM (مثلاً با اسپری مخصوص) می‌تونیم محتویات اون رو برای چند دقیقه بعد از خاموش شدن هم حفظ کنیم و دامپ بگیریم. این یعنی **حتی داده‌های فرّار هم ممکنه در شرایط خاص، به داده‌های نیمه‌فرّار تبدیل بشن.** 

---



| سوال | پاسخ فنی |
| :--- | :--- |
| **آیا داده‌های غیرفرّار روی مموری هست؟** | بله، به صورت **بارگذاری‌شده (Loaded)** در RAM وجود دارند. |
| **چطور ازشون استفاده کنیم؟** | با **دامپ گرفتن از RAM** و تحلیل اون با ابزارهایی مثل **Volatility** . |
| **چه داده‌هایی رو می‌تونیم پیدا کنیم؟** | کلیدهای رمز، بدافزارهای در حال اجرا، دستورات تایپ‌شده و محتوای فایل‌های باز . |
| **چالش اصلی چیه؟** | **فرّاریت (Volatility)**. RAM با قطع برق یا حتی در حین اجرا، مدام در حال تغییره. پس **زمان** در جمع‌آوری این داده‌ها، حیاتی‌ترین نقش رو داره . |
| **اگر سیستم خاموش بود چطور؟** | ممکنه بشه با تکنیک **Cold Boot Attack** ازش دامپ گرفت، ولی成功率 به شرایط بستگی داره . |

# ⚡ Volatile Data vs Non-Volatile Data

تفاوت اصلی خیلی ساده است:

> ⚡ **Volatile Data** = با خاموش شدن یا تغییر وضعیت سیستم ممکنه از بین بره.  
> 💾 **Non-Volatile Data** = بعد از خاموش شدن سیستم هم روی Storage باقی می‌مونه.

---

## ⚡ 1. Volatile Data

درواقع **Volatile** یعنی «ناپایدار».

این اطلاعات معمولاً در **RAM یا وضعیت فعلی سیستم** وجود دارند و با خاموش شدن سیستم از بین می‌روند.

### مثال‌های مهم در Windows:

- 🧠 **RAM / Memory**
    
- ⚙️ Running Processes
    
- 🌐 Active Network Connections
    
- 👤 Logged-on Users
    
- 🔌 Open Network Sessions
    
- 📂 Open Files / Handles
    
- 🖥️ Command History موجود در Memory
    
- 🔑 بعضی Credentialها یا Keyهای موجود در Memory
    
- ⚙️ Current System State
    

مثلاً الان روی سیستم این Process در حال اجراست:

```text
explorer.exe
powershell.exe
svchost.exe
```

این وضعیت بخشی از **Live System State** است.

اگر سیستم را خاموش کنیم:

```text
💻 Running System
      ↓
🔴 Shutdown
      ↓
🧠 RAM Content → Lost
```

بنابراین اگر Investigation به اطلاعات RAM نیاز داشته باشد، **قبل از خاموش شدن سیستم باید به فکر Acquisition آن باشیم.**

---

# 💾 2. Non-Volatile Data

**Non-Volatile** یعنی «پایدار».

این اطلاعات روی Storage ذخیره شده‌اند و با خاموش شدن سیستم معمولاً باقی می‌مانند.

مثلاً:

- 💽 HDD
    
- 💾 SSD
    
- 🔌 USB
    
- 📁 Files
    
- 🗂️ Windows Registry
    
- 📜 Windows Event Logs
    
- 🧾 Prefetch
    
- 📊 Amcache
    
- 🕵️ Shimcache
    
- 📋 SRUM
    
- 📝 Browser History
    
- 🗃️ `$MFT`
    
- 🔄 USN Journal
    

مثلاً:

```text
💻 Computer
   ↓
🔴 Shutdown
   ↓
💽 HDD / SSD
   ↓
📁 Evidence remains
```

---

# 🚨 چرا این تفاوت برای Forensics مهمه؟

چون روی **Order of Volatility** تأثیر می‌گذارد.

یعنی:

> ⏱️ **اطلاعاتی که سریع‌تر از بین می‌روند، معمولاً باید زودتر جمع‌آوری شوند.**

به‌صورت ساده:

```text
⚡ سریع‌تر از بین می‌رود
        ↓
🧠 RAM
🌐 Active Connections
⚙️ Running Processes
        ↓
📋 Temporary / System State
        ↓
📜 Event Logs
🗂️ Registry
        ↓
💽 Files
        ↓
💾 Disk Image
        ↓
⏳ پایدارتر
```

البته **Order of Volatility یک ترتیب مطلق و یکسان برای همه Incidentها نیست**؛ بسته به شرایط Investigation تصمیم می‌گیریم چه چیزی را اول Acquisition کنیم.

# 🧪 یک سناریوی واقعی Forensics

فرض کن یک سیستم Windows را در حالی پیدا کردی که **روشن است** و احتمال می‌دهی روی آن Malware اجرا شده.

### اگر فوراً خاموشش کنی:

```text
🔴 Shutdown
      ↓
🧠 RAM پاک می‌شود
      ↓
❌ Running Malware State
❌ Active Connections
❌ بعضی اطلاعات موجود در Memory
```

ممکن است Evidence مهمی را از دست بدهی.

پس در یک **Live Response** ممکن است ابتدا اطلاعات volatile را جمع‌آوری کنی:

```text
⚡ Volatile Acquisition

🧠 Memory
⚙️ Processes
🌐 Network Connections
👤 Logged-on Users
📂 Open Handles
```

بعد بروی سراغ اطلاعات پایدار:

```text
💾 Non-Volatile Acquisition

📜 Event Logs
🗂️ Registry
📁 File System
🧾 Prefetch
📊 Amcache
🕵️ Shimcache
📋 SRUM
💽 Disk Image
```

---


### ⚡ Volatile Data

> **Data that can be lost or changed when the system is powered off or its state changes. It is typically collected during live response.**

**Examples:** RAM, running processes, active network connections, logged-on users.

### 💾 Non-Volatile Data

> **Data that persists after system shutdown and is generally stored on persistent storage media.**

**Examples:** Disk files, Registry, Event Logs, Prefetch, Amcache, Shimcache, SRUM.

---

### 🧠 نکته طلایی

**خاموش شدن سیستم = لزوماً همه Evidence از بین نمی‌رود.**

فقط بخش‌هایی از **Volatile Data** ممکن است از دست بروند.

```text
⚡ VOLATILE
RAM
Processes
Network State
     ↓
   Shutdown
     ↓
   ❌ Lost

💾 NON-VOLATILE
Disk
Registry
Event Logs
Files
     ↓
   Shutdown
     ↓
   ✅ Remains
```

برای **Windows Forensics** این تفاوت خیلی مهمه، چون بعداً وقتی برسیم به **Memory Forensics، Event Logs، Registry، Prefetch، Amcache و SRUM** دقیقاً می‌بینی هرکدوم چه نوع Evidenceای در اختیارمون می‌ذارن. 🔎🧠
