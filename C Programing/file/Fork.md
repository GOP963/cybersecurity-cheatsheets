## 💡 تعریف ساده:
تابع (یا سیستم‌کال) `fork()` در لینوکس/یونیکس یعنی:

> «یه نسخه‌ی جدید از همین برنامه بساز، که تقریباً همه‌چیزش مثل من (پردازه‌ی فعلی) باشه، اما مستقل کار کنه.»

به زبان سیستم‌عامل، یعنی:
> پردازه (process) فعلی تقسیم میشه به دو تا پردازه:  
> یکی **پدر (Parent Process)** و یکی **فرزند (Child Process)**.

---

## 🔩 پشت صحنه چه اتفاقی می‌افته؟

وقتی شما توی کد `fork()` رو صدا می‌زنی، کرنل:
1. یه **Process Control Block (PCB)** جدید می‌سازه (یعنی همون اطلاعات مدیریتی مثل PID، وضعیت، حافظه و ...)،  
2. حافظه‌ی برنامه‌ی فعلی رو **کپی** می‌کنه (ولی با تکنیک Copy-on-Write که در ادامه توضیح می‌دم)،  
3. به برنامه برمی‌گردونه:  
   - در پدر → مقدار `pid` فرزند  
   - در فرزند → مقدار `0`  
   - اگر خطا → مقدار منفی  

بعد از اون، هر دو پردازه از هم جدا می‌شن و هرکدوم به مسیر خودش ادامه میدن.

---

## ⚙️ تکنیک Copy-on-Write
در گذشته fork واقعاً حافظه را کپی می‌کرد، اما الان با روش بهینه‌تری انجام میشه:
- تا وقتی هیچ‌کدوم (پدر یا فرزند) در حافظه ننویسن، هر دو از یه نسخه‌ی مشترک استفاده می‌کنن.
- به محض اینکه یکی تغییری بده، اون صفحه از حافظه جدا میشه و فقط برای همون پردازه کپی میشه.

✅ نتیجه:  
ساخت پردازه‌ی جدید خیلی سریع‌تر و کم‌هزینه‌تر میشه.

---

## 🎯 هدف از fork چیست؟

### 1️⃣ اجرای همزمان چند کار (Concurrency)
سیستم‌عامل‌ها برای انجام چند کار همزمان نیاز دارن چند پردازه داشته باشن.  
مثلاً یه وب‌سرور باید بتونه به چندین کاربر همزمان پاسخ بده.

**نمونه:**
```c
pid_t pid = fork();
if (pid == 0) {
    // فرزند: پاسخ به یک کلاینت
} else {
    // والد: گوش دادن برای کلاینت بعدی
}
```
یعنی سرور برای هر درخواست، یه child جدید می‌سازه.

---

### 2️⃣ اجرای یک برنامه‌ی جدید
اغلب فورک به همراه `exec()` استفاده میشه:
- `fork()` → ساخت یه پردازه جدید
- `exec()` → جایگزین کردن محتوای اون پردازه با یه برنامه‌ی جدید

**مثلاً:**
وقتی در ترمینال می‌نویسی:
```bash
ls -l
```
در واقع:
1. Shell (مثل bash) خودش یه برنامه است.  
2. `bash` برای اجرای `ls` → یک `fork()` می‌زنه.  
3. پردازه‌ی جدید (فرزند) با `exec()` برنامه‌ی `ls` رو اجرا می‌کنه.  
4. وقتی `ls` تموم شد، فرزند می‌میره و والد ادامه میده.

---

### 3️⃣ ساخت دیمون‌ها (Daemon processes)
خیلی از سرویس‌های لینوکس (مثل sshd، apache، cron و غیره) دیمون هستن.  
یعنی برنامه‌هایی که در پس‌زمینه کار می‌کنن.

این دیمون‌ها معمولاً در ابتدای اجرا:
1. یه `fork()` می‌زنن تا از ترمینال جدا شن،  
2. فرزند تبدیل به سرویس دائمی میشه،  
3. والد خودش رو می‌بنده.

---

### 4️⃣ مدیریت Jobها و Pipelineها در Shell
وقتی توی شل دستورهایی مثل زیر می‌نویسی:
```bash
cat file.txt | grep hello | sort
```
برای هر بخش از این خط، Shell با `fork()` یه پردازه‌ی جدید می‌سازه:
- یکی برای `cat`
- یکی برای `grep`
- یکی برای `sort`

و با **pipe** خروجی یکی رو ورودی بعدی می‌کنه.

---

### 5️⃣ در محیط‌های چند‌پردازشی (Multiprocessing)
در برنامه‌نویسی، `fork()` می‌تونه برای اجرای چند تابع در پردازه‌های جدا استفاده بشه (برخلاف thread که در همون پردازه هست).

مثلاً در پایتون با `os.fork()` می‌تونی این کار رو انجام بدی:
```python
import os

pid = os.fork()

if pid == 0:
    print("Child doing work...")
else:
    print("Parent waiting...")
```

## 🧱 خلاصه تصویری ذهنی
می‌تونی اینطوری تصورش کنی:

| مرحله | توضیح |
|--------|--------|
| `main process` | برنامه‌ی اصلی در حال اجراست. |
| `fork()` | دستور داده میشه تا یه نسخه از خودم بسازم. |
| `child process` | کپی جدید از برنامه ایجاد میشه (دارای PID جدید). |
| اجرا | از این لحظه دو مسیر جدا وجود داره: پدر و فرزند. |

---

## ⚠️ نکات مهم و محدودیت‌ها
- fork در **ویندوز** وجود نداره به‌صورت مستقیم (چون مدل پردازه‌اش فرق داره)، ولی مفاهیمی مشابه داره مثل `CreateProcess()`.
- در لینوکس معمولاً بعد از fork باید از `wait()` یا `waitpid()` در والد استفاده کرد تا زامبی‌پروسس‌ها تمیز بشن.
- هرچقدر fork زیاد بزنی، منابع بیشتری (حافظه، جدول فایل، CPU) مصرف می‌کنی.

## 📘 یه مثال واقعی از دنیای لینوکس

فرض کن داری داخل `bash` هستی و دستور زیر رو می‌زنی:

```
ls
```

به نظرت چی میشه؟  
در واقع:

1. `bash` خودش یه برنامه است (یه پردازه).
    
2. وقتی می‌زنی `ls`، bash نمی‌ره `ls` رو مستقیم اجرا کنه — چون `bash` خودش هم باید زنده بمونه تا خروجی رو بگیره یا فرمان بعدی رو بخونه.
    
3. پس bash → `fork()` می‌زنه تا یه **کپی از خودش** بسازه.
    
4. اون نسخه‌ی کپی (`child`) حالا با `exec()` برنامه‌ی `ls` رو جایگزین خودش می‌کنه.
    
5. حالا:
    
    - فرزند تبدیل میشه به برنامه‌ی `ls`
        
    - والد (bash) صبر می‌کنه تا خروجی `ls` تموم بشه
        
    - بعدش دوباره منتظر دستور بعدی می‌مونه
        

🔁 یعنی `fork()` در واقع یه سکوی پرتابه برای اجرای یه برنامه جدید، نه فقط یه کپی بی‌هدف.

### 🧠 اول از همه: مشکل اصلی بدون fork()

فرض کن یه وب‌سرور داریم که روی پورت 80 منتظر درخواست‌هاست.  
اگر سرور **فقط یک process** داشت، اون process باید:
1. درخواست اول کاربر رو بگیره،
2. پردازش کنه (مثلاً فایل HTML رو بخونه، هدرها رو تنظیم کنه)،
3. جواب بده،
4. بعد تازه بره سراغ درخواست بعدی.

❌ یعنی اگه کاربر A یه فایل سنگین بخواد، کاربر B باید منتظر بمونه تا A تموم شه!  
این باعث میشه سرور فقط **به صورت تک‌وظیفه‌ای (sequential)** کار کنه — و در عمل اصلاً مقیاس‌پذیر نیست.

---

### ⚙️ حالا نقش fork()

وقتی وب‌سرور یه اتصال جدید از کاربر دریافت می‌کنه (مثلاً از مرورگر کاربر)،  
به جای اینکه خودش بره اون درخواست رو هندل کنه،  
میاد و از خودش **یک کپی جدید (child process)** با دستور `fork()` می‌سازه 👇

```c
int pid = fork();

if (pid == 0) {
    // child process — کاربر جدید رو هندل کن
    handle_client(socket);
    exit(0);
} else {
    // parent process — برگرد و منتظر درخواست‌های بعدی باش
}
```

---

### 🧩 نتیجه:
- Process اصلی (وب‌سرور اصلی) همیشه زنده می‌مونه و فقط منتظر کانکشن‌های جدید می‌مونه.  
- هر بار که درخواست جدیدی میاد، یه process جدید با `fork()` ساخته میشه که فقط مسئول **اون درخواست خاص** هست.  
- وقتی کارش تموم شد، اون process **خودش می‌میره**.

---

### 🔥 مزیت بزرگ:
- چند کاربر می‌تونن **به‌صورت هم‌زمان** از سرور پاسخ بگیرن.
- اگر در حین پردازش یه درخواست خطایی پیش بیاد، فقط اون child process آسیب می‌بینه، نه کل سرور.
- parent process همیشه در حال listen کردن می‌مونه.

---

### 💡 مثال واقعی:
سرور Apache در حالت "prefork MPM" دقیقاً همین مدل رو استفاده می‌کنه.  
وقتی Apache شروع به کار می‌کنه، چند تا child process از قبل با `fork()` می‌سازه (بهش می‌گن *pre-forking*).  
وقتی درخواست کاربر جدیدی میاد، یکی از اون processها وظیفه‌ی پاسخ‌گویی رو می‌گیره.

---

### 🚀 نکته نهایی:
در دنیای جدید، بعضی سرورها (مثل Nginx) به جای fork از **thread** یا **event-driven I/O** استفاده می‌کنن (چون fork سنگین‌تره)،  
ولی ایده‌ی اصلی همونه:  
هر درخواست باید **به‌صورت مستقل و موازی** از بقیه هندل بشه تا کارایی بالا بره.
