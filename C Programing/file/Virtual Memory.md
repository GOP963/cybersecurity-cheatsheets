

## تعریف ساده

**حافظه مجازی** یک تکنیک در سیستم‌عامل هست که باعث میشه برنامه‌ها فکر کنن به مقدار زیادی حافظه RAM دسترسی دارن، حتی اگه حافظه فیزیکی (RAM واقعی) کمتر از اون باشه.  
سیستم‌عامل این کارو با ترکیب **RAM** و **فضای دیسک (HDD/SSD)** انجام میده.

---

## چطوری کار می‌کنه؟

1. وقتی برنامه‌ای اجرا میشه، سیستم‌عامل بهش یه **Virtual Address Space** (فضای آدرس مجازی) اختصاص میده.
    
    - مثلاً برنامه فکر می‌کنه آدرس `0x00001000` واقعاً توی RAM هست.
        
    - اما سیستم‌عامل این آدرس رو به یک آدرس واقعی (Physical Address) توی RAM یا حتی دیسک مپ می‌کنه.
        
2. اگر RAM پر بشه، سیستم‌عامل بخشی از داده‌های غیرفعال RAM رو به **دیسک** منتقل می‌کنه (Swap/Page File).
    
    - به این کار **Paging** یا **Swapping** میگن.
        
    - وقتی دوباره به اون داده نیاز شد، سیستم‌عامل اونو از دیسک برمی‌گردونه به RAM.
        

---

## اجزای مهم

- **Page**:
- حافظه به بلوک‌های کوچیک (مثلاً 4KB) تقسیم میشه.
    
- **Page Table**:
- جدولی که سیستم‌عامل نگه می‌داره تا بفهمه هر آدرس مجازی به کدوم آدرس فیزیکی اشاره می‌کنه.
    
- **MMU (Memory Management Unit)**: 
- سخت‌افزاری توی CPU که ترجمه‌ی آدرس‌های مجازی به آدرس‌های فیزیکی رو انجام میده.
    

---

## مزایا

1. **اجرای برنامه‌های بزرگ‌تر از RAM**: چون میشه از دیسک کمک گرفت.
    
2. **ایزوله‌سازی**: هر برنامه فضای آدرس جدا داره، پس به حافظه‌ی برنامه‌های دیگه دسترسی نداره (امنیت بیشتر).
    
3. **استفاده بهینه از RAM**: فقط بخش‌های لازم از برنامه توی RAM نگه داشته میشه.
    

---

## معایب

- **کندی**: دسترسی به دیسک خیلی کندتر از RAM هست. وقتی داده روی دیسک باشه (Page Fault اتفاق بیفته)، برنامه کند میشه.
    
- **فرسودگی SSD**: استفاده‌ی زیاد از swap روی SSD می‌تونه عمرش رو کم کنه.
    

---

## مثال ساده

فرض کن:

- کامپیوترت 4GB RAM داره.
    
- ولی یه برنامه 6GB حافظه نیاز داره.
    

سیستم‌عامل 4GB رو از RAM میده، 2GB اضافه رو روی دیسک (Swap File) نگه می‌داره.  
برنامه **اصلاً متوجه نمی‌شه** و فکر می‌کنه کل 6GB رو داره.



---

فرض کن **کامپیوتر یک میز کار** داره (این میز یعنی **RAM**) و یه **کمد یا انبار** پشتیه (این هم **هارد/SSD**).  
وقتی برنامه‌ها کار می‌کنن، با کاغذ و برگه‌ها کار دارن. میز جا محدوده؛ پس هر چی لازم نداریم می‌فرستیم توی کمد. وقتی دوباره لازم شد، از کمد میاریم روی میز.  
حافظه‌ی مجازی (Virtual Memory) هم دقیقاً همین کار رو برای حافظه انجام می‌ده — طوری که برنامه‌ها فکر می‌کنن یه میز خیلی بزرگ دارن، در صورتی که بخشی روی میز (RAM) و بخش دیگه توی کمد (دیسک) قرار داره.



---


هر برنامه وقتی اجرا میشه، **یک فضای آدرس کاملاً مستقل** بهش داده میشه.  
برنامه فکر می‌کنه که:

- از آدرس `0x00000000` تا مثلاً `0xFFFFFFFF` (۴ گیگابایت در سیستم ۳۲ بیتی) فقط برای خودشه.
    
- یعنی انگار کل حافظه‌ی سیستم در اختیارشه، هیچ برنامه‌ی دیگه‌ای وجود نداره!
    

---

### واقعیت پشت پرده

- اون آدرس‌ها **مجازی** هستن.
    
- سیستم‌عامل و **MMU (Memory Management Unit)** تصمیم می‌گیرن هر بخش از اون آدرس‌های مجازی واقعاً کجای RAM یا حتی روی دیسک (swap) باشه.
    
- برنامه هیچ وقت مستقیم با آدرس فیزیکی RAM کار نمی‌کنه، همه چیز از طریق آدرس مجازی اتفاق میفته.
    

---

### نتیجه‌های مهم

1. **ایزوله بودن (Isolation):**  
    برنامه‌ها نمی‌تونن به حافظه‌ی همدیگه سرک بکشن. چون هرکدوم توی دنیای خودشون هستن.
    
2. **سادگی برای برنامه‌نویس:**  
    برنامه‌نویس لازم نیست بدونه چند گیگ RAM هست یا کجا پره، فقط از فضای مجازی استفاده می‌کنه.
    
3. **اجرای برنامه‌های بزرگ‌تر از RAM:**  
    چون swap وجود داره، برنامه فکر می‌کنه رم بیشتری داره.
    

---

یه مثال تصویری ساده:

```
[برنامه A]        آدرس مجازی: 0x0000 → 0xFFFF
[برنامه B]        آدرس مجازی: 0x0000 → 0xFFFF
[برنامه C]        آدرس مجازی: 0x0000 → 0xFFFF
```

همه‌شون فکر می‌کنن از صفر تا آخر مال خودشونه 😄  
ولی سیستم‌عامل پشت صحنه هرکدوم رو به بخش‌های متفاوتی از **RAM فیزیکی + دیسک** نگاشت می‌کنه.

سوال خیلی خوبی پرسیدی 👌  
ببین، **Virtual Memory** یک ایده‌ی خیلی مهم بود که به‌خاطر چند مشکل بزرگ در کامپیوترهای قدیمی به وجود اومد.

---

## چرا Virtual Memory اومد؟

### 1. **کمبود RAM**

اوایل، RAM خیلی گرون و کم‌ظرفیت بود.  
مثلاً برنامه‌ای ۸ مگابایت لازم داشت ولی سیستم فقط ۴ مگابایت RAM داشت.  
راه‌حل: بخشی از داده‌ها رو بفرستیم روی دیسک و برنامه فکر کنه هنوز کل ۸ مگابایت رو داره → Virtual Memory.

---

### 2. **سادگی برای برنامه‌نویس**

بدون حافظه‌ی مجازی، برنامه‌نویس باید دقیقاً می‌دونست:

- کدوم بخش از RAM خالیه؟
    
- کجا باید داده‌هاش رو بذاره که با برنامه‌های دیگه قاطی نشه؟
    

این خیلی سخت بود.  
Virtual Memory باعث شد هر برنامه **فضای آدرس مجازی خودش** رو داشته باشه، انگار تنها برنامه‌ی در حال اجراست.  
پس برنامه‌نویس راحت شد: لازم نیست حواسش به بقیه باشه.

---

### 3. **ایزوله‌سازی و امنیت**

اگه برنامه‌ها مستقیماً به RAM دسترسی داشتن، می‌تونستن داده‌های همدیگه رو خراب کنن.  
با Virtual Memory، هر برنامه توی «دنیای خودش» کار می‌کنه و به برنامه‌های دیگه دسترسی نداره.  
→ امنیت و پایداری بیشتر.

---

### 4. **اجرای برنامه‌های بزرگ‌تر از RAM**

فرض کن یه سیستم ۴GB RAM داره، ولی می‌خوای یه نرم‌افزار ۶GB اجرا کنی.  
بدون Virtual Memory اصلاً نمی‌شد.  
ولی با Virtual Memory، سیستم‌عامل بخشی از برنامه رو تو RAM و بخشی رو روی دیسک (swap) نگه می‌داره.  
برنامه **فکر می‌کنه کل ۶GB مال خودشه**.

---

### 5. **بهینه‌سازی استفاده از RAM**

همه‌ی قسمت‌های یه برنامه همیشه لازم نیست.  
مثلاً اگه فتوشاپ بازه، بخش‌هایی از کدش که مربوط به پرینت هست شاید اصلاً استفاده نشن.  
Virtual Memory باعث میشه فقط بخش‌های لازم بیاد تو RAM → بقیه روی دیسک بمونن → RAM آزادتر.

---

## جمع‌بندی

Virtual Memory اومد چون:

- RAM کم بود و گرون بود.
    
- برنامه‌نویسی بدونش سخت و پر از خطا بود.
    
- امنیت بین برنامه‌ها لازم بود.
    
- باید می‌شد برنامه‌های بزرگ‌تر از RAM اجرا بشن.
    
- استفاده‌ی بهینه از RAM لازم بود.
    

---

## تعریف کلی Virtual Memory

**Virtual Memory** یا حافظه‌ی مجازی، یک تکنیک در سیستم‌عامل‌هاست که باعث میشه:

1. هر برنامه فکر کنه کل حافظه‌ی کامپیوتر (RAM) فقط مال خودش هست.
    
2. حتی اگر RAM کافی نباشه، سیستم‌عامل با استفاده از بخشی از هارد/SSD (swap/pagefile) طوری وانمود می‌کنه که انگار حافظه‌ی بیشتری وجود داره.
    
3. این کار توسط سخت‌افزار (MMU) و نرم‌افزار (سیستم‌عامل) مدیریت میشه.
    

---

## ساده بگم 👇

Virtual Memory یعنی **ترکیب RAM + دیسک** به یک فضای حافظه‌ی یکپارچه و بزرگ،  
که هر برنامه بتونه راحت کار کنه، بدون اینکه بدونه حافظه‌ی واقعی چقدره یا کجاست.

- **بهینه‌سازی:** فقط بخش‌های لازم برنامه وارد RAM میشن.

## 1. محدوده‌های اصلی حافظه
در این تصویر فضای آدرس 32بیتی از **0x00000000** تا **0xFFFFFFFF** رو نشون میده (معادل 4GB).

| بخش                 | محدوده آدرس                                             | توضیح                                                                                                                                                              |
| ------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **OS Kernel Space** | `0xC0000000` تا `0xFFFFFFFF`                            | فضای رزرو شده برای هسته سیستم‌عامل (Kernel). برنامه کاربر **اجازه خواندن/نوشتن** این ناحیه رو نداره، وگرنه خطای `Segmentation Fault` ایجاد میشه. اندازه معمول: 1GB |
| **Stack**           | پایین‌تر از `0xC0000000` به سمت پایین رشد می‌کند        | محل نگهداری متغیرهای محلی، return addresses، و پارامترهای فانکشن‌ها. رشد آن از آدرس‌های بالا به سمت پایین است.                                                     |
| **Heap**            | بعد از بخش BSS و DATA به سمت آدرس‌های بالاتر رشد می‌کند | محل تخصیص حافظه دینامیک (`malloc/new`) و آزادسازی (`free/delete`).                                                                                                 |
| **BSS**             | زیر Heap (معمولاً قبل از آن)                            | برای متغیرهای static/global که **مقدار اولیه ندارند**؛ پر شده با صفر.                                                                                              |
| **Data**            | زیر BSS                                                 | برای متغیرهای static/global که **مقدار اولیه دارند**.                                                                                                              |
| **Text**            | پایین‌ترین بخش (`0x00000000` تا ~`0x08048000`)          | کد اجرایی برنامه و دستورات CPU، معمولاً فقط `read-only`.                                                                                                           |

## 📌 “مقدار اولیه” یعنی چی؟

وقتی متغیرهای **static** یا **global** در برنامه تعریف می‌شوند، دو حالت کلی دارند:

### 1. مقدار اولیه دارند (**Initialized Data segment – .data**)

یعنی موقع **کامپایل** شما یک مقدار مشخص بهشون دادید. این مقدار می‌تواند:

- یک **عدد ثابت**: `int count = 10;`
- یک **رشته ثابت**: `char name[] = "Ali";`
- یک **ساختار پر شده** با مقادیر مشخص.

💡 این مقدار در فایل اجرایی (exe/dll) **قبل از اجرا** ذخیره شده و هنگام شروع برنامه دقیقاً همان مقدار در حافظه بار می‌شود.

---

### 2. مقدار اولیه ندارند (**Uninitialized Data segment – .bss**)

یعنی موقع **تعریف**، هیچ مقداری ندادی:

- `int count;`
- `static int flag;`

📌 سیستم عامل وقت بارگذاری برنامه، این بخش را **با صفر** پر می‌کند (در ویندوز همه‌ی بایت‌ها صفر می‌شوند).

---

متغیر heap و موارد بالاتر میشه حافظه dynamic و از همون اول وجود ندارد و به تدریج تولید میشن 

اینا حافظه runtime هستند و در حین اجرای برنامه ایجاد و یا پاک میشوند  

این متغیر همونطور که در عکس پیداس ادرس هاش به سمت بالا رشد میکنند 

اما حافظه stack بر عکسه ادرسش از تهه شروع میشه   و اگر در heap داده اومدن بالا و در stack داده ها اومدن پایین این دو بهم رسیدن به این معنی است که ram پر شده است 




---

## 2. نحوه رشد بخش‌ها
- **Stack**: از بالا به پایین رشد می‌کند → نزدیک به مرز Kernel.
- **Heap**: از پایین به بالا رشد می‌کند → می‌تواند به سمت Stack بیاید.
- اگر Heap و Stack به هم برسند، **Stack overflow یا heap collision** رخ می‌دهد.

---

## 3. نکات مهم امنیتی و عملکردی
1. **Kernel Space** محافظت شده است → مانع دسترسی از کد کاربر (User Mode).
2. **Segmentation Fault** زمانی رخ می‌دهد که کد به آدرس غیرمجاز (مثل داخل Kernel یا خارج از محدوده مجاز) دسترسی پیدا کند.
3. **Text section** معمولاً از نوشتن محافظت شده (`read-only`) است تا از تغییر ناخواسته کد جلوگیری شود.
4. مقدار ثابت `0xC0000000` نشان‌دهنده مرز User Space و Kernel Space در مدل استاندارد **Linux 32-bit** است.

---

📌 به طور خلاصه:  
این تصویر **Memory Layout** یک پروسه را نشان می‌دهد که شامل **User Space (3GB)** + **Kernel Space (1GB)** است، همراه با بخش‌های مشخصی مثل Text، Data، BSS، Heap، و Stack، که هر کدام وظیفه خاصی در اجرا و مدیریت حافظه یک برنامه دارند.

## 2️⃣ نقش MMU (Memory Management Unit)

**MMU** سخت‌افزاری است که وظیفه دارد:

1. **ترجمه آدرس مجازی (VA) به آدرس فیزیکی (PA)** بر اساس جدول‌های حافظه (Page Table).
2. **اعمال مجوزها** مثل read/write/execute.
3. **حفاظت از حافظه** — جلوگیری از اینکه یک پروسس به حافظه پروسس دیگر یا کرنل دسترسی داشته باشد.

## 🗂 Heap Memory
**Heap**
یک ناحیه دینامیک از Virtual Address Space هر پروسسه که برای ذخیره داده‌هایی استفاده میشه که در زمان اجرا (runtime) مشخص میشن — برعکس stack که بیشتر برای مقادیر محلی و موقتیه.

| ویژگی | توضیح |
|-------|-------|
| **مدیریت** | توسط **Heap Manager** (در `ntdll.dll`) و APIهایی مثل `HeapAlloc`, `HeapFree` یا توی C/C++ توسط `malloc` / `free`. |
| **هدف** | نگهداری objectها یا داده‌هایی که طول عمرشون مشخص نیست و ممکنه بین فانکشن‌ها یا thread‌ها استفاده بشن. |
| **ساختار** | شامل بخش‌هایی به نام Heap Segments و Heap Blocks؛ وقتی `HeapAlloc` یا `malloc` می‌گیری، فضای مناسب رو پیدا و برمی‌گردونه. |
| **تعداد Heap** | هر پروسسه حداقل یک **Default Process Heap** داره، ولی می‌تونه چند تا heap بسازه (با `HeapCreate`) برای جداسازی داده‌ها. |
| **معایب امنیتی** | هدف رایج برای حملات مثل **Heap Overflow** و **Use-After-Free**؛ قابلیت اجرا (RWX) به ندرت ولی با سوءاستفاده میشه فعال کرد برای shellcode injection. |

## 🌍 Global Variables
**Global Variables** متغیرهایی هستن که طول عمرشون برابر با عمر پروسسه است و از هر نقطه برنامه قابل دسترسی هستن.

| ویژگی | توضیح |
|-------|-------|
| **Scope** | در کل کد برنامه و تمام فانکشن‌ها قابل دیدن (در یک executable)، ولی میشه visibility رو با `static` یا `extern` کنترل کرد. |
| **محل ذخیره‌سازی** | در ناحیه‌ای از حافظه به نام **Data Segment**:  
   - **.data** → متغیرهای global که مقدار اولیه دارند.  
   - **.bss** → متغیرهای global که مقدار اولیه ندارند (صفر می‌شوند). |
| **مدت عمر** | از شروع اجرای برنامه تا پایان آن ثابت در حافظه باقی می‌مانند. |
| **مشکل امنیتی** | تغییر غیرمجاز این مقادیر می‌تونه رفتار برنامه رو تغییر بده؛ معمولاً توسط **data corruption** یا کنترل pointerها. |

📌 در Layout، بخش **Global Variables** معمولاً نزدیک به ناحیه code/text نیست، بلکه در **Data Segment** برنامه ذخیره میشه، جایی که کامپایلر در زمان build رزرو کرده.

---

## 🖇 ارتباط Heap و Global
- **Global variables** معمولاً pointer به داده‌های Heap رو نگه می‌دارن.  
- این یعنی اگر heap corrupt بشه، global هم ممکنه خراب بشه یا به shellcode اشاره کنه.  
- تکنیک‌های حمله زیادی از این link استفاده می‌کنن (مثل تغییر pointerهای global برای اجرای کد دلخواه داخل heap).
