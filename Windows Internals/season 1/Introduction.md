به طور خلاصه و کلی وقتی یه کد روی CPU داره اجرا میشه با سطوح دسترسی مختلفی داره کار میکنه و با توجه به سطح دسترسی که داره کار های مختلفی رو میتونه انجام میده مثلا اگر برنامه ما در سطح USER اجرا بشه یعنی Ring 3 دسترسی به خیلی از Structure های Kernel نداره، و دسترسی به سخت افزار نداریم 
اما یه سری API هایی رو سیستم عامل در این زمان برای اون برنامه فراهم کرده تحت عنوان SYSCALL 
در واقع syscall ها API هایی هستند که مختص اون سیستم عامل هستند بر خلافه library ها که میتونن هم در سیستم عامل windows و هم در سیستم عامل linux کار کنند syscall ها API هایی هستند که این اجازه رو به ما میدهند تا به واسطه اون syscall ها بیایم یه سری درخواست هایی رو به Kernel بزنیم و جواب هایی رو ازش بگیریم 
ولی تا اینجای کار ما از Ring3 به Ring 0 دسترسی پیدا میکنیم 

و میشه گفت که API یه عبارت کلیه و به این معنی است که ما بیایم یه interface رو برای سایر developer ها فراهم کنیم یا با مثال بگم یه پل ارتباطی رو به اشتراک بگذاریم تا سایر developer ها بتونن از طریق اون پل به منابع برنامه من دسترسی پیدا کنند مثلا در سطح وب اپلیکیشن API ها از طریق React به وجود می آیند و خیلی موارد دیگر ........ هر چیزی استاندارد خواص خودش رو دارد 

حالا اگر ما بخواهیم از mode virtual در CPU بهرهمند شویم و بتونیم از قابلیت هایی از جمله WSL یا از ماشین مجازی خوده ویندوز Hyper-v استفاده کنیم باید از قابلیتی تحت عنوان Hypervisor رو فعال کنیم 
حالا اگر منابعی رو از سیستم عامل اصلی و ماشین مجازی مون به اشترک بگذاریم از API تحت عنوان Hypercall استفاده میکنیم

در ابتدا، **Windows API** تنها شامل توابعی به سبک زبان **C** بود. امروزه هزاران تابع از این نوع در اختیار توسعه‌دهندگان قرار دارد. زبان C در زمان شکل‌گیری ویندوز انتخابی طبیعی بود، زیرا به‌عنوان **کم‌خرج‌ترین مخرج مشترک** عمل می‌کرد (یعنی از زبان‌های دیگر نیز قابل دسترسی بود) و در عین حال به اندازه‌ی کافی سطح پایین بود تا سرویس‌های سیستم‌عامل را در اختیار برنامه‌نویس قرار دهد.

نقطه‌ضعف این رویکرد، **تعداد بسیار زیاد توابع** به همراه **نبود یکپارچگی در نام‌گذاری** و **عدم گروه‌بندی منطقی** آن‌ها بود (برای مثال، نبود مفاهیمی مانند فضای نام‌ها در C++). یکی از نتایج این مشکلات، حرکت برخی از APIهای جدیدتر به سمت استفاده از مکانیزم متفاوتی به نام **Component Object Model (COM)** بود.

مدل **COM** در ابتدا برای این هدف ایجاد شد که برنامه‌های **Microsoft Office** بتوانند با یکدیگر ارتباط برقرار کرده و داده‌ها را بین اسناد مختلف ردوبدل کنند (برای مثال، قراردادن یک نمودار Excel در داخل یک سند Word یا ارائه‌ی PowerPoint). این قابلیت با نام **Object Linking and Embedding (OLE)** شناخته می‌شود.  
در نسخه‌های اولیه، OLE با استفاده از یک مکانیزم قدیمی پیام‌رسانی در ویندوز به نام **Dynamic Data Exchange (DDE)** پیاده‌سازی شده بود. از آنجا که DDE ذاتاً محدودیت‌های زیادی داشت، روش ارتباطی جدیدی توسعه داده شد: **COM**. در واقع، COM در ابتدا با نام **OLE 2** شناخته می‌شد و حدود سال ۱۹۹۳ به‌صورت عمومی منتشر شد.

## ‎.NET Framework

چارچوب **.NET Framework** بخشی از سیستم‌عامل ویندوز است. **جدول ۱-۲** نسخه‌ی ‎.NET Framework‎ای را نشان می‌دهد که به‌صورت پیش‌فرض همراه با هر نسخه از ویندوز نصب می‌شود. با این حال، امکان نصب نسخه‌های جدیدتر ‎.NET Framework‎ بر روی نسخه‌های قدیمی‌تر سیستم‌عامل نیز وجود دارد.

**جدول ۱-۲ — نسخه‌های پیش‌فرض ‎.NET Framework‎ در ویندوز**

چارچوب ‎.NET Framework‎ از دو مؤلفه‌ی اصلی تشکیل شده است:

**Common Language Runtime (CLR)**  
این بخش، موتور اجرایی ‎.NET‎ محسوب می‌شود و شامل یک **کامپایلر Just-In-Time (JIT)** است که دستورالعمل‌های **Common Intermediate Language (CIL)** را به زبان ماشین پردازنده‌ی مقصد ترجمه می‌کند. CLR همچنین قابلیت‌هایی مانند **Garbage Collection**، **اعتبارسنجی نوع‌ها (Type Verification)**، **امنیت دسترسی به کد (Code Access Security)** و موارد دیگر را فراهم می‌کند. این مؤلفه به‌صورت یک **COM In-Process Server (DLL)** پیاده‌سازی شده و از امکانات مختلف ارائه‌شده توسط **Windows API** استفاده می‌کند.

**.NET Framework Class Library (FCL)**  
این بخش مجموعه‌ای بزرگ از نوع‌ها (Types) است که قابلیت‌هایی را پیاده‌سازی می‌کنند که معمولاً در برنامه‌های سمت کاربر (Client) و سمت سرور مورد نیاز هستند؛ از جمله **سرویس‌های رابط کاربری، شبکه، دسترسی به پایگاه داده** و بسیاری امکانات دیگر.

با ارائه‌ی این قابلیت‌ها و امکانات دیگر—از جمله زبان‌های برنامه‌نویسی سطح بالا مانند **C#، Visual Basic و F#** به همراه ابزارهای پشتیبان—چارچوب ‎.NET Framework‎ بهره‌وری توسعه‌دهندگان را افزایش داده و سطح **ایمنی و قابلیت اطمینان** برنامه‌هایی را که برای این پلتفرم توسعه داده می‌شوند بهبود می‌بخشد.

## سرویس‌ها، توابع و رویه‌ها (Services, Functions, and Routines)

برخی از اصطلاحات موجود در مستندات برنامه‌نویسی و کاربری ویندوز در زمینه‌های مختلف معانی متفاوتی دارند. برای مثال، واژه‌ی **Service** می‌تواند به یک **رویه‌ی قابل فراخوانی در سیستم‌عامل**، یک **درایور دستگاه** یا یک **پردازه‌ی سرور** اشاره کند. فهرست زیر معنای برخی اصطلاحات را در این کتاب مشخص می‌کند:

---

### Windows API Functions
این‌ها **زیرروال‌های مستندسازی‌شده و قابل فراخوانی** در Windows API هستند.  
مثال‌ها: `CreateProcess`، `CreateFile`، `GetMessage`.

---

### Native System Services (یا System Calls)
این‌ها **سرویس‌های داخلی و مستندسازی‌نشده سیستم‌عامل** هستند که از **حالت کاربر (User Mode)** قابل فراخوانی‌اند.  
برای مثال، `NtCreateUserProcess` سرویس داخلی است که تابع `CreateProcess` ویندوز برای ایجاد پردازه‌ی جدید از آن استفاده می‌کند.

---

### Kernel Support Functions (یا Routines)
این‌ها **زیرروال‌هایی هستند که تنها از حالت هسته (Kernel Mode)** قابل فراخوانی‌اند (در ادامه‌ی این فصل تعریف می‌شوند).  
مثال: `ExAllocatePoolWithTag`، روشی که درایورهای دستگاه برای **اختصاص حافظه از Heapهای سیستم ویندوز** (که Pool نامیده می‌شوند) استفاده می‌کنند.

---

### Windows Services
این‌ها **پردازه‌هایی هستند که توسط Service Control Manager ویندوز** راه‌اندازی می‌شوند.  
مثال: سرویس **Task Scheduler** که در یک پردازه‌ی User Mode اجرا می‌شود و فرمان `schtasks` را پشتیبانی می‌کند (مشابه دستورهای UNIX مانند `at` و `cron`).  
> توجه: اگرچه رجیستری درایورهای دستگاه ویندوز را به عنوان «Service» تعریف می‌کند، اما در این کتاب چنین نام‌گذاری‌ای به کار نمی‌رود.

---

### Dynamic Link Libraries (DLLs)
این‌ها **زیرروال‌هایی هستند که به‌صورت فایل باینری به هم پیوند خورده و می‌توانند به‌صورت پویا توسط برنامه‌ها بارگذاری شوند**.  
مثال‌ها: `Msvcrt.dll` (کتابخانه‌ی زمان اجرا در C) و `Kernel32.dll` (یکی از کتابخانه‌های زیرسیستم Windows API).  
کامپوننت‌ها و برنامه‌های User Mode ویندوز به شدت از DLLها استفاده می‌کنند.  
مزیت DLLها نسبت به کتابخانه‌های ایستا (Static Libraries) این است که **چندین برنامه می‌توانند یک DLL را به اشتراک بگذارند** و ویندوز تضمین می‌کند که در حافظه تنها یک نسخه از کد DLL برای تمام برنامه‌هایی که به آن ارجاع می‌دهند وجود داشته باشد.

> توجه: اسمبلی‌های کتابخانه‌ای **.NET** نیز به صورت DLL کامپایل می‌شوند، اما هیچ زیرروال Export شده‌ی unmanaged ندارند. در عوض، **CLR** متادیتای کامپایل‌شده را تحلیل می‌کند تا به نوع‌ها و اعضای متناظر دسترسی پیدا کند.
