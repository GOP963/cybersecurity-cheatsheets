## 🧠 جمع‌بندی کلی: DNS، رکوردها، و Name Server

### 🔹 1. DNS چیه؟

DNS (Domain Name System) مثل دفترچه تلفن اینترنت می‌مونه.  
وظیفه‌ش اینه که:

> 🔁 نام‌ها (مثل `martin.com`) رو تبدیل کنه به IP (مثل `185.10.10.10`) تا کامپیوترها بفهمن کجا باید برن.

---

### 🔹 2. رکوردهای DNS چی‌ان؟

هر دامنه یه سری اطلاعات داره که بهش می‌گیم **رکورد DNS**.  
مهم‌ترین‌ها:

| نوع رکورد | توضیح                                          |
| --------- | ---------------------------------------------- |
| A         | آدرس IP برای دامنه                             |
| MX        | مشخص می‌کنه ایمیل‌ها کجا برن                   |
| NS        | می‌گه کدوم سرورها مسئول DNS دامنه‌ان           |
| CNAME     | اسم مستعار برای یه دامنه دیگه                  |
| TXT       | رکوردهای متنی، مثلاً برای تأیید یا امنیت ایمیل |
| SOA       | اطلاعات مدیریتی دامنه                          |
| PTR       | برای پیدا کردن نام از روی IP (برعکس A رکورد)   |
|           |                                                |

---

### 🔹 3. Name Server چیه؟

**Name Server** یا **NS**، یه سرور خاصه که:

> مسئول نگهداری و پاسخ‌گویی به رکوردهای DNS یه دامنه‌ست.

یعنی وقتی کسی تو اینترنت بپرسه «IP سایت `martin.com` چیه؟»، Name Server باید جواب بده.

📌 معمولاً Name Serverها به شکل `ns1.domain.com`، `ns2.domain.com` نام‌گذاری می‌شن.

---

### 🔹 4. Name Serverها از کجا میان؟

دو حالت داره:

- **سرور شخصی**: خودت Name Server درست می‌کنی (مثلاً `ns1.martin.com`)
    
- **سرویس‌دهنده‌ها**: از شرکت‌هایی مثل Cloudflare، Namecheap، یا GoDaddy استفاده می‌کنی و اونا Name Server خودشونو بهت می‌دن (مثلاً `ns1.digitalocean.com`)
    

تو فقط رکوردها رو توی پنل اون شرکت وارد می‌کنی.

---

### 🔹 5. Zone و Zone Transfer چیه؟

- **Zone**
- یعنی کل اطلاعات DNS یه دامنه
    
- **Zone Transfer** 
- یعنی انتقال اون اطلاعات از یه Name Server به یه سرور دیگه (مثلاً برای پشتیبان‌گیری یا هماهنگی)
    
- اگر این امکان باز باشه، ممکنه یه مهاجم با `dig AXFR` همه اطلاعات دامنه رو بکشه بیرون (حمله اطلاعاتی)
    

---

### 🔒 امنیت در DNS چرا مهمه؟

- تغییر رکوردهای DNS باعث می‌شه ترافیک سایت بره سمت سرور مهاجم (DNS Hijacking)
    
- Zone Transfer باز = افشای کل ساختار دامنه
    
- رکوردهای اشتباه = اختلال در ایمیل، سایت، یا حتی از دست دادن کنترل دامنه
    

---

## ✅ خلاصه خیلی کوتاه:

> DNS مثل نقشه‌ی مسیر برای رسیدن به سایت‌هاست  
> Name Server نگهبان این نقشه‌ست  
> رکوردها آدرس و دستورالعمل‌های این نقشه‌ن  
> امنیت DNS یعنی مطمئن بشی هیچ‌کس نمی‌تونه نقشه رو دستکاری کنه یا بدزده

## 🛠 ابزار 1: nslookup

`nslookup` یه ابزار ساده و پایه‌ای برای پرس‌وجوی DNS هست، هم توی لینوکس کار می‌کنه هم ویندوز.

### 🔍 مثال: گرفتن رکورد A (آدرس IP) دامنه

```bash
nslookup google.com
```

🔸 **خروجی:**

```
Name:    google.com
Addresses:  142.250.190.14
```

---

### 🔍 گرفتن Name Serverهای دامنه:

```bash
nslookup -type=ns google.com
```

🔸 **خروجی:**

```
google.com     nameserver = ns1.google.com
google.com     nameserver = ns2.google.com
...
```

---

### 🔍 پرسیدن از یک Name Server خاص:

مثلاً می‌خوایم از Name Server گوگل بپرسیم که `google.com` چه IPای داره:

```bash
nslookup google.com ns1.google.com
```

🔸 **خروجی:**

```
Server:  ns1.google.com
Address:  216.239.32.10

Name:    google.com
Address: 142.250.190.14
```

---

## 🛠 ابزار 2: dig

`dig` حرفه‌ای‌تره و در دنیای لینوکس و امنیت خیلی محبوبه.

---

### 🔍 گرفتن رکورد A دامنه:

```bash
dig google.com
```

🔸 در بخش `ANSWER SECTION` می‌بینی:

```
;; ANSWER SECTION:
google.com.    300  IN  A  142.250.190.14
```

---

### 🔍 گرفتن Name Serverهای دامنه:

```bash
dig NS google.com
```

🔸 خروجی:

```
google.com.    86400  IN  NS  ns1.google.com.
google.com.    86400  IN  NS  ns2.google.com.
```

---

### 🔍 پرسیدن از Name Server خاص (مثل Zone Transfer):

```bash
dig @ns1.google.com google.com A
```

یعنی بپرس از `ns1.google.com` که رکورد A دامنه‌ی `google.com` چیه.

---

### 🔍 تلاش برای Zone Transfer (برای آموزش، بعضی دامنه‌ها جواب نمی‌دن):

```bash
dig @ns1.targetdomain.com targetdomain.com AXFR
```

🔴 بیشتر Name Serverها اجازه Zone Transfer نمی‌دن. اگه بدن، کل اطلاعات DNS رو می‌گیری.  
و اگه بدن، یعنی مشکل امنیتی دارن.

---

## 🔍 ۱. Recursive Query (درخواست بازگشتی)

### ✅ تعریف ساده:

در این نوع درخواست، **کاربر (یا کلاینت)** از DNS Resolver می‌خواد که **تمام مسیر پیدا کردن IP را خودش انجام بده** و **فقط جواب نهایی رو بده**.

### 📦 مثال:

کلاینت می‌پرسه:

> "آقا! IP سایت `example.com` رو بده."

و DNS Resolver باید:

1. بره از Root Server بپرسه
    
2. بعد از `.com` Name Server بپرسه
    
3. بعد از Authoritative DNS بپرسه
    
4. و **خودش همه اینا رو دنبال کنه**
    
5. در نهایت فقط IP نهایی رو به کلاینت بده
    

✅ کلاینت اصلاً نمی‌فهمه چه مراحلی طی شده  
❗ همش به عهده‌ی Resolver هست  
📍 این نوع کوئری بیشتر از سمت کاربران به DNS Resolver داده می‌شه


## 🔄 ۲. Iterative Query (درخواست تکراری / مرحله‌ای)

### ✅ تعریف ساده:

در این مدل، DNS Server می‌گه:

> "من جواب نهایی رو ندارم، ولی آدرس کسی رو دارم که شاید بتونه کمکت کنه!"

پس:

- Resolver از Root Server 
- می‌پرسه → اون می‌گه برو سراغ `.com`
    
- بعد می‌ره سراغ `.com` → اون می‌گه برو سراغ `example.com` NS
    
- همین‌طور ادامه می‌ده، تا به جواب نهایی برسه
    

📍 این نوع معمولاً بین **DNS Serverها** استفاده می‌شه  
❗ سرعت بیشتری داره چون فقط بخشی از وظیفه روی هر سروره


| ویژگی        | Recursive Query                             | Iterative Query                |
| ------------ | ------------------------------------------- | ------------------------------ |
| مسئول نهایی  | DNS Resolver                                | DNS Resolver                   |
| بار مسئولیت  | کامل روی Resolver                           | توزیع‌شده بین سرورها           |
| سرعت         | کندتر (همه مراحل توسط یک سیستم انجام می‌شه) | سریع‌تر                        |
| استفاده توسط | کاربر یا سیستم‌عامل                         | بین DNS Serverها               |
| مثال         | کلاینت به 8.8.8.8 → "IP این دامنه چیه؟"     | 8.8.8.8 از Root → ".com" → ... |

| نوع           | کی استفاده می‌کنه؟       | کی مراحل رو طی می‌کنه؟ |
| ------------- | ------------------------ | ---------------------- |
| **Recursive** | کلاینت → DNS Resolver    | فقط DNS Resolver       |
| **Iterative** | DNS Server ←→ DNS Server | هر سرور یه قدم         |


اگر یک **سرور DNS recursion** فعال داشته باشد، یعنی آن سرور توانایی دارد که **درخواست‌های DNS را گرفته، خودش دنبال پاسخ بگردد، و پاسخ نهایی را برگرداند**.

اما بسته به **نحوه پیکربندی** آن، این ویژگی می‌تواند:

---

## ✅ **سودمند یا امن باشد، اگر:**

- فقط برای **کلاینت‌های داخلی** (مثلاً در شبکه سازمانی) فعال شده باشد.
    
- به عنوان **سرور کش (Caching DNS Resolver)** برای کاهش زمان پاسخ‌دهی استفاده شود.
    
- به‌درستی محدود شده باشد (مثلاً فقط IPهای خاص مجاز باشند).
    

### 🎯 مثال کاربردی:

کاربران یک شرکت به جای استفاده از DNS عمومی مثل 8.8.8.8 از DNS داخلی شرکت با recursion استفاده می‌کنند. وقتی یک نفر آدرس google.com را می‌زند:

- سرور DNS شرکت درخواست را گرفته،
    
- اگر پاسخ را ندارد، به root و سپس سرورهای دیگر مراجعه می‌کند،
    
- و پاسخ نهایی را ذخیره و به کاربر می‌دهد.
    

---

## ❗ **اما اگر بدون محدودیت باشد (یعنی تبدیل شود به Open DNS Resolver):**

### 🔓 مشکلات امنیتی جدی به‌وجود می‌آیند:

### 1. 💥 حملات **DNS Amplification**:

- مهاجم درخواست‌هایی با آدرس جعلی (قربانی) به سرور recursive می‌فرستد.
    
- سرور پاسخ‌های بزرگ می‌فرستد به قربانی.
    
- باعث **حمله DDoS تقویتی** می‌شود.
    

### 2. 🎯 سوءاستفاده برای اسکن DNS:

- مهاجم می‌تواند از سرور به‌عنوان بخشی از زنجیره‌ی اسکن دامنه استفاده کند.
    

### 3. ⚠️ افشای اطلاعات کش:

- اگر سرور recursion پاسخ‌های cache شده را در اختیار همه قرار دهد، ممکن است مهاجم بفهمد کاربرها از چه دامنه‌هایی استفاده کرده‌اند (cache snooping attack).
    

---

## 📌 نتیجه‌گیری:

|حالت|توضیح|
|---|---|
|✅ Recursion فقط برای کلاینت‌های داخلی|✔️ امن و مفید (سرعت و کنترل بهتر)|
|❌ Recursion برای همه دنیا (بدون محدودیت IP)|❗ خطرناک، ممکن است به Open DNS Resolver تبدیل شود|

## ✅ تعریف کلی:

|اصطلاح|تعریف|
|---|---|
|**AXFR (Full Zone Transfer)**|انتقال کامل کل رکوردهای یک زون DNS از سرور اصلی به سرور ثانویه.|
|**IXFR (Incremental Zone Transfer)**|انتقال فقط رکوردهایی که **تغییر کرده‌اند** (به‌روزرسانی‌های افزایشی) از آخرین انتقال قبلی.|

---

## 🔍 فرق اصلی:

|ویژگی|AXFR|IXFR|
|---|---|---|
|نوع انتقال|**کامل**|**افزایشی (تغییرات فقط)**|
|حجم داده|زیاد|کمتر|
|عملکرد|ساده، حتی اگه یه رکورد تغییر کرده کل زون فرستاده میشه|فقط رکوردهای جدید، حذف‌شده یا آپدیت‌شده فرستاده میشه|
|مناسب برای|اولین بار همگام‌سازی، یا وقتی پشتیبانی از IXFR نیست|به‌روزرسانی‌های سریع و کم‌هزینه در منابع|
|نیاز به سوابق تغییر|❌ نیاز ندارد|✅ نیاز دارد (history of changes)|

---

## 🧪 مثال واقعی:

فرض کن یک زون DNS داری به شکل زیر:

```
example.com.    IN   A    192.168.1.1
www             IN   CNAME    example.com.
mail            IN   MX   10 mail.example.com.
```

### در حالت AXFR:

اگر فقط رکورد mail تغییر کند، **همه رکوردهای بالا دوباره منتقل می‌شوند**.

### در حالت IXFR:

فقط تغییرات مربوط به `mail` منتقل می‌شود — خیلی سریع‌تر و کم‌حجم‌تر.

---

## 🧠 SOA و نقش آن در IXFR

هر زون DNS یک رکورد SOA (Start of Authority) دارد.  
در IXFR، سرور ثانویه بررسی می‌کند که شماره سریال (serial number) در SOA تغییر کرده یا نه.

اگر تغییر کرده بود، درخواست می‌دهد:

> لطفاً فقط تغییراتی که از سریال X تا Y اتفاق افتاده‌اند رو برایم بفرست.

---

## 🔐 از نظر امنیتی چطور؟

- هر دو (AXFR و IXFR) می‌تونند مورد سوءاستفاده قرار بگیرند، چون اگر **باز باشند**، مهاجم می‌تونه ساختار کامل رکوردهای DNS رو بگیره.
    
- بنابراین در سرورهای واقعی **Zone Transfer فقط باید برای IPهای مشخص (سرور ثانویه) مجاز باشه**.
    

---

## 🔧 بررسی از بیرون:

برای بررسی اینکه یک سرور AXFR باز داره یا نه، از ابزار زیر استفاده می‌کنن:

```bash
dig AXFR example.com @ns1.example.com
```

اگر باز باشه، کل رکوردها رو برمی‌گردونه که خطرناکه.
